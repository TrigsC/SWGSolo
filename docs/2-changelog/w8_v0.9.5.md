## Changes

### Training turns earned XP into progression

`trainPlayerBotSkill` is the single entry point, checking gate, record,
prerequisites, preclusions, the 250-point budget and available XP — reading the
skill data straight from `SkillManager` rather than `awardSkill`, which rejects
every ghostless creature.

**Derived spend makes training atomic.** `simbot_experience` means *lifetime
earned* — already what F_0.9.1 wrote — so available XP is `earned − Σ cost of
trained boxes` and `skill_points_spent` is recomputed from `simbot_skills`.
Training therefore mutates exactly **one** durable row, atomic under MyISAM,
self-healing at boot, with no write-ahead journal. The ceiling correctly applies
to *spendable* XP (`room = cap − available`), so progression cannot stall.

### The ladder derives itself from game data

Lua names only the terminal box; C++ walks `getSkillsRequired()` transitively and
topologically orders it. The shipped brawler plan resolves to **23 boxes / 92
skill points** with no external research — the prerequisite graph, XP costs and
skill mods are all already in `skillMap` from `datatables/skill/skills.iff`.
Adding marksman or artisan is one Lua line.

### Bots are minted as novices on a purpose-built body

New `sim_playerbot_novice` template, calibrated to a **starting player
character** rather than a level-1 creature (the first cut needed ~750 s to kill a
`dwarf_nuna` that killed it in ~17 s). An unarmed plan skips weapon creation
entirely and keeps the stock creature weapon, whose `xpType` already credits
`combat_meleespecialize_unarmed`.

### Two corrections to already-released F_0.9.1 behaviour

- The lifetime XP ceiling now follows the stock rule (max `Skill::getXpCap()`
  over trained skills), not just `getDefaultXpLimit`.
- The per-kill cap tier now derives from trained skill mods using the stock
  `min(25, private_<weapon>_combat_difficulty/100 + 1)` formula instead of a
  static `skillTier` frozen at mint.

### `pveMaxHunters` becomes a true population cap

`governPvePopulation` was a spawn-batch cap: it skipped identities that already
had bodies *before* counting them, so adding a novice produced an extra body
rather than a replacement. It is now a desired-active-set reconciler — compute
the set, drain at most one out-of-set body per tick, then spawn at most
`cap − liveCount` recounted after the drain.

Ownership is explicit and deliberately independent of eligibility
(`isGovernorManagedIdentity`), and eligibility is computed **once** into a set
that both selection passes filter to, so they decide ordering only. Four review
findings in this function all traced to the same shape: one predicate written in
more than one place, then drifting.

### Also

Novice mint at `orderedSkills[0]` via `freeGrant` with idempotent boot repair;
gated bounded retirement of legacy hunters mirroring `drainSimPresenceBodies`,
with two independently-guarded flags; `training` dashboard section; schema 1013
(`simbot_identities.training_plan`, renumbered ahead of F_0.9.3).

## Verification

17 runs were required. Two product defects were unreachable by build, unit tests
or code review because they only manifest under the shipped default-off
configuration: the training gate checked its capability flag *before* the parity
override, making training unverifiable; and the population governor destroyed
bodies it did not own. Nine failures were in the harness itself. One
mid-verification stall (141 % CPU, REST unresponsive ~30 min) was **never
explained**, did not recur across the final runs, and is recorded as such.

## Known limitations

- The "2000 identity" scale scenarios are arithmetic bounds checks, **not** load
  tests — nothing in this release exercised 2000 concurrent bots.
- Per-bot runtime combat state is not on the dashboard, so a combat failure
  cannot be distinguished between "engaged but too weak" and "never engaged".
- The parity matrix carries order-dependent global state; per-scenario isolation
  is recommended as a follow-up chunk.
