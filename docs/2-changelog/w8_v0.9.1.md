**Release Date**: Week 8, 03-09-2026 at 16:18
**Version**: 0.9.1 (previously 0.9.0)
**Object**: F_0.9.1 P.10b: roster PlayerBots earn real kill XP — player-parity award from the victim's ThreatMap via a lock-free deferred task inside disseminateExperience, with a Lua-tunable killXpRate, a lifetime ceiling inside the award API, and a live harness in which a bot kills a spawned dwarf_nuna for the exact oracle amount; all gates ship default-off

## Changes

F_0.9.0 shipped the progression store with **no production caller**. F_0.9.1 is that
caller: the first real economy mutation in the P.10 line. Roster PlayerBots now earn
combat experience for the creatures they kill, using the same arithmetic the engine
applies to human players.

### The hook, and why it moved

The award branch lives **inside** `PlayerManagerImplementation::disseminateExperience`,
not at the `CreatureManagerImplementation.cpp:677` call site the roadmap sketched.
`disseminateExperience` has two callers — single-creature death and
`DisseminateExperienceTask` for lairs — so hooking inside covers both with one branch and
reuses the already-computed `baseXp`, `totalDamage` and `gcwBonus`. The P.7.4b FRS block
already lives in that function and set the precedent. The roadmap now records the
correction so later chunks inherit the decision rather than the sketch.

No combat-side change was needed. `ThreatMap::addDamage` already records **every**
attacker, AiAgents included, keyed by that attacker's weapon `getXpType()` — bot hunters
were always in the victim's threat map. The data existed; nothing collected it.

### Lock posture

`disseminateExperience` runs with the corpse already locked, so the branch takes **no
object lock and no mutex**. It copies a plain POD and hands it to a deferred
`SimPlayerBotKillXpTask`, which resolves identities under `pveMutex` and writes under
`progressionMutex` — never nested, never while holding an agent lock. No
`ManagedReference` to the corpse is captured.

The synchronous pre-filter uses `AiAgent::getSimPlayerBot()` **only as a cost filter,
never as authority**. That is the flag that leaked onto wild creatures (fixed in
`d38877020c`), and both failure modes are safe: a stale true costs one task that resolves
nothing, a stale false costs one kill's XP. Authority remains `resolvePlayerBotIdentity`.
Live verification observed this working on production traffic — 29 wildlife deaths reached
the task and were rejected as non-roster.

### Parity, down to the rounding

The formula mirrors the player path step for step, including where it truncates: the
direct path truncates twice (at `awardExperience`'s `int amount` boundary, then again
inside after `globalExpMultiplier`), while `combat_general` truncates once because
`combatXp` is already a `uint32`. `combatXp` accumulates per iteration, excludes
`jedi_general`, and includes `dotDMG` — which feeds combat XP without earning a row of
its own. Bot level comes from the identity's `skillTier`, **never** the body template's
level; a wraith-templated body would otherwise cap at 178x300.

`killXpRate` (Lua, default `1.0`) multiplies after the per-kill cap, so a bot at the
shipped rate earns exactly what an equivalent unskilled player would, and raising it
genuinely accelerates rather than being swallowed by the cap.

### Lifetime ceiling moved into the award API

`grantPlayerBotExperience` now applies the ceiling itself, mirroring
`PlayerObjectImplementation::addExperience:708-717` with defaults from the new
`SkillManager::getDefaultXpLimit` accessor (2000 fallback, `prestige_` uncapped). Every
future XP source inherits it rather than re-implementing it. A type already at its ceiling
returns `false` without a rejection counter — the caller passed a valid amount; the store
simply had no room.

### Verification

Scenarios 19-28 extend the parity matrix to 28. Nine are deterministic, driving the
production award function through `simulateKillXp` with exact expected values. Scenario 28
is the call-site proof: a harness bot kills a spawned `dwarf_nuna` with real rifle combat
and banks the exact oracle award, durable across flush+reload and a real process restart.
It needed **no controller change** — harness and hunter identities share one body path
(rifle, faction 0, `ATTACKABLE`), and `simParityTest` overrides only `IDLE`, leaving the
stock combat sockets live.

Live verification: 32/32 required assertions, 28/28 matrix, no crash, gates restored and
re-confirmed inert. It found one defect nothing else had: `deleteIdentity` re-resolves its
identity on every async poll, but the request handler pruned the named ref on completion,
so the poll observing completion failed. Positional addressing never hit it. Fixed and
re-reviewed.

### Shipped state

Both gates default off — `playerBotProgression.enabled` and `awardKillXp` must **both** be
flipped before a single point of XP is written. Credits and skills remain untouched
(F_0.9.2 and F_0.9.5), and no auction or character state is involved.

One additive line in `PlayerManager.idl` (`getExperienceMultiplier()`) was a documented
deviation from the plan's "no IDL": the harness oracle needs the same server-wide
multiplier `awardExperience` applies, and the alternative was deriving the expected value
from the code under test. `src/autogen/` is gitignored, so the commit carries one line.
