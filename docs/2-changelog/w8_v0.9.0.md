**Object**: F_0.9.0 P.10a: PlayerBot progression store — identity-keyed MySQL XP/credits/skills with award-requires-record semantics, atomic-swap flush and orphan reaper, plus an 18-scenario two-boot live harness; award API has no production caller and all gates ship default-off
**Code review**: `docs/3-code-review/CR_w8_v0.9.0.md` (Codex loop, 6 rounds -> APPROVED)

## Changes

This opens the **P.10 player-parity line** and is the first release under the
owner's explicit economy-phase approval: roster PlayerBots may eventually earn
real XP, credits, loot, skills and trade on the bazaar. This chunk builds only
the place that state lives. Nothing awards anything yet — a hunter's kill pays
exactly what it paid in 0.8.2.

### Why a store at all

A PlayerBot body is an `AiAgent` with **no `PlayerObject` ghost**, and it is
destroyed and rebuilt on every death (`CLONE_HOME` → `spawnPveIdentityBody`).
Every engine reward path either writes the ghost — `awardExperience` returns 0
without one — or gates on `isPlayerCreature()`, as `disseminateExperience` and
loot creation both do. So player-parity state cannot live on the body at all.
Worse, anything reachable *from* an object risks repeating the `simPlayerBot`
sticky-flag leak that put a stale bot flag onto wild creatures.

### What shipped

Three additive MySQL tables (`simbot_progression`, `simbot_experience`,
`simbot_skills`; schema 1010-1012, all `CREATE TABLE IF NOT EXISTS`) keyed by
**roster identity id** — never by object ID, never on `AiAgent`. Three
invariants carry the design:

- **One creation function.** `ensurePlayerBotProgressionRecord` refuses any id
  absent from the loaded roster. It runs at roster mint and again from
  reconciliation as an idempotent repair, because MyISAM cannot make the
  identity INSERT and the record INSERT atomic.
- **Award-requires-record.** A missing record is counted and skipped, never
  created. A leaked flag on a wild creature resolves to identity 0 and is
  rejected — the leak class is closed by construction rather than by a guard.
- **One SQL lane.** Every store query runs on the PvE maintenance task; the
  harness enqueues requests rather than issuing SQL itself.

The flush **atomically swaps** its dirty batch before I/O and merges failures
back, so an award landing mid-SQL is never dropped. The roster's
clear-after-write shape was deliberately not copied. `dbAvailable` recovers
through a bounded `SELECT 1` re-probe rather than requiring a restart.

`pveMaintenanceTaskScheduled` became a `scheduled/running/rerunPending` state
machine so the lane can be pulled forward without ever running two bodies, with
the successor scheduled one interval from **body entry** to preserve the
existing cadence.

Verification vehicle: the 18-scenario `playerBotParityTest` matrix, including a
durable **two-boot restart probe** whose phase-A verdict file is written only
after every other scenario passes and is read fail-closed.

### Four defects only live verification found

The build was warning-clean and Codex had already approved when these surfaced.
Each is a class worth remembering:

1. **`LuaObject::getStringField(key, default)` returns an empty string when the
   field is nil.** It assigns the default pointer but leaves the length at zero,
   then builds `String(result, size)`. Every award was recording an empty source.
   Nothing in this codebase should rely on that default.
2. **A struct field served two meanings.** `step.phase` was both the restart A/B
   gate and the request state, so `phase="started"` read as "not phase A" and
   silently skipped the waits it needed.
3. **A log path assumed the wrong working directory.** The verdict file used
   `bin/log/...` while the server's cwd *is* `bin/`, so it could never open and
   the two-boot protocol would have failed closed on every run.
4. **Two assertions chased self-healing transients.** They checked states the
   recovery path clears within ~5s, through a poll that can lag a full
   maintenance interval.

### The maintenance-lane follow-up, root-caused

A `flushNow` request was once observed taking 32s. It was **not** the scheduler:
the fault knobs were global and consumed by whichever flush ran next, so the
routine end-of-tick flush could steal the fault armed for the harness's own
request. The stolen fault failed an unrelated flush and the real request then
waited for a later tick. It was also a latent flaky test. Faults are now passed
as arguments from the request that armed them, and kick/latency telemetry was
added. Measured **32010ms → 1011ms** maximum request wait.

### Verification

18/18 harness scenarios and 26/26 contract assertions across four boots:
gates-off baseline, phase A, restart phase B, and restored configuration. The
probe's 4242 XP and 777 credits survived a real process restart. Boot repair
created records for all six pre-existing roster identities. Cleanup left zero
harness rows. With gates off the store is inert and production is untouched —
10 miners, 8 PvP bots, 6 PvE roster — with maintenance cadence at 28.3s against
a 30s interval.
