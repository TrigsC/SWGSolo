## Changes

### Feature — market-driven mission hunting (P.8.7)

Replaces the scripted single-kill PvE hunt with a real, market-driven mission loop:

1. **Dispatch** — the market matchmaker (`SimPlayerManager.cpp`) ranks each idle
   hunter against the highest demand-pressure resource family that a
   level-qualified lair can actually yield (`dispatchScore = pressure ×
   expectedYield / huntTimeEstimate`), reserving the summed exact-type family
   yield with a strict-tier-first, upper-bound-only fallback that mirrors the
   lair selector.
2. **Travel** — shared interplanetary/overland travel now lives in the base
   `SimPlayerController` (miners and hunters share it), with a per-controller
   boarding hook so hunter journeys no longer pollute miner `planetDispatch`
   telemetry. Routing-only cities are excluded from *automatic* placement but
   remain valid for *deliberate* PvE work.
3. **Terminal & offer** — the hunter walks to a discovered mission terminal,
   opens the board, and holds a generated destroy-mission offer.
4. **Real lair** — reveals a real three-wave lair (capacity reserved *before*
   construction; the lair is retained via `ManagedReference` and destroyed
   safely on any late failure; capacity exhaustion defers-and-retries rather
   than abandoning). Reveal uses the spatial hunter announcement path so it is
   client-visible; wave progress is emitted to the dashboard.
5. **Fight & harvest** — real combat (`CombatManager::startCombat`), simulated
   harvest booked into the acquisition/demand ledger, closing the
   crafter→hunter demand loop. Optional gated cross-planet **buff trips**.

New dashboard telemetry: mission wave column + a **Completed Missions** metric
on the WILDS page.

### Concurrency hardening (C1–C4)

The hunter's two tick loops (`onTick`, `runActiveTick`/`SimHunterActiveTickTask`)
run on independent task-pool threads. F_0.5.0 makes the terminal mission-board
handoff race-safe:

- **C1** — `activeTickGeneration` is now `std::atomic<uint64>` (latest-wins
  before entry; the read-modify-write in `scheduleActiveTick` was a data race).
- **C2** — `tickRunning` is a non-blocking single-flight guard: a second
  `runActiveTick` reschedules instead of running concurrently.
- **C3** — the terminal→accept transition is routed through the single tick lane
  (`setPhase(ACCEPT_MISSION); scheduleActiveTick()`), not called inline from the
  arrival thread.
- **C4** — a globally-monotonic **terminal-visit epoch**
  (`SimPlayerManager::openTerminalVisit` / `pveTerminalVisitEpoch`) is captured
  on board-open and compared at commit; `generatePveBotMissionOffers` discards
  any offer set that finishes after the order concluded or the body drained
  (invalidated at order-clear, config reload, and world-presence drain; ABA-safe
  because the sequence is never reset).

Verified live: offer churn **558→0**, 0 `staleVisit`, 0 crashes/deadlocks.

### Offer-retry

An empty/partial board no longer abandons the trip — the hunter dwells at the
terminal and re-generates for a bounded `offerMaxAttempts`×`offerRetrySeconds`
budget (default 3×25s, retry span clamped ≤480s).

### Saturation fix (live-verified, this release)

Hunters sat idle across restarts. Root cause: the market dispatcher gates on
`signalUnits > 0`, where `signalUnits = max(0, effectiveCeiling − supply) +
max(0, reserveTarget − supply)`. The meat family's `effectiveCeiling` defaulted
to **25% of `desiredReserve`** (`familyAllocationCeilingFraction.meat = 0.25` →
25k of a 100k target). Accumulated hunter meat (27998, persisted from prior
sessions) exceeded that cap → zero headroom → zero pressure → **no hunt orders
ever issued**, even though the profile was genuinely 70k short. The 25% fraction
is an anti-domination cap for *multi-family* profiles; meat is the **only**
family hunters supply, so it was raised to **1.0**. On reload: meat
`effectiveCeiling` 25k→70.6k, `signalUnits` 0→41k, `pressure` 0→412; hunters left
IDLE_HOME immediately (live config reload via `refreshPvpConfig`, no restart).
