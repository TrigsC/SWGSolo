# P.8.6 — Player-Mimetic Real Buffs (Hunter Buff Acquisition) Implementation Plan

_Plan version: F_0.4.6 → server VERSION 0.4.5 → 0.4.6. Branch:
`feat/pve-acquisition-demand-ledger` (PvE train; do NOT merge to `miner-ai`;
engine3 excluded). Fulfils the originally-scoped "P.8.3 doctor/entertainer
bots" intent._

## Overview

PvE hunter bots currently "buff" via a placeholder: at the start of every
mission cycle they loiter 3s at their home-city cantina point, 3s at a med-center
point, then call `applyHunterBuffs()` which stamps **synthetic** `Buff` objects
onto themselves from config — regardless of whether they already have buffs. This
plan replaces that with **real, player-mimetic buffs** obtained from the owner's
existing in-world buffer NPCs — the **Doctor Buffer** (Mos Eisley / Coronet /
Moenia / Theed med centers, chat "Need a Buff" → 6-step medical HAM buff), the
**Musician Buffer** (cantina, `/listen` → focus + willpower), and the **Dancer
Buffer** (cantina, `/watch` → mind) — and gates the buff detour on **actual
need** (a tracked buff missing, or its remaining duration below a configurable
threshold, default 15 min) so hunters only buff when they should and otherwise go
straight to hunting. Credit cost is bypassed for sim bots for now (owner
decision). If no real buffer NPC is reachable (e.g. a Bestine-homed hunter), the
existing synthetic path remains as a fallback so a hunter is never left unbuffed.

## Problem Statement

Owner-observed in-game: the running hunter "is going to a spot every time,
getting a mission, running and getting a buff on almost a recycle." Root causes:

1. **Buffs are fake.** `SimHunterController::applyHunterBuffs()`
   (`SimHunterController.cpp:271`) constructs `Buff` objects directly from
   `pveConfig` (`getPveHunterBuffs`), never touching the real Doctor/Musician/
   Dancer buffer NPCs the owner built. The `BUFF_UP` cantina/med-center stops are
   explicit placeholders (`SimHunterController.cpp:490` comment: "real doctor/
   entertainer BOT providers are P.8.3").
2. **Buffs are applied unconditionally, every cycle.** `beginBuffUp()`
   (`SimHunterController.cpp:248`) runs at the head of every mission and always
   ends in `applyHunterBuffs(true)` (`SimHunterController.cpp:511`). There is no
   "do I already have fresh buffs?" check, producing the recycle the owner sees.

Buffs are reapplicable — the owner's guidance is to top up when a buff is within
~10–20 min of dropping rather than waiting for it to lapse.

## Solution Architecture

Keep the phase machine and travel/movement ownership in the C++
`SimHunterController` (where `BUFF_UP`, travel legs, dwell, and the hybrid
navmesh mover already live), and drive the **real** buff interactions through the
existing owner-built systems:

- **Need detection (C++).** Before the buff detour, snapshot the hunter's buffs
  under its lock and compute two independent needs — `needDoctor` (any of the 6
  medical HAM buffs absent or `getTimeLeft()` < threshold) and `needEntertainer`
  (dance-mind and/or music focus/willpower absent or below threshold). If neither
  is needed, skip straight to the mission leg.
- **Provider resolution (C++, `SimPlayerManager`).** Locate the actual **Doctor
  Buffer**, **Musician Buffer**, and **Dancer Buffer** NPCs near the hunter's
  home-city med center / cantina using the proven
  `zone->getInRangeObjects(...)` pattern (already used for mission-terminal
  enumeration at `SimPlayerManager.cpp:~26267` and `scanForTarget`), filtered by
  custom object name and/or creature template, returning each provider's OID +
  parent cell + world position. Guarded (stays "pending" until the zone is up and
  the NPC is found); a home city with no buffer NPCs resolves "absent" → fallback.
- **Entertainer buffs — real `/watch` + `/listen` (C++).** With locks released
  (the `scanForTarget` discipline), call
  `PlayerManager::startListen(hunter, musicianOid)` and
  `PlayerManager::startWatch(hunter, dancerOid)`. The owner has already patched
  both to accept the `entertainer`-template NPC and any `CreatureObject` watcher
  (`PlayerManagerImplementation.cpp:3690`/`:3784`); each fires the real
  `WASWATCHED` / `WASLISTENEDTO` observer on the NPC → the existing
  `smartDancerBuffer.lua` / `smartMusicianBuffer.lua` handlers apply the real
  performance buffs to the hunter. Requires the hunter to be inside the cantina
  cell, in LOS, while the entertainer is performing. **One more guard must be
  relaxed for sim bots:** the entertainer handlers apply their buff only after
  `SmartEntertainerHelper.isValidAudienceMember(...)`, which currently rejects any
  target that is not `isPlayerCreature()` (`smart_entertainer_helper.lua:24-30`),
  so `applyWatcherBuff`/`applyListenerBuff` would silently no-op on a bot. That
  helper must be extended to also accept a verified sim bot (via the new
  `isSimPlayerBot` Lua binding), scoped so real-player behavior is unchanged
  (see §5b).
- **Doctor buff — real chat negotiation (C++ → screenplay).** The hunter emits
  **visible** spatial chat ("I need a buff") via
  `ChatManager::broadcastChatMessage` (already used by `announcePveHunterEvent`,
  `SimPlayerManager.cpp:9377`) for the in-world effect, and the controller
  triggers the doctor's **real** negotiation + 6-step buff by scheduling a
  `ScreenPlayTask` into a small new entry `SmartDoctorBuffer:botBuffRequest`
  (see §5). That entry drives the existing `handleChat`/`startBuffingNow`/
  `applyNextStep` flow (`smartDoctorBuffer.lua`) against the hunter with the 5k
  charge bypassed for sim bots. **Queue-safe confirmation (not a one-shot
  "yes"):** the doctor serializes patrons through a NEGOTIATING→confirm→BUFFING
  queue (`smartDoctorBuffer.lua:advanceToNextTarget`/`onConfirmTimeout`), so a
  bot promoted to the queue head later would never see a controller-timed reply.
  Instead, sim-bot confirmation is handled **inside** the doctor screenplay:
  whenever a sim bot becomes the NEGOTIATING target (initial request AND every
  `advanceToNextTarget` promotion), auto-confirm straight into `startBuffingNow`
  (no wait). On controller-side timeout/abort, the bot must be actively removed
  via a new `SmartDoctorBuffer:botCancel` entry (drops it from
  `queue`/`negotiating`/`current`) so a stale request can never fire a late
  `wipeMedicalBuffs` + re-buff mid-hunt (see §5). **Engine constraint that forces this indirection
  (documented, not worked around):** `broadcastChatMessage` only notifies the
  `SPATIALCHATSENT` observer for **player creatures with a ghost**
  (`ChatManagerImplementation.cpp:1078-1108`), so a bot's spatial chat is
  displayed but cannot trigger the player chat pipeline
  (`AiGlobalChatHandler:notifySpatialChatSent`) the way a human's does. Directly
  invoking the doctor's own handler preserves the same NPC, same buffs, same
  visible dialogue.
- **Fallback (C++).** Any provider that is absent/unreachable or times out falls
  back to synthetic buffs for just the missing buff family, so the contract never
  stalls. **Critical:** the fallback specs must cover the SAME CRCs the need check
  tracks, or a fallback hunter would still read "missing" and detour every cycle.
  Today `pveConfig.buffs` (`sim_player_manager.lua:676`) supplies only a subset
  (e.g. medical health/action + dance mind). **Do NOT expand the legacy
  `pveConfig.buffs`** — that would change the gated-off behavior (finding P1).
  Instead add a NEW full 9-CRC spec set under `realBuffs.fallbackBuffs` (all 6
  medical CRCs + dance-mind + music focus/willpower), used ONLY on the realBuffs
  fallback path via `applyHunterBuffsForFamily`. The legacy `applyHunterBuffs`
  and its `pveConfig.buffs` stay byte-for-byte unchanged for the gated-off path,
  death/clone, etc. (see §1 and §2).
- **Gating.** All new behavior sits behind a `pveConfig.realBuffs.enabled` flag
  (default **false**, per the project's reversible/gated standard), with
  `fallbackToSynthetic` (default **true**) and a `reapplyThresholdSeconds`
  (default 900).

## Implementation Details

### 1. Config surface

**File**: `bin/scripts/managers/sim_player_manager.lua`

Add a `realBuffs` table under `pveConfig` (sibling of `missionHunt`,
`acquisitionLedger`, `combat`, `species`). Proposed keys (all owner-tunable):

- `enabled = false` — master gate (default off).
- `fallbackToSynthetic = true` — use `applyHunterBuffs()` when a real provider is
  unreachable/times out.
- `reapplyThresholdSeconds = 900` — re-buff when a tracked buff is absent or its
  `getTimeLeft()` is below this (owner: 10–20 min → default 15).
- `providerScanRadiusMeters = 400` — radius for `getInRangeObjects` around the
  resolved med-center / cantina point.
- `doctorProviderName = "Doctor Buffer"`, `musicianProviderName =
  "Musician Buffer"`, `dancerProviderName = "Dancer Buffer"` — **role-specific
  custom-name filters** (match `smart*Buffer.lua` `customName`). These are the
  PRIMARY discriminator: the Musician Buffer and Dancer Buffer share the SAME
  `entertainer` creature template, so a template-only filter cannot tell them
  apart. Resolution keys on the custom name; template + performance state
  (`isDancing`/`isPlayingMusic`) are validation only.
- `entertainerTemplate = "entertainer"`, `doctorTemplate =
  "smart_doctor_buffer"` — template filters (validation, not the discriminator
  for the two entertainers).
- `doctorInteractionTimeoutMs = 45000` — max dwell for the doctor's ~6×4.5s buff
  + possible queue wait before falling back.
- `entertainerDwellMs = 4000` — dwell after issuing watch/listen for the observer
  events to land.
- `providerApproachRangeMeters = 8` — how close the bot must get to a provider
  (doctor `max_range` is 10; watch/listen need LOS) before interacting.
- `fallbackBuffs = { ... }` — NEW full 9-CRC synthetic spec set (6 medical +
  dance-mind + music focus/willpower) used ONLY by the realBuffs fallback path
  (`applyHunterBuffsForFamily`); the legacy `pveConfig.buffs` is left untouched.

Also add a **`realBuffs.fallbackBuffs`** spec list covering the full tracked set
(all 6 medical CRCs + dance-mind + music focus/willpower) — a NEW list, **leaving
the legacy `pveConfig.buffs` untouched** so the gated-off path is byte-for-byte
unchanged (finding P1). `applyHunterBuffsForFamily` uses `fallbackBuffs` on the
realBuffs fallback path only. Keep `fallbackBuffs` and `getPveTrackedBuffCrcs`
driven from the same tracked-CRC source of truth (§2) so fallback fully satisfies
`computeBuffNeeds`.

**Live Lua**: leave `realBuffs.enabled = false` in the committed config; owner
flips it on to live-verify, mirroring the `missionHunt`/`acquisitionLedger`
rollout.

Load + clamp these in `SimPlayerManager::applyPveConfig(...)` (where
`missionHunt`/`combat` are parsed), storing into new `SimPlayerManager` members
(see §6, Type Definitions).

### 3. Provider NPC resolution

**File**: `SimPlayerManager.{h,cpp}`

**New**: `bool resolvePveBuffProviders(const String& planet, const String& city,
PveBuffProviders& out)` returning, per provider (doctor/musician/dancer), a
record carrying enough to path INTO the interior cell: `{ found, oid,
ManagedReference<CellObject*> cell, uint64 cellId, worldPos, localPos }` — both
the world position (distance math + hybrid overland) AND the cell-local position
with a **strong `CellObject` reference** (the interior path request needs the cell
pointer, not just an id; finding P2). `PveBuffProviders` is declared
**header-visible** in `SimPlayerManager.h` because the controller consumes its
fields. Because the resolver runs lock-free (below), the controller re-validates
the `cell`/`oid` to live strong refs immediately before `moveTo`/interaction.

- Reuse `getPveHomeLocations(planet, city, cantina, medCenter, cityHome)`
  (`SimPlayerManager.cpp:8588`) to get the med-center and cantina anchor points,
  then `zone->getInRangeObjects(x, 0, y, providerScanRadiusMeters, &objs, ...)`
  around each anchor (release manager/agent locks first, per the `scanForTarget`
  fix pattern noted in ARCHI §12), filtering `isCreatureObject()` +
  **role-specific `getCustomObjectName()==providerName`** as the discriminator
  (the two entertainers share the `entertainer` template, so template-only cannot
  separate Musician from Dancer — finding P1). Use the template + performance
  state (`isDancing`/`isPlayingMusic`) as validation only. Capture each hit's OID,
  a strong `ManagedReference<CellObject*>` to its parent cell (`getParent()` cast
  to `CellObject`) and `cellId`, its `getWorldPosition()`, AND its cell-local
  position (the object's `getPosition()` within the cell / `WorldCoordinates`). If
  a provider is found but not currently in a cell (outdoor), `localPos==worldPos`,
  `cell==nullptr`, `cellId==0`.
- Guard exactly like the mission-terminal resolver: while the zone is not yet up
  or `getInRangeObjects` returns nothing, report **pending** (retry), never
  falsely **absent**, so a boot-time scan miss doesn't strand the flow.
- A city whose scan is up but yields no provider of a kind → that kind is
  **absent** (→ fallback for that buff family).

### 4. BUFF_UP sub-flow rework (controller)

**File**: `SimHunterController.{h,cpp}`

**Current state**: `beginBuffUp()` (`:248`) → `moveTo(cantina)`; `onArrived()`
`BUFF_UP` block (`:487-520`) walks cantina-dwell → med-center-dwell →
`applyHunterBuffs(true)` → mission. New sub-state flags
(`cantinaArrived`/`medCenterReached`/…) already exist and will be repurposed.

**Modifications** (keep the existing `BUFF_UP` phase; refine its internal state
machine; do not add travel-phase churn that could destabilize the hybrid mover):

1. `beginBuffUp()`:
   - If `!realBuffs.enabled` → preserve today's behavior exactly (synthetic path),
     so the feature is a no-op when gated off.
   - Else `computeBuffNeeds(needDoctor, needEntertainer)`. If neither → skip the
     detour: `missionHuntOrder ? beginMissionTerminalLeg() : (TRAVEL_OUT +
     moveTo(huntGround))`.
   - Else `resolvePveBuffProviders(...)`. On **pending**, `scheduleActiveTick`
     retry (bounded), mirroring `beginMissionTerminalLeg`'s wait handling.
   - Order the needed stops: **entertainers first** (cantina), then **doctor**
     (med center) — matching today's cantina→med-center ordering. Skip any stop
     whose family isn't needed or whose provider is absent (absent → mark that
     family for fallback).
   - `moveTo` the first needed provider using the real cell-aware overload
     `moveTo(worldPos, localPos, CellObject*)` (`SimPlayerController.h:205`,
     P.6.5b). **Interior-routing gap that must be closed (finding P1):** hunters
     set `usesNavmeshHybridMovement()==true`, and that branch
     (`SimPlayerController.cpp:213-238`) records only `finalDestination=worldPos`
     then `requestHybridPath()` — it **discards** `destinationLocal`/
     `destinationCell`, so the hybrid mover cannot enter a cell today. **The
     override must be a single leg-scoped predicate, not a one-off branch swap
     (finding P1 round 2):** hybrid logic governs not just `moveTo`'s path
     selection but also `onPathFound` (`:263`, drops a base-path result when there
     is no hybrid final destination), the arrival-mode transitions, and
     `checkArrival` stuck re-pathing (`:742`, can switch back to
     `requestHybridPath`). Introduce one latch — e.g. `interiorApproachLeg` (set on
     the buff-approach `moveTo`, cleared on arrival/cancel/relocation) — and make
     EVERY `usesNavmeshHybridMovement()`-gated site treat this leg as non-hybrid
     consistently (path submission → the base `WorldCoordinates(localPos,
     targetCell)` + `SimPathFindTask` path at `:250-256`; result handling; arrival;
     retry). Miners/PvP and the hunter's wild-leg hybrid movement stay byte-for-
     byte unchanged (latch is false for them). If interior pathing still can't
     reach LOS range, degrade to the nearest reachable doorway/LOS point and,
     failing the approach timeout, synthetic fallback. This interior leg is
     validated live in Phase 2 BEFORE the buff wiring is trusted.
2. `onArrived()` `BUFF_UP` handling, per sub-stop:
   - **Entertainer stop**: verify within `providerApproachRangeMeters` + the
     entertainer is performing; release the agent lock; call
     `PlayerManager::startListen(hunter, musicianOid)` and/or
     `startWatch(hunter, dancerOid)`; `scheduleActiveTick(entertainerDwellMs)`;
     on the follow-up tick re-`computeBuffNeeds` to confirm the entertainer buffs
     landed (else fallback for that family); advance to the doctor stop or the
     mission.
   - **Doctor stop**: verify range; emit visible `broadcastChatMessage(hunter,
     "I need a buff.")`; schedule the doctor `ScreenPlayTask` (see §5); enter a
     bounded dwell (`doctorInteractionTimeoutMs`) polling `computeBuffNeeds` each
     `scheduleActiveTick`; when the 6 medical buffs are present, proceed. **On
     timeout/abort/early-leave, the controller MUST issue a `botCancel`
     `ScreenPlayTask` (finding P1)** to remove the bot from the doctor's
     queue/negotiation/current before departing — otherwise a still-queued bot can
     be promoted and buffed later, and `startBuffingNow`'s `wipeMedicalBuffs`
     would wipe the hunter's buffs mid-hunt. Then synthetic fallback for the
     medical family.
3. On completing (or falling back on) all needed stops → `beginMissionTerminalLeg`
   / `TRAVEL_OUT` exactly as today.
4. **Fallback**: a small `applyHunterBuffsForFamily(doctor|entertainer)` stamps
   only the missing family from the new `realBuffs.fallbackBuffs` spec set (NOT
   the legacy `pveConfig.buffs`), guarded by `fallbackToSynthetic`. The legacy
   `applyHunterBuffs`/`pveConfig.buffs` remain for the gated-off + death/clone
   paths, unchanged.

### 5. Doctor screenplay: bot entry + credit bypass

**File**: `bin/scripts/screenplays/custom/smartDoctorBuffer.lua`
(+ `bin/scripts/custom_scripts/smart_doctor_config.lua` if a flag is preferred
over template detection)

**Modifications**:

- **Arg format + generation ownership + controller-absolute deadline (findings
  P2/P1).** The **controller owns** the request generation AND the deadline: it
  keeps a per-hunter monotonic `pveDoctorRequestGen` (uint32, incremented on each
  new doctor request) and a `pveDoctorRequestActive` flag, and it computes its own
  absolute `deadlineSec` at SEND time (`now + doctorInteractionTimeoutMs/1000`).
  Both screenplay entries take `argsString = "<botOid>:<generation>:<deadlineSec>"`.
  `botBuffRequest` records the carried generation as the bot's stored latest
  generation and stores the **controller-supplied** `deadlineSec` as
  `expiresAtSec` (NOT a doctor-recomputed value — a `ScreenPlayTask` delivery
  delay must never extend validity past the controller's deadline; finding P1),
  and rejects the request outright if `now > deadlineSec` on receipt. `botCancel`
  compares its carried generation to the stored latest and acts **only if
  `carried >= stored`** (compare-before-cancel) — so a delayed cancel for
  generation N cannot cancel a freshly-issued N+1.
- **New entry** `function SmartDoctorBuffer:botBuffRequest(pDoctor, argsString)`:
  decode `botOid`+`generation`, resolve the bot via `getSceneObject`, write the
  token, then enter the real flow with `handleChat(pDoctor, pBot, "need a buff")`
  (which enqueues/negotiates through the existing machinery,
  `smartDoctorBuffer.lua:868`).
- **Queue-safe auto-confirm (finding P1) — NOT a one-shot delayed "yes".** The
  doctor promotes patrons through its queue over time
  (`advanceToNextTarget`/`onConfirmTimeout`, `:592`/`:776`), so a fixed-delay
  "yes" only works if the doctor is idle at request time. Instead, at every point
  a target ENTERS the NEGOTIATING state — the initial `handleChat` request AND
  each `advanceToNextTarget` promotion — detect a sim-bot negotiating target and
  auto-advance it straight into `startBuffingNow` (skip waiting for a confirm).
  This makes queued bots confirm correctly whenever they reach the head. The bot
  is then funneled through the real `startBuffingNow` → `applyNextStep`
  (`:833/693`): doctor animates (`heal_other`), speaks, applies the real 6-step
  medical buff.
- **Per-request validity token — the authoritative stale guard (finding P1
  round 2).** `botCancel` (below) is issued as its own async `ScreenPlayTask` and
  therefore CANNOT be guaranteed to run before a concurrent `advanceToNextTarget`
  promotes the bot into `startBuffingNow`; a removal-only cancel still races.
  Make validity the source of truth instead of ordering: `botBuffRequest` writes
  a per-bot request token (a monotonically increasing generation, plus an absolute
  `expiresAtSec`) into the doctor's persisted state keyed by the bot OID. **Every**
  point that would begin/continue buffing a sim bot — the auto-confirm promotion,
  `startBuffingNow` (before `wipeMedicalBuffs`), and each `applyNextStep` — first
  re-validates: bot still resolvable, `getSimPlayerBot()`, token generation
  matches the latest, and not expired. Any mismatch/expiry → treat as canceled
  (`advanceToNextTarget`, no wipe/buff). This makes a late promotion a safe no-op
  even if `botCancel` hasn't executed yet.
- **No-strip design: eliminate the up-front bulk wipe for sim-bot sessions
  (finding P1 round 4).** The root hazard is `startBuffingNow`'s up-front
  `wipeMedicalBuffs` (`smartDoctorBuffer.lua:859`), which clears ALL 6 medical
  pools at once; any interruption after that (bot leaves range / enters combat /
  request canceled mid-sequence) leaves some pools stripped-and-unfilled — a
  partially-buffed or stripped hunter. **Fix: for sim-bot doctor sessions, SKIP
  the up-front `wipeMedicalBuffs` entirely and make each step a self-contained
  single-pool refresh** — each step removes ONLY that step's medical CRC then
  applies it. Mechanism (no IDL change): change the existing hand-written
  `AiAgentImplementation::healEnhanceCreatureTarget` (`AiAgentImplementation.cpp:
  5228`) so that instead of early-returning when `target->hasBuff(crc)`, it
  removes that single CRC and re-applies (refresh-in-place). This is
  behavior-neutral for the existing real-player doctor caller (which already
  cleared all medical buffs via the up-front wipe, so `hasBuff` was already false)
  and is exactly the per-step refresh the no-wipe sim-bot path needs. The IDL
  signature is unchanged (edit is in `*Implementation.cpp`, not the `.idl`).
  Consequences: an interrupted sim-bot session leaves already-done
  pools freshly buffed and not-yet-done pools still holding their PRIOR buff — no
  pool is ever left both stripped and unfilled, so an early departure or a late
  promotion can never degrade the hunter. (Real-player sessions keep the existing
  up-front wipe + wound heal, unchanged.)
- **Belt-and-suspenders validity re-check.** In addition, before each per-step
  refresh re-validate the request token (generation matches, not past
  `expiresAtSec`) AND the doctor's existing `isValidBuffTarget(pDoctor, pBot)`
  (not-dead / in-range / not-in-combat, `smartDoctorBuffer.lua:260`); any failure
  → stop the sequence and `advanceToNextTarget` (leaving completed pools intact).
  With the no-strip design this is purely an early-exit optimization, not a
  correctness dependency — there is no longer a destructive up-front step whose
  timing must be guarded. The controller still issues `botCancel` on abort to free
  the queue slot promptly.
- **New entry** `function SmartDoctorBuffer:botCancel(pDoctor, argsString)`
  (finding P1): parses `botOid` + `generation`; **only if `generation >=` the
  bot's stored latest generation** does it bump/invalidate the token and remove
  the bot from `queue`/`queueSet`, `negotiating`, `current`
  (`removeFromQueue`/`advanceToNextTarget`), persisting the cleared state — the
  compare-before-cancel rule prevents a delayed cancel for generation N from
  nuking a newer generation N+1 request (see §5 arg format). Removal is
  best-effort; the actual safety guarantee is the **no-strip per-pool refresh**
  above (an interrupted session never leaves a pool stripped-and-unfilled), with
  the token/`isValidBuffTarget` re-checks as early-exit optimizations.
- Both entries are invoked from C++ via `ScreenPlayTask` (§ Technical
  Considerations). The controller carries the same generation it sent so it can
  correlate; the token expiry (`expiresAtSec` = the **controller-supplied**
  absolute deadline, stored unchanged) is a belt-and-suspenders bound independent
  of `botCancel` delivery.
- **Credit bypass (scoped to sim bots)** in `tryChargePlayer`/`startBuffingNow`
  (`:567`/`:833`): if the target is a sim bot, skip `subtractCashCredits` and
  treat as paid. Detection needs `getSimPlayerBot()` in **Lua** — it is currently
  native-only (`AiAgent.idl:1282`) and **not bound to Lua**
  (absent from `LuaAiAgent.cpp`/`LuaCreatureObject.cpp`). Add a thin Lua binding
  `LuaAiAgent::isSimPlayerBot` (see §6). Bypass is **only** for
  `getSimPlayerBot()==true` targets — real players still pay in full.
- No change to the doctor's `isValidBuffTarget` (in-range/not-dead/not-in-combat)
  — the bot must satisfy it, which the controller's approach range + non-combat
  dwell ensure.

### 5b. Entertainer audience guard: permit sim bots

**File**: `bin/scripts/custom_scripts/smart_entertainer_helper.lua`

## Technical Considerations

- **Pattern usage**: Provider lookup mirrors the mission-terminal enumeration and
  the `scanForTarget` `getInRangeObjects` fix (ARCHI §12; memory
  `pve-playerbot-project`). The doctor `ScreenPlayTask` invocation follows the
  `new ScreenPlayTask(obj, key, play, args)` pattern
  (`DirectorManager.cpp:1700`, `LuaSceneObject.cpp:944`); the new
  `botBuffRequest`/`botCancel` entries adapt the (obj,argsString) task convention
  to the doctor's flow. The realBuffs fallback uses the NEW
  `applyHunterBuffsForFamily` over `realBuffs.fallbackBuffs`
  (`getPveRealBuffFallbackSpecs`); the legacy `applyHunterBuffs`/`pveConfig.buffs`
  path is retained unchanged for gated-off + death/clone.
- **Locking & references**: This is the highest-risk area — match existing
  choreography exactly.
  - `PlayerManager::startWatch`/`startListen` each take their own
    `Locker(creature)` then `Locker(entertainer, creature)`
    (`PlayerManagerImplementation.cpp:3690/3883`). The controller MUST call them
    with **no agent lock held** — release `agentLock` first, exactly as the
    `scanForTarget` rewrite releases the lock before `getInRangeObjects`
    (ARCHI §12). Hold `ManagedReference` strong refs to the hunter and provider
    OIDs across the call.
  - `healEnhanceCreatureTarget` (invoked through the doctor screenplay, not the
    controller) takes `Locker(target)` + `@preLocked` `Locker(buff)` internally
    (`AiAgentImplementation.cpp:5226-5236`) — unchanged; the controller never
    calls it directly.
  - `computeBuffNeeds`/buff reads snapshot under `Locker agentLock(hunter)`, then
    release before any manager query, matching the single-writer / snapshot
    discipline the P.8.4 work established (ARCHI §12: defender-list reads snapshot
    under the hunter lock).
  - Provider resolution's `getInRangeObjects` runs lock-free (release first),
    returning OIDs; re-resolve to strong refs before use.
- **C++ vs Lua placement**: Phase/travel/need-detection/provider-resolution are
  perf-relevant and belong with the existing controller/manager C++. The buff
  *interaction* stays in the owner's existing Lua screenplays (doctor negotiation,
  entertainer observers) — invoked, not reimplemented — so a single source of
  truth for buff CRCs/animations/dialogue remains in Lua. Only a thin
  `botBuffRequest` entry + credit bypass + one Lua binding are added.
- **IDL impact**: none. `getSimPlayerBot()` already exists in `AiAgent.idl`; only
  a hand-written `LuaAiAgent` binding is added. No `src/autogen` regeneration
  concerns.
- **Gating & simulation-only**: `realBuffs.enabled` defaults **false**. The only
  economic relaxation is *skipping* the doctor's 5k charge for sim bots (owner
  decision) — a NON-mutation (no credits move), scoped strictly to
  `getSimPlayerBot()==true`, so **real players are never buffed for free or
  affected**. Buffs are applied only to sim-bot bodies (as the synthetic path
  already does). No inventory/market/persistence mutation. Stays within the
  simulation-only posture.
- **Dashboard visibility**: new `realBuffs` section + roster buff fields (above),
  so the behavior is verifiable on the live dashboard, not just in-game.
- **Live verification plan**: with `realBuffs.enabled=true` and an owner restart —
  (1) a Mos-Eisley-homed hunter with no/expiring buffs walks INTO the med center
  to the Doctor Buffer, "I need a buff" appears in spatial chat, the doctor quotes
  + animates + applies 6 medical buffs (verify via `/dumpTargetInformation` on the
  hunter or the dashboard `medicalBuffed=true`, `minBuffSecondsLeft≈3600`); (2)
  the hunter walks into the cantina and `/watch`+`/listen` land dance-mind +
  music focus/willpower (dashboard `entertainerBuffed=true`); (3) a hunter that
  already has fresh buffs SKIPS the detour (`buffDetoursSkipped` increments, goes
  straight to the mission — the recycle is gone); (4) a Bestine-homed hunter (no
  buffer NPCs) uses `syntheticFallbacks`; (5) `hunterKillsTotal` keeps climbing
  (loop unbroken). Pull a dashboard snapshot before/after per the project norm.
- **Edge cases**:
  - **Bestine hunters** (`eligibleHomeCities={"bestine"}`,
    `sim_player_manager.lua:767/788`) — Bestine has no buffer NPC → absent →
    synthetic fallback.
  - **Interior-cell navigation** — the providers sit in med-center / cantina
    **cells** (e.g. Mos Eisley doctor cell `9655496`, entertainers cell
    `1082877`). The bot must path into the interior via
    `moveTo(worldPos, localPos, CellObject*)`, and because the hunter's hybrid
    mover discards the cell target (§4 finding P1), the buff-approach leg routes
    through the base cell-aware path. If interior pathing proves unreliable,
    degrade gracefully: dwell at the doorway/nearest reachable LOS point; if
    range/LOS can't be met within the approach timeout → synthetic fallback.
    **This is the largest technical risk; Phase 2 validates it live before the
    doctor/entertainer flows are trusted.**
  - **Bot enters combat mid-buff** (an interceptor) — `healEnhanceCreatureTarget`
    and watch/listen abort while in combat; the dwell poll times out → fallback,
    no stall.
  - **Entertainer between heartbeats** (not currently performing) — `startWatch`/
    `startListen` no-op ("not dancing/playing"); retry within dwell, else
    fallback.
  - **Doctor queue contention** (multiple hunters) — the doctor's own queue
    handles ordering; the controller's `doctorInteractionTimeoutMs` bounds the
    wait → fallback if it exceeds.
  - **Provider despawn/reload mid-interaction** — strong-ref re-resolve guards;
    missing → fallback.
  - **Fresh buffs** — the whole point: needed-family check prevents the recycle.

## Performance & Cost Impact

Negligible. Need-detection is a handful of `hasBuff`/`getTimeLeft` reads per
mission cycle (not per tick). Provider resolution is one `getInRangeObjects` per
buff detour (not per tick), reusing the mission-terminal pattern already run at
similar cadence. No new per-tick O(n) work across the SimPlayer population. The
detour now runs **less** often than today (need-gated), reducing churn.

byte-for-byte unchanged. The `isSimPlayerBot` Lua binding and doctor credit bypass
only affect sim-bot targets. No migration.
