# P.6.5e Combat Stalemate Break + Collector Wait Jitter Implementation Plan

## Overview

Owner-observed live (2026-07-15, recurring): two opposing sim bots frozen
inside each other at Theed Spaceport's interior ticket collector, standing
for many minutes until a squad reform's remnant-despawn swept them. Root
cause is a structural combat deadlock: both factions path to the identical
cached collector coordinate; when enemies meet there, combat freezes sim
movement by design, the cell-portal wall blocks attack line-of-sight so no
hits ever land, and the P.6.2a phantom-combat guard cannot clear (the
defender is alive and 0m away — it only clears dead/gone/>72m defenders).
Only the 600-1200s hard-stuck backstop or a reform ends it. This plan ships
the fix P.6.2b already flagged as follow-up polish — a fast stalemate break
keyed on combat *progress* — plus a small deterministic jitter on collector
wait points so two squads never occupy one exact spot.

## Problem Statement

- 12.3h soak: 26 `SimPvpHardStuck ... action=clearCombat+forceAdvance` and
  72 stateTtl escapes — the majority are combat stalemates waiting out the
  600s+ cap; every one is up to 10-20 minutes of frozen statues.
- The phantom-combat guard (`SimPvpBotController::onTick`, P.6.2a) clears
  combat only when `getMainDefender()` is null/dead/incapacitated/
  different-zone/beyond the 72m leash. Two live enemies adjacent but unable
  to hit each other (LOS through a cell portal, terrain lip, doorway frame)
  is a hole it structurally cannot cover.
- All squads of both factions share ONE collector wait coordinate per port
  (P.6.5b cache) — overlapping statues are guaranteed whenever two squads
  wait simultaneously, and adjacency at a doorway is exactly the stalemate
  geometry above. Theed (the one interior collector) is the worst case.

## Solution Architecture

1. **Stalemate break by combat-progress tracking** (in
   `SimPvpBotController::onTick`, same proven read-only choreography as the
   phantom guard, so it covers leaders AND members): while in combat, track
   whether the fight is *progressing* — the bot's own HAM decreased since
   the last tick, or the current main defender's HAM decreased. Any
   progress stamps `lastCombatProgressMs`; switching defenders re-baselines.
   If in combat continuously with no progress for
   `stalemateBreakSeconds` (Lua default 45, C++ default 0 = off), call the
   existing `clearCombatState(true)` path (exactly what the phantom guard
   uses) — the bot resumes its loop via the normal IDLE-resume.
   **Re-engage suppression** (without it the break loops forever: the
   stalemated enemy is alive meters away and would be re-acquired on the
   next scan): breaking records the broken defender's OID +
   `stalemateIgnoreUntilMs` (now + `stalemateGraceSeconds`, Lua default
   20); while unexpired, the bot's own target acquisition
   (`scanForTargets`/engage path) skips exactly that OID. Movement is
   already free after the clear, so the bot walks off toward its phase
   target. If the ignored enemy attacks and lands a hit, the defender list
   refills through the normal engine path and HAM progress resets the
   tracker — genuine fights are never suppressed, only the mutual-statue
   case. "Progress" = a decrease in the CURRENT values of the three main
   pools — HEALTH, ACTION, MIND (attribute indices 0/3/6) — on self or the
   tracked defender; the six sub-pools are excluded so wound/regen noise
   never masks a stalemate. Passive regen only increases values and never
   counts; incapacitated or vanished defenders remain the phantom guard's
   job. Counter `pvpStalemateBreaksTotal` via a small manager helper
   (mutex-guarded) + log `SimPvpStalemateBreak oid= squad= defender=
   idleMs=`.
2. **Collector wait jitter**: when a departure target is a collector
   (`departureIsCollector`), displace it by a deterministic per-squad
   offset — angle from `squadId` (e.g. squadId * golden-angle), radius
   `collectorJitterMeters` (Lua default 3, C++ default 0 = off). Outdoor
   collectors (`cellOid == 0`): world == local, one offset applied to both.
   Interior collectors (Theed): apply the offset in **cell-local space
   only** (a world-space delta is wrong under building rotation; ±3m stays
   inside the collector hall) and recompute nothing else — the cell-aware
   path request and world-distance arrival math already tolerate a
   few-meter target shift, and a pathologically-placed jittered point
   degrades through the existing watchdog ladder. Jitter applies at leg
   build time so the leg fields stay self-consistent through
   `onPvpSquadDepartureIntent`.

Both knobs live in existing Lua blocks and are runtime-flippable; C++
defaults off, so knobs-off is byte-identical to v0.3.0 behavior.

## Implementation Details

### 1. SimPvPController.h / SimPvPController.cpp

**Files**: `MMOCoreORB/src/server/zone/objects/creature/simplayer/SimPvPController.{h,cpp}`

**Current state**: `SimPvpBotController::onTick` holds the P.6.2a phantom-
combat guard: it inspects `isInCombat()` + `getMainDefender()` each tick
with a 6-tick grace and calls `clearCombatState(true)` — the exact
lock/read pattern to reuse.

**Modifications**:

- `SimPvpBotController` gains stalemate-tracking members: last observed own
  main-pool total (HEALTH+ACTION+MIND current values, indices 0/3/6), last
  observed defender main-pool total, tracked defender OID,
  `lastCombatProgressMs`, plus the re-engage suppression pair
  `stalemateIgnoredOid` / `stalemateIgnoreUntilMs`.
- In `onTick`, alongside the phantom guard: not in combat → reset the
  PROGRESS baselines only (defender OID, HAM baselines, progress clock) —
  the ignore pair explicitly SURVIVES non-combat ticks (it exists precisely
  for the post-break walk-away) and dies only at expiry or relocation.
  In combat: if the main defender's OID changed, re-baseline and stamp
  progress. Otherwise compare own/defender HAM totals against the stored
  baselines — any DECREASE stamps `lastCombatProgressMs` (then store new
  baselines). If `stalemateBreakSeconds > 0` and
  `now - lastCombatProgressMs` exceeds it, call `clearCombatState(true)`,
  record `stalemateIgnoredOid = defenderOid` +
  `stalemateIgnoreUntilMs = now + graceSeconds`, notify the manager
  (counter + log), and reset progress tracking. HAM reads are read-only
  member access on references the phantom guard already holds — no new
  locks.
- **Target-scan suppression**: in the leader's `scanForTargets` engage
  decision (and any member engage path that selects targets), skip a
  candidate whose OID equals an unexpired `stalemateIgnoredOid`. The
  engine-side defender path is deliberately NOT filtered — if the ignored
  enemy lands a hit, real combat resumes with fresh progress.
- Reset tracking (including the ignore pair) in `prepareForRelocation`
  (teleports must not carry a stale progress clock or blacklist).

### 2. SimPlayerManager.h / SimPlayerManager.cpp

**Files**: `MMOCoreORB/src/server/zone/objects/creature/simplayer/SimPlayerManager.{h,cpp}`

**Modifications**:

- Config members: `pvpStalemateBreakSeconds` (default 0),
  `pvpStalemateGraceSeconds` (default 20), `pvpCollectorJitterMeters`
  (default 0.f). Parsing is **zero-preserving** — `clampMinerInt` treats an
  out-of-range value as "retain current", which would make a Lua `0`
  (runtime disable) impossible under a 15s floor. Spec:
  `raw <= 0 → 0 (off); else clamp(raw, 15, 300)` for stalemateBreakSeconds
  (explicit two-step, not clampMinerInt); grace clamp 5..60;
  `collectorJitterMeters` raw `<= 0 → 0` else clamp 1..8. Accessors for the
  controller.
- `recordPvpStalemateBreak(squadId, oid, defenderOid, idleMs)` — increments
  `pvpStalemateBreaksTotal` under `pvpSquadMutex`, emits
  `SimPvpStalemateBreak` log line.
- **Jitter at leg build** (`planPvpRoute`, inside the existing
  collector-cache application block): when `departureIsCollector` and
  `pvpCollectorJitterMeters > 0`, compute the per-squad offset
  (deterministic from squadId; no `System::random` so replans are stable)
  and add it to `departureLocalPos` — and to `departurePos` only when
  `departureCellOid == 0` (outdoor; world==local). For interior collectors
  the world position stays the cache's collector point (arrival radius
  math tolerates the ±3m divergence; documented in a comment).
- Dashboard: `routedTravel` += `stalemateBreaksTotal`,
  `collectorJitterMeters` echo; cohesion echo += `stalemateBreakSeconds`.

## Technical Considerations

- **Pattern Usage**: the break rides the phantom guard's exact tick-side
  read pattern and `clearCombatState(true)` exit; jitter rides the
  P.6.2c formation-offset idea (deterministic spatial spread) applied at
  the leg-build site where collector coordinates already flow.
- **Locking & References**: no new lock orders — HAM reads use references
  the phantom guard already resolves per tick; the manager helper takes
  `pvpSquadMutex` alone (never while holding an agent lock; the controller
  calls it after releasing its own work, mirroring how phantom-clear logs
  today).
- **IDL Impact**: none. `clearCombatState`/HAM getters are existing public
  surface.
- **C++ vs Lua Placement**: thresholds in Lua; mechanics in C++.
- **Gating & Simulation-Only**: both C++ defaults 0/off — knobs-off is
  byte-identical to v0.3.0. No economy/inventory/player-state writes.
- **Dashboard Visibility**: `stalemateBreaksTotal` is the primary live
  signal; expected to absorb most of the current
  `clearCombat+forceAdvance` hard-stuck volume.
- **Live Verification Plan**: see Test Impact.
- **Edge Cases**:
  - Legitimate slow fight (kiting, out-of-range archery with occasional
    hits): any landed hit within the window resets the clock — only
    genuinely progress-free fights break.
  - Defender swap mid-fight: re-baseline + progress stamp (never breaks a
    fresh engagement).
  - Both sides stalemated: both clocks expire within a tick of each other;
    both clear; both resume loops — no half-cleared pair (clearCombatState
    already handles one-sided clears safely today).
  - Passive regen / healing: HAM increases ignored — a heal-only fight is
    still a stalemate and correctly breaks.
  - DOT ticks: HAM decreases = progress; a poison standoff keeps combat
    (acceptable: damage IS landing).
  - Jitter pushing an interior point against a wall: findPath to the
    jittered local point may end short or fail — existing stuck-watchdog /
    board-anyway ladder degrades exactly as any short path does.
  - `stalemateBreakSeconds` shorter than combat approach time: enforced
    15s floor for any non-zero value (zero-preserving parse keeps 0 = off
    reachable at runtime); default 45s is 3x the phantom guard's 6-tick
    grace.
  - Clear → re-scan → re-engage loop: prevented by the per-bot ignore pair
    (grace default 20s — long enough to walk out of scan range); a THIRD
    enemy appearing during the grace engages normally (only one OID is
    ignored).
  - Both bots break and both ignore each other: both walk away — desired.
  - One breaks, the other (not yet expired) keeps attacking: hits land →
    defender refills → progress stamps → no thrash.

## Performance & Cost Impact

- Per-tick additions: a few integer HAM reads on references already
  resolved by the phantom guard — negligible at current populations.
- Jitter: one deterministic trig computation per planned collector leg.

## Backward Compatibility

- C++ defaults off ⇒ identical to v0.3.0 until the Lua knobs load.
- Runtime-flippable both directions via the 30s config refresh.
- Miners untouched (no shared-base changes).

## Test Impact

- Gate: `-Werror` build + `luac -p` + `node --check` (no SimPvP gtests —
  standing coverage-debt pattern; ledger line for the progress tracker).
- Live verification (post-restart):
  1. `stalemateBreaksTotal` climbs; `SimPvpStalemateBreak` log lines show
     idleMs ≈ 45-50s (not 600s+).
  2. `SimPvpHardStuck ... clearCombat+forceAdvance` rate drops sharply vs
     the 12.3h baseline (26 in 12h).
  3. No frozen statue pairs at Theed's collector across a session
     (owner spot-check).
  4. Two squads waiting at one port stand visibly apart (~3m+).
  5. Combat sanity: bot-vs-bot fights still resolve with deaths (breaks
     only fire on progress-free fights — deathsTotal rate roughly holds).
  6. Miners/travel counters at v0.3.0 baseline; 0 fallbacks preserved.
