# P.6.5b Starport Boarding Realism Implementation Plan

## Overview

P.6.5b makes PvP squad starport departures look like real player travel: before a
cross-planet teleport the squad runs to the actual starport's ticket collector
(instead of the generic city shuttle pad), waits there for a real ship, and —
for randomly-picked destinations — arrives one city away from "hot" destinations
and shuttles in (the owner's "Kor Vella, then Coronet shuttle B" tactic).
Everything reuses the P.6.5a router/leg machinery and the proven teleport
choreography; all new behavior is Lua-gated and simulation-only.

Owner decisions captured during discovery (2026-07-13):
- **Full scope**: departure-port runs + `boardOnActualShuttle` knob + `avoidHotArrival` in one release.
- **Interior runs where pathable**: squads enter Theed Spaceport to its in-cell collector (spike-verified, 22 path nodes); runtime failure degrades to the pad via existing watchdogs.
- **Convergence goes direct**: tactical arrival applies only to random patrol destinations; gank responders take the fastest route.

## Problem Statement

- `PvpTravelLeg` (SimPlayerManager.h:506) stores only the arrival side; the
  departure is "wherever the squad currently stands". A squad leaving Theed
  cross-planet runs to the Theed **shuttle pad** and teleports — it never
  visits Theed Spaceport 574m away. Departures read as fake.
- Route planning happens at `onPvpSquadReadyToTravel` (AWAITING_SHUTTLE entry,
  SimPlayerManager.cpp:22017) — *after* the squad already ran to the pad — so
  the run target can never be leg-type-aware today.
- Intra-planet legs arrive at the **starport** pad (`pads.get(cityIdx)` in
  `planPvpRoute` leg building, ~SimPlayerManager.cpp:22350) — shuttles should
  land at the city shuttle pad.
- No tactical arrival: routes teleport squads straight into contested cities.
- The P.6.5-0 spike (design doc §9.1) already proved every enabler: all 11
  starports path street→ticket-collector; 10/11 collectors are outdoors;
  Theed's in-cell collector paths fine via the world→cell pipeline; Kaadara's
  z=-192 data quirk demands a z-sanity check.

## Prerequisite (verification ordering, not code)

The P.6.5a §12 orphan fixes + MOVEOUT-timing fix are SHIPPED PENDING RESTART.
Per project discipline (instrument first, verify against the live dashboard),
that restart+verify — orphan sweep counters staying ~0, MOVEOUT lines landing

## Solution Architecture

Four cooperating changes, all inside the existing P.6.5a structures:

1. **Plan-at-departure-intent.** Move primary route planning from
   `onPvpSquadReadyToTravel` to a new manager hook called by
   `SimPvPController::finishLoitering()` *before* it enters `PVP_TO_SHUTTLE`.
   Knowing the first leg's type at that moment lets the controller run to the
   correct departure point: starport ticket collector for interplanetary legs,
   city shuttle pad (today's target) for intra-planet legs. The MOVEOUT
   announce moves with planning (fires as the squad leaves its hangout — even
   earlier than the current shuttle-wait announce, same non-racing property).
   `onPvpSquadReadyToTravel` keeps plan-if-empty as the fallback safety net
   (board-anyway paths, convergence replans), exactly as `boardPvpSquad` does.

2. **Per-starport boarding point cache.** Extract the spike's collector scan
   (`runPvpTravelDiagnostics`, octree `getInRangeObjects` + building-cell walk
   for TICKETCOLLECTOR, ~SimPlayerManager.cpp:21590-21660) into a reusable
   resolver caching **both coordinate forms**: the collector's **world**
   position (used for run-target distance/arrival/stale checks) and, for
   in-cell collectors, its **cell-local** position + cell OID (used to build
   the `WorldCoordinates` the path request needs — Core3 treats the position
   as cell-local whenever a cell is attached). Outdoor collectors get the
   Kaadara z-sanity check (|collector z − terrain height| beyond a small
   threshold → fall back to the pad); in-cell collectors are exempt (buildings
   legitimately differ from terrain). Scan runs outside `pvpSquadMutex`;
   result stored under it (spike-proven pattern).

3. **Tactical arrival in the router.** In `planPvpRoute`, after the
   destination pick and **only when the pick is not a convergence** (owner
   decision), test the destination for "hot": an enemy-faction squad currently
   stationed there, or the faction's unexpired enemy contact
   (`SimPvpFactionContact`, TTL 300s) pointing at that city. If hot and the
   destination planet has another routable city, BFS to the best alternate
   same-planet city (prefer not-hot, not same-faction-occupied) and append a
   final intra-planet shuttle leg into the destination. Falls back to the
   direct route when no alternate exists (e.g. Restuss, Rori's only city).

4. **`boardOnActualShuttle` formalized.** `runPvpShuttleWaitTask` already
   gates boarding on `isNearestShuttleBoardable` (real ship present, 5s×24
   board-anyway cap) — the design-doc knob exists de facto. Expose it as
   config: default true preserves today's behavior; false boards after the
   dwell without waiting for a ship (owner escape hatch if ship-wait ever
   misbehaves at a port).

`isNearestShuttleBoardable` needs no change for collector waits: it resolves
`getNearestPlanetTravelPoint(creature, 128m)` from the creature's position —
at or inside a starport the nearest point is that starport — and it already
special-cases Theed Spaceport to true (SimPlayerManager.cpp:21128-21155).

## Implementation Details

### 1. SimPlayerManager.h

**File**: `MMOCoreORB/src/server/zone/objects/creature/simplayer/SimPlayerManager.h`

**Modifications**:

- `PvpTravelLeg` (line ~506): add departure-side fields — departure boarding
  position, an "is collector" marker, and an optional departure cell object ID
  (0 = outdoor). Populated at plan time from the boarding-point cache. Update
  the struct comment that currently says "only the arrival side is stored".
- New cached boarding-point struct (starport point name → **`worldPos`**
  (Vector3, world space — all distance/arrival math), **`localPos`** (Vector3,
  cell-local — path-request destination; equals `worldPos` when outdoor),
  **`cellOid`** (uint64, 0 = outdoor), resolved flag, fellBackToPad flag) + a
  `VectorMap` cache member guarded by `pvpSquadMutex`.
- New config members mirroring the Lua knobs (`pvpUseCollectorBoarding`,
  `pvpAvoidHotArrival`, `pvpBoardOnActualShuttle`, scan radius, z-sanity
  threshold) — C++ defaults: collector boarding **off**, hot-arrival **off**,
  boardOnActualShuttle **true** (matches current behavior).
- New counters: `pvpCollectorBoardingsTotal`, `pvpCollectorFallbacksTotal`,
  `pvpTacticalArrivalsTotal`.
- Method declarations: boarding-point resolver; `onPvpSquadDepartureIntent`
  — returns the full coordinate pair to the controller (out-params or a small
  result struct: `worldPos` + `localPos` + `cellOid`), never a single
  position; hot-city test helper.

### 2. SimPlayerManager.cpp

**File**: `MMOCoreORB/src/server/zone/objects/creature/simplayer/SimPlayerManager.cpp`

**Current state**: route planning + MOVEOUT at `onPvpSquadReadyToTravel`
(:22017); `planPvpRoute` (:22146) resolves pads/adjacency outside the mutex
then picks/BFS/stores under it; `boardPvpSquad` (:22508) pops legs with
plan-if-empty fallback; spike collector scan inline in
`runPvpTravelDiagnostics` (:21470).

**Modifications**:

- **Extract collector resolution** from `runPvpTravelDiagnostics` into the
  shared resolver (diagnostics task becomes a caller of it). Resolver: pad
  position from `getPlanetTravelPoint`, octree scan (config radius, default
  175m) for nearest TICKETCOLLECTOR top-level or in-cell, z-sanity for outdoor
  hits, cache write under `pvpSquadMutex`. On any failure: boarding point =
  pad, `fellBackToPad=true`, `pvpCollectorFallbacksTotal++`.
- **`onPvpSquadDepartureIntent(squadId, ...)`** — new: called by the
  controller at loiter end. Plans a route if none pending (same call shape as
  `onPvpSquadReadyToTravel`, including the MOVEOUT announce, which moves
  here); then peeks (not pops) the first pending leg and returns the departure
  run target: interplanetary → current city's starport boarding point (from
  the cache; respects `pvpUseCollectorBoarding`); intra-planet or no
  leg/disabled → the city shuttle pad (today's behavior, also the return value
  whenever routed travel is off). No agent locks taken inside; mirrors the
  existing controller→manager call discipline.
- **`onPvpSquadReadyToTravel`**: keep as fallback plan-if-empty only (route
  usually already planned at departure intent); announce only when it actually
  plans.
- **`planPvpRoute`**: (a) populate the new leg departure fields per leg
  (leg N's departure = leg N-1's arrival port; first leg's departure = the
  squad's current city); (b) intra-planet legs' `arrivalPos` becomes the
  destination city's shuttle pad (`loc.spawn`) instead of the starport pad —
  shuttles land at shuttleports; (c) **tactical arrival**: after a
  non-convergence destination pick, if `pvpAvoidHotArrival` and the
  destination is hot (enemy squad stationed there under the already-held
  `pvpSquadMutex`, or the faction contact record matches it and is unexpired),
  retarget BFS to the chosen alternate same-planet city and append the final
  shuttle leg; `pvpTacticalArrivalsTotal++`; extend the `SimPvpRoutePlanned`
  log line with `tactical=`.
- **`boardPvpSquad`**: teleport target logic unchanged (arrival side); transit
  stops (`beginTransitStop` call site, :22856) are **unchanged — the squad
  dwells at the arrival pad it landed on** (shuffling to the collector during
  a 20-45s connection wait is dropped as future polish; this also removes any
  cell-aware state from the transit path, where `beginTransitStop` clears the
  target cell). Departure realism for the NEXT leg still applies via the
  centralized TO_SHUTTLE entry. **Counter definition**:
  `pvpCollectorBoardingsTotal` increments exactly here — once per
  interplanetary leg *consumed* (`popNextPvpRouteLeg` succeeded) whose stored
  departure flag says the squad was sent to a collector. Pop-site-only
  incrementing means the departure-intent *peek* and wait-task retries can
  never double-count.
- **`runPvpShuttleWaitTask`** (:22059): honor `pvpBoardOnActualShuttle=false`
  by boarding on the first wait tick.
- **Config parse**: read the new `pvpConfig.travel` keys in the existing
  travel-config block (30s runtime refresh applies automatically).
- **Dashboard** (`pvpActivity.routedTravel`, :9429 area): add the three
  counters + config echo + per-port cache summary (resolved count, fallback
  count). Per-squad row: current departure target kind (`collector`/`pad`)
  while a route is active.

### 3. SimPvPController.h / SimPvPController.cpp

**Files**: `MMOCoreORB/src/server/zone/objects/creature/simplayer/SimPvPController.{h,cpp}`

**Current state**: THREE call sites enter `PVP_TO_SHUTTLE`: `finishLoitering`
(:536, normal loiter end), `interruptForConvergence` (:566, sets phase
directly after halt+prepareForRelocation), and `forceAdvancePhase` (the
hard-stuck/TTL ladder). `drivePhase` moves to `shuttleLocation` (:302-303)
which is always the city pad from `beginCityLoop`/`beginTransitStop`
(:251, :266).

**Modifications**:

- **Centralize the TO_SHUTTLE entry**: a single departure-run helper that
  calls `onPvpSquadDepartureIntent`, overwrites `shuttleLocation` (+ the new
  optional target cell) with the returned departure target, then sets the
  phase. ALL THREE entry points route through it — `finishLoitering`,
  `interruptForConvergence` (the convergence stamp is placed on the squad by
  `dispatchPvpConvergence` *before* the nudge, so departure-intent planning
  consumes it there and the first leg of the convergence route gets the
  correct starport target), and `forceAdvancePhase`'s TO_SHUTTLE transition.
  Combat/dead guards and the transit-stop suppressed-announce behavior are
  unchanged.
- Accepted edge (documented, not fixed): a FRESH convergence stamp arriving
  while the squad is already TO_SHUTTLE/AWAITING_SHUTTLE keeps today's
  behavior — `interruptForConvergence` early-returns and boarding consumes
  the stamp with a replan from wherever the squad stands, so that one
  exceptional leg departs without collector realism. Rare, self-corrects on
  the next leg, and avoids retargeting a mid-run squad.
- Store an optional boarding target cell OID alongside `shuttleLocation`;
  clear it in `beginCityLoop`, `beginTransitStop`, and all relocation resets
  (`prepareForRelocation` path) so a stale cell can never leak across a
  teleport — same hygiene class as the P.6.1d `clearCurrentPath` lesson.
- Arrival math in `checkArrival`-equivalent logic stays world-distance based,
  always comparing against the collector's **world** position (never the
  cell-local form).

### 4. SimPlayerController.h / SimPlayerController.cpp (shared base — additive only)

**Files**: `MMOCoreORB/src/server/zone/objects/creature/simplayer/SimPlayerController.{h,cpp}`

**Current state**: `moveTo(Vector3)` (SimPlayerController.h:140) is
world-space only. Critically, the path-consumption pipeline is world-space
end to end: `queuePatrolPointsFromSimPath` (SimPlayerController.cpp:~320-347)
reads each `simPath` node via `.getPoint()` and builds
`PatrolPoint pp(x, z, y, nullptr)` — **every node's cell is discarded** — and
first-node skip / arrival / stale-path comparisons mix node positions with
`agent->getWorldPosition()`, which is only correct while cells are null.

**Modifications** (cell-aware path support, additive, default = today):

- `moveTo` gains an optional target cell (overload or defaulted parameter).
  When a cell is supplied, the path request's destination is built as
  cell-local `WorldCoordinates(localPos, cell)` — the form
  `findPathFromWorldToCell` expects; the world-space form is kept alongside
  for all distance math.
- **Preserve cells through the pipeline**: `simPath` nodes keep their
  `WorldCoordinates` cell; `queuePatrolPointsFromSimPath` passes each node's
  own cell into the `PatrolPoint` (instead of hard-coded `nullptr`) and uses
  `getWorldPosition()` (not raw `.getPoint()`) for the first-node proximity
  skip. For outdoor paths — every miner path and 10/11 PvP boarding runs —
  node cells are null, so both changes are exact no-ops; only a genuinely
  in-cell path node behaves differently.
- All arrival/stale checks (`checkArrival` distance, `acceptFoundPath`'s 96m
  gate) compare **world** positions on both sides — an in-cell path end is
  converted via `getWorldPosition()` before comparison.
- The pending target cell participates in every reset the target position
  does (`prepareForRelocation`, generation bumps) so retries re-issue the
  same cell-aware destination and teleports clear it.

## Technical Considerations

- **Pattern Usage**: departure-intent hook mirrors the existing
  `notifyReadyToTravel`→`onPvpSquadReadyToTravel` controller→manager call;
  collector scan is the spike's proven read-only octree pattern; route
  storage/consumption stays inside the P.6.5a leg machinery.
- **Locking & References**: no new lock orders. Zone/planet-manager/octree
  lookups happen outside `pvpSquadMutex` (as `planPvpRoute` already does);
  cache and route mutations under `pvpSquadMutex`; the mutex is never held
  while locking agents (existing rule); collectors are static snapshot objects
  held via `SceneObject*` only within the scan, position copied out.
- **IDL Impact**: none — all changes live in non-IDL controller/manager
  classes and Lua.
- **C++ vs Lua Placement**: behavior in C++ (path/phase machinery), every knob
  in `sim_player_manager.lua` with 30s runtime refresh.
- **Gating & Simulation-Only**: C++ defaults off for both new behaviors;
  `useCollectorBoarding=false` + `avoidHotArrival=false` disables all gated
  behavior at runtime — departure targets and route shapes then match shipped
  P.6.5a, modulo the two unconditional correctness changes named in Backward
  Compatibility (plan-at-loiter-end timing; intra-planet legs arriving at
  shuttle pads). Read-only world data throughout — no tickets, credits,
  inventory, or player-state writes.
- **Dashboard Visibility**: three new counters + config echo + per-squad
  departure-target kind under `routedTravel`; `app.js`'s `pageWarfront`
  selects fields explicitly, so it gets a matching render addition
  (file-copy deploy). Verification acceptance stays on the raw API JSON.
- **Live Verification Plan**: see Test Impact; primary signals are the new
  counters, `SimPvpRoutePlanned tactical=` logs, and a visual Theed check.
- **Edge Cases**:
  - Kaadara-style z-quirk ports → z-sanity fallback to pad (counter visible).
  - Port with no collector found in radius → pad fallback, never a wedge.
  - Hot destination on a single-city planet (Restuss) → direct route.
  - Fresh convergence stamp mid-route → existing drop-and-replan wins; replan
    is convergence → tactical arrival correctly skipped.
  - In-cell run path failure at runtime → existing stuck-watchdog ladder
    (stateTtl → board-anyway) degrades gracefully; nothing new to invent.
  - Squad already standing at its starport (transit stop) → departure target
    resolves to the same port's collector meters away; run is trivial.
  - Stale target cell across teleports → cleared in every relocation reset.

## Type Definitions

- `PvpTravelLeg` += departure boarding **world** position (Vector3),
  departure **cell-local** position (Vector3; equals the world position when
  outdoor), departure cell OID (uint64, 0 = outdoor), boarding-is-collector
  flag.
- New private cache struct: starport point name → { worldPos, localPos,
  cellOid, resolved, fellBackToPad } in a `VectorMap` (with the standard
  toBinaryStream/parseFromBinaryStream stubs if held in engine containers).
- `onPvpSquadDepartureIntent` result: { worldPos, localPos, cellOid,
  isCollector } — the controller stores worldPos for arrival math and passes
  localPos+cell into the cell-aware `moveTo`.

## Performance & Cost Impact

- Collector resolution: one octree scan (~175m) per starport, once per boot
  (cached) — the spike already did all 11 per boot with no measurable cost.
- Router additions: an O(squads + 1 contact) hot test and at most one extra
  BFS per plan over ≤10 cities — negligible.
- No new per-tick work; departure-intent fires once per loiter cycle.

## Backward Compatibility

- With both Lua knobs off, **collector runs and tactical arrival are fully
  disabled** — departure targets and route shapes match shipped P.6.5a.
  Two small changes are deliberately **unconditional** (correctness fixes,
  not gated features, called out so the rollback claim is honest):
  1. Route planning + MOVEOUT move from AWAITING_SHUTTLE entry to loiter end —
     a timing-only shift with the same non-racing announce property the
     2026-07-09 fix established (the callout lands even earlier).
  2. Intra-planet legs arrive at the destination's shuttle pad instead of its
     starport pad (shuttles land at shuttleports).
- Miners: `SimPlayerController` changes are exact no-ops for outdoor paths
  (null node cells preserve today's `PatrolPoint` behavior byte-for-byte);
  miner call sites never supply a cell.
- Runtime-flippable via the existing 30s config refresh; no restart needed to
  disable the gated behaviors.

- New pure logic worth a unit test if cheaply isolable: none — hot-test and
  leg-building are interwoven with manager state; live verification covers
  them (coverage-debt ledger entry if the reviewer disagrees).
- Live dashboard verification (post-restart, owner's call):

  4. Convergence responses stay direct (`convergence=true` rows never gain an
     appended leg).
  5. Intra-planet legs arrive at shuttle pads (spot-check a moenia→theed
     travel's arrival coordinates).
  6. No regression: `fallbacksTotal` ≈0, stuck/hardStuck rates at P.6.5a
     baseline, orphan sweep still ~0.
