# F_0.9.2 — Mission credits and the first credit sink (P.10c) Implementation Plan

**Status:** RELEASED as v0.9.9 (2026-10-14). Plan approved by owner 2026-10-13 (Codex plan review: 6 rounds); code review APPROVED; live receipt 16/16
**Branch (at implementation):** `feat/p10c-mission-credits`
**Gates:** `playerBotProgression.awardMissionCredits` and
`playerBotProgression.buffPayment.enabled`, both default off

## Overview

A roster PlayerBot that destroys its mission lair is paid what a player's destroy
mission pays on this server, into its bank balance in the progression store. A
bot that takes doctor buffs pays a configurable fee from that balance, and goes
without doctor buffs when it cannot afford them. This is the first real credit
mutation in the P.10 line and the first thing that spends credits.

Owner decisions (2026-10-13):

| Question | Decision |
|---|---|
| Payout | The stock formula, read from the live mission config. No Lua multiplier, no slicer or city bonus |
| Scope | Income **and** the doctor-buff payment sink |
| Back pay for the ~1,200 missions already completed | None. Balances start from zero when the gate is armed |
| Holdings journal | Added in this release: a durable per-bot journal of every change to what a bot holds (schema 1014) |

## Problem Statement

Bots complete destroy missions end to end since v0.9.8 (17 of 26 in the release
run) and are paid nothing. `grantPlayerBotCredits` and `spendPlayerBotCredits`
have existed since F_0.9.0 with the harness as their only caller. Every roster
bot's `bank_credits` is 0, and the dashboard reports
`gates.awardMissionCredits = false` as a hard-coded literal
(`SimPlayerManager.cpp:16475`). Without a credit source, the loot, vault and
bazaar chunks (F_0.9.3, F_0.9.9 to F_0.9.11) have nothing to trade with.

## Solution Architecture

Two independent pieces, each behind its own gate.

**1. Mission award.** `SimPlayerManager::onPveBotMissionLairDestroyed`
(`SimPlayerManager.cpp:20165`) already performs a single-shot transition under
`pveMutex`: it matches the offer on body and lair, sets `offer.completed`, and
bumps `pveMissionsCompletedTotal`. The award hangs off that transition. Under the
lock it copies `(identityId, offerId, difficultyLevel)`; after the lock is
released it rolls the reward and calls `grantPlayerBotCredits(..., bank = true)`.

The reward comes from one new `MissionManager` method that owns the formula.
The stock generator is changed to call the same method, so the two cannot
drift:

```
reward = base + factor * level + random(randomReward) + random(difficultyRandomReward * level)
```

With the shipped `mission_manager.lua` values (base 0, factor 375, random 0,
difficulty-random 15) a level-10 lair pays 3,750 to 3,900 credits.

**2. Doctor-buff payment.** When a hunter starts its buff-up and needs doctor
buffs, the controller asks the manager whether the bot can afford the fee. If it
cannot, the doctor buffs are skipped for that buff-up (entertainer buffs are
unaffected). If it can, the fee is spent at the moment doctor buffs actually
land, whichever source provided them (a real doctor bot or the synthetic
fallback). The credits are destroyed; no provider is paid.

Bots with no progression record (any legacy hunter, miners, PvP bots) are never
charged and never refused: with no record there is nothing to charge, so their
buff path is byte-for-byte today's.

## Holdings model — the precedent this chunk sets

Credits are the first thing a bot owns. Items follow (a starter weapon, loot,
bazaar stock), so the rules are fixed here and every later chunk inherits them.
They restate roadmap §2 invariants 2 to 6 for holdings and add three things:
the journal, the reserve step, and the rule for equipped gear.

| # | Rule | Credits (this chunk) | Items (F_0.9.3 onward) |
|---|---|---|---|
| 1 | **The owner is the roster identity id**, never a body or an object id | `simbot_progression.identity_id` | `simbot_items.identity_id` |
| 2 | **Nothing durable lives on the body.** What a body carries is a projection rebuilt at spawn from the store, the way trained skills already are | Never on the body's `CreditObject` | The real object sits in the hive item vault. Equipped gear (a vibro knuckler) is an item row in an `equipped` state that the spawn path re-applies; the body's copy is never the record |
| 3 | **One authority per kind** | The MySQL balance | The `simbot_items` state row; the object's containment is checked against it at boot |
| 4 | **One manager API per kind.** No code writes a holding directly | `grantPlayerBotCredits`, `spendPlayerBotCredits`, reserve / commit / release | The vault transfer functions of F_0.9.3 |
| 5 | **Every change has a source and a reference, and writes a journal row** | `source = mission`, `ref = lair oid`; `source = doctor_buff` | `source = loot / bazaar_buy / starter`, `ref = object oid` |
| 6 | **Anything that takes time is reserve → commit or release.** A reserved holding cannot be used twice | Doctor-buff fee | `pending → held`, `held → listed` |
| 7 | **No record, no holding.** A missing progression record is skipped and counted, never created | Existing rule | Same |
| 8 | **Death, respawn and restart lose nothing** beyond the unflushed window (60 s) | Balance is in the store | Objects are in the vault |
| 9 | **The reaper removes every holding with the identity** | Balance and journal rows | Never reaps an identity that still owns `held` / `listed` items (roadmap F_0.9.3) |
| 10 | **Visible per bot on the dashboard** | `bankCredits`, recent journal rows | Item list |

Rule 2's equipped-gear half is stated here and built in F_0.9.3, where roadmap
§5b.4 already records the constraint (gear equipped on an `AiAgent` establishes
containment but its stats do not flow through the player equipment path).

## Implementation Details

### 0. Holdings journal

**Files**: `src/server/db/ServerDatabase.cpp`, the base schema SQL file updated
by F_0.9.0, `SimPlayerManager.{h,cpp}`

**Schema 1014** (`CREATE TABLE IF NOT EXISTS`, MyISAM, as the other `simbot_*`
tables): `simbot_ledger` — `id` BIGINT AUTO_INCREMENT primary key,
`identity_id` BIGINT, `kind` VARCHAR(16) (`credits_bank`, `credits_cash`; `item`
from F_0.9.3), `delta` BIGINT (signed), `balance_after` BIGINT, `source`
VARCHAR(32), `ref_id` BIGINT (lair oid now, object oid later; 0 when none),
`detail` VARCHAR(64) (for a mission: `level=<n>`), `created_at` DATETIME; indexes
on `(identity_id, kind, id)` (per-bot reads and the newest-row-per-kind lookup)
and on `(created_at)` (the retention prune filters on it). The loot/vault chunk moves to schema 1015 and bazaar
sell to 1016; the roadmap is updated in this chunk.

**Modifications**:

- `grantPlayerBotCredits` and `spendPlayerBotCredits` gain optional `refId` and
  `detail` arguments. On success, under the `progressionMutex` they already
  hold, they append one entry (identity, kind, delta, balance after, source,
  ref, detail, time) to an in-memory pending vector. The fee commit does the
  same. Reservations and releases are not journaled: they change no balance.
- `flushPlayerBotProgressionStore` swaps the pending vector out in the same
  locked block that swaps the dirty batch (`SimPlayerManager.cpp:12433-12445`),
  INSERTs the rows **before** the balance UPDATEs, and on failure puts the
  unwritten entries back at the front, the same merge-back rule as the dirty
  batch. SQL stays on the PvE maintenance task.
- No transaction spans the two writes (MyISAM), so a crash between them can
  leave the journal ahead of the balance. That is detected and **repaired in
  the journal, never in the balance** (rule 3: the balance column is the
  authority). At store load, for every identity that has journal rows, the
  newest row's `balance_after` per kind is compared with the stored balance. On
  a difference the loader queues a durable row with `source = reconcile`,
  `delta = balance - balance_after` and `balance_after = balance`, counts
  `ledger.balanceMismatch`, and logs it. After that row the journal's deltas
  again sum to the balance, and the gap stays visible as a `reconcile` row
  instead of being masked by the next ordinary entry. `reconcile` rows are
  exempt from the retention prune, and the prune never deletes the newest row
  of an identity and kind, so the row the mismatch check reads is always the
  true latest entry and an old `reconcile` row can never become "newest". The row is queued like any other entry and
  written by the next flush.
- A flush that fails **after** an identity's journal rows were inserted (for
  example on its balance UPDATE) does not requeue those rows; only entries not
  yet inserted go back to the front of the pending vector. The balance stays
  dirty and is retried, so the journal is never written twice.
- Bounds: the pending vector is capped at 10,000 entries (overflow drops the
  oldest and counts `ledger.dropped`; balances are unaffected). Rows older than
  `playerBotProgression.ledgerRetentionDays` (default 30, 0 = keep forever) are
  pruned by the maintenance task at most once a day. The mismatch check skips
  an identity whose newest row was pruned away.
- The three identity-delete paths (`:12368-12375` reaper, `:12748` harness row
  delete, `:17446-17452` identity delete) also delete the identity's ledger
  rows and drop its pending entries.
- Dashboard `playerBotProgression.ledger`: `pending`, `written`, `dropped`,
  `balanceMismatch`, `retentionDays`, `lastPruneAgeSeconds`; each identity row
  gains `recentLedger[]` (the last 5 entries held in memory since boot).
- The journal is part of the store, so it follows the master
  `playerBotProgression.enabled` gate and needs no gate of its own.

### 1. Reward formula — one owner

**Files**: `src/server/zone/managers/mission/MissionManager.idl`,
`src/server/zone/managers/mission/MissionManagerImplementation.cpp`

**Current state**: the four inputs (`destroyMissionBaseReward`,
`destroyMissionDifficultyRewardFactor`, `destroyMissionRandomReward`,
`destroyMissionDifficultyRandomReward`) are private IDL fields
(`MissionManager.idl:68-71`) loaded once at boot
(`MissionManagerImplementation.cpp:110-113`). The formula is inline in
`randomizeGenericDestroyMission` (`:920-921`).

**Modifications**:

- Add `public native int rollDestroyMissionReward(int difficultyLevel)` to the
  IDL, annotated the way the nearest read-only native on this class is
  (`getRealBountyReward` is `@dirty`), so it takes no manager lock. It reads four
  values that are written only at boot.
- Implement it with the two existing lines, unchanged in order and arithmetic. A
  `difficultyLevel` below 1 is treated as 1.
- Replace lines 920-921 with a call to it. Player missions get the identical
  value distribution; this is a move, not a behaviour change.
- Add `public native void getDestroyMissionRewardBounds(int difficultyLevel, int& min, int& max)`
  only if the IDL compiler accepts reference out-parameters on a native; if not,
  expose two `@dirty` getters `getDestroyMissionRewardMin(level)` and
  `getDestroyMissionRewardMax(level)`. The harness oracle and the live assertion
  need the bounds, and they must come from the same loaded values.

The previous design (four raw accessors, formula copied into
`SimPlayerManager`) is dropped: it would leave two copies of the formula.

### 3. Mission credit award

**Files**: `SimPlayerManager.{h,cpp}`, new
`src/server/zone/objects/creature/simplayer/SimBotMissionCredits.h`

**Modifications**:

- `SimBotMissionCredits.h` (pure, no locks, no agents): `dividedReward(reward, divisor)`
  mirroring `MissionObjectiveImplementation.cpp:320` (`reward / max(divisor, 1)`),
  and `withinBounds(amount, min, max, divisor)`. Solo bots pass divisor 1. The
  divisor is a parameter now so F_0.9.4 (group split) changes a value, not a
  shape.
- In `onPveBotMissionLairDestroyed`, inside the existing `if (missionCompleted)`
  block under `pveMutex`, copy the matched offer's `offerId` and
  `difficultyLevel` into locals. Nothing else changes under the lock.
- After the `pveMutex` scope closes, when `missionCompleted` is true, call a new
  private `awardPlayerBotMissionCredits(identityId, offerId, lairOid, difficultyLevel, divisor)`:
  1. gate off → count `skippedGateOff`, return;
  2. roll the reward through `MissionManager::rollDestroyMissionReward`
     (`zoneServer->getMissionManager()`; null manager → count `skippedNoManager`);
  3. apply the divisor;
  4. `grantPlayerBotCredits(identityId, amount, true, "mission", lairOid, "level=<n>")`; on success
     bump `awarded` and `creditsTotal` and remember the last amount, level and
     time; on failure bump `rejected` (the store already counts the reason —
     no record, disabled, invalid amount — in `awards.*`).
  5. emit `MISSION_CREDIT id= offerId= difficultyLevel= amount= divisor= result=`
     to `missiondiag.log`.
- The award returns a **disposition** (`AWARDED`, `GATE_OFF`, `NO_MANAGER`,
  `REJECTED_NO_RECORD`, `REJECTED_OTHER`), and `onPveBotMissionLairDestroyed`
  returns it to its caller, with `NOT_COMPLETED` when no offer transition
  happened. Production callers ignore it; the harness asserts it, so a scenario
  cannot pass because completion silently never reached the award branch.
  `grantPlayerBotCredits` gains an optional out-parameter naming its rejection
  reason so `REJECTED_NO_RECORD` is exact.
- **Idempotency** is the existing guarded transition, not a new structure.
  `pveHuntLairs.drop(bodyOid)` and `offer.completed = true` both happen under
  `pveMutex` before any award, so a second destruction callback for the same
  lair finds no tracked lair and returns before `missionCompleted` can be set.
  The earlier design's `pveMissionCreditedOfferIds` ring is dropped: offer ids
  restart at 1 on every boot (`pveNextMissionOfferId`), so a ring keyed on them
  would be wrong across restarts and adds nothing within one.
- **What is not paid**: the grind fallback and lone-creature hunting (no offer,
  as for a player with no mission), the legacy non-board completion path
  (`recordPveHunterCompleted`, no difficulty on the order), and any mission that
  ends for another reason (`hunter_died`, `travel_home`, `timeout`,
  `max_retreat_cycles`, `wave_pack_avoided`). A bot that dies and whose lair is
  later destroyed by something else is paid only if the offer still matches its
  body and lair, which is today's completion rule.

### 4. Doctor-buff payment

**Files**: `SimPlayerManager.{h,cpp}`, `SimHunterController.{h,cpp}`

**Current state**: `beginBuffUp` (`SimHunterController.cpp:1640`) calls
`computeBuffNeeds` and stores the result in `pveNeedDoctorBuff`. Doctor buffs
land in two places: the real-doctor success branch in `runBuffUpTick`
(`:3912-3924`, `recordPveBuffSource(bodyOid, "real-doctor")`) and the synthetic
fallback in `applyHunterBuffsForFamily(PVE_BUFF_FAMILY_DOCTOR)` when `appliedAny`
is true (`:1313-1317`).

**Modifications**:

- Manager, a **reserve → commit / release** trio so the fee decided at the start
  of a buff-up is the fee charged at delivery, whatever is hot-reloaded in
  between. Reservations live in a small `VectorMap<identityId, int64>` guarded
  by `progressionMutex`; they are in-memory only and never persisted.
  - `PlayerBotBuffFee reservePlayerBotDoctorBuffFee(uint64 identityId)` returns
    one of `NOT_CHARGED` (gate off, fee 0, or no progression record — not a
    charged population), `RESERVED` (snapshots the current fee; requires
    `bankCredits - alreadyReserved >= fee`), or `UNAFFORDABLE`. A new reserve
    replaces any stale reservation for that identity.
  - `commitPlayerBotDoctorBuffFee(uint64 identityId)` spends the **snapshotted**
    amount through the same balance mutation as `spendPlayerBotCredits`
    (source `doctor_buff`), drops the reservation, and counts
    `charged`/`creditsSpent`. With no reservation it does nothing. Because the
    reservation was subtracted from the spendable balance and this controller
    is the only spender for its identity, the commit cannot fail on balance;
    the one failure left is the record having been reaped mid-trip, counted as
    `chargeFailed`. Commit **rechecks the identity-scoped gate**: with the
    gate now off it releases the reservation instead of spending (counted
    `releasedGateOff`), so turning the gate off stops charges at once, including
    for buff-ups already in flight. The buff that was arranged stays.
  - `releasePlayerBotDoctorBuffFee(uint64 identityId)` drops an uncommitted
    reservation and counts `released`.
  - `spendPlayerBotCredits` itself treats reserved credits as unavailable, so a
    future second spender cannot take them.
- Controller, `beginBuffUp`: after `computeBuffNeeds`, when `needDoctor` is true,
  call the reserve. `UNAFFORDABLE` sets `needDoctor = false` before it is stored
  in `pveNeedDoctorBuff` and counts `skippedUnaffordable`; if that leaves
  nothing needed, the existing "no detour" branch runs. The result is kept in a
  controller field for the rest of the buff-up.
- Controller: call the commit at the two landing sites above, after the agent
  lock is released (the real-doctor branch already releases it; the fallback
  call moves below the block that holds it). Commit is idempotent per
  reservation, so a buff-up in which both sites fire charges once.
- Controller: call the release at the end of `finishPveBuffProviderFlow` and in
  the controller's order reset / death cleanup, so a buff-up that delivered no
  doctor buff, or was abandoned, charges nothing.
- `finishPveBuffProviderFlow` applies the synthetic doctor fallback only when
  `pveNeedDoctorBuff` is true. Every site that sets `pveDoctorFallbackNeeded`
  on a provider failure is conditioned on the doctor stage (checked:
  `:1130`, `:1382`, `:1401`, `:1418`, `:1448`, `:1522`, `:2546`, `:3929`), so
  this guard is defensive; it makes "unaffordable means no doctor buffs" hold
  by construction.
- Charged once per buff-up that delivers doctor buffs. The existing reapply
  threshold (`realBuffReapplyThresholdSeconds`, 900 s) already stops a bot from
  re-buying buffs that are still running.
- Entertainer buffs stay free in this chunk.

### 6. Parity harness

**Files**: `SimPlayerManager.cpp` (step runner), `sim_player_manager.lua`
(`playerBotParityTest` scenarios)

**Isolation rules for every new scenario** (the existing matrix leaves shared
identities with balances, e.g. identity 0 holds 600 credits, and the production
bots run while the harness does):

- Each scenario mints its own identity (`mintIdentity` with an `identityRef`)
  and removes it at the end (`deleteIdentity`). No scenario reuses another's
  record.
- Assertions are on that identity's **balance delta** and on the op's own
  result, never on global counters. `missionCredits.*` and `buffPayment.*` are
  telemetry and are not test oracles.
- The two gate overrides are **identity-scoped**, in the shape of
  `playerBotCombatAbilitiesGateEnabled(identityId)` (`SimPlayerManager.cpp:10740`):
  the override applies only to identities in the scenario's scoped-id set, so
  arming a gate for a scenario never pays or charges a production bot. Both
  gate functions therefore take the identity id. The fee override is scoped the
  same way.

New ops:

- `setMissionCreditGate{identityRef, expect}` and
  `setBuffPaymentGate{identityRef, expect, feeCredits}` — identity-scoped
  overrides, restored at scenario end.
- `completeMission{identityRef, difficultyLevel, repeat}` — in a **closed**
  `pveMutex` scope, seeds a `PveHuntLair` record and one accepted
  `PveBotMissionOffer` for the harness body with a synthetic lair oid. After
  that scope has ended, it calls the real `onPveBotMissionLairDestroyed`, which
  takes `pveMutex` itself. With `repeat = true` it calls it a second time with
  the same arguments. The harness body's controller is not a
  `SimHunterController`, so the hunter callback is skipped by the existing
  `dynamic_cast`. The op requires a live body for the identity (it fails the
  step with `no_body` otherwise; scenarios call `respawnBody{identityRef}` after
  `mintIdentity`, which leaves body oid 0). It records the returned disposition
  of each call and the bank delta, and takes `expectDisposition` (and
  `expectRepeatDisposition` when `repeat = true`).
- `assertLedger{identityRef, source, delta, count}` — reads the identity's
  `simbot_ledger` rows through the queued SQL lane, like `assertPersisted`.
- `assertCreditDeltaInBounds{identityRef, difficultyLevel, missions}` — the
  delta since the scenario baseline lies within `missions × [min, max]` from
  the `MissionManager` bounds.
- `reserveDoctorBuffFee{identityRef, expect}`, `commitDoctorBuffFee{identityRef}`,
  `releaseDoctorBuffFee{identityRef}` — call the three manager functions and
  check the returned state.

New scenarios:

Scenarios 1 to 5 each run `mintIdentity`, `respawnBody`, the steps below, then
`deleteIdentity`.

1. `mission_credit_awarded` — level 10, one completion → `AWARDED`, delta
   within bounds.
2. `mission_credit_once_per_offer` — `repeat = true` → `AWARDED` then
   `NOT_COMPLETED`, delta within the bounds of one mission.
3. `mission_credit_gate_off` — override false → `GATE_OFF`, delta 0.
4. `mission_credit_no_record` — `deleteProgressionRow` on the scenario's own
   identity, then complete → `REJECTED_NO_RECORD`, and no record exists
   afterwards.
5. `mission_credit_persisted` — complete (`AWARDED`), `flushNow`,
   `assertPersisted` on `bankCredits` equals the in-memory balance.
6. `buff_payment_charges` — grant 1,000, fee 400 → reserve `RESERVED`, commit →
   delta −400.
7. `buff_payment_unaffordable` — grant 100, fee 400 → reserve `UNAFFORDABLE`,
   commit is a no-op, delta 0.
8. `buff_payment_released` — grant 1,000, fee 400, reserve, release → delta 0;
   a second reserve still succeeds.
9. `buff_payment_fee_snapshot` — reserve at fee 400, change the scoped fee to
   900, commit → delta −400.
10. `buff_payment_gate_off_or_zero_fee` — reserve returns `NOT_CHARGED`, delta 0.
11. `buff_payment_gate_off_mid_trip` — reserve at fee 400, set the scoped gate
    false, commit → delta 0 and no reservation left.
12. `ledger_records_grant_and_spend` — one mission and one committed fee, then
    `flushNow` → exactly two rows for the identity, with matching deltas,
    sources and a final `balance_after` equal to the balance.
13. Two scenarios, each on its own minted identity, both asserting that
    identity's rows only:
    - `ledger_not_duplicated_after_failed_flush` — `injectFault{failNextFlush}`
      (fires after the first balance UPDATE, so the journal row is already
      written): complete a mission, flush (fails), flush again →
      `assertLedger{count = 1}`.
    - `ledger_requeued_after_failed_insert` — a new fault point
      `injectFault{failLedgerInsert}` fails the journal INSERT itself: complete
      a mission, flush (fails) → `assertCounterDelta{flushFailures, 1}`; flush
      again → `assertLedger{count = 1}` and `assertLedgerPending{expect = 0}`.
      **Amended at live verification (run 20261013-225200):** the original
      intermediate checks (zero rows, one pending entry) cannot be observed.
      The maintenance lane retries the failed insert before a queued SQL
      assertion runs; the first two runs saw the row already written
      (`got=1 want=0`). The oracle is therefore the fault having fired plus
      the row existing exactly once with nothing pending.
14. `ledger_removed_with_identity` — complete a mission, `flushNow`,
    `assertLedger{count = 1}` first; then `deleteIdentity`,
    `runReaper{force = true}`, and `assertLedger{count = 0}`.
15. `ledger_reconciles_mismatch` — complete a mission and flush; write a
    different `bank_credits` straight to the row through the SQL lane;
    `reloadStore`, `flushNow` → one `reconcile` row whose `balance_after` equals the stored
    balance, the balance itself unchanged, and the identity's deltas sum to it.
    Ends with `runReaper{force = true}`: `deleteIdentity` leaves an orphan
    record by design and this is the last scenario, so nothing else reaps it.

## Technical Considerations

- **Pattern Usage**: the award is the F_0.9.1 kill-XP shape — decide under the
  owning mutex, release, then write the store. Gates follow
  `playerBotTrainingGateEnabled`. The single-formula-owner move follows
  `PlayerManager::getExperienceMultiplier()` from F_0.9.1: the oracle reads the
  server's real configuration.
- **Locking & References**: `progressionMutex` is never taken inside `pveMutex`
  (roadmap §2.6). The award and both buff-payment calls run with no agent lock
  and no `pveMutex` held. `rollDestroyMissionReward` takes no lock.
  `reservePlayerBotDoctorBuffFee` is called from `beginBuffUp` at a point where
  the controller holds no agent lock (`computeBuffNeeds` releases its own).
- **IDL Impact**: `MissionManager.idl` gains read-only natives; `src/autogen/` is
  regenerated by the build, never hand-edited. Expect a wider rebuild than usual
  because `MissionManager.h` is widely included.
- **C++ vs Lua Placement**: mechanics in C++; the two gates and the fee in Lua.
- **Gating & Simulation-Only**: this chunk performs a **real mutation**
  (`simbot_progression.bank_credits`, journaled in `simbot_ledger`) under the P.10 persistence policy: roster
  identities only, behind default-off capability gates, armed live only after a
  TRIP-verify PASS. Credits never touch a body's `CreditObject`, a player, a
  real doctor's balance, or the hive stockpile. Bots without a record are
  untouched.
- **Dashboard Visibility**: section 5.
- **Edge Cases**:
  - Offer ids restart per boot: nothing persists them, and idempotency does not
    depend on them.
  - Server stops between the award and the next store flush (60 s): the award
    and its journal entry are lost together with the rest of that flush window,
    exactly like kill XP. Accepted.
  - A bot whose record is missing: skipped and counted, never created.
  - Fee set above any reachable balance: every progression bot hunts without
    doctor buffs. This is a configuration choice, visible as
    `skippedUnaffordable` climbing; the default fee is 0.
  - A new bot has 0 credits, so with a non-zero fee its first missions run
    without doctor buffs. One level-5 mission pays about 1,875. The live run
    measures whether unbuffed first missions cost deaths before a fee is
    recommended.
  - Int overflow: the reward is an `int` in stock code and stays one; the bank
    balance is `int64`.

## Safety analysis

| Risk | Why it is contained |
|---|---|
| Double payment | Single-shot transition under `pveMutex`; scenario 2 proves it; live assertion `awarded == LAIR_DESTROYED_CREDIT` delta |
| Payment to a non-roster body | `grantPlayerBotCredits` requires an existing record; scenario 4 |
| Changing what players earn | The stock call site calls the same two lines moved into a method; no constants change. Checked live by reading a real player mission's reward against the bounds |
| Lock inversion in the destruction callback | The award runs after the `pveMutex` scope closes and takes only `progressionMutex`, the same order as kill XP |
| A bot stranded in BUFF_UP by the affordability skip | The skip only flips `needDoctor` before the existing branches run; no new phase or wait is added. Live assertion: no bot sits in BUFF_UP longer than today's bound |
| Buff payment making bots die more | Fee defaults to 0; the gate ships off; the live run reports deaths per mission with the fee on against the v0.9.8 baseline (4 deaths in 26 missions) |
| Journal grows without bound or stalls the flush | Pending cap with a drop counter, daily retention prune, rows written on the existing maintenance SQL lane in the existing batch; about 16 rows per bot-hour at the v0.9.8 mission rate |
| Journal and balance disagree after a crash | Detected at load, counted, and closed with a durable `reconcile` row; the balance stays the authority and is never rewritten from the journal |
| Rollback | Both gates are hot-reloaded Lua flags. Turning them off stops awards and charges at once. Balances already granted stay in the store and are harmless with no consumer |

     - `missionCredits.awarded` delta equals the `LAIR_DESTROYED_CREDIT` count

     - every `MISSION_CREDIT amount` lies within the bounds for its
       `difficultyLevel`;
     - for each bot, bank balance equals the sum of its `MISSION_CREDIT`
       amounts;
     - `simbot_progression.bank_credits` in MySQL equals the dashboard value
       after a flush;
     - for each bot, the sum of its `simbot_ledger` deltas equals its bank
       balance, the row count equals its awards, and `ledger.balanceMismatch`
       and `ledger.dropped` are 0, including after the verification restart;
     - no award for any mission that ended another way;
     - a player's terminal destroy mission still shows a reward inside the
       bounds.

       `doctor_buff` row per charge;
     - `skippedUnaffordable` rises only for bots whose balance was below 500 at
       that moment;
     - `chargeFailed == 0` and `reservedNow` returns to 0 when no bot is in a buff-up;
     - deaths per mission reported against the v0.9.8 baseline.
