# Multi-Family Hunter Demand Implementation Plan

**Version:** F_0.6.0 (minor — new economy behavior, backward-compatible)
**Branch:** `feat/p87-market-driven-mission-hunting` (continues from F_0.5.0 / v0.5.0; not merged to `miner-ai`)
**Builds on:** F_0.5.0 (P.8.7 market-driven mission hunting)

## Overview

Today a PvE hunter kill credits **exactly one** resource family (the order's
`harvestKind`, in practice always `meat`), and only chef profiles demand that
family. When accumulated meat crosses its ceiling, **every** hunter idles,
because meat is the *sole* dispatch signal (the F_0.5.0 saturation class).

This feature makes each kill **credit all three creature families the corpse
yields — hide, bone, meat** — and gives **hide and bone their own demand
signals** by teaching the existing armorsmith (`composite_armor_supply`) and
weaponsmith (`master_weaponsmith_staples`) demand profiles to recognize those
creature families, each with an independent reserve target and ceiling. Hunt
dispatch is already gated per-family and the market matchmaker already loops over
every family signal, so once hide/bone emit signals the roster spreads across
three **independent** families: when meat saturates, hide/bone (which start near
zero, because miners are excluded from creature resources and hunters have never
credited them) still have large headroom and keep hunters working. No single
family's saturation can idle the whole roster.

**Scope boundary (owner decision — "spread only"):** creature-family supply is
**monotonic within a session** (`familySupply = bootBaseline + sessionHarvest`;
`consumeReservation` does not feed back until the next boot's baseline snapshot).
This is a pre-existing, already-accepted property of the meat path shipped in
F_0.5.0. F_0.6.0 therefore does **not** attempt in-session consumption feedback
or crafter-drain closure — that remains the documented "resource consumer"
economy phase and applies equally to meat. Consequently hide/bone, like meat,
will eventually fill their reserve targets and the roster idles again until a
consumer phase drains them or the server restarts. The concrete, in-scope win is:
**meat saturation alone no longer idles the roster**, and dispatch/harvest are
spread across three families.

## Problem Statement

- `recordPveHunterHarvest` (`SimPlayerManager.cpp:11993`) resolves and deposits
  **one** family from `order.harvestKind`, even though the corpse's
  `CreatureTemplate`/`Creature` already expose `getHideType/getBoneType/
  getMeatType` and `getHideMax/getBoneMax/getMeatMax`. Two of the three families
  are discarded every kill.
- `demandStateProfileUsesConceptualLabel` (`SimPlayerManager.cpp:1870`) only maps
  the creature family `meat` (to the two chef profiles). Nothing maps `hide` or
  `bone`, so `deriveDemandFamilySignals` (`:2128`) never emits a hide/bone signal
  and `runPveHunterMatchmaker` never dispatches for them — even though
  `marketDispatch.families` in lua is already `{ "meat", "hide", "bone" }`.
- The acquisition-ledger config lists only `creatureFamilies = { "meat" }`
  (`sim_player_manager.lua:734`). The loader iterates that list; hide/bone would
  need to be added or the demand loop never produces their supply/signal, and any
  hide/bone ceiling/reserve keys are ignored.
- Inbound reservation (`computeReservedInboundByProfileFamily`, `:11844`) and the
  matchmaker's post-assignment decrement (`:11456`, `:11641`) each track only the
  **single** dispatched family. A multi-family kill credits families neither path
  anticipates, so both across passes (reservation) and within one pass
  (decrement) two hunters can chase the same hide/bone gap.

## Solution Architecture

Four coordinated, always-on changes (owner decision: no gate), all within the
existing SimPlayer/AiEconomy demand machinery, all simulation-only:

1. **Supply — credit all three families per kill.** Refactor
   `recordPveHunterHarvest` to resolve hide+bone+meat type/max in one target-lock
   pass and deposit up to three provenance-tagged (`pve_hunter`) accumulators,
   incrementing `pveSessionHarvestByFamily` per family. Skip any family whose type
   is empty or max < 3. Once-per-corpse dedup stays in `recordPveHunterKill`.

2. **Demand recognition — hide/bone as demanded families.** Extend
   `demandStateProfileUsesConceptualLabel` so `composite_armor_supply` recognizes
   the `hide` creature family and `master_weaponsmith_staples` recognizes `bone`
   (creature-family-gated, mirroring the chef→`meat` idiom). No change to those
   profiles' mineral demand or to their crafter consumption queries (consumption
   is out of scope — see scope boundary).

3. **Config — register hide/bone families + ceilings.** In
   `sim_player_manager.lua`, add `hide`/`bone` to `acquisitionLedger.creatureFamilies`
   and give them `familyReserveTargets` and `familyAllocationCeilingFraction = 1.0`
   (matching the meat saturation fix) so each emits an independent reserve-driven
   signal even when the profile's mineral shared gap is small.

4. **Inbound + intra-pass — reserve/decrement all three (owner decision).** Track
   per-family expected and harvested units on `PveHuntOrder`; capture per-family
   expected yields at order creation; reserve each family's remaining expected
   against every profile that recognizes it (between passes); and after each
   in-pass assignment decrement all three family signals across matching profiles
   (within a pass).

## Implementation Details

### 1. Multi-family kill crediting (supply side)

**File:** `src/server/zone/objects/creature/simplayer/SimPlayerManager.cpp`

**Current state:** `recordPveHunterHarvest` (`:11993`) validates a single
`harvestKind ∈ {hide,bone,meat}`, resolves one `resourceType` + `harvestAmount`
under the target lock, deposits one accumulator (`:12067`), then increments the
scalar `pveHunterHarvestUnitsTotal`, the single-family `pveSessionHarvestByFamily`
entry, `order.harvestedUnits`, and `identity.harvestUnits`.
`recordPveHunterKill` (`:12130`) calls it once with `order.harvestKind` at
`:12160`.

**Modifications:**
- Refactor the per-family body into a helper invoked for each of
  `{hide, bone, meat}`. Under **one** `Locker targetLock(targetAgent)` read all
  three types + maxes; then for each family with a non-empty type and max ≥ 3,
  resolve the `ResourceSpawn`, build the accumulator (existing logic
  `:12063–12103`, unchanged per family), and record it under
  `spawnYieldAccumulatorMutex` (copy values out of the target lock first — do not
  nest).
- Under `pveMutex` (single acquisition after all deposits): sum the three
  `harvestAmount`s into `pveHunterHarvestUnitsTotal`, `order.harvestedUnits`
  (display grand total), and `identity.harvestUnits`; increment
  `pveSessionHarvestByFamily[family]` **and** the new per-family
  `order.harvested{Hide,Bone,Meat}Units` for each family actually deposited.
- A family whose type is empty / max < 3 / spawn missing increments
  `pveHunterHarvestMisses` (as today) via a per-family `continue`, never aborting
  the other families (change the current early `return` guards to `continue`).
- `recordPveHunterKill` calls the refactored function which now always attempts
  all three families; `harvestKind` is still logged as the *dispatched* family.

**Locking:** unchanged choreography — target lock for reads,
`spawnYieldAccumulatorMutex` for accumulator writes (never nested inside the
target lock), `pveMutex` for counters. No new lock order.

### 2. Demand recognition for hide/bone

**File:** `src/server/zone/objects/creature/simplayer/SimPlayerManager.cpp`

`demandStateProfileUsesConceptualLabel` (`:1870`):
- For `composite_armor_supply`, additionally return true when
  `includeCreatureFamilies && (resourceLabel == "hide" || resourceLabel.beginsWith("hide_"))`.
- For `master_weaponsmith_staples`, additionally return true when
  `includeCreatureFamilies && (resourceLabel == "bone" || resourceLabel.beginsWith("bone_"))`.
- Keep the existing mineral returns intact. Each of these profiles then has
  exactly **one** creature family in `deriveDemandFamilySignals`' eligible set
  (minerals are not in `creatureFamilies`), so the ANY-OF shared-gap split is
  trivial (one family gets the whole creature-family allocation + its own
  reserve).

No edit to `createDemandProfileDefinitions` — consumption of hide/bone is out of
scope, so the profiles' crafter query lists are left unchanged.

### 3. Config: register hide/bone families + ceilings

**File:** `bin/scripts/managers/sim_player_manager.lua`

**Current state (`:727–745`):**
```
acquisitionLedger = {
    creatureFamilies = { "meat" },
    familyReserveTargets = { meat = 2500 },
    familyAllocationCeilingUnits = { meat = 0 },
    familyAllocationCeilingFraction = { meat = 1.0 },
    ...
}
```

**Modifications:**
- `creatureFamilies = { "meat", "hide", "bone" }` (the loader iterates this list
  to build `familySupplyByFamily` and derive signals; without it hide/bone never
  get supply/signals and the `1.0` ceilings below are ignored — the loader
  otherwise auto-adds market families at the 0.25 fallback fraction).
- `familyReserveTargets = { meat = 2500, hide = 2500, bone = 2500 }` (owner-tunable
  starting values).
- `familyAllocationCeilingUnits = { meat = 0, hide = 0, bone = 0 }`.
- `familyAllocationCeilingFraction = { meat = 1.0, hide = 1.0, bone = 1.0 }`.
- Verify in the config loader (the `applyPveConfig` / acquisition-ledger parse
  path) that `familyReserveTargets` and `familyAllocationCeiling*` are read
  **per entry in `creatureFamilies`** (not a hardcoded `meat` key). If the loader
  hardcodes `meat`, generalize it to iterate `creatureFamilies`.

### 4. Reserve-all-three inbound + intra-pass decrement

**File:** `src/server/zone/objects/creature/simplayer/SimPlayerManager.{h,cpp}`

**Current state:** `PveHuntOrder` (`SimPlayerManager.h:234`) has scalar
`expectedYieldUnits`/`harvestedUnits`. `computeReservedInboundByProfileFamily`
(`:11844`) reserves `expectedYieldUnits − harvestedUnits` under key
`order.demandProfileKey + "|" + order.harvestKind`. The market matchmaker
(`:11451–11457`) and legacy matchmaker (`:11636–11641`) each decrement only the
*selected* `DemandFamilySignal` after an assignment.

**Per-family fields (`PveHuntOrder`):** add `expected{Hide,Bone,Meat}Units` and
`harvested{Hide,Bone,Meat}Units` (uint64, default 0). Keep scalar
`harvestedUnits` as the display grand total. These are plain in-`.h` struct
fields (trivial binary-stream stubs) — no `.idl`/autogen/migration.

**Capture per-family expected at order creation.** Everywhere
`order.expectedYieldUnits` is set from a selected lair source:
- **Market path** (`:11424–11428`): read the per-family expected from the
  selected `PveLairYieldEntry`'s **`amountsByFamily`** map (`SimPlayerManager.h`,
  `VectorMap<String,uint64>` keyed by `"hide"/"bone"/"meat"`), multiplied by
  `quota` the same way `expectedYieldUnits` is. Thread the selected lair entry (or
  its three amounts) to the order — carry the three amounts on `PveMarketCandidate`
  (`SimPlayerManager.cpp:624`) if the entry is not otherwise available at the
  write site.
- **Legacy path** (`:11610–11616`, `:11781`): read the per-family expected from
  the **`PveHuntSpecies`** scalar fields `estimatedHide/Bone/MeatUnits`
  (`SimPlayerManager.h:119` struct), × quota.
- Set the dispatched family's `expected*Units` consistently with the existing
  scalar `expectedYieldUnits` so the two agree for the dispatched family.

**Increment per-family harvested.** `recordPveHunterHarvest` (§1) increments the
matching `order.harvested{Hide,Bone,Meat}Units` per deposited family under the
existing `pveMutex` block.

**Rewrite `computeReservedInboundByProfileFamily` (between passes).** For each
order and each family `f ∈ {hide,bone,meat}` with `expected_f > harvested_f`,
compute `remaining_f`; then for **every enabled demand profile `p`** where
`demandStateProfileUsesConceptualLabel(p, f, true)` is true, add `remaining_f` to
key `p + "|" + f`. Enabled profiles come from the `demandStateSimulationProfileEnabled`
gate. This keys incidental hide/bone against their real consumers
(armorsmith/weaponsmith) and meat against the chef profiles, matching how
`deriveDemandFamilySignals` reads `familyInbound` by `profileKey|family` (`:2187`).
Runs under `pveMutex` (already held at `:11850`); profile list is a snapshot.

**Add intra-pass decrement (fixes over-dispatch within one matchmaker run).** In
both matchmaker assignment sites, after committing an assignment, replace the
"decrement the selected signal only" step with: for each family
`f ∈ {hide,bone,meat}` with the assigned hunt's expected `expected_f` (× quota),
decrement `signalUnits` on **every** `DemandFamilySignal` in the live
`demandResults` whose `family == f` (saturating at 0). This suppresses the same
hunt's incidental hide/bone from being chased by the next hunter in the same
pass, complementing the between-pass reservation. Encapsulate in a small helper
so both matchmaker paths share it.

### 5. Dashboard visibility

**File:** `src/server/zone/objects/creature/simplayer/SimPlayerManager.cpp` (JSON) +

## Technical Considerations

- **Pattern Usage:** mirror the single-family deposit and the chef→`meat`
  demand-label idiom exactly; reuse `PveLairYieldEntry.amountsByFamily` (already
  populated by the lair index) for market expected yields and the
  `PveHuntSpecies` scalars for the legacy path.
- **Locking & References:** no new locks. Per-family deposits reuse the existing
  target-lock → `spawnYieldAccumulatorMutex` → `pveMutex` sequence with values
  copied out of each lock before the next (the P.4.4 orphan class came from
  mismatched lock/lifecycle order — none introduced here).
- **IDL Impact:** none. `PveHuntOrder`/`PveMarketCandidate`/`PveHuntSpecies` are
  plain in-`.h` structs (trivial `toBinaryStream`/`parseFromBinaryStream`), not
  `.idl` objects — added uint64 fields need no autogen regen and no schema/BDB
  migration.
- **C++ vs Lua Placement:** crediting/accounting/decrement logic is structural →
  C++; family list, reserve targets, ceilings, and the already-present
  `marketDispatch.families` are tunable → lua.
- **Gating & Simulation-Only:** owner chose always-on (no new flag). Strictly
  simulation-only — deposits go to `spawnYieldAccumulators` → the hive stockpile
  ledger exactly as the meat path does today; no real inventory/credit/market
  mutation. All new demand runs under the existing `acquisitionLedger` /
  `demandStateSimulationProfileEnabled` gates.
- **Dashboard Visibility:** `demandFamilies` + new `harvestByFamily`.
- **Live Verification Plan:** after owner restart, pull the dashboard
  (`curl -sk .../v1/aieconomy/dashboard/`) and confirm:
  (1) `pveActivity.demandFamilies` contains `hide` and `bone` rows with
  `signalUnits > 0`; (2) `harvestByFamily` shows hide/bone/meat all climbing after
  kills; (3) hunter orders dispatch with mixed `harvestKind ∈ {hide,bone,meat}`
  (not meat-only) — most decisively, **with meat saturated the roster keeps
  hunting hide/bone instead of all going `IDLE_HOME`**; (4) no over-dispatch
  thrash (multiple hunters redundantly assigned the same family in one pass).
- **Edge Cases:**
  - Creatures with no hide/bone (or max < 3): skip that family, credit the rest;
    increment `pveHunterHarvestMisses` per skipped family without aborting.
  - Per-family expected vs harvested drift (actual max ≠ index estimate): inbound
    `remaining_f` clamps at 0; harmless over/under-reserve self-corrects next
    pass (matches today's single-family behavior).
  - Eventual hide/bone saturation is **expected and not a regression** — it is the
    same in-session monotonic-supply property meat has today, deferred to the
    consumer phase (scope boundary).
  - ANY-OF substitution: hide/bone now formally substitute for metal in
    armor/weapon demand (simulation abstraction). Because minerals aren't in
    `creatureFamilies`, hide/bone only ever appear via the independent reserve
    target — this is why the `familyReserveTargets`/`1.0` ceiling entries (§3) are
    required for a non-zero signal, not optional.
  - Double-count guard: once-per-corpse via `order.lastCreditedTargetOid`
    (`:12142–12145`), untouched.

## Performance & Cost Impact

- Per kill: up to 3 `getCurrentSpawn` + accumulator upserts instead of 1 (bounded,
  event-frequency, not per-tick). Negligible.
- `computeReservedInboundByProfileFamily`: O(orders × 3 families × enabled
  profiles ~6) — trivial at roster scale (≤ a few dozen orders).
- Intra-pass decrement: O(assignments × 3 × familySignals) per matchmaker run —
  trivial. No new per-tick O(n²) SimPlayer iteration.

## Backward Compatibility

- New struct fields default 0; in-memory only (orders/candidates aren't persisted
  objects) → no migration. An order predating the change reads per-family
  expected/harvested as 0 → inbound simply under-reserves it until completion;
  self-healing, no crash.
- Reverting = restore single-family `recordPveHunterHarvest`, drop the two label
  cases, remove the lua hide/bone keys, restore the single-family decrement.
  Purely additive.

## Test Impact

- Affects demand/harvest paths verified only via live dashboard today; no existing
  unit test covers `recordPveHunterHarvest` or
  `computeReservedInboundByProfileFamily`.
- New pure logic worth a fixture-free unit test (COVERAGE-DEBT candidate): the

- `deriveDemandFamilySignals` gains hide/bone paths — a targeted test that a

- Primary acceptance remains **live-dashboard before/after** per project standard
