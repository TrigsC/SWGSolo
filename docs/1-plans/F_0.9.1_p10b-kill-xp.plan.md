# F_0.9.1 — XP per kill for roster PlayerBots (P.10b) Implementation Plan

## Overview

Give roster PlayerBots real combat experience for the creatures they kill, using
the same formula the engine already applies to human players — including the
server's `globalExpMultiplier` — scaled by a single Lua-tunable `killXpRate`
that ships at `1.0`, so a bot at the default rate earns exactly what an
equivalent unskilled player would. The award is
computed from the victim's `ThreatMap`, which already keys every attacker —
AiAgents included — by that attacker's weapon XP type, so no combat-side change
is needed. XP lands in the F_0.9.0 identity-keyed progression store
(`simbot_experience`), never on any object.

This is the first chunk in the P.10 line with a **production caller** of the
award API. It is therefore the first chunk where the roadmap's award-requires-record
invariant is exercised by live traffic rather than only by the harness.

## Problem Statement

F_0.9.0 shipped the store, the award API, the reaper, the dashboard section and
an 18-scenario harness — but with `awards.accepted = 0` and no production caller
by design. Roster hunters kill creatures continuously (114 kills observed in a
single P.8 soak) and gain nothing. Every downstream chunk depends on bots having
an XP history: F_0.9.5 skill training spends XP, and the F_0.9.8 allocation
policy reads profession progress to decide what to grow next.

Two engine facts make this the right next step and constrain how it is done:

1. `ThreatMap::addDamage` (`ThreatMap.cpp:69-105`) records **all** attackers,
   resolving the XP type from `tarCreo->getWeapon()->getXpType()` when no
   explicit type is passed. Bot hunters already appear in the victim's threat map
   with `combat_rangedspecialize_rifle` damage. The data exists; nothing collects it.
2. Every reward path downstream of the threat map is ghost-shaped.
   `PlayerManagerImplementation::awardExperience` (`:2703-2707`) returns `0`
   immediately when `getPlayerObject()` is null, and the dissemination loop is
   fenced by `attacker->isPlayerCreature()` (`:2216`). A PlayerBot can never
   traverse it. The reusable asset is the threat-map data and the formula, not
   the award call.

## Solution Architecture

### Hook site — a deviation from the roadmap, with rationale

The roadmap sketched the branch at `CreatureManagerImplementation.cpp:677`,
beside the `disseminateExperience` call. **This plan hooks inside
`PlayerManagerImplementation::disseminateExperience` instead**, immediately after
`baseXp` is derived (`:2069-2092`) and before the attacker loop. Three reasons:

- **Coverage.** `disseminateExperience` has two callers: `CreatureManagerImplementation.cpp:677`
  (single-creature death) and `DisseminateExperienceTask.h:39` (lair death, which
  additionally passes `spawnedCreatures` and `lairZone`). Hooking at the
  CreatureManager site alone silently omits every lair kill. Hooking inside
  covers both with one branch.
- **Reuse.** `baseXp`, `totalDamage`, `zone`, `gcwBonus` and `winningFaction` are
  already computed at that point. The CreatureManager site would have to
  recompute `baseXp` from `AiAgent::getBaseXp()` and re-derive the lair case,
  duplicating logic that already exists ten lines away.
- **Precedent.** The P.7.4b ranked-NPC-Jedi FRS block already lives in exactly
  this function (`:1936-2067`) and already calls `SimPlayerManager::instance()`
  from it. The include, the singleton access and the lock posture are established.

`threatMap->removeAll()` runs at the end of `disseminateExperience` (`:2329`), so
the branch must read the map before that — which placing it before the attacker
loop guarantees.

### Lock posture — collect synchronously, award on a deferred task

`disseminateExperience` runs with `destructedObject` already locked; the FRS block
proves this by using cross-lockers (`Locker crossLocker(attackerCreo, destructedObject)`,
`:1985`). The bot branch must therefore take **no object lock at all**, and must
not block the destruction path on a mutex that the PvE maintenance thread can
hold across SQL.

The FRS block's own answer is the pattern to copy: it collects what it needs
synchronously, then does the award inside
`Core::getTaskManager()->executeTask(lambda, "SimPvpNpcFrsXpAwardTask")`
(`:2007-2065`). F_0.9.1 does the same:

**In the destruction path (synchronous, arithmetic only, zero mutexes):**
build a plain POD carrying, per eligible attacker, its OID, its
`(xpType, damage)` pairs copied out of the `ThreatMapEntry`, and **that
attacker's own** `groupMultiplier` and `gcwMultiplier`; plus the event-level
scalars `baseXp`, `totalDamage` and `globalMultiplier`. Nothing is resolved,
nothing is locked, nothing is written.

Group and GCW status are strictly per-attacker and cannot be hoisted to the
event: two bots in the same threat map can be in different groups, and
`winningFaction == attacker->getFaction()` is a per-attacker test that two
attackers of opposing factions answer differently. Each is resolved engine-side,
where the answer is already in hand, and reaches the task pre-multiplied — so the
task never needs a `GroupObject` or a `GCWManager`, and never needs the object
lock that reading them would require.

`globalMultiplier` is genuinely event-level. `PlayerManager::globalExpMultiplier`
is a private server-wide field (`PlayerManager.idl:111`) that
`awardExperience` applies to every award at `:2732`, and that administrators can
change at runtime. Omitting it would make "parity at rate 1.0" false on any
server that has ever tuned it. `PlayerManagerImplementation` reads its own member
directly and folds it into the event, so no accessor is added to `PlayerManager`.

**On the task (off the critical path):** resolve each OID to a roster identity
under `pveMutex`, derive the bot's level, apply the formula, and grant under
`progressionMutex`. Both are plain `Mutex`, neither is held while the other is
taken, and no agent lock is acquired inside either — the discipline F_0.9.0
established and documented in `SimPlayerManager.h:1841-1845`.

### Eligibility pre-filter — cheap, and deliberately not authoritative

Wildlife kills wildlife constantly. Every one of those victims has AiAgent
attackers in its threat map, so an unfiltered branch would spawn a task per
wildlife death. The synchronous pre-filter is therefore:

1. `simManager != nullptr && simManager->isPlayerBotKillXpEnabled()` — two plain
   bool reads; false is the shipped default and short-circuits everything below.
2. `attacker` is an AiAgent, is not a player creature, and is not a pet.
3. `attacker->getZone() == zone && destructedObject->isInRangeZoneless(attacker, 80)`
   — the identical range fence the player branch uses at `:2216`.
4. `attacker->asAiAgent()->getSimPlayerBot()` — an unlocked plain-member read,
   used **only** to skip obvious wildlife.

Filter 4 is explicitly **not** the authority on "is this a PlayerBot". That flag
is the one that leaked onto wild creatures through engine object reuse and was
fixed in `d38877020c` by resetting it in `AiAgentImplementation::loadTemplateData`.
It is used here purely as a cost filter, and the failure modes are both safe:

- **Stale true** on a wild creature costs one extra task that resolves no identity
  and awards nothing.
- **Stale false** on a real bot costs that bot one kill's XP. Not a correctness
  or safety defect.

Authority remains `resolvePlayerBotIdentity`, on the task, under `pveMutex`.
A body with no roster identity resolves to `0` and is dropped.

### The formula

Mirrors `PlayerManagerImplementation::disseminateExperience:2247-2284` step for
step, with the rate knob applied where the owner chose — after the per-kill cap,
before the lifetime ceiling:

```
for each (xpType, damage) in the attacker's entry:
    xp  = baseXp * (damage / totalDamage)
    xp  = min(xp, botLevel * 300)                 -- parity cap; counts cappedByLevel
    xp *= groupMultiplier                         -- 1.0f when ungrouped
    xp *= gcwMultiplier                            -- 1.0f when not on the winning faction
    if xpType != "jedi_general":
        combatXp = (uint32)(combatXp + xp)         -- truncates each iteration
    else:
        xp *= 0.2                                  -- and never enters combatXp
    if xpType == "dotDMG": continue                -- in combatXp, never awarded directly
    awardDirect(xpType, (int)xp)                   -- FIRST truncation, at the int boundary

awardCombatGeneral((int)(combatXp * 0.1f * globalMultiplier * killXpRate))
```

`awardDirect(type, n)` applies the tail terms and truncates a second time:
`(int)(n * globalMultiplier * killXpRate)`.

`combat_general` is deliberately **not** routed through `awardDirect`. It has
only one truncation, because the engine computes it in a single expression:
`combatXp` is already a `uint32` when it reaches `awardExperience`, so there is
no float-to-int boundary to cross, and `localMultiplier` (`0.1f`) and
`globalExpMultiplier` are multiplied together inside the same cast at `:2732`.
Passing it through the two-stage direct helper would truncate `combatXp * 0.1`
before applying the global multiplier and diverge from the engine in exactly the
way the direct path must *not*.

**The truncation counts differ by path, and that difference is the parity.**
`awardExperience` declares `int amount` (`:2703`), so the player's float
`xpAmount` is truncated at the call boundary *before* `globalExpMultiplier` is
applied inside at `:2732`, which truncates a second time. Collapsing that into
one multiply-then-truncate diverges: at `xp = 1.9` with a global multiplier of
`2`, a player earns `(int)((int)1.9 * 2) = 2` and a single-stage bot would earn
`(int)(1.9 * 2) = 3`. `combat_general` keeps its single stage for the reason given above.

`combatXp` accumulates the post-cap, post-group, post-GCW value once per type,
excludes `jedi_general`, and *includes* `dotDMG` — the engine's `continue` for
`dotDMG` comes after the accumulation (`:2270-2278`), so DoT damage earns combat
XP without touching the weapon's own type. The accumulation itself truncates on
every iteration because `combatXp` is a `uint32` and `xp` a `float` (`:2272`), so
fractional remainders are dropped per type rather than carried to the total;
mirroring that is part of the parity, not an implementation detail.

where `award(type, value)` truncates to `int` first and **skips the grant
entirely when the result is `<= 0`**, incrementing `killXpSkippedZero` rather
than calling into the API. This matters for two real cases: a configured
`killXpRate = 0.0`, which the clamp explicitly permits as a "wire it up but pay
nothing" soak setting, and an ordinary fractional result truncating to zero on a
low-damage share. Without the guard both would reach
`grantPlayerBotExperience`'s `amount <= 0` branch (`:9098-9101`) and inflate
`rejectedInvalidAmount` — a counter that F_0.9.0's harness asserts exact deltas
against, and that should mean "a caller passed something nonsensical", not
"the arithmetic rounded down".

`groupMultiplier` and `gcwMultiplier` are per-attacker values arriving on the
POD, each `1.0f` when the attacker is ungrouped or not on the winning faction.

The `combat_general` 10% mirrors `awardExperience(attackerCreo, "combat_general", combatXp, true, 0.1f)`
at `:2284`, where `0.1f` is the `localMultiplier` argument consumed at `:2732`.
Species and food-buff modifiers are **not** mirrored: bots have no species XP
modifier table entry and no food buffs, so those terms are `1.0` for a player in
the same position.

### Bot level

`calculatePlayerLevel` (`:4587-4606`) reads
`private_<weapontype>_combat_difficulty`, a skill mod that only trained skill
boxes provide. A bot with no trained skills scores `min(25, 0/100 + 1) = 1`,
so an unskilled player and an unskilled bot both cap at `1 * 300 = 300` per XP
type per kill. That is the parity bar, and it is the honest starting point.

Level therefore comes from `SimBotIdentity::skillTier` (`SimPlayerManager.h:112`,
default `1`, set from `pveConfig.skillTier`), clamped to `[1, 25]`, read on the
task in the same `pveMutex` acquisition that resolves the identity. It is
deliberately **never** taken from the body's template level — the roadmap's
standing warning, and a real hazard: a bot wearing a death-watch-wraith template
would report level 178 and earn 178×300 per type per kill. When F_0.9.5 lands
trained skills in the store, this helper is the single place that changes.

### Lifetime ceiling

`PlayerObjectImplementation::addExperience:708-717` is the authority on how a
player's XP stops growing:

```
xpCap = xpTypeCapList.contains(xpType) ? xpTypeCapList.get(xpType) : -1;
if (xpType.beginsWith("prestige_")) xpCap = INT_MAX;
else if (xpCap < 0)                 xpCap = 2000;
```

`xpTypeCapList` is populated by `SkillManager::updateXpLimits` (`:800-836`) from
trained skill-box caps first, then from `defaultXpLimits` for every type no
trained box covers. A bot with no trained skills therefore takes the defaults for
everything — which is precisely `defaultXpLimits`, loaded from
`datatables/skill/xp_limits.iff` at `SkillManager.cpp:202-226`.

`defaultXpLimits` is private (`SkillManager.h:51`). This chunk adds one
read accessor. The rejected alternative was re-parsing `xp_limits.iff` inside
`SimPlayerManager`, which would duplicate a datatable read and silently drift
from the engine the first time that table changes.

**The ceiling goes inside `grantPlayerBotExperience`, not in the kill path.** The
API already has an `int* awarded` out-parameter (`SimPlayerManager.h:2785-2786`)
that today can only ever report the full amount. Clamping inside grant makes that
parameter mean what its name says, gives every future XP source — F_0.9.2 onward —
the ceiling for free, and keeps the rule in one place rather than in each caller.

**This changes one already-verified F_0.9.0 harness expectation and must be
handled deliberately.** Scenario 11 `retained_record_survives_restart` grants
`4242` of `harness_restart`, a type absent from `xp_limits.iff`, which would now
clamp to the `2000` fallback and fail the restart probe. The fix is a one-value
edit — `4242` → `1234` — preserving the scenario's purpose (a distinctive value
surviving a real process restart) while staying under the fallback. Every other
F_0.9.0 XP amount (`250`, `10`, `0`, `1`) is already below any ceiling. Credit
amounts are unaffected; the ceiling applies to XP only.

### 2. PlayerManagerImplementation — the bot branch

**Modifications**:
- After `baseXp` is derived and before `playerList` is built, add the collection
  block described above. Guarded so the first statement is the disabled-gate

  else, keeping the engine-side edit small and reviewable.

### 4. Harness — ten new scenarios and three new ops

**File**: `MMOCoreORB/bin/scripts/managers/sim_player_manager.lua`
**File**: `MMOCoreORB/src/server/zone/objects/creature/simplayer/SimPlayerManager.cpp` (runner)

New step ops, parsed in `parsePlayerBotParityTestStep` (`:7578`) and dispatched
in the runner:

- `simulateKillXp{identityIndex|bodyOid, baseXp, totalDamage, damageByType={{xpType=..., damage=...}, ...}, groupMultiplier, gcwMultiplier, globalMultiplier, gateEnabled, rate}`
  — builds a synthetic `PlayerBotKillXpEvent` and drives
  `awardPlayerBotKillExperience`, the exact function the production task calls.
  The formula, the caps and the counters are therefore asserted against
  production code, not a test double.

  `damageByType` is a **list**, because a single kill routinely produces several
  types in one `ThreatMapEntry` and the interesting assertions live in how they
  combine: scenario 23 needs normal damage and `dotDMG` in the *same* event to
  prove `dotDMG` feeds `combat_general` without earning a row of its own, and to
  pin the rounding of a `combat_general` total summed across types rather than
  computed from one. The scalar `xpType`/`damage` shorthand is retained for the
  single-type scenarios so those steps stay readable.

  `groupMultiplier`, `gcwMultiplier` and `globalMultiplier` each default to
  `1.0` when the step omits them, and `gateEnabled`/`rate` default to the live
  configured values, so only the scenario that asserts a given term has to
  mention it. Because these are per-call parameters, a scenario asserting a
  non-default value cannot affect any concurrent production award.
There is deliberately **no global override op.** An earlier draft had one, and
it was wrong: the harness runs on the live server alongside active production
hunters, so globally clearing `awardKillXp` for scenario 19's duration would
silently drop real hunter awards, and globally setting `killXpRate = 2.0` for
scenario 24 would durably double-pay an unrelated hunter that happened to kill
during that window. Neither is acceptable in a chunk whose whole point is real
persistence.

Instead the gate and the rate are **parameters of the award call**, not reads of
global state at the point of use:

```
struct PlayerBotKillXpParams { bool enabled; float rate; };

awardPlayerBotKillExperience(event)          // production: params = live config
awardPlayerBotKillExperience(event, params)  // harness: params from the step
```

The single-argument overload is the production entry point and resolves
`params` from `isPlayerBotKillXpEnabled()` and `progressionKillXpRate` exactly
once per event. Both overloads then run the *same* implementation, which reads
`params.enabled` and `params.rate` — so scenario 19 exercises the real gate
branch and scenario 24 the real rate term, in the real function, while global
configuration is never mutated and concurrent production kills are unaffected.

The authoritative proof that the *shipped* gate value is honoured stays where it
belongs and cannot be faked: Boot A of the verification contract runs the shipped
configuration with `awardKillXp = false` and asserts every `killXp.*` counter at
zero and `gates.awardKillXp` false.
- `spawnKillTarget{identityIndex, template}` / `awaitKillTargetDeath{budgetMs}` —
  the call-site proof, driven rather than waited for. Together they make a
  dedicated harness bot kill a real creature and assert the exact XP it earns.

  **Why the harness bot can already do this without a single controller change**
  is the key finding: harness identities and hunter identities are created by
  the *same* body function (`SimPlayerManager.cpp:11780-11862`). A harness body
  therefore already carries the equipped `rifle_cdef` (`:11801-11815`), `faction
  0` so wildlife is attackable (`:11788`), and `ObjectFlag::ATTACKABLE` so the
  fight is two-way (`:11841`). The only harness-specific branches are the AI map
  (`:11878`) and the controller (`:15864`) — and `simParityTest`, exactly like
  `simHunter` and `simTraversalTest`, overrides **only** the `IDLE` socket
  (`templates.lua:66-80`), leaving the inherited root/attack/target/equip/kill
  sockets live. The body has been combat-capable since F_0.9.0; only its
  controller keeps it idle, and combat here is initiated by the manager, not the
  controller.

  `spawnKillTarget` therefore follows the *shape* of
  `spawnStructureTraversalTestAttacker` (`:33968-34029`) with the roles
  reversed — spawn the configured template a few metres from the bot via
  `CreatureManager::spawnCreature`, record its OID and its
  `AiAgent::getBaseXp()`, then `CombatManager::instance()->startCombat(bot, target)`
  and `activateAiBehavior(true)` — but it does **not** call into the traversal
  harness's helpers. `despawnStructureTraversalTestAttacker` is traversal-owned:
  it accepts only bot indices `0-1` and clears traversal-harness state, so
  borrowing it would corrupt an unrelated suite. The parity harness gets its own
  `playerBotParityTestKillTargetOid` (guarded by `playerBotParityTestMutex`, like
  every other runner field) and its own `despawnPlayerBotParityKillTarget()`. The stock combat tree drives real rifle
  attacks from there — the same combat the production hunters run — so the
  victim's `ThreatMap` gets a genuine `combat_rangedspecialize_rifle` entry and
  the award arrives through the real `CreatureManager::notifyDestruction` →
  `disseminateExperience` path. Nothing about the hook is simulated.

  `despawnPlayerBotParityKillTarget()` runs on **every** exit path: scenario
  success, assertion failure, budget timeout, a runtime disable of the harness,
  harness interruption, and the suite-wide cleanup pass — the same set the
  existing body/row cleanup already covers. It is idempotent and a no-op when
  the OID is zero or the object is already gone, so the death path and the
  cleanup path can both call it. A creature that outlives the run is the one
  leak this scenario could plausibly cause, and the verification contract
  asserts against it directly.

  `awaitKillTargetDeath{budgetMs}` must **not** treat death as the completion
  signal, and this is the subtlest hazard in the scenario. The award runs on the
  deferred `SimPlayerBotKillXpTask`, so the harness tick that observes the victim
  dead can easily run *before* the task has written to the store — the exact
  assertions that follow would then read zero and fail a working hook. The step
  therefore completes only when **all three** hold, inside the one budget:

  1. the recorded target is dead or gone;
  2. `killXp.kills` has advanced by at least one **from the baseline
     `spawnKillTarget` captured immediately before `startCombat`**;
  3. the identity's stored XP for the expected type is non-zero — required only
     when the computed expected award is itself positive.

  Only then do the exact-value assertions run. Condition 2 is what makes this a
  settle rather than a sleep: it is the counter the award task itself increments,
  so waiting on it waits on the actual work rather than on wall-clock time.

  The baseline must be captured **in `spawnKillTarget`, before combat starts**,
  and stored beside `playerBotParityTestKillTargetOid` — not read when the await
  step first runs. A rifle against a 135-165 HAM herbivore can finish the kill,
  and the award task with it, inside a single harness tick; an await step that
  sampled its own baseline on entry would then be waiting for a *second*
  increment that never comes, and would time out on a scenario that had already
  succeeded.

  Condition 3 carries the positive-award qualifier for the same reason the rate
  is allowed to be `0.0` at all: at `killXpRate = 0.0` the correct award **is**
  zero, and an unconditional non-zero requirement would make a correct
  configuration unsatisfiable. The oracle already computes the expected value, so
  the settle simply asks for non-zero XP when that value is positive and relies
  on conditions 1 and 2 alone when it is not. Verification runs at the shipped
  rate of `1.0`, where the expected award is `85` and condition 3 is live.

  Durability is then proven the way the rest of the matrix proves it — a
  `flushNow{force=true}`, a `reloadStore`, and a repeat of the same exact
  assertions — so the kill's XP is shown to survive the round trip to MySQL and
  not merely to exist in the dirty in-memory record.

## Technical Considerations

- **Pattern Usage**: The P.7.4b FRS block in the same function is the direct
  model — same singleton access, same deferred-task shape, same "collect
  synchronously, award asynchronously" split.
- **Locking & References**: No object lock is taken by the new code, in either
  the destruction path or the task. `pveMutex` and `progressionMutex` are taken
  sequentially and never nested, matching `SimPlayerManager.h:1841-1845`. The
  task captures OIDs and scalars by value and holds no reference to the corpse
  or to any attacker.
- **IDL Impact**: **DEVIATION, taken during code review.** The plan said none;
  one line was added to `PlayerManager.idl` — `public float
  getExperienceMultiplier()`, symmetric with the existing
  `setExperienceMultiplier` — because the scenario-28 oracle must recompute
  the expected award from the same server-wide multiplier `awardExperience`
  applies, or a tuned server would fail a correct award. The rejected
  alternative was having the harness borrow that term from the code under
  test, which is circular. `src/autogen/` is gitignored and untracked, so the
  commit footprint is the single `.idl` line and the stubs regenerate at build
  time; no generated file is hand-edited.
- **engine3**: Untouched. The pre-existing dirty `TaskManager.h` stays excluded
  as in every release since v0.4.4.
- **C++ vs Lua Placement**: The formula and the store are C++; the gate, the rate
  and the whole scenario matrix are Lua. `killXpRate` is read per award, so it is
  tunable by editing Lua and restarting — the same cadence as every other knob in
  this file.
- **Gating**: `awardKillXp` ships `false`, under `playerBotProgression.enabled`
  which also ships `false`. Two gates must both be flipped before a single point
  of XP is written. This is a real mutation, authorised by the P.10 persistence
  policy in CLAUDE.md, and confined to roster identities.
- **Dashboard Visibility**: Yes — the `killXp` object and the real `awardKillXp`
  gate value, both in the existing `playerBotProgression` root.
- **Live Verification Plan**: Boot with both gates off and assert
  `killXp.*` all zero and `gates.awardKillXp` false. Boot with both on and run
  the 28-scenario matrix, including the driven-kill scenario, and re-assert
  `gates.awardKillXp` still true and `killXp.rate` still the configured value
  afterwards, proving no scenario mutated global configuration. Restore and
  re-assert inert. Cross-check `simbot_experience` rows directly in MySQL for the
  scenario 28's minted identity, which is where its claim is settled. Then
  confirm no `dwarf_nuna` spawned by the harness survives the run and no harness
  identity rows remain — the same leak assertions F_0.9.0's contract already
  carries, extended to the kill target.
- **Edge Cases**: `totalDamage == 0` (returns earlier); `baseXp <= 0` (skip);
  an attacker whose body is destroyed between collection and task execution
  (resolution simply fails, nothing is awarded); a bot that damages a victim then
  leaves the 80 m fence (excluded, exactly as a player would be); `dotDMG`
  (counted toward `combat_general`, never awarded directly); `jedi_general`
  (0.2× and excluded from `combat_general`, matching the player rule);
  `prestige_*` types (`INT_MAX` ceiling, mirrored); a rate of `0.0`, or any
  fractional share truncating to zero (grant skipped, `killXpSkippedZero`
  advances, `rejectedInvalidAmount` untouched); an administrator changing
  `globalExpMultiplier` at runtime (read per event, so it follows); attackers of
  opposing factions in one threat map (GCW eligibility is per-attacker, so each
  gets its own answer); a kill-target that survives its budget or that kills the
  harness bot instead (despawned on every exit path, scenario fails cleanly, no
  creature leaks); a kill that completes within one harness tick (the settle
  compares against a baseline captured before combat, so it cannot miss the
  increment); a verification run at `killXpRate = 0.0` (the settle drops its
  non-zero XP condition and the exact assertion expects zero); integer overflow on accumulated XP (the existing check at
  `:9106` already guards it and now precedes the clamp).

## Performance & Cost Impact

Gate off (shipped): two bool reads per creature death. Immeasurable.

Gate on: for each death with at least one attacker passing the pre-filter, one
short POD build and one task dispatch. Wildlife-on-wildlife deaths are rejected
by the `getSimPlayerBot()` pre-filter without allocating. The SQL cost is zero at
award time — awards mark the record dirty and ride the existing 60 s atomic-swap
flush, adding no new writer to the single maintenance SQL lane.

## Backward Compatibility

No schema change and no migration. Existing `simbot_experience` rows are
unaffected. The one behavioural change to already-shipped code is the ceiling
inside `grantPlayerBotExperience`, which cannot affect production — F_0.9.0 has
no production caller — and affects exactly one harness scenario, corrected in
this plan.
