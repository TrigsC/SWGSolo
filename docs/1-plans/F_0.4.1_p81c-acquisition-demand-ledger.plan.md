# P.8.1c PvE Acquisition Demand-Ledger (Substitution-Pool Family Signals) Implementation Plan

## Overview

Phase 2 hunters are live and correct but every one is stuck in `IDLE_HOME`:
the hunter matchmaker is strict demand-pull and only reads each crafter
profile's single collapsed "active opportunity" resource, which mineable
vegetables/minerals always win. The meat the hunt species produce is therefore
invisible as demand. This plan teaches the shared demand ledger to expose
**per-eligible-satisfier-family demand signals** out of each profile's shared
shortage, using the owner's **shared substitution-pool** model with **stable
per-family targets**, feeds **simulated hunter harvest back into supply** so the
loop self-limits, and makes the hunter matchmaker consume those family signals
ranked by a v1 expected-value-per-time proxy — **reserving each accepted hunt's
yield within the same pass** so hunters don't overbook one gap. Result: hunters
see genuine latent chef meat-demand, dispatch, gather, and the signal quiets as
meat is stocked — the Phase 2 combat loop finally runs, without overproduction.

## Problem Statement

- `runPveHunterMatchmaker` (`SimPlayerManager.cpp:7563-7588`) picks the
  highest-pressure demand **only among `demand.activeResource.type`** — the one
  collapsed winner per profile. Live, `chef_buff_foods` resolves its active
  opportunity to `vegetable_beans` (Kehesko); the meat families in the same
  basket (`SimPlayerManager.cpp:1360-1373`) never surface. `demandedType` stays
  empty → no dispatch → 0 hunts over ~9h (verified live 2026-07-17).
- The per-tick `DemandStateSimulationResult` only carries the collapsed
  `activeResource`/`activeMatch`, not a family-level breakdown.
- **Supply plumbing gap (self-limiting is impossible today):**
  `demandStateProfileUsesConceptualLabel` (`SimPlayerManager.cpp` static)
  recognizes **only `water`** as supply for the two chef profiles, and hunter
  harvest is booked in a *separate* accumulator
  (`recordPveHunterHarvest`/`pveHunterHarvestUnitsTotal`, `:7789-7805`) that
  never feeds `estimateConceptualDemandStateSupply`. So produced meat never
  reduces the chef `shortageUnits`; any family-only post-pass would reopen
  demand forever.
- No inbound/reservation accounting exists, and the current matchmaker assigns
  **every** available identity in a single invocation (`:7590+`), so even once
  meat is visible, all hunters would book against the same gap in one pass.

## Solution Architecture

Owner model (2026-07-17): **shared substitution-pool gate with small,
independently-capped per-family reserves**, refined here (post Codex review) to
use **stable per-family targets** so a family cannot creep to fill the whole
pool.

- Demand-family kinds: **AND** (recipe needs meat + spice + water → each family
  its own demand) vs **ANY-OF** (meat OR vegetable OR fruit → one shared pool).
  Existing profiles are pure ANY-OF (`exactTypes`/`premiumFamilies`/
  `bulkFamilies` are alternative satisfiers), so **each profile is already one
  shared pool** and its `shortageUnits` is the shared gap. This slice
  implements ANY-OF only; AND-decomposition is future.
- **v1 scope is the `meat` family only.** All currently-configured hunt species
  have `harvestKind == "meat"` (hide/bone estimates are 0) and the only
  meat-consuming profiles are `chef_buff_foods` / `chef_high_value_consumables`.
  `hide`/`bone` are carried as config-listed channels but emit nothing until a
  species produces them AND a profile consumes them (documented, not built).
- Shared gap (per profile), reusing the ledger's numbers **after** the supply
  fix below:

  ```
  shared_gap = shortageUnits                            (desiredReserve − totalKnownSupply)
             − reserved_inbound_for_THIS_profile_family (NEW, per (profileKey,family))
  ```

- **Stable per-family target with two SEPARATE components** (anti-creep fix
  Codex P1-2, plus reserve-floor fix Codex R2-P1). The signal is the sum of an
  allocation component (bounded by the shared gap) and an **independent** reserve
  component (NOT bounded by the shared gap, so it survives a zero gap):

  ```
  family_supply    = GLOBAL: immutable boot baseline (durable hive lots incl.
                     exact_type, captured once) + monotonic session harvest
                     tally for the family (see §1 — restart-durable, race-free)
  family_inbound   = per (profileKey, family) outstanding hunt reservations

  alloc_component  = family's floor+largest-remainder share of shared_gap,
                     further capped so
                     family_supply + family_inbound + alloc_component
                        ≤ family_allocation_ceiling          (STABLE cap)
                     (clamped ≥ 0; Σ alloc_component over families ≤ shared_gap)

  reserve_component = clamp( 0, family_reserve_cap,
                             family_reserve_target
                             − family_supply − family_inbound )   (INDEPENDENT
                     of shared_gap — provides a diversity floor even at gap 0)

  signal_units     = alloc_component + reserve_component
  ```

  Because both the allocation ceiling and the reserve target are stable (not a
  moving percentage of the remaining gap), the meat signal genuinely quiets once
  `family_supply + family_inbound` reaches them — even while the profile is
  still "short" and being filled by veggies. `family_supply` is **global**
  (harvested meat counts toward every meat-accepting profile); `family_inbound`
  is scoped to `(profileKey, family)` so working one profile's gap does not mask
  another profile's genuine need.
- **Pressure** (so reserve-only demand can still be ranked/dispatched, Codex
  R2-P1): `pressure = shortagePressure * alloc_component / max(1, shortageUnits)
  + (reserve_component > 0 ? reservePressureFloor : 0)`, where
  `reservePressureFloor` is a small config constant. A reserve-only signal
  (shared gap 0) thus carries a defined nonzero pressure instead of inheriting
  zero.
- **Allocation across multiple creature families** (when >1 exists) uses floor +
  largest-remainder distribution of the shared gap so the summed `alloc_component`
  never exceeds `shared_gap` (Codex P2-3). The independent reserve component is
  added on top and may intentionally exceed the pure gap for diversity.
- **Intra-pass reservation** (Codex P1-3): the matchmaker, after selecting a
  hunt, immediately decrements that `(profileKey, family)` signal's remaining
  capacity and **re-scores** before assigning the next identity, so N hunters in
  one invocation spread across real remaining need instead of stacking one gap.
- Hunters rank candidate hunts by a v1 **expected economic value per unit time**
  proxy; loot/mission/secondary-output value are additive hooks left at `+0`
  this slice.

This is **simulation-only** (meat "supply", "harvest", and "reservation" are
the existing conceptual/sim-harvest bookkeeping; no real inventory/credit/market
mutation) and **gated** behind a new default-off Lua flag; the miner-side demand
path is unchanged when the flag is off.

## Implementation Details

### 1. Feed simulated hunter harvest into supply (the self-limiting fix)

**File**: `MMOCoreORB/src/server/zone/objects/creature/simplayer/SimPlayerManager.cpp`

**Current state**: chef profiles count only `water`
(`demandStateProfileUsesConceptualLabel`); hunter harvest accrues into the
in-memory `spawnYieldAccumulators` session map (`recordPveHunterHarvest`,
`:7772-7801`, `sessionQuantity`/`lastFlushedQuantity`) and, on flush, deposits to
the hive as `AiEconomyStockpileLot` objects tagged
`acquisitionSource="conceptual_miner"`, `identityConfidence="exact_type"`
(`:15905-15930`). **Crucially (Codex R2-P2):** the durable snapshot the demand
engine uses today, `AiEconomyManager::snapshotPersistentConceptualMinerSupplyForDemand`
(→ `persistentConceptualTotals`), returns **only** `conceptual`/`conceptual_label`
lots and **excludes `exact_type` hunter lots** — so it cannot be the durable
meat source. And chef supply filters everything anyway because it only
recognizes the `water` label.

**Restart durability AND a consistent accounting point (Codex R4-P1):** three
independent per-tick snapshots are NOT atomic — a flush landing between the
session-delta read and the durable-lot read double-counts the same yield, and a
harvest between the reservation read and the session read appears as both inbound
and supply. Instead use a **boot-time durable baseline + a monotonic session
tally** so supply has a single, race-free accounting point:

**Modifications** — `familySupply[family]` (GLOBAL) = `bootBaseline[family] +
sessionHarvest[family]`:

1. **Boot durable baseline (captured once, immutable)** — capture
   `bootBaseline[family]` by summing durable hive lots (incl. `exact_type`) per
   family via a **new `bool
   AiEconomyManager::snapshotStockpileTotalsByFamily(const Vector<String>&
   families, VectorMap<String,uint64>& totalsByFamily, String& status)`** accessor
   (returns `false` on failure; a totals-only sibling of
   `snapshotStockpileInspection` —
   no per-lot row cap, no per-lot vector copy). The caller passes the configured
   `creatureFamilies`; a lot matches a family when its `resourceType` **or**
   `resourceClassChain` contains the family token (lowercased), mirroring the
   demand engine's `resourceTypeMatches` semantics (Codex R5-P2). Captured once
   and never mutated afterward — no per-tick full-lot scan, no drift.
   - **Guarded capture state machine (Codex R5-P1):** a `pveMutex`-guarded
     `pveBaselineState ∈ {pending, capturing, ready}` (default `pending`). At the
     top of the family-signal derivation: under `pveMutex`, if `pending` **and**
     `AiEconomyManager::isPersistenceReady()`, compare-and-set to `capturing`
     (only one caller wins) and release; that winner runs the slow
     `snapshotStockpileTotalsByFamily` **without** holding `pveMutex`, then
     re-takes `pveMutex` to publish the completed map into
     `pveCreatureSupplyBootBaseline` and set `ready` atomically. Other callers
     seeing `pending`/`capturing` (or persistence not ready) **emit no creature
     family signals this tick** (so no dispatch against a false zero baseline —
     directly addresses that PvE readiness at `:8016` does not gate on
     `AiEconomyManager` persistence). Dashboard exposes `baselineState` so the
     `baseline_pending` window is visible.
   - **Failure path (Codex R6-P2):** `snapshotStockpileTotalsByFamily` returns
     `bool`. On failure (returns false, or throws and is caught), the winner
     re-takes `pveMutex`, sets state **back to `pending`** — never publishes a
     partial/empty baseline, never leaves it stuck in `capturing` — records
     `baselineLastError`, increments a retry counter, and logs. Recapture is
     retried on a later tick with a bounded backoff (`baselineRetryBackoffMs`);
     until a capture succeeds the state stays `pending` and no creature-family
     signals are emitted. `baselineState`/`baselineLastError` are on the
     dashboard.
2. **Monotonic session tally** — add a `pveMutex`-protected
   `VectorMap<String,uint64> pveSessionHarvestByFamily`, incremented by
   `harvestAmount` **inside the existing `pveMutex` block in
   `recordPveHunterHarvest` (`:7803`)**, atomically with
   `pveHunterHarvestUnitsTotal` and the order's `harvestedUnits`. It counts all
   meat harvested this boot (whether or not since flushed).
   - No double-count with the baseline: the baseline is frozen at boot and never
     absorbs this-boot flushes; on the next restart, this-boot's flushed meat
     becomes part of the new immutable baseline and the session tally resets to
     0. (v1 assumption: creature families are produced only by hunters, so the
     pve session tally is the complete this-boot creature-family supply;
     documented, revisit if a non-hunter meat producer is added.)
3. (Reservations are `familyInbound`, §3 — not part of supply; snapshotted under
   the SAME `pveMutex` acquisition as the session tally so supply and inbound are
   mutually consistent.)

- Make chef profiles recognize the creature family as supply: extend
  `demandStateProfileUsesConceptualLabel` so `chef_buff_foods`/
  `chef_high_value_consumables` also return true for `meat` (and its
  subfamilies), so bucketed meat is added to `totalKnownSupply`. Net effect:
  produced meat reduces the chef shared gap, closing the loop and surviving
  restart.
- Keep this gated: when `acquisitionLedger.enabled` is off, meat is **not**
  recognized/injected for chef profiles (preserves today's numbers exactly).

### 2. Per-family demand decomposition in the real demand ledger

**File**: `SimPlayerManager.cpp` — `SimPlayerManager::computeDemandStateResults`
(**definition at `:22107`**; called from `:7553`, `:16201`, `:22356`). The
`:12736` loop is a separate dashboard-assembly duplicate and is **not** the
compute path to modify.

**Current state**: builds one `DemandStateSimulationResult` per profile, sets a
single `activeResource`/`activeMatch`, and calls `calculateDemandStatePressure`
to fill `shortageUnits`/`shortagePressure`/`pressureScore`.

**Modifications** (structs live in the **`.cpp`** beside `:448-513`, not the
header — Codex P2-1):

- Add (with the same no-op `toBinaryStream`/`parseFromBinaryStream` pattern, next
  to the other demand structs at `:448-477`) a struct that exposes **both
  components separately** so the two-component behavior is observable on the
  dashboard (Codex R3-P2):
  `struct DemandFamilySignal { String family; String channel; uint64
  effectiveCeiling = 0; uint64 reserveTarget = 0; uint64 familySupply = 0;
  uint64 familyInbound = 0; uint64 allocComponent = 0; uint64 reserveComponent =
  0; uint64 signalUnits = 0; float pressure = 0.f; };`
- Extend `DemandStateSimulationResult` (`:479-513`) with
  `Vector<DemandFamilySignal> familySignals;` and `uint64 reservedInboundSupply
  = 0;`.
- After `calculateDemandStatePressure`, call a new
  `deriveDemandFamilySignals(demandResult, profile, familySupplyByFamily,
  reservedInboundByProfileFamily, config)` that, per configured creature family
  eligible for this profile, computes the **two-component** signal exactly as in
  Solution Architecture (superseding any earlier single-`min` formulation):
  - `allocComponent` = the family's floor + largest-remainder share of
    `sharedGap`, further clamped so
    `familySupply + familyInbound + allocComponent ≤ effectiveCeiling`
    (and `Σ allocComponent ≤ sharedGap`).
  - `reserveComponent = clamp(0, familyReserveCap, familyReserveTarget −
    familySupply − familyInbound)` — **independent of `sharedGap`**.
  - `signalUnits = allocComponent + reserveComponent`.
  - `pressure = shortagePressure * allocComponent / max(1, shortageUnits) +
    (reserveComponent > 0 ? reservePressureFloor : 0)`.
  `familySupply` is global (§1); `familyInbound` is this profile+family (§3).
- Avoid double-counting a family that appears in both `exactTypes` and
  `premiumFamilies` of the same profile (dedupe eligible families).

### 3. Inbound / reservation accounting, scoped to (profileKey, family)

**File**: `SimPlayerManager.cpp` (+ `PveHuntOrder` in `SimPlayerManager.h`)

**Current state**: `PveHuntOrder` (`SimPlayerManager.h:124-145`) has `quota`,
`requestedResourceType`, `harvestKind`, `kills`; orders in `pveHuntOrders` under
`pveMutex`.

**Modifications**:

- Add to `PveHuntOrder`: `String demandProfileKey;` (the profile whose gap this
  hunt was dispatched against — Codex P1-4), `uint64 expectedYieldUnits = 0;`,
  `uint64 harvestedUnits = 0;`. On dispatch set `expectedYieldUnits =
  species.estimated<Family>Units * quota` and record `demandProfileKey`; credit
  `harvestedUnits` as harvest accrues.
- Add `computeReservedInboundByProfileFamily(VectorMap<String,uint64>& out)`
  keyed by `profileKey + "|" + family`: for each active order,
  `remaining = max(0, expectedYieldUnits − harvestedUnits)`.
- **One consistent `pveMutex` snapshot for the live figures (Codex R4-P1):**
  under a **single** `pveMutex` acquisition, copy out **both** the reserved-inbound
  map (from `pveHuntOrders`, `remaining = expectedYieldUnits − harvestedUnits`)
  **and** `pveSessionHarvestByFamily`, then release before any demand math. Since
  `recordPveHunterHarvest` updates the order's `harvestedUnits` and the session
  tally together under that same `pveMutex` (`:7803`), the inbound and supply
  figures are mutually consistent — a harvest can never appear as both full
  inbound and new supply. The immutable `bootBaseline` needs no per-tick lock
  (frozen after capture). This mirrors the snapshot-then-compute discipline in
  `runPveHunterMatchmaker` (`:7534-7548`) and adds no new lock ordering.
- Completed/abandoned/timed-out orders leave `pveHuntOrders`, so their
  reservation naturally releases; their yield persists via §1's global family
  supply.

### 4. Hunter matchmaker: value/time ranking with intra-pass reservation

**File**: `SimPlayerManager.cpp`, `runPveHunterMatchmaker` (`:7514-7643+`)

**Current state**: ranks `activeResource.type`, filters to species-satisfiable,
assigns every eligible identity in one pass.

**Modifications**:

- Build the candidate set from all `familySignals` (creature families) across
  in-phase demand results with `signalUnits > 0`. Match a signal to a species
  by an explicit rule: **`species.harvestKind == signal.family`** and
  `species.usable && species.soloable` (Codex P1-5) — this bridges
  `requestedResourceType` (`meat_wild`) to family (`meat`) via `harvestKind`.
- Reuse the existing species/identity eligibility gates (tier, planet, home
  city, hunt distance at `:7595-7630`).
- Score each candidate by the v1 value/time proxy (§5) and pick the max.
- **After each assignment, decrement the selected `(profileKey, family)`
  signal's remaining capacity by the order's `expectedYieldUnits` and re-score
  the remaining identities** (Codex P1-3), so multiple hunters in one pass
  spread across genuine remaining need. **Saturating-subtract (Codex R2-P2):**
  the decrement clamps at 0 (uint64, no underflow); a candidate is eligible
  while its remaining `signal_units > 0`, and a hunt whose `expectedYieldUnits`
  exceeds the remaining signal is **allowed exactly once as a bounded overshoot**
  (meat is fungible and total production is still bounded by the stable target/
  reserve caps), after which that signal reads 0 and drops out of scoring.
- Preserve strict-pull: if no creature-family signal is satisfiable, return (no
  dispatch); the speculative floor stays out of scope.

### 5. v1 value/time proxy + stable target derivation

**File**: `SimPlayerManager.cpp` (helpers) + `sim_player_manager.lua`

- **Hunt value/time** (v1): `score = familyPressure * estimatedYieldUnitsPerHunt
  / estimatedHuntTimeSeconds`. `estimatedYieldUnits` from
  `PveHuntSpecies.estimated<Family>Units`; `estimatedHuntTimeSeconds` from a
  config default (travel + kill cadence). Loot-table value, mission credits,
  and secondary-output terms are **additive hooks at `+0`**, documented so a
  later slice adds them without reshaping the score.
- **Stable per-family ceiling schema** (Codex R2-P2, one schema not two): the
  allocation ceiling is defined by **two explicit config fields per family** —
  `familyAllocationCeilingUnits` (absolute unit cap, default 0 = unset) and
  `familyAllocationCeilingFraction` (fraction of the profile `desiredReserve`,
  default 0 = unset). Effective ceiling =
  `min( unitsIfSet, round(fraction*desiredReserve) IfSet )` when both are set,
  otherwise whichever one is set, and **when both are unset the default is
  `fraction = 0.25` of `desiredReserve`** (Codex R3-P2 — a concrete, documented,
  tunable default so hunters do meaningful work out of the box rather than
  collapsing to reserve-only). Result is clamped to
  `[0, shared_gap + family_supply + family_inbound]` so it can never demand
  negative or beyond the pool. The reserve component is independently
  capped (`familyReserveCap`) and must not reproduce the full profile shortage.
  The owner's fuller "weight by availability/quality/acquisition-cost/producer-
  capability" is the documented next refinement of how the ceiling is derived,
  not built this slice.

## Technical Considerations

- **Pattern Usage**: mirrors the existing demand-compute + `DemandProfileMatch`
  pattern and the `runPveHunterMatchmaker` snapshot-then-compute structure. No
  new manager or IDL object.
- **Locking & References**: the live figures (reserved-inbound + session-family
  harvest tally) are copied out together under a **single** `pveMutex`
  acquisition and released before the demand math (no lock held across compute);
  because `recordPveHunterHarvest` updates `harvestedUnits` and the session tally
  under that same `pveMutex` (`:7803`), the snapshot is internally consistent. The
  boot durable baseline is captured once via
  `AiEconomyManager::snapshotStockpileTotalsByFamily` (its own persistence guard)
  and is immutable thereafter (no per-tick lock). This mirrors the
  snapshot-then-compute discipline in `runPveHunterMatchmaker` (`:7534-7548`) and
  introduces no new lock ordering — avoiding the P.4.4-class regression
  (ARCHI.md §5).
- **IDL Impact**: none. `DemandStateSimulationResult`/`DemandFamilySignal`/
  `PveHuntOrder` are plain in-memory structs with no-op binary streams; no
  `.idl`, no `src/autogen/`, no schema migration.
- **C++ vs Lua Placement**: structural math (supply injection, allocation,
  reservation, intra-pass rescore) is C++ beside the demand engine; all weights,
  targets, reserve caps, family list, hunt-time estimate, and the enable flag
  are Lua tunables.
- **Gating & Simulation-Only**: gated by `pveConfig.acquisitionLedger.enabled`;
  off = exact current behavior including no harvest injection. "Supply",
  "harvest", "reservation" are existing conceptual/sim bookkeeping — no real
  mutation. Within simulation-only policy.
- **Dashboard Visibility**: new `demandFamilies`/reservation/`familySupply`
  fields under `pveActivity` are the acceptance surface (ARCHI.md §11).
- **Live Verification Plan**: after owner restart with the flag on, pull the
  dashboard: (1) `pveActivity.demandFamilies` shows a non-zero `meat` signal;
  (2) hunters leave `IDLE_HOME` → `ANNOUNCE_JOB`/`TRAVEL_OUT`/`HUNTING`;
  (3) `hunterKillsTotal` and typed `hunterHarvestUnitsTotal` climb, and
  per-family `familySupply` rises; (4) the meat `allocComponent` **shrinks as
  harvest accrues** and reaches 0 once `familySupply + familyInbound` hits the
  `effectiveCeiling` (self-limiting — the core check that the supply loop and
  stable cap are fixed), leaving only `reserveComponent`; (5) with 6 hunters, one
  pass spreads across profiles/gaps rather than stacking one (P1-3); (6)
  retreat/death paths observed per the Phase 2 contract. Same live-dashboard
  acceptance bar as every prior slice.
- **Edge Cases**: cold start (meat supply 0 → alloc + reserve components →
  dispatch); meat at ceiling (`allocComponent` 0; only `reserveComponent`
  remains; hunters mostly idle, veggies fill pool); two chef profiles both
  wanting meat (global supply counts for both; inbound scoped per profile so
  neither masks the other); order abandon/timeout (inbound releases, harvested
  portion persists as durable global supply); **shared gap 0 but reserve floor >
  0** (`reserveComponent` drives small diversity hunts with a defined
  `reservePressureFloor`, since it's independent of shared_gap); restart
  (familySupply = fresh immutable bootBaseline from durable hive lots incl.
  exact_type, session tally reset — no re-restock, no double-count); dedupe
  family in exact+premium; largest-remainder so summed alloc ≤ gap; oversized
  hunt vs small remaining signal (one bounded overshoot then drop); flag off
  (no-op fallback).

## Performance & Cost Impact

- The durable hive scan runs **once** at boot (baseline capture via
  `snapshotStockpileTotalsByFamily`), not per tick. Per-tick work is an extra
  pass over each profile's small fixed creature-family set plus the `pveMutex`
  snapshot of the session tally + reservations — O(profiles × families) +
  O(active orders), negligible against the existing demand scan. The matchmaker's
  intra-pass rescore is O(active orders × identities) ≤ `pveMaxHunters²` (36). No
  new per-tick O(n) full-lot scan and no new O(n²) over the SimPlayer population
  (ARCHI.md §Performance).

## Backward Compatibility

- Flag-gated: `enabled=false` reproduces today's matchmaker exactly **and**
  skips harvest injection, so demand numbers are unchanged. Structs gain fields
  with safe defaults; no persistence, no schema, no IDL. Miner-side demand path
  untouched.
