## 2. Three corrections to the original D7 framing

Each is evidence-backed and each makes Phase 2 **smaller** than the D7 proposal
assumed. They matter because the proposal's stated blockers were the reason
Phase 2 was deferred.

**2.1 — "Blocked on probe cost" is wrong; the cost is already off the movement
path.** `probeEmittedPathClearance` runs inside `SimPathFindTask::run()`, on the
pathfinding worker thread, and the result is carried by value into the delivery
lambda (`SimPlayerController.cpp:410-460`). Enforcement reads a value that has
**already been computed** before the mover ever sees the path. Flipping
`enforce = true` adds no new work to any tick. The measured p50 8.3 ms / p95
47.4 ms / max 91 ms is a cost this server is **already paying today** whenever
`zeroClip.enabled = true`; it is a reason to think about the observation gate's
default, not a blocker on enforcement.

**2.2 — The 51% skip rate is not an enforcement blocker.** `skipped` is produced
by worst-evidence-first aggregation: any cell-local segment, degenerate segment,
or over-long segment downgrades the whole path (`:186-210, :344`). That rule is
correct for *measuring* — it stops an inflated clear rate — but enforcement does
not need path-level certainty. It needs one conclusive obstruction. Enforcement
therefore acts on `WouldBlock` alone and **fails open on everything
inconclusive**. Action rate is 11.3% of accepted paths, not 51%.

**2.3 — The straight-line fallback is not where the clipping comes from.** The
D7 proposal named `SimPathFindTask::run()`'s 2-node overland branch as the root
cause, later corrected to add `PathFinderManager`'s `size() < 2` fallback. Run 10
says **neither**: all 1226 probes were `leg=generic`, zero `directOverland`, and
**all 139 would_blocks had `nodes > 2`**. Not one was a 2-node straight line.
These are real multi-node routes that clip. Enforcement must therefore reject a
*returned route*, not merely refuse to synthesise straight lines.

Also of note: `zeroClip.exitSetEnabled = false` in runs 9 and 10 and
`exitCandidatesTried = 0`, so D7 Part 2's per-candidate egress ladder is compiled
in but has **never executed live**. Phase 2 is what puts it into use.

## 3. Design

### 3.1 Where enforcement hooks

There is an exact precedent already shipped and live-verified: the D2b rejection
in `onPathFound` (`:1876-1893`). Enforcement becomes a second rejection reason at
the same site, reusing the same fall-through.

```
onPathFound(path, ...)
  ├─ acceptFoundPath(pathEnd) == false   → existing D2b/P.6.1b rejection
  └─ NEW: zeroClipRejects(path)          → identical treatment
       delete path
       if (cellEgressActive) failCellEgress(); else onPathFailed();
```

`onPathFailed`/`onPathTaskFailed` already carry the bounded retry ladder
(`:1996-2026`: cell-egress failure, navmesh repath budget, terminal failure), so
no new failure machinery is introduced.

### 3.2 The predicate — fail open on everything inconclusive

```
reject  ⟺  enforce == true
        &&  outcome == WouldBlock
        &&  zeroClipRejections < zeroClipRejectionCap
```

`Skipped`, `Truncated`, `Error` and `Clear` never reject. This is deliberately
the opposite of the harness assertion policy fixed this week: a test oracle must
fail closed, a live mover must not — failing closed on inconclusive would refuse
55% of all movement and freeze the server.

### 3.3 Own-structure exemption — REJECTED BY OWNER (2026-08-28)

The probe exempts only `ignoredAgentOid` (`:283`). Nothing exempts the building
the bot is entering or leaving, and 17 of the 56 POB hits have `hitAt < 0.05` —
a ray originating inside the shell's collision volume, which is what a bot
standing in a doorway looks like. I proposed exempting the traversal's owning
building.

**Owner decided: no exemption at all.** Enforce against every structure,
including the one being entered. The rejection cap (§3.4) is what makes this
safe rather than brittle: a bot at a doorway is refused `rejectionCap` times and
then walks, so the doorway case degrades into wasted repaths rather than a
frozen bot. Accepted cost: extra path requests per structure transit, which may
push matrix scenarios against their `enterMs`/`exitMs` budgets. That is a
measurable outcome and is called out as a watch item in §5.

### 3.4 Bounded — the one way this bricks the server

If the pathfinder deterministically returns the same clipping route, rejecting it
forever means the bot never moves. Mitigation, mirroring
`hollowEscalationAttempts`:

- a per-traversal `zeroClipRejections` counter with a Lua cap
  (`zeroClip.rejectionCap`, default 2);
- on cap exhaustion the path is **accepted and walked**, with an explicit
  `ST_CLEARANCE result=would_block action=accepted_cap_exhausted` line;
- the counter resets with the rest of the traversal state.

Accepting on exhaustion, rather than failing the leg, is the safe direction: a
bot that clips is a cosmetic defect, a bot that is permanently frozen is an
outage. The counter makes the residual clip rate measurable rather than silent.

## 4. Safety analysis

| Risk | Assessment |
|---|---|
| New per-tick cost | **None.** The probe already runs, on a worker thread, before delivery (§2.1). |
| New lock acquisition | **None.** Enforcement reads a value already captured in the lambda. No new zone/agent lock. |
| Frozen bots | Bounded by `rejectionCap`, terminating in accept-and-walk (§3.4). |
| Breaking real players | None. Every path is `SimPlayerController` only; stock movement is untouched. |
| Persistence / economy | None. Simulation-only; no counters outside `zeroClip.*`. |
| **Matrix regression** | **Expected, and it is the point.** D1 Option C "passes the matrix by clipping". Some of the 22 PASS may be doing the same. A scenario that fails once clipping is denied is a real defect surfaced, not a Phase 2 bug. |

The regression risk is the honest headline: **this change can lower the pass
count**, and that outcome would still be correct. I would not fold it into a
release quietly.

## 5. Plan

1. Own-structure exemption (§3.3) — behind the existing `zeroClip.enabled`.
2. `enforce` predicate + `rejectionCap` (§3.2, §3.4), default **off**.
3. Matrix run with `enforce = true`: record pass count, `blocked`, cap
   exhaustions, and every scenario that changes verdict.
4. Triage each regression: genuine defect vs. exemption gap.
5. Codex review, then re-verify. **The D2b PASS receipt goes stale the moment
   this lands** — it is bound to the current source fingerprint — so the matrix
   is re-run and a fresh receipt issued regardless.

## 6. Owner decisions (2026-08-28) — ALL ANSWERED

1. **Blocked-leg policy** (D7 §6.1, open since 2026-08-19) — **treat a blocked
   path exactly as a failed path** and route it into the existing bounded retry.
   Waypoint-detour generation is not built; it is a real pathfinder and stays
   unbuilt unless the retry ladder is measured insufficient.
2. **Cap-exhaustion behaviour** — **accept and walk**, with
   `zeroClip.capExhausted` and `ST_CLEARANCE action=walked` recording it. A
   clipping bot is a cosmetic defect; a frozen bot is an outage.
3. **Own-structure exemption** — **none** (§3.3). Stricter than proposed;
   bounded by the cap.

### 7.1 Enforcement (runs 11-12)

| Item | State |
| --- | --- |
| `zeroClip.rejectionCap` config + accessor + dashboard | DONE |
| `zeroClipCapExhausted` counter + dashboard `capExhausted` | DONE |
| `shouldRejectClippingPath()` / `rejectClippingPath()` | DONE |
| Delivery-lambda hook before the virtual `onPathFound` dispatch | DONE |
| Evidence trail: refusals counted despite never reaching `MOVING` | DONE |
| `ST_CLEARANCE action=rejected|walked|none` | DONE |

**Run 11 defect.** Routing a refusal into `onPathFailed()` — mirroring the
`acceptFoundPath` rejection — cost 7 scenarios. For a structure traversal
`onPathFailed()` is TERMINAL (`ST_FAIL reason=path_failed` straight to Idle), so
one obstruction killed the traversal and `rejectionCap` was never reachable. The
two rejections are not alike: a stale endpoint means the REQUEST was wrong, a
clipping route means only THIS ANSWER is unusable. Fixed by re-issuing the same
destination as a fresh path request.

### 7.2 The navmesh rung (run 13) — TRIED AND FAILED, code retained

`rejectClippingPath()` retries onto recast when both ends share a NavArea and the
destination is outdoors. It fired 68 times and **all 68 recast answers were also
flagged**; clip rate got slightly worse. The rung is retained because it is
correct in principle and now harmless, but it is not what produced the
improvement.

The failure was diagnostic gold: 64 of those 68 were ONE Naboo bridge staircase.

### 7.3 Walkable confirmation (run 15) — the actual fix

| Item | State |
| --- | --- |
| `zeroClip.walkableConfirm` + `walkableToleranceRatio` config | DONE |
| `isSegmentWalkableByNavmesh()` recast confirmation | DONE |
| `zeroClipWalkableReclassified` counter + `walkableReclassified` on result/log | DONE |

The appearance ray tests the straight CHORD between two path nodes, which for a
staircase or bridge deck dives through the solid mass beneath the walkable
surface. Stock `checkMovementCollision` never sees this because its ray is a
per-tick micro-segment hugging the surface; D7's chord is tens of metres.

A flagged chord is confirmed against the navmesh — the authority on what an
agent can stand on. Recast walking it without meaningfully detouring
(<= `walkableToleranceRatio`, default 1.25) means the hit is a false positive.

**110 of 206 raw mesh hits (53%) were overruled.** The 25.4% block rate that has
driven this defect since 2026-08-20 was roughly half false positive.

**Engine defect found doing this.** `PathFinderManager::getRecastPath`'s
`float& len` is NOT a path length — it accumulates `x^2 + z^2` of each point's
ABSOLUTE world coordinates (~1.2e7 per point at x=3500). The first confirmation
attempt trusted it and reclassified 0 of 63. Length is now measured from the
returned points.

It is not unused, though — an earlier draft of this section wrongly said so, and
the code review caught it. `findPathFromWorldToWorld` feeds it to a
`finalLengthSq` comparison to choose between candidate routes
(`PathFinderManager.cpp:380`). That is a relative comparator between candidates,
not a distance; the other stock caller,
`CollisionManager::checkMovementCollision`, passes a value IN and ignores what
comes back. Neither reads it as a length, and neither can.

### 7.4 Not done

**3.5% is not 0.** The residual 32 obstructions are genuine clips through
starport shells and debris, walked once the rejection budget is spent, because
no rung produces a route around them. Reaching 0 needs a detour generator or
navmesh coverage including those objects.

Confirmation limits: a short wall on a long chord could detour under the
tolerance and be wrongly cleared (not observed; the tolerance is a knob, not a
proof), and segments with no navmesh at either end fall back to the raw ray.

### 7.5 Review attention

- Enforcement is hooked in the delivery lambda, not inside `onPathFound`, which
  is virtual and overridden by `SimTraversalTestController`. One branch covers
  every subclass.
- A refusal never reaches `state = MOVING`, so `consumeProbePathAccepted()` is
  false for it; the recording branch admits refusals explicitly or enforcement
  would erase its own evidence.
- `isSegmentWalkableByNavmesh` runs on the pathfinding worker thread, where
  `getRecastPath` is normally called from, and only on already-flagged segments.
