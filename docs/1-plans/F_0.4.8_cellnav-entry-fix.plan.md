# POB Cell-Entry Navigation Fix (Pass 2) Implementation Plan

## Overview

Pass 1 (`F_0.4.7`, instrumentation-only, shipped to the working tree of branch
`feat/cellnav-entry-diagnostics` — **not committed**) put a gated diagnostic bot
and a full movement trace (`bin/log/cellnav.log`) in place, drove it toward the
Mos Eisley cantina interior, and **captured the exact defect** behind the
long-standing "NPC teleports into the wall/corner when entering a building cell"
bug (seen with PvP bots at Theed and PvE hunters at the cantina).

Pass 2 fixes it. There are two changes:

1. **The production bug (universal):** a coordinate-space error in the shared
   engine mover `AiAgentImplementation::findNextPosition` at the world→cell portal
   handoff. This is the real fix and it benefits **every** AI agent that crosses a
   world↔cell portal, not just SimPlayer bots.
2. **The Pass-1 diagnostic resolver (transient):** correct the cell-resolution
   axis mapping in `SimPlayerManager::resolveCellNavDiagnosticRoute` so the
   diagnostic bot targets the **actual** cantina cell, giving a faithful live
   verification of change #1. (Live data disproved code-review finding #1 from
   F_0.4.7 — see Problem Statement — so this partly reverts that change.)

After the fix is **live-verified** (the diagnostic bot walks into the cantina cell
and arrives; real NPCs enter buildings without teleporting), Pass 2 **strips the
entire F_0.4.7 diagnostic scaffolding**, shipping only the small `findNextPosition`
fix plus the retained design doc. Owner decisions for this plan: **universal engine
fix**, and **strip the diagnostic after verifying**.

## Problem Statement

### Root cause of the teleport (definitive, from `cellnav.log`)

The pathfinder produces a correct cell-aware route — the cell-entry node carries
proper cell-**local** coordinates (`local=(0.007,-12.38,0.6)`, cell `1105846`) and
the portal transform math is right (`checkPosInNextSpace=(0.0068,-12.38,0.6)`
matches the node). The failure is in **consuming** that node inside
`findNextPosition`'s multi-node loop (`AiAgentImplementation.cpp` ~`:4776-4862`):

1. When the agent sits essentially on the portal point, the cell-entry node is
   ~0 distance away **in cell-local space**, so it hits the **duplicate-skip**
   branch (`if (distToNode < 0.01f) { path->remove(1); continue; }`). That branch
   removes the node **without adopting its cell** — `currentParent`/`currentPosition`
   stay in the **outdoor/world** frame. The reparent-into-the-cell information is
   silently dropped. Log evidence: `ENGINE_NODE_CANDIDATE ... distance=0.000371`.
2. Removing that node drops the working path below two nodes, so the loop exits
   with `finalPosSet == false`.
3. The `!finalPosSet && path->size() < 2` **fallback** (~`:4853-4862`) sets
   `nextMovementPosition`'s X/Y/Z to `currentPosition` — still the **outdoor world
   coordinate** `(3300.99,-4766.28,5.6)` — while leaving `nextMovementPosition.getCell()`
   pointing at the **new cell** `1105846`. Log evidence:
   `ENGINE_UPDATE_POSITION setPositionArgs=(3300.99,5.6,-4766.28) incomingCell=1105846`.
4. `updateCurrentPosition` then applies a **world-magnitude coordinate as a
   cell-local position** under a cell parent, so `getWorldPosition()` re-applies the
   cell's transform → world `(9088,-4712,10.6)` — a ~5,700 m jump. Log evidence:
   `ENGINE_STEP_APPLIED world=(9088.32,-4712.3,10.6) cell=1105846 local=(3300.99,-4766.28,5.6)`.
   Every subsequent tick re-pathfinds from the garbage position and drifts further
   (`distance2d` to target grows to ~5,200 m and never converges) — the observed
   "stuck in a wall/corner."

So two coupled defects: **(a)** the duplicate-skip discards a cell/parent
transition, and **(b)** the fallback constructs a space-inconsistent
(world-coordinate, cell-parent) pair.

### The Pass-1 resolver mis-mapping (my harness, secondary)

`cellnav.log` also shows the F_0.4.7 resolver chose a cell in a **neighboring
building ~100 m from the target** (`RESOLVE_CHOSEN ... world=(3300.69,-4753.61)`
vs requested `(3385,-4811)`), and the real cantina building returned `floor=none`
for all cells. The logged `modelPoint` values prove the axis convention:
`transformToModelSpace` returns a Vector3 with `getX()=east`, `getY()=north`,
`getZ()=height` (e.g. building at height 5, target height 0 → `modelPoint.getZ()=-5`).
**The F_0.4.7 code-review "axis swap" finding was therefore incorrect, and the fix
applied for it is what broke the resolver** — it feeds `modelPoint.getZ()` (height)
as a horizontal ray coordinate to `getCellFloorCollision`, so the real cantina
floors are missed. This is a live-verification catching a bad review call.

## Solution Architecture

- **Change 1 — engine handoff fix (universal, permanent):** in
  `findNextPosition`, make the world↔cell transition coordinate-consistent:
  (a) a near-zero-distance node that is also a parent change must **adopt** the new
  cell and its cell-local position before being dropped; (b) the final-position
  fallback must keep `nextMovementPosition`'s cell consistent with `currentParent`
  so it can never emit a world coord under a cell parent. Minimal, targeted;
  behavior only differs from today at the exact portal-coincident case.
- **Change 2 — resolver axis correction + self-validation (transient):** fix the
  three axis assignments in `resolveCellNavDiagnosticRoute` back to
  `(east=getX, north=getY, height=getZ)`, and add a **round-trip guard** — accept a
  cell only if `WorldCoordinates(localPos, cell).getWorldPosition()` lands within a
  tight tolerance of the requested target — so the resolver is convention-proof.
- **Verification:** owner restarts with the fix; confirm via `cellnav.log` that the
  diagnostic bot enters the cantina cell with **small cell-local** coordinates and
  fires `ARRIVAL_BRANCH=arrived` (no teleport, `distance2d` converges), and confirm
  a real NPC (or the diagnostic bot) is physically inside the cantina in-game.
- **Cleanup — strip diagnostic:** once verified, remove **all** F_0.4.7
  instrumentation, keeping only Change 1 and the design doc.

## Implementation Details

### 1. Engine cell-transition handoff fix

**File**: `src/server/zone/objects/creature/ai/AiAgentImplementation.cpp`
(`findNextPosition`, the multi-node consumption loop ~`:4776-4862`).

**Current state**: The duplicate-skip branch drops a node without touching
`currentParent`/`currentPosition`; the `!finalPosSet` fallback copies
`currentPosition` into `nextMovementPosition`'s X/Y/Z but leaves its cell as
whatever the last `path->get(pathIndex)` set.

**Modifications** (behavior change only at a world↔cell transition; runs under the
already-held `Locker locker(&targetMutex)` — no new lock, no lock-order change):
- **Duplicate-skip branch** (`if (distToNode < 0.01f)`): before `path->remove(1)`,
  when `currentParentID != nextParentID`, adopt the transition —
  `currentPosition = nextMovementPosition.getPoint();` and
  `currentParent = nextMovementCell;` — so the reparent is not lost. For
  same-parent duplicates (the common case) behavior is unchanged.
- **`!finalPosSet && path->size() < 2` fallback**: after copying
  `currentPosition` into `nextMovementPosition`'s X/Y/Z, also set its cell to match
  `currentParent`, **null-guarded** —
  `currentParent != nullptr && currentParent->isCellObject() ? currentParent.castTo<CellObject*>() : nullptr`
  (outdoor movement commonly has `currentParent == nullptr`, so the guard is
  required to avoid a null deref) — so the emitted position/cell pair is always in
  one space. Belt-and-suspenders with the adopt fix above.
- No change to the interpolation or normal-consume branches (they already set
  `currentPosition`/`currentParent` together correctly).

**Why universal is safe**: the only code path whose output changes is a
near-zero-distance node that is simultaneously a cell/parent change — i.e. exactly
the portal-coincident handoff that is broken today. Agents not crossing a portal,
and portal crossings where the node is not coincident (normal consume/interpolate),
are unaffected.

### 2. Diagnostic resolver axis fix + round-trip validation

**File**: `src/server/zone/objects/creature/simplayer/SimPlayerManager.cpp`
(`resolveCellNavDiagnosticRoute`).

**Modifications** (transient — removed in Phase 3, but required for a faithful
cantina verification of Change 1):
- Correct the axis mapping to the convention proven by `cellnav.log`:
  `localX = modelPoint.getX()` (east), `localNorth = modelPoint.getY()` (north),
  `expectedHeight = modelPoint.getZ()` (height). This reverts the erroneous F_0.4.7
  "axis swap" edit; `getCellFloorCollision(localX, localNorth, cell)` then rays the
  correct horizontal point and `localPos = Vector3(localX, localNorth, floorZ)`.
- Add a **round-trip guard**: for each candidate cell that produces a floor hit,
  compute `worldPos = WorldCoordinates(localPos, cell).getWorldPosition()` and
  accept the cell only if its horizontal distance to the requested target is within
  a tight tolerance (e.g. ≤ 3 m); select the minimum round-trip error across all
  candidate buildings/cells. If none qualifies, keep `CELLNAV_RESOLVE_UNRESOLVED`
  (bounded retry, then loud abort) rather than routing to a wrong cell. This makes
  the resolver self-checking regardless of engine coordinate conventions.

## Technical Considerations

- **Pattern Usage**: Change 1 stays entirely within the existing P.6.5b cell-aware
  mover; it mirrors the normal-consume branch's own `currentPosition = node.getPoint();
  currentParent = nextMovementCell;` pairing. No new subsystem.
- **Locking & References**: Change 1 executes inside the existing
  `Locker locker(&targetMutex)` in `findNextPosition`; it adds no lock and changes
  no ordering. `currentParent` remains a `ManagedReference<SceneObject*>` assigned a
  `CellObject*` (upcast) exactly as the existing consume branch does — matching the
  proven choreography.
- **IDL Impact**: None. No `.idl`/`src/autogen` changes; `getPoint`, `getCell`,
  `setCell`, `isCellObject`, `castTo` are existing accessors.
- **C++ vs Lua Placement**: Change 1 is structural engine movement math → C++.
  The diagnostic config it removes was Lua; after strip there is no new Lua.
- **Gating & Simulation-Only**: Change 1 is a pure correctness fix to movement and
  mutates no inventory/credit/market/persistence — it only affects where an agent is
  positioned during a portal crossing. The diagnostic (gated, simulation-only) is
  removed entirely.
- **Universal-fix blast radius**: The change is observable only for AI crossing a
  world↔cell portal at a coincident node. Validate against BOTH the diagnostic bot
  and real NPCs entering the cantina before stripping/releasing, per the project's
  live-verification standard. (Real NPCs largely spawn in-place and rarely hit this
  path, but the fix is correct for them regardless.)
- **Dashboard Visibility**: None required; verification is `cellnav.log` (pre-strip)
  and in-game observation. No dashboard section added or removed.
- **Live Verification Plan**: See §3. Success = diagnostic bot enters the cantina
  cell with small cell-local coords, `distance2d` converges, `ARRIVAL_BRANCH=arrived`,
  no teleport; and an agent is physically inside the cantina in-game. This gates §4.
- **Edge Cases**: portal crossing where the node is NOT coincident (normal consume
  path — unchanged); multi-cell buildings (round-trip guard picks the correct cell);
  agent already inside a cell moving to another cell (same-parent or cell→cell — the
  adopt-on-transition logic keeps it consistent); outdoor-only movement (no parent
  change — unchanged); resolver finds no round-trip-valid cell (retry then abort,
  no wrong-cell route).

## Performance & Cost Impact

- Change 1 adds at most a couple of assignments on the portal-coincident branch of
  an already-running loop — negligible, and it *reduces* wasted work (today the bot
  re-pathfinds every tick from a garbage position forever).
- Phase 3 removes all diagnostic logging/spawn cost.

## Backward Compatibility

Fully compatible: no schema/IDL/persistence changes. Change 1 corrects positioning
at a portal crossing; agents that previously teleported now transition correctly.
The diagnostic is removed cleanly (it was never committed).

## Test Impact

- No new unit tests are required for the diagnostic (it is removed). Change 1 is a
  movement-math fix in the shared engine mover; the project's acceptance bar for
  AI-movement work is **live verification** (§3), not unit tests, and mocking the
  full zone/portal/floor-mesh geometry would exceed the mock-pain tripwire.
- If a lightweight seam is cheap, a `findNextPosition`-adjacent behavioral check
  that a world↔cell transition yields a cell-local (not world-magnitude) position
  could be considered during TRIP-2, but is not required; record any deferral in
  `docs/4-unit-tests/COVERAGE-DEBT.md`.
- Change 1 touches shared movement — the release code review must cover it, and the
  live check must include a real NPC (not only the diagnostic bot).
