# Novice Early-Game Loop (P.10g) Implementation Plan

**Chunk**: F_0.9.6 — P.10g
**Line**: P.10 PlayerBot player-parity (`docs/1-plans/ROADMAP_p10-playerbot-parity.md`)
**Depends on**: F_0.9.0 (progression store), F_0.9.1 (kill XP), F_0.9.5 (skill training, novice bodies)
**Gate**: `playerBotProgression.earlyGameEnabled` (default off)
**Schema**: none — this chunk adds no MySQL migration

## Overview

F_0.9.0/0.9.1/0.9.5 built a complete progression system — a durable store, real
kill XP, and a goal-driven training ladder — and then left it with nothing to
feed it. This chunk gives a roster PlayerBot an **internally motivated** reason
to fight: it spawns as a novice, walks out of its city, picks a creature it can
actually beat, kills it with a real weapon through real combat, rests, and
trains the next box on its template. It repeats that until every box its
grinding can actually fund is trained — the 60 combat boxes of the 63-box
template; the 3 Medic boxes need medical XP, which no activity in this chunk
produces, and are carried as explicitly deferred (see "The medical-XP stall").

The chunk is deliberately **demand-independent**. Every existing hunt path is
gated on market pressure (`signalUnits > 0`); a novice's motivation is its own
skill ladder, so it consults no demand signal at all. That is the entire point:
it is what makes progression observable in production rather than only under
the harness.

## Problem Statement

Four concrete defects, each verified rather than assumed.

**1. The progression system has no production input.** A live dashboard
snapshot taken 2026-09-08 shows `playerBotProgression.killXp.kills = 0`,
`awardsGranted = 0`, `training.configured = false`, and every
`demandFamilies[*].signalUnits = 0` with `missionBoard.offers = []`. Supply sits
at a boot baseline of ~587k meat, so the market matchmaker issues no orders, so
no hunter fights, so no XP is earned, so no box is ever trained. The novice
introduced by F_0.9.5 inherits that same gate and idles identically.

**2. A single `goalSkill` cannot express a real template.** `SimBotTrainingPlan`
holds one `String goalSkill` (`SimPlayerManager.h:151`). A genuine PVE build is
a *set* of boxes, and the SWG box-count shorthand the owner uses ("Fencer 32xx",
"Medic 2xxx") names partial trees by position and depth, not masters.

**3. A bot's weapon is cosmetic.** `AiAgentImplementation::setWeaponStats()`
(`:2186-2200`) overwrites the equipped weapon's damage with the *mobile
template's* `minDamage`/`maxDamage`:

```
primaryWeap->setMinDamage(minDamage * mod);
primaryWeap->setMaxDamage(maxDamage * mod);
```

So a novice holding a stone knife and a novice holding a heavy axe both hit for
the template's 25-40. Weapon choice, and therefore purchased gear, changes
nothing. This is **not** how a player works and per the owner's decision must
not be how a SimBot works.

**4. Nothing arbitrates what a bot does when its loop has nothing to offer.**
Each controller *is* the bot's whole identity, so an idle miner, an idle hunter
and an idle novice are three faces of one missing abstraction.

## Solution Architecture

Four phases, delegated in order. Phases 1 and 2 are mechanical and
independently verifiable; phase 3 is the behavioural core; phase 4 is a
deliberately minimal seam.

```
P1  multi-goal ladder      goalSkill -> goalSkills, union of closures, one sort
P2  loadout + real damage  weapon chosen by NEXT BOX'S xpType; true weapon stats
P3  the grind loop         leave city -> TTK target -> real combat -> rest ->
                           train -> repeat;  flee low HAM;  clone on death
P4  thin arbiter           grind vs demand-hunt, two activities only
```

### Measured facts this design rests on

Established by live probe against the running server on 2026-09-08 (probe
config deployed and self-reverted; `md5` confirmed restored). The manager
re-reads `sim_player_manager.lua` from disk on every PvP maintenance tick
(`refreshPvpConfig` → `Lua::runFile`, `SimPlayerManager.cpp:38020`), which is
why derived ladder costs can be measured without a restart.

|---|---|---|
| `combat_brawler_novice` | 1 | 15 |
| one brawler branch (4 boxes) | 4 | 14 |
| `combat_brawler_master` (full brawler tree) | 18 | 77 |
| an elite melee tree alone (2hsword / polearm / 1hsword) | 18 | 63 |
| elite novice box | 1 | 6 |

| any elite branch to depth 2 | 2 | 9 |
| `science_medic_novice` | 1 | 15 |

**The owner's template totals exactly 250 skill points across 63 boxes** — the
hard cap enforced at `SimPlayerManager.cpp:10143-10144` and
`:7839-7841`. There is **zero slack**:

```
Master Brawler                      77 pts / 18 boxes
+ Master Swordsman  (2hsword tree)  63 pts / 18 boxes
+ Master Pikeman    (polearm tree)  63 pts / 18 boxes
+ Fencer 32xx                       27 pts /  6 boxes
+ Medic 2xxx                        20 pts /  3 boxes
--------------------------------------------------------
  TOTAL                            250 pts / 63 boxes   (cap = 250)
```

All four elite branches cost identically (47 pts at depth 3, 44 at depth 2 for
the whole closure), and all four medic branches cost identically (20 at depth
2). **The 250 total is therefore invariant to which branches the shorthand
names** — branch identity is a gameplay choice, not a budget risk.

### Naming the Fencer and Medic branches from live data, not from guesswork

The owner specifies the partials by their in-game branch names: Fencer `3xxx` is
*Expert Fencing Stances and Grips* (melee and ranged defense), Fencer `x2xx` is
*Advanced Footwork* (knockdown defense), and Medic `2xxx` is *First Aid II*,
which grants the First Aid skill. The code names those branches
`accuracy`/`speed`/`ability`/`support` (1hsword) and
`ability`/`crafting`/`injury`/`injury_speed` (medic), and the mapping between
display name and code name lives in `skills.iff` inside the client TRE archives
(`/tre`, 53 files) — there is no standalone extractor in the tree.

This plan does **not** guess the mapping. Implementation must identify each
branch by what it actually grants, using a run-scoped read-only dump of each
candidate box's skill mods and granted commands, and the acceptance criterion is
explicit:

- the branch shipped as Fencer `3xxx` grants melee/ranged **defense** mods;
- the branch shipped as Fencer `x2xx` grants **knockdown defense**;
- the branch shipped as Medic `2xxx` grants the **`firstaid`** command.

Because all branches cost the same, choosing wrong is a gameplay error that is
correctable in Lua without a rebuild — never a budget overrun.

### The medical-XP stall (design issue found during planning)

Three of the template's 63 boxes are Medic boxes, and Medic boxes are funded by
**medical** XP, which is earned by healing — not by killing. A pure grind loop
can never fund them. Today `deriveNextTrainingStep` (`:7794-7820`) walks
`orderedSkills` in order and returns the **first untrained box**, so an
unfundable box would stall the ladder permanently behind it, stranding the 60
combat boxes that follow. It also makes full-template completion permanently
unreachable, which is why Phase 4 defines graduation against *fundable*
completion rather than all 63 boxes.

The fix is contained and reversible: make step derivation **skip-tolerant**. It
selects the first untrained box whose `xpType` is **not on the explicit
`earlyGame.deferredXpTypes` list**, and records the skipped boxes as
`training.stalledBoxes` on the dashboard. Fundability is decided by that list
alone, never by whether a source is enabled right now — see Phase 4 for why
testing live gate state inverts the rule. Medic boxes then simply wait for a medical-XP source (a healing
activity, a later chunk) while everything else proceeds. Ordering and the Kahn
tie-break are untouched; only the *selection* step gains the predicate.

### 2. Starter loadout and real weapon damage (Phase 2)

**File**: `src/server/zone/objects/creature/simplayer/SimPlayerManager.cpp`

**Current state**: the body spawn path (around `:14190-14250`) already performs
the complete, verified AI weapon-equip choreography — remove the stock weapon,
`transferObject(weaponObject, 4)`, then `setPrimaryWeapon` / `setDefaultWeapon`
/ `setCurrentWeapon(nullptr)` / `setWeapon` / `setWeaponStats` /
`setupAttackMaps` / `equipPrimaryWeapon`, with an `equipped` postcondition
check. It handles both the unarmed (stock default weapon) and armed cases. **The
equip mechanism does not need to be built — it needs to be driven by the right
input, stopped from discarding the weapon's stats, and corrected on one
postcondition.**

**Required correction — the armed postcondition rejects melee.** The armed
branch currently ends its `equipped` check with `&& weapon->isRangedWeapon()`
(`:14250`), which was correct when the only armed body was the rifle hunter.
Every weapon this chunk maps is melee, so that clause makes `equipped` false and
sends a correctly-equipped novice down the `if (!equipped)` failure branch.
Replace the rangedness clause with a check that actually expresses the intent:
the weapon occupies the expected slot, every AI weapon slot points at it
(`getPrimaryWeapon`/`getDefaultWeapon`/`getCurrentWeapon`/`getWeapon` — already
asserted), and its `getXpType()` matches the XP type the plan step requires.
The rifle hunter keeps passing, because a rifle satisfies the slot and XP-type
form too.

**Modifications**:

**(a) Choose the weapon from the next box's XP type, not from a static field.**
A box is funded by exactly one `xpType`, and XP of that type is only earned
while wielding a weapon whose `WeaponObject::getXpType()` matches
(`CombatManager.cpp:1476`, `:1688` — `xpType = weapon->getXpType()`, recorded
per attacker by `ThreatMap::addDamage` and paid out by
`disseminateExperience`). Weapon selection therefore **derives from
`SimBotTrainingStep::xpType`**, which the manager already computes and caches
(`:7814`). Verified starter weapons and their XP types:

| Weapon template | `xpType` | Template line |
|---|---|---|
| `melee/knife/knife_stone.iff` | `combat_meleespecialize_onehand` | Fencer |
| `melee/axe/axe_heavy_duty.iff` | `combat_meleespecialize_twohand` | Swordsman |
| `melee/polearm/lance_staff_wood_s1.iff` | `combat_meleespecialize_polearm` | Pikeman |
| stock `creature_default_weapon` | `combat_meleespecialize_unarmed` | Brawler unarmed |

- Add a re-equip check to the existing training/maintenance lane: when the
  cached next step's `xpType` maps to a different weapon than the one currently
  held, re-run the existing equip choreography under the agent lock.
- Boxes whose `xpType` is not in the map (e.g. `combat_general`) leave the
  current weapon untouched.

**(b) Preserve true weapon damage for roster PlayerBots.** After
`setWeaponStats()` has run, restore the weapon's own
`minDamage`/`maxDamage`/`attackSpeed` from its
`SharedWeaponObjectTemplate`. Do this **in the sim layer's equip path only** —
`AiAgentImplementation::setWeaponStats()` is shared by every NPC in the world
and must not be modified. Gate it on `earlyGameEnabled` and on the identity
being a roster PlayerBot, so a gate-off bot keeps today's behaviour exactly.

Two supporting facts confirmed during planning:
- `CreatureObjectImplementation::isPlayerCreature()` (`:4297-4302`) reads the
  *template*, not the PvP bitmask, so a sim bot is never subject to
  `CombatManager`'s uncertified-player damage clamp to 5-10
  (`:1296-1299`). Real weapon damage applies cleanly.
- `CreatureObjectImplementation::getWeapon()` (`:4040-4055`) routes AiAgents to
  `getCurrentWeapon()`, **not** the `hold_r` slot — which is why the existing
  choreography sets every weapon slot rather than transferring alone.

**File**: `bin/scripts/managers/sim_player_manager.lua`
- New `playerBotProgression.earlyGame.weaponsByXpType` map (above table).
- `earlyGame.realWeaponDamage` sub-gate, default off, so damage passthrough can
  be disabled independently of the loop for bisection.

### 3. The grind loop (Phase 3)

**File**: `src/server/zone/objects/creature/simplayer/SimHunterController.{h,cpp}`
(novice mode) and `SimPlayerManager.cpp` (target selection, policy)

**The novice mode belongs in `SimHunterController`, not in the abstract
`SimPlayerController`.** Every production roster body runs
`SimHunterController` — the manager reaches its bodies through
`dynamic_cast<SimHunterController*>` in every per-bot path (`:16221`, `:17465`,
`:17732`, `:17888`) — so a loop added to the base class would never be
scheduled. `SimHunterController`'s active tick currently idles when it holds no
hunt order, and that idle branch is the insertion point.

**Scheduler and transition path.** The mode runs on the existing
`SimHunterActiveTickTask` (`runActiveTick`), which is already the **single
writer** of combat-target state — `targetOid` and the target observer are
HUNTING-scoped and owned by `runActiveTick`, while `onTick` only self-defends
and never writes them (ARCHI §12). The novice loop must obey that same rule: it
writes target state only from `runActiveTick`, guarded by the existing
`activeTickGeneration` (latest-wins) and the non-blocking `tickRunning`
single-flight guard. It must not introduce a second tick task.

A self-motivated activity with five states: `LeaveCity → SelectTarget → Engage →
Recover → Train`, evaluated on that tick.

**Leave city — the grind anchor.** `LeaveCity` needs a *destination*, not just a
movement mechanism. Selection is deterministic and bounded:

- The anchor is an outdoor point at a Lua-configured ring distance
  (`earlyGame.grindAnchorMinMeters` / `MaxMeters`, default ~400-900 m) from the
  bot's resolved home-city centre, chosen from a fixed set of bearings seeded by
  the identity id, so a given bot picks the same anchor every time and different
  bots spread around the city rather than stacking.
- A candidate anchor is rejected if it is in water or out of bounds, reusing the
  miner's existing `isOverlandPointInWater` overland guard (P.4.1) — this is the
  proven predicate for "can a bot stand here", and no new terrain logic is
  written.
- On rejection, advance to the next bearing; after
  `earlyGame.anchorMaxAttempts` failures, widen the ring once, then fall back to
  the city's existing resolved hangout point and record
  `earlyGame.anchorFallbacks` on the dashboard.
- **Transition to `SelectTarget`** fires when the bot is within
  `earlyGame.anchorArriveMeters` of the anchor **or** a valid target is already
  in scan range en route — a bot that walks past a suitable creature should
  fight it rather than march to an arbitrary point first.
- On path failure, back off with the controller's existing bounded
  re-path/`onPathFailed` ladder and re-select the anchor. Never retry a
  straight-line re-path against a target already known unreachable (the P.4.2
  futile-repath lesson).
- **An empty scan is a normal wilderness condition, not a failure.** When
  `SelectTarget` completes a valid scan with zero eligible candidates, dwell and
  re-scan up to `earlyGame.scanMaxAttempts` times at `scanRetrySeconds`, then
  rotate to the identity's next seeded bearing and walk to that anchor before
  scanning again. After a full rotation with no candidate anywhere, widen the
  ring once and record `earlyGame.emptyScanRotations` on the dashboard. The bot
  must never sit still indefinitely, and must never treat an empty scan as a
  path failure.

The novice must not enter buildings — miners are deliberately not migrated to
structure traversal for the same reason (ARCHI §12), and this chunk keeps that
posture.

**Target selection — the time-to-kill window.** Server-side knowledge may inform
**selection only** (see the invariant below). For each candidate creature:

```
ttkSeconds = effectiveHam * attackPeriodSeconds
             / (averageEffectiveDamage * expectedHitRate)

reject if ttkSeconds < earlyGame.minTtkSeconds   (trivial: an AFK mob grind)
reject if ttkSeconds > earlyGame.maxTtkSeconds   (unwinnable)
reject if creature->getLevel() > derivedTier + earlyGame.levelCeilingOffset
reject if the creature is a player, a sim bot, or already engaged
prefer   nearest surviving candidate
```

The three derived terms must be defined precisely, because a formula that omits
attack period yields a count of *swings*, not seconds:

- **`attackPeriodSeconds`** — the weapon's actual attack speed. Note that
  `setWeaponStats()` also overwrites this with the agent's `weaponSpeed`
  (`AiAgentImplementation.cpp:2199-2206`), so once P2 restores the weapon's true
  stats, the value read here must be the same one combat will actually use.
- **`effectiveHam`** — the **minimum of the three primary pools** (health,
  action, mind), not health alone and not their sum. A creature is incapacitated
  when *any* primary pool is depleted: `inflictDamage` clamps only secondaries
  to zero (`damageType % 3 != 0`, `CreatureObjectImplementation.cpp:1100-1101`),
  so a primary crossing zero ends the fight. Summing the pools would
  overestimate TTK by roughly 3x; taking health alone would miss a fight that
  ends on action or mind. The minimum is a deliberate, documented
  **conservative approximation** — it can only make the bot judge a target
  *easier* than it is, which is why the level ceiling below is the hard guard,
  not the TTK band.
- **`averageEffectiveDamage`** — the weapon's mean damage after the target's
  mitigation, which is **two** factors, not one. First,
  `getDefenderToughnessModifier` is **not** the right function at all: it applies
  toughness *skill mods* (`CombatManager.cpp:2445`), not armour. The real path
  applies, in order (`:2766-2772`):

  1. an **armour-rating vs armour-piercing** multiplier,
     `getArmorPiercing()` (`:2953-2978`), which is
     `pow(1.25, ap - armor)` when piercing wins and `pow(0.50, armor - ap)` when
     armour wins — a **halving per armour level**, so an armoured creature can
     absorb 2x, 4x or 8x; and then
  2. the **damage-type resist**, `getArmorNpcReduction()` (`:2588`), a switch
     over the target's resist for that damage type.

  Mirroring both in the sim layer was considered and **rejected**: the piercing
  term is a power law that dominates TTK, and a two-factor copy of live combat
  math is exactly the kind of duplicate that drifts silently and misjudges every
  armoured target by 2x or more. Instead, add **one** side-effect-free public
  helper to `CombatManager` — a `const` estimator taking the defender, the
  weapon and a raw damage value, returning the mitigated value by calling the
  existing `getArmorPiercing` and `getArmorNpcReduction` internally. It reads
  state and mutates nothing, adds no IDL and no `src/autogen/` churn, and keeps
  one authority for the math. Both existing members stay `protected`
  (`CombatManager.h:221+`); only the new estimator is public.
- **`expectedHitRate`** — a Lua constant (`earlyGame.assumedHitRate`), not a
  computed to-hit roll. This is deliberate: it is an *estimate* a player also
  makes by eye, and computing the real hit chance would edge toward using combat
  math the bot should not have.

This self-tunes: a better weapon widens the eligible band, which is precisely
the credits→gear→tougher-targets loop the owner described. The level ceiling is
a hard guard so a low-HAM elite can never look attractive. Reuse
`SimHunterController`'s existing `getInRangeObjects` scan and its player-safe
target guard rather than writing a second scanner.

**Engage.** `CombatManager::instance()->startCombat(...)` exactly as
`SimHunterController` already does (`:2957`, `:3051`, `:3505`), plus
`activateAiBehavior(true)` so the stock tree's combat sockets wake (ARCHI §10).
No new combat primitive is introduced by this chunk.

**Flee at low HAM.** Below `earlyGame.fleeHamFraction`, break off, clear the
target, and withdraw to a rest point before re-entering `Recover`. This is the
main defence against death churn and is player-mimetic.

**Recover.** Dwell until HAM crosses `earlyGame.restHamFraction`. No healing
shortcut — the bot waits, as a player without stims does.

**Death and respawn.** PlayerBots have **no `PlayerObject` ghost**, so the real
cloning flow is unavailable to them: `sendActivateCloneRequest`
(`PlayerManagerImplementation.cpp:1545-1556`) returns immediately on a null
ghost, and there is no SUI prompt to answer.

**This is a spawn-location override, not a relocation of the corpse.** A dead
sim bot is not revived in place — the existing path drops the body from
`pveIdentityBodyOids`, increments `identity.deaths`, requeues the order
(`clearPveHunterOrderLocked(..., "DEATH_REQUEUED")`), schedules
`pveRespawnDueAtMs = now + pveRespawnDelaySeconds`, retires the controller, and
then calls `destroyObjectFromWorld` / `destroyObjectFromDatabase` on the corpse
(`:14480-14516`). A later `spawnPveIdentityBody` builds a **new** body and
re-creates its weapons. Calling `switchZone` on the corpse would therefore move
an object that is about to be destroyed, and would neither revive the bot nor
restore its weapons.

The correct design keeps that lifecycle untouched and adds one piece of state:
at death, resolve the nearest cloning facility with the ghost-free
`zone->getPlanetaryObjectList("cloningfacility")` (`Zone.idl:165`, the same list
the player path walks at `:1608`), compute an **outdoor** point beside it, and
record it as a per-identity **spawn override** alongside `pveRespawnDueAtMs`.
`spawnPveIdentityBody` consumes and clears that override when it places the
replacement body, falling back to today's spawn location when it is absent (no
facility on the planet, an unresolvable zone, or a stale override). The override
must be cleared on consumption, on identity retirement, and on roster reload, so
it can never outlive the death that set it.

**The outdoor point is `BuildingObject::getEjectionPoint()`** (`BuildingObject.idl:188`,
implemented at `BuildingObjectImplementation.cpp:211` with a portal-geometry
fallback) — the engine's own answer to "where does someone stand when they leave
this building", which is exactly the semantics wanted here. Station travel's
arrival points are `PlanetTravelPoint` data and supply no building-relative
equivalent, so they cannot be reused for this. The resulting point is then
validated with the same overland guards as the grind anchor (in-bounds, not on
open water); on a sentinel/invalid ejection point or a failed guard, fall back
to the nearest exterior portal point
(`BuildingObject::getNearestExteriorPortalPoint`, already used by the cell-nav
work), and failing that, drop the override entirely and respawn at today's
location. The body is placed with `parentID 0`, so a respawn never lands inside
an un-navmeshed interior. Note the existing respawn already applies
`pveCloneWoundAmount` clone wounds when `identity.deaths > 0` (`:14253-14257`),
which is the correct player-mimetic cost and needs no change.

Progression is unaffected throughout: it lives in MySQL keyed by roster
identity, never on the body.

**Train.** Unchanged — the existing training lane consumes earned XP. This phase
only supplies the XP and, via P2, keeps its type correct.

**Skip-tolerant step derivation.** As described above, `deriveNextTrainingStep`
gains a fundability predicate and a `stalledBoxes` counter.

### 4. Thin activity arbiter (Phase 4)

**File**: `src/server/zone/objects/creature/simplayer/SimPlayerManager.cpp`

One scoring function on a slow tick choosing between exactly **two**
activities: `grind` and the existing demand-driven `hunt`. Per the owner's
decision a bot grinds its template before joining the demand loop; there is no
partial-progress graduation.

**Graduation must be defined against *fundable* completion, or it is
unreachable.** The template's three Medic boxes are funded by `medical` XP,
which this chunk provides no way to earn, so "all 63 boxes trained" can never
become true and every bot would grind forever — making the arbiter dead code and
leaving the demand loop as starved as it is today. Graduation is therefore:

> **no untrained box remains whose `xpType` is fundable**, where an `xpType` is
> fundable unless it appears in an explicit `earlyGame.deferredXpTypes` list —
> i.e. all 60 combat boxes trained, with the 3 Medic boxes recorded in
> `training.stalledBoxes`.

**Deferred is not the same as gated off, and conflating them inverts the
rule.** Fundability must be decided by that explicit deferral list, *not* by
asking whether an XP source is currently enabled. `awardKillXp` is an
independent default-off gate, so a fresh deployment has zero enabled sources; a
"currently-enabled" test would find no fundable untrained box and declare every
bot instantly graduated — the exact opposite of the intent. A temporarily
disabled source leaves its boxes **blocked** (untrained, ungraduated, and
counted as blocked on the dashboard); only an explicitly deferred type is
excluded from the graduation set.

When a healing activity later supplies medical XP, those boxes become fundable
and are trained without any change to this rule. The terminal state of a
fully-graduated bot is the demand-driven hunt, not an idle grind.

**The predicate must be enforced in both places, or it leaks.** Today a roster
identity with a training plan is still hunt-eligible, so the market matchmaker
can hand a mid-grind novice a demand order and pull it out of its loop behind
the arbiter's back. The same graduation/activity predicate must therefore gate
**(a)** matchmaker candidate selection, so a grinding bot is never offered an
order, and **(b)** controller dispatch, so an order that somehow arrives is
declined rather than silently overriding the grind. Following the F_0.9.5
governor lesson, that predicate is written **once** and called from both sites —
one membership rule expressed in two places is exactly the shape that drifted
into four separate review findings in the last chunk.

Otherwise deliberately minimal: it exists so a novice can graduate at all, and
so later chunks (lair tactics, bazaar, and a future Scout/harvesting template)
have a seam to add modes to. Generalising it now is explicitly out of scope.

## Technical Considerations

- **Pattern usage**: the nearest analogue is `SimHunterController` — it already
  owns a multi-state travel/engage/harvest loop, real combat, and a
  player-safe target guard. The novice mode should be a mode of that shape, not
  a new parallel controller.
- **Locking & references**: match the existing spawn/equip choreography
  verbatim — `Locker agentLock(agent)`, then `Locker weaponLock(weaponObject,

## Invariant Introduced — No Cheat Kills

Server-side knowledge (`getLevel()`, HAM pools, template statistics) may inform
**target selection** only. It may never influence a combat outcome. A real
player reads con-colour and makes the same estimate; the TTK computation is that
estimate, not a damage advantage. No bot may bypass
`CombatManager::startCombat`, short-circuit damage application, or ignore HAM
cost. Real weapon damage is *parity*, not an exemption: the bot gets the
weapon's real numbers, exactly as a player does, and nothing more.
