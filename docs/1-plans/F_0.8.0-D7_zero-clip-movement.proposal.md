**§2 correction.** The proposal claimed the root cause was "one function". That
was wrong, and the code review caught it. There are **two** producers of
unchecked straight lines: `SimPathFindTask::run()`'s explicit overland branch,
and `PathFinderManager::findPathFromWorldToWorld`'s `size() < 2` fallback
("path could not be evaluated"). **Non-hybrid miners — the dominant population
and the dominant Phase 2 risk — reach the second one via the generic branch.**
The probe therefore instruments the path actually handed to the mover in every
branch, not just the overland one.

**Evidence-integrity rules the implementation now enforces** (all four review
rounds landed here, not on movement logic — Phase 1's only product is the number
that decides whether enforcement is safe, so an inflated "clear" rate is the one
failure mode that would look like success):

1. Outcomes are explicit — `clear`, `would_block`, `skipped`, `truncated`,
   `error`. A probe that could not finish is never reported as clear.
2. Aggregation is worst-evidence-first (`Error > Truncated > Skipped > Clear`);
   a path is only `clear` when **every** probed segment was conclusively clear.
3. Probe inputs (ray height, agent OID) are bound per-task at construction, so a
   newer task's refresh cannot re-label an older task's path.
4. Nothing is committed until the path is **actually walked** — past the
   generation check *and* past `onPathFound`'s rejection gates to `state =
   MOVING`. Counters are per accepted path, so
   `clear == checks - (wouldBlock + truncated + skipped + errors)`.

**Known Phase-1 limitation:** ray height is measured under the agent lock for
`directOverland` legs; generic/navmesh legs use the last snapshot or a 1.0 m
torso default. The value used is logged on every line.
**Raised by**: owner requirement, 2026-08-18 — "We for sure want 0 clipping …
ensuring they do not clip through ANY building or structure is key."
**Supersedes**: D1 AMENDMENT 1 Option C as a shippable answer (it passes the
matrix by clipping — see `docs/4-unit-tests/live_d1-option-c_20260817-084235.md`).

## 2. Root cause of R3 — one function

`SimPathFindTask::run()`, the overland branch
(`SimPlayerController.cpp:107-119`):

```cpp
} else if (useDirectOverlandPath) {
    Vector3 start = startCoord.getWorldPosition();
    Vector3 end = endCoord.getWorldPosition();
    if (directTargetUsesTerrainHeight)
        end.setZ(zone->getHeight(end.getX(), end.getY()));

    path = new Vector<WorldCoordinates>();
    path->add(WorldCoordinates(start, nullptr));
    path->add(WorldCoordinates(end, nullptr));
}
```

A `directOverland` "path" is a **literal two-node straight line with no geometry
consulted at all**. Everything downstream just walks it. This is the single,
global clipping vector for *every* sim bot — miners, hunters, PvP bots, and the
D1 starport escape. It was safe by accident in open wilderness (P.4.2's original
scope: no structures there) and is unsafe everywhere else.

The D1 Option C clip (`crossesGeometry=1 hitAt=0.0694`, 3.47 m into a 49.97 m
walk) is not a D1 bug. It is the first place we *instrumented* this, so it is
the first place we saw it.

**The engine already owns the correct test and does not run it.**
`CollisionManager::checkMovementCollision(creature, closeObjects, zone,
lastValidWorld, transformPosition)` is the anti-clip validator for **player**
movement — navmesh phase, then a broad-phase bounding sphere and a narrow-phase
`getAppearanceIntersection` against every `COLLIDABLETYPE` close object. It
returns `true` = clear, `false` = blocked, and fails safe (null zone → blocked).
Its only call site, `DataTransform.h:338`, is **commented out**. So no entity on
this server — player or bot — is currently anti-clip validated.

## 3. Proposed design

Two independent parts. Part 1 makes clipping structurally impossible; Part 2
gives the bot somewhere sensible to go when a straight line is refused.

### Part 1 — segment-clearance invariant (the backstop)

Add a clearance test on every `directOverland` leg, before the 2-node path is
emitted. Reuse the engine's own narrow phase rather than editing stock files:

- collect candidates with `zone->getInRangeObjects(...)` over the segment's
  bounding radius;
- reject any candidate whose appearance mesh the segment enters, via
  `CollisionManager::getAppearanceIntersection(object, rayStart, rayEnd, radius,
  distance)` — the same call the D1 diagnostic already uses successfully
  (`SimPlayerController.cpp:1776`);
- ray height from `CollisionManager::getRayOriginPoint(creature)` so the test is
  taken at torso height like the player test, not at the feet.

This mirrors `checkMovementCollision`'s phase 2 without touching
`CollisionManager.cpp` or the shared player path. It differs deliberately in one
respect: the player version only rays **25% of the way** to the destination
(`dx * 0.25f`), which suits a per-tick transform delta and is useless for a 50 m
leg. We test the **whole segment**.

**Rollout is observe-only first.** Phase 1 logs `would_block` and changes
nothing — exactly how P.4.1's overland guards and D1's telemetry were validated.
Only after a live run shows the true block rate and cost do we let it gate
movement (Phase 2).

### 3.1 Threading — resolved

The blocker flagged in the first draft is settled, and my earlier note that
world queries run *under* the agent lock was **backwards**. Our own code states
the rule (`SimPlayerManager.cpp:11280`):

> "No manager or agent lock is held across either world query, matching
> `scanForTarget` and the mission-terminal resolver's lock choreography."

Three facts make the clearance test safe from `SimPathFindTask::run()`:

1. `Zone::getInRangeObjects(x, z, y, range, objects, readLockZone,
   includeBuildingObjects)` takes **its own zone read lock** (`Zone.idl:131`).
   Called with `readLockZone = true` and no other lock held it is exactly the
   sanctioned pattern — the same call the PvE buff-provider resolver makes at
   `SimPlayerManager.cpp:11335`.
2. `SimPathFindTask::run()` **already holds no locks** — it calls
   `PathFinderManager::findPath` bare. There is no lock order to invent and none
   to violate.
3. `CollisionManager::getAppearanceIntersection` reads immutable template
   appearance data plus the object transform. Stock `checkMovementCollision`
   does precisely this over unlocked close objects, so the precedent is the
   engine's own.

One deliberate consequence: `getRayOriginPoint(creature)` reads creature height
and posture, which are agent state. **Precompute the ray height on the issuing
thread**, where the controller's lock choreography already applies, and pass it
into the task as a plain `float` — so the worker thread never touches the
creature at all.

### Part 2 — exit selection (revised after the POB question, 2026-08-19)

**Yes — the POB explicitly marks valid exits, and stock code already prefers the
nearest one to where the bot is going.** Leaving by a different door than it
entered is not exotic behaviour to be built; it is the **default**.

What the data model gives us:

| Datum | Meaning | Used anywhere today? |
| --- | --- | --- |
| `PathNode::BuildingEntrance` (type 3) nodes in the exterior floor mesh's path graph | the building's doors | — |
| `PathGraph::getEntrances()` | returns exactly those door nodes | **NO consumers in the entire codebase** |
| `CellProperty::hasWorldPortal()` | "this cell opens to the outside" | **NO consumers** — parsed at load and never read |
| `CellProperty::getConnectedCells()` | interior cell adjacency graph | used by pathing |
| `CellPortal::getGeometryIndex()` → `PortalLayout::getPortalBounds(idx)` | the doorway's actual AABB | — |

And stock `PathFinderManager::findPathFromCellToWorld` already does:

```cpp
const PathNode* exteriorNode = exteriorPathGraph->findNearestGlobalNode(transformedPosition);
Vector<const PathNode*>* exitPath = portalLayout->getPath(exitNode, exteriorNode);
```

`transformedPosition` is the **final destination** in model space — so the
engine picks the exterior node closest to the destination and A*'s the portal
graph to it. Multi-door, destination-aware egress is already there. Our repair
ladder only runs when `getPath` returns nullptr.

#### The two failure modes are different, and only one is a POB problem

1. **Stuck inside a cell** — the owner's stated worry ("if combat stops it
   leaving, it must not clear and get stuck in the cell"). This is fully
   answerable from POB data, and today it is not: `cellEgressAttempts >=
   egressAttemptCap` (default **2**) gives up on *the building*, not on *a door*.
2. **Stuck in a walled courtyard** — D1/Mos Eisley. The bot is **not in a cell**;
   it is on the landing pad, which is cell 0, i.e. already "outside" as far as
   the POB is concerned. Run 4 measured this: `nodes examined=3
   rejectedHollow=3` — all three of the starport's entrance nodes are *inside*
   the hollow, because you exit the building **onto** the pad. The enclosure is
   surrounding city geometry that the starport's POB knows nothing about.
   **No amount of portal data solves this one.**

#### Revised egress ladder

For **mode 1** (in a cell), never give up while an unused door remains:

1. stock `findPathFromCellToWorld` (destination-nearest door) — unchanged;
2. on failure, build the **exit set** — `getEntrances()` on the exterior path
   graph, plus a BFS over `getConnectedCells()` to any cell with
   `hasWorldPortal()` — and try candidates **ordered by distance from the bot**
   (not from the destination; the goal here is *out*, then re-plan);
3. **budget per candidate, not per building.** Today's `egressAttemptCap = 2`
   is the stuck-in-cell bug the owner is describing: two failures against one
   door and the bot is done. Retry budget should be spent across the exit set,
   with a total ceiling.

For **mode 2** (walled courtyard), the POB is silent, so:

4. **doorstep** — the recorded outdoor world point the bot occupied immediately
   before ingress. Provably outside the hollow and provably walkable, because
   the bot walked it. Demoted from "the answer" to "the fallback for the case
   portal data cannot see";
5. **navmesh route** — retry as a recast path, which routes around geometry;
6. fail the leg and let the bounded watchdog + P.4.3 recovery re-acquire.

Never "move anyway" — that is Option C, and it is what we are removing.

#### Caveat to verify before relying on it

`worldPortal` is set when `portal->getTargetCellIndex() <= 1`
(`CellProperty.cpp:125,179`) — **`<= 1`, not `== 0`**, while
`PortalLayout::getCellTotalNumber()` documents index 0 as the outside cell.
Either there is a second convention or this is a stock off-by-one. Since nothing
in the codebase consumes the flag, it has never been exercised. **Verify
empirically against real buildings before trusting it**; `getEntrances()` needs
no such assumption and should be the primary source.

## 4. Safety analysis

| Risk | Assessment | Mitigation |
| --- | --- | --- |
| **Stranding hundreds of miners** — the P.4.4 vehicle lesson. If the guard rejects legs miners cannot re-path, the economy stops | **This is the dominant risk.** `directOverland` is what made miners work at all (P.4.2) | Observe-only Phase 1 measures the real block rate before anything gates. Gated (`zeroClipConfig.enabled`, default false). Ladder step 3 lands on the *existing, proven* failure path, not a new one |
| **Threading** — a world query from `SimPathFindTask`'s worker thread | **RESOLVED, 2026-08-19 — see §3.1.** The sanctioned pattern is a **lock-free** query with the zone taking its own read lock; `SimPathFindTask::run()` already holds no locks, so it matches without change | Call `getInRangeObjects(..., readLockZone=true, ...)` with no manager/agent lock held; precompute ray height at issue time so the worker never touches the creature |
| **Performance** — narrow-phase mesh intersection per path request | Path requests are per-assignment, not per-tick; D1's probe already runs one such call per escalation at no measurable cost | Phase 1 logs elapsed µs per check; set a candidate cap and a segment-length cap |
| **False positives** — a bot refused a legitimate route because a mesh grazes it | Would show up as a raised block rate on wilderness legs | Phase 1 reports block rate split by leg type before Phase 2 turns on gating |
| **Bot stranded inside a cell** — owner-raised. Today `cellEgressAttempts >= egressAttemptCap` (2) abandons the whole building after two failures against one door | **Real today**, independent of D7's guard; a combat interrupt during egress is the likeliest trigger | Per-candidate budget over the POB exit set (§3 Part 2), so a door failing does not end the attempt. Exit set is derived from already-parsed data — no new geometry search |
| **Scope creep into stock movement** | Deliberately avoided | No edits to `CollisionManager.*`, `DataTransform.h`, or the stock player path. The commented-out player validator stays commented out — re-enabling it is an owner decision, not part of D7 |

## 5. Acceptance criteria

1. `crossesGeometry == 0` on **every** escalation and every overland leg
   instrumented — the criterion Option C failed.
2. The 25-scenario matrix runs to completion with no regression against run 3's
   10 PASS baseline, and scenarios 3, 4, 8, 11 (the starport/hollow group) pass
   **without** a clipping segment.
3. Miner economy steady state unchanged after Phase 2: `pathFailures` and
   `minerRecovery` churn no worse than the current post-restart baseline
   (`6 stationed / 1 moving / 0 pathFailures`).
4. Phase 1 evidence published before Phase 2 is enabled.
