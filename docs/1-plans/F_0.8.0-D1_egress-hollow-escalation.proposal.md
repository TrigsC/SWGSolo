# D1 Proposal — Egress escalation out of an enclosed hollow

**Status**: APPROVED — owner said "start on D1" (2026-08-16). Implementing the
§4 recommendation **A + B + C**; option D is not built.
**Parent**: `docs/1-plans/F_0.8.0_structure-traversal-foundation.plan.md`
**Evidence**: `docs/4-unit-tests/live_structure-traversal-foundation_20260814-091057.md`,
`..._20260814-132303.md`, `..._20260816-132600.md`
**Scope**: **10 of the 15** failing scenarios in run 3 (`exit_not_outdoors`) —
scenarios 3, 4, 8, 11, 12, 13, 14, 15, 17, 24, 25. D1 is now the single dominant
blocker for the feature.

## 1. The defect, precisely

Observed on `mos_eisley_starport_front` (building `1106368`):

```
ST_PHASE gen=6 Idle→Egress cell=0 reason=exit_requested
ST_PATH  request  world=(3527,-4803,5)
ST_PATH  accepted nodes=42 world=(3616.28,-4845.67,5.10)   <- short of request
ST_PATH  request  world=(3527,-4803,5)
ST_PATH  accepted nodes=13 world=(3573.4,-4813.2,5.09)     <- short of request
SCENARIO_STEP exit FAIL 55592ms reason=exit_not_outdoors
```

Mechanism, traced through the code:

1. `beginCellEgressIfNeeded()` (`SimPlayerController.cpp:638`) fires while the bot
   is in a cell. It targets
   `building->getNearestExteriorPortalPoint(agentWorld)`, falling back to
   `getEjectionPoint()`. For a starport this lands the bot on the **landing pad**
   — which is `cell 0` (outdoors by parent) but enclosed by the building's walls.
2. `cellEgressActive` clears; the normal overland leg takes over toward the real
   outdoor destination.
3. `findPath` cannot route off the walled pad, so it returns a **truncated** path
   ending inside the hollow. The controller reaches that path's last node and
   reports arrival.
4. `completeStructureTraversalIfArrived()` (`SimPlayerController.cpp:1643`)
   correctly declines to finish, because
   `isWithinOwningBuildingHollow()` is still true.
5. Nothing escalates. After `egressAttemptCap = 2` the leg is abandoned with the
   bot stranded inside the hollow.

**The hollow guard is not the bug — it is the only reason we noticed.** The gap
is that egress has no answer when the navmesh cannot produce a path clear of the
hollow.

`isWithinOwningBuildingHollow()` tests the building's AABB in model space plus
`hollowContainmentMarginMeters` (default 15). So *any* fix must deliver the bot
to a point provably outside `bounds + margin`.

## 2. Why this is the P.4 problem again

This is the same root condition the miner work already hit: **SWG only navmeshes
cities and POIs, not every traversable surface.** P.4.2 resolved it by adding the
`directOverland` trust tier — a bot may walk a straight overland line to a target
that no navmesh path reaches, because SWG physics lets it (cliffs climbable,
water swimmable). The walled landing pad has a real, walkable gap; it simply is
not navmeshed.

That precedent matters: we already accepted, shipped, and live-verified
"move without a navmesh path" for exactly this class of terrain.

## 3. Options

### Option A — Escalate to an exterior path-graph node (recommended primary)

The building's own portal layout carries an exterior floor mesh at index 0
(confirmed: `resolveStarportInteriorWaypoint` treats
`getFloorMesh(1..getFloorMeshNumber()-1)` as interiors). Its path graph's global
nodes are the game's own "just outside this building" points.

On a truncated-arrival-inside-hollow condition:
1. enumerate `portalLayout->getFloorMesh(0)->getPathGraph()->getGlobalNodes()`;
2. transform each to world space, keep only those **outside** the hollow test;
3. pick the one nearest the final outdoor destination;
4. move to it as an internal egress leg, then resume the normal overland leg.

*Pros*: uses the client's own geometry; works for any POB, not just starports;
no invented coordinates. *Cons*: a building could expose no qualifying node.

### Option B — Escalate to the nearest PlanetTravelPoint

P.4.5a station travel already resolves starport outdoor arrival points and has
been live-verified as reachable and genuinely outdoors.

*Pros*: proven data path, already in the codebase. *Cons*: only exists for
starports; a hospital or cantina hollow has none. Best as a **preference** when
the owning building is a starport, not as the general mechanism.

### Option C — Direct overland walk to the escalation target

Whichever target A or B yields, reach it with the existing `directOverland`
trust tier instead of `findPath`, since by construction `findPath` has already
failed to leave the hollow.

*Pros*: matches shipped, verified P.4.2 precedent; the only option that works
when the aperture is simply un-navmeshed. *Cons*: straight-line movement could
clip building geometry if the target is chosen badly — which is why the target
must come from A or B, never from a raw radial guess.

### Option D — Radial escape ray (rejected)

Project a ray from the building centre through the bot and step outward past
`bounds + margin`. **Not recommended**: it can point straight at a wall and
would be the one option capable of pushing a bot into geometry. I would only
build this as a diagnostics-only observation, never as movement.

## 4. Recommendation

**A + B + C**: target selection prefers B when the owning building is a starport
(proven data), else A (general geometry); movement to that target uses C
(`directOverland`), because `findPath` has definitionally already failed. D is
not built.

This keeps every coordinate sourced from real game data and reuses two mechanisms
this project has already live-verified.

## 5. Safety analysis

| Risk | Mitigation |
| --- | --- |
| Infinite escalation loop | New `hollowEscalationAttempts` counter, own cap (default 1), reset only on a genuinely-outdoors transition. Escalation cannot re-arm itself. |
| Bot pushed into geometry | Targets come only from portal-layout/travel-point data, never a computed ray. Reject any candidate failing `zone->isWithinBoundaries()` or `isOverlandPointInWater()`. |
| Teleport-looking jump | Escalation is a *movement leg*, never a `switchZone`/position set. The existing `recordTraversalMovementStep()` teleport and z-sanity detectors stay armed and would flag a violation. |
| Regression to gate-off behavior | All of it lives behind `structureTraversal.enabled`, which is default-off. Gate-off path byte-for-byte unchanged, as enforced in the Codex review of Phase 1. |
| Locking | Target resolution reads `PortalLayout`/`SharedObjectTemplate` (template data, not managed state). The one managed touch — `building->getNearestExteriorPortalPoint()` — already runs under `Locker buildingLocker(building)` at `SimPlayerController.cpp:721`; the escalation reuses that exact choreography and takes no new lock while holding the agent lock. |
| Combat interaction | Escalation is suppressed while `!isTraversalActive()` or the compound peace predicate is false, identical to the existing egress leg, so a combat pause still wins. |

## 9. Open question — ANSWERED by runs 2 and 3

The question was whether the Theed hospital (`controller_path_failed`) shares
this root cause, in which case one escalation could cover both. **It does not.**
Run 2's per-retry diagnostics established that the two failures are distinct:

| | D1 (starport) | D2 (med center) |
| --- | --- | --- |
| Path result | **truncated** path, accepted, ends inside the hollow | **no portal path at all**, all three repair strategies fail |
| Bot ends up | outdoors-by-parent (cell 0) but walled in | still in the interior cell |
| Failure | `exit_not_outdoors` | `controller_path_failed` |
| Cause | walled landing pad is not navmeshed | cell's 5 global nodes match no exterior floor-mesh global ID |

So D1's escalation must **not** be expected to fix D2, and D1's target selection
is designed against starport-hollow topology only. The recommended pre-D1
matrix run has been executed (run 3), so this proposal now rests on measured
topology rather than assumption.

**One caveat carried into implementation**: D2 proved that a cell's path graph
can have global nodes that link to nothing. Option A enumerates the *exterior*
floor mesh's global nodes, which is a different graph — but the same "nodes may
exist yet be useless" caution applies, which is exactly why A validates every
candidate against the hollow test rather than trusting node membership.

# AMENDMENT 1 — Option C alone (direct-to-destination fallback)

**Status**: APPROVED — owner said "pursue Option C" (2026-08-17), after run 4
invalidated the original A+B target selection.
**Supersedes**: §4's recommendation, for the starport-hollow case.
**Evidence**: `docs/4-unit-tests/live_d1-hollow-escalation_20260817-180013.md`

## A1.1 Why the original recommendation failed

Run 4: 11 escalations, 11 `no_candidate`, **0 targets ever selected**, across 2
arrival points and 3 agents. Both candidate sources name points *inside* the
region the escalation must escape:

- **Option B** resolved *Mos Eisley Starport* (`planet_manager.lua:502`,
  interplanetary, ~40 m away — so it was found and accepted by the search) but
  its arrival position **is the landing pad**, which is the hollow. P.4.5a uses
  that datum to send a miner *to* a starport, which is correct there and exactly
  wrong as an escape target.
- **Option A** enumerates the exterior floor mesh's global nodes — the building's
  own door points, inside `AABB + hollowContainmentMarginMeters` — i.e. precisely
  the nodes its own validity filter rejects.

§3's premise, that these datasets supply points outside the hollow, is false.

## A1.2 The amendment

Keep A and B as a first attempt, and add a **direct-to-destination fallback**:
when target selection yields no candidate, issue the `directOverland` leg
straight to `structureTraversalIntent.finalTargetWorld` — the traversal's real
outdoor destination, which is a legitimate reachable point the caller already
chose (~50 m west of the stuck position in the failing scenarios).

A and B are retained rather than deleted because they are already implemented and
reviewed, they fail fast (~3 ms, measured), and they have only ever been
exercised against **one** building — a cantina or hospital hollow may still yield
a valid node. The fallback covers the case that demonstrably matters.

## A1.3 The honest risk, and how this run measures it

§3's own critique of Option C was: *"straight-line movement could clip building
geometry if the target is chosen badly."* That objection does **not** disappear
here — the destination is well chosen (the caller's real target, not a radial
guess), but the straight line from a walled landing pad to a street outside may
still pass through the starport's geometry.

This matters beyond aesthetics: the owner's standing requirement is
player-mimetic movement (bots **run** to starports rather than warping, see the
`player-mimetic-travel` note), so a bot clipping through a starport wall is a
realism regression even if the traversal reports success.

I cannot settle this from the code — it depends on the building's actual mesh —
so the amendment **instruments it rather than assuming it**:

- `escalation=direct dest=… crossesFootprint=0|1 segmentLen=…` — tests whether
  the arrival→destination segment intersects the owning building's AABB in model
  space. `crossesFootprint=1` means the bot's straight line goes *through* the
  building, which is a **realism failure even on a functional PASS**.
- the existing `recordTraversalMovementStep` teleport and z-sanity detectors stay
  armed throughout.

Acceptance therefore adds a criterion the original proposal did not have:
**`crossesFootprint` must be 0 on every successful escalation.** A PASS with
`crossesFootprint=1` is reported as a realism failure and returns to design, not
as a green run.

## A1.4 Closing the observability gap

Run 4 could not distinguish "no nodes existed" from "all nodes rejected", name
the rejecting filter, or report Option B's outcome at all. Added:

- `escalation=travelpoint found=0|1 interplanetary=0|1 rejected=none|hollow|bounds|water`
- `escalation=nodes examined=N rejectedHollow=N rejectedBounds=N rejectedWater=N accepted=N`

## A1.5 Config

```lua
hollowEscalationDirectFallback = true,   -- reachable only when
                                         -- hollowEscalationEnabled is on,
                                         -- which is default false
```

Kept as its own flag so an A/B-only run can be compared against a
fallback-enabled run without a rebuild. Effective default remains off, because
its parent gate is off.

## A1.6 Acceptance

- the 10 `exit_not_outdoors`/`controller_path_failed` starport scenarios reach
  `exit_complete_outdoors`;
- `hollowEscalationsFailed` is 0;
- **`crossesFootprint` is 0 on every escalation that succeeds**;
- `teleportsDetected` and `zSanityViolations` stay 0;
- the 10 currently-passing scenarios still pass, in particular
  `ten_sequential_cycles`;
- gate-off snapshot unchanged.
