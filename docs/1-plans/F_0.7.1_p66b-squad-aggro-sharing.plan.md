# P.6.6b Squad Aggro-Sharing (Combat Contagion) Implementation Plan

## Overview

When any member of a PvP squad enters combat, the **whole squad** converges on
that fight: living squadmates acquire the shared enemy target(s), path in with the
existing navmesh/cell-aware combat approach (never clipping through buildings), and
engage — they never sit back and heal while a squadmate fights and dies. This is a
follow-on to P.6.6 (F_0.7.0) controller-driven combat and reuses its combat lane
wholesale; it adds a squad-level "shared combat target" broadcast so combat becomes
contagious within a squad. Owner decision: **whole squad converges** (not allied
squads). Gated default-off behind a new `pvpConfig.combat.squadAggroSharing` block.

## Problem Statement

Verified against P.6.6 code and the 2026-07-29 live observation:

1. **Members don't join a squadmate's fight.** Members are engine FOLLOWers that
   each independently scan a ~100 m bubble (`scanForTargets`). If a squadmate is
   fighting an enemy the member hasn't personally scanned (out of its bubble, or
   it's mid-follow/heal), the member does nothing useful — the owner observed a
   bot fighting (and dying) while a nearby squadmate only "provided light
   healing" and never joined the fight.
2. **No shared aggro/target list.** Each bot's target is private
   (`controllerCombatTarget`); there is no squad-level notion of "the enemies this
   squad is engaged with," so members can't pull the team's aggro list and pile
   on.
3. **Result:** fights are 1-on-1 attrition instead of squad-on-squad, squadmates
   die unsupported, and the squad's numerical/positional advantage is wasted.

## Solution Architecture

Reuse the P.6.6 combat lane; add a thin squad-level broadcast:

- **Shared combat target on the squad row.** When any bot **acquires** a valid PvP
  combat target (`acquireControllerCombatTarget` — the single funnel for both scan
  hits and defender adoption, Codex P2-1), it publishes that enemy OID to its
  `SimPvpSquad` via the manager (`recordPvpSquadCombatTarget(squadId, enemyOid)`),
  guarded by `pvpSquadMutex` with a short TTL — mirroring the existing
  `SimPvpFactionContact` pattern (`SimPlayerManager.h:1032`, TTL + `pvpSquadMutex`).
  The squad keeps a small **shared aggro set** (the distinct enemy OIDs its members
  are currently engaged with).
- **TTL kept alive for the duration of the fight (Codex P1-2).** Acquisition is a
  one-shot transition, so a fixed 8 s TTL would expire mid-fight and squadmates
  would stop converging on a still-live enemy. `driveCombatMovement` therefore
  **re-publishes** the held target periodically while a controller still owns a
  live target — throttled well below the TTL (e.g. every ~2–3 s) so it is cheap but
  the shared entry never lapses during an ongoing fight or while a squadmate is
  still finishing a traversal leg to join.
- **Idle squadmates converge.** In the controller tick, a controller-driven bot
  that has **no** `controllerCombatTarget`, is **not** interior-traversing
  (P.6.6a `isInteriorTraversalActive()` still wins), and whose squad has a live
  shared aggro target **acquires that target** (`acquireControllerCombatTarget`)
  and runs the normal `driveCombatMovement` approach → engage. The existing
  combat-scoped navmesh/cell-aware approach provides "path in, no clipping" for
  free.
- **Convergence radius, not scan radius (Codex P1-1).** A shared target is a
  *known* teammate contact, not a fresh LOS-free scan hit, so convergence is bounded
  by a larger `squadAggroConvergeRadiusMeters` (e.g. same-city / a few hundred
  metres), not the 100 m engage-detection radius — otherwise a member 120 m from the
  fight would never converge. **This requires a code change to the combat lane, not
  just a wider acquire gate:** `driveCombatMovement` currently tears down a
  not-yet-in-combat target the instant `distance > approachRadiusMeters` (100 m), so
  a 300 m shared target would be dropped on the first tick. Add a per-controller
  `combatIsConvergenceTarget` flag (set when a target is acquired via convergence,
  cleared on teardown/engage-normalization) and, while it is set, use
  `squadAggroConvergeRadiusMeters` as the approach's outer-bound teardown distance
  instead of `approachRadiusMeters`. The approach-timeout still bounds the leg in
  time; the in-combat leash bounds the holding phase once engaged.
- **Fight, don't heal.** Driving members into the shared target via the combat lane
  makes them attack (stock combat fires once engaged). The Jedi heal reflex still
  exists in the stock tree, but a converging+engaged member prioritizes attacking;
  no new heal-suppression is planned for v1 (revisit only if members still idle-heal
  in the soak).
- **Self-limiting.** Shared target dies/leaves → its OID drops from the aggro set
  (TTL + liveness check) → members get `targetUnavailable` teardown → resume
  normal follow/loiter. Whole-squad only (owner's call): no cross-squad broadcast,
  so a fight never snowballs across the map.

## Implementation Details

### 1. Squad shared-aggro state + manager API

**File**: `SimPlayerManager.{h,cpp}`

**Current state**: `SimPvpSquad` (`SimPlayerManager.h:950`) holds `leaderOid` +
`memberOids`; `recordPvpEngagement(squadId, wasPlayer)` already fires on engage;
`SimPvpFactionContact` shows the TTL + `pvpSquadMutex` pattern to copy.

**Modifications**:
- Add a small shared-aggro structure to `SimPvpSquad` (a short `Vector<uint64>` of
  enemy OIDs + last-refresh ms, or a primary OID + TTL for v1 simplicity), guarded
  by `pvpSquadMutex`.
- `void recordPvpSquadCombatTarget(uint64 squadId, uint64 enemyOid)` — inserts/
  refreshes the enemy OID (with a fresh timestamp) in the squad's aggro set under
  `pvpSquadMutex`. Called both on acquisition (initial publish) **and** on the
  throttled in-fight refresh (Codex P1-2), so a long fight never lets the entry
  lapse.
- `uint64 getPvpSquadSharedCombatTarget(uint64 squadId, uint64 excludeOid)` —
  returns a live shared enemy OID for a squadmate to converge on (skips entries
  older than `squadAggroTargetTtlSeconds`; `excludeOid` lets a bot avoid re-picking
  a target it just failed to reach — see §3). Prunes dead/stale OIDs lazily.
- All access read-mostly and **never holds `pvpSquadMutex` while locking an
  agent** (project rule).

### 2. Publish on acquire (single point) + keep-alive refresh

**File**: `SimPvPController.cpp` (`acquireControllerCombatTarget` + `driveCombatMovement`)

**Initial publish (Codex P2-1):** the **only** publish point is
`acquireControllerCombatTarget` — it already funnels *both* scan hits and defender
adoption, whereas `recordPvpEngagement` does not cover adoption. Do **not** hang the
publish off `recordPvpEngagement` (that stays engagement accounting only). On
acquire, call `recordPvpSquadCombatTarget(squadId, target->getObjectID())`.

**Keep-alive refresh (Codex P1-2):** in `driveCombatMovement`, while the controller
owns a live target, re-publish the target on a throttle (a per-controller
`lastSquadAggroPublishMs`, re-publish when `now - last >= refreshInterval` with
`refreshInterval` a few seconds, < `squadAggroTargetTtlSeconds`). This keeps the
shared entry alive for the whole fight and while squadmates are still pathing in.

### 3. Converge when idle

**File**: `SimPvPController.cpp` (`SimPvpBotController::onTick`, the no-target tail
that currently calls `scanForTargets()`)

Before/after the normal scan, when the bot has no `controllerCombatTarget`, is not
interior-traversing, and `squadAggroSharing` is enabled: query
`getPvpSquadSharedCombatTarget(squadId, failedSharedTargetOid)` (passing the
failed-target exclusion below); if it returns a live, eligible, same-zone enemy
within `squadAggroConvergeRadiusMeters`, `acquireControllerCombatTarget` it, set the
per-controller `combatIsConvergenceTarget` flag (so the approach's outer bound is the
converge radius, §Solution-Architecture P1-1), and `driveCombatMovement()`. Scan
still runs as the primary detector; the shared target is the fallback that pulls in
members who didn't personally detect the enemy. Members already run the combat lane
(P.6.6), so `assertFollow` already yields to `hasControllerCombatTarget()`.

**Give-up + don't-immediately-re-pick (Codex P2-2):** add per-controller
`failedSharedTargetOid` + `failedSharedTargetIgnoreUntilMs`. When a
`combatIsConvergenceTarget` engagement tears down without ever reaching the fight
(`approachRadius`/`approachTimeout`), stamp that OID + an ignore window of
`squadAggroFailedTargetIgnoreSeconds` (new config, default 10 s; clamped positive)
before resuming follow. `getPvpSquadSharedCombatTarget` receives that OID as `excludeOid`
while the window is live, so the member doesn't thrash re-acquiring a shared target
it just proved it can't reach (it can still converge on a *different* shared enemy,
and re-try the same one after the window). Clear the flag/OID on a successful engage
or when the shared target changes.

**Prefer own closer target:** if the member's own scan finds an eligible enemy
closer than the shared target, prefer that (the shared target is a fallback, not an
override) — avoids dragging a member past a nearer threat.

### 4. Config (Lua, default-off)

**File**: `bin/scripts/managers/sim_player_manager.lua` (`pvpConfig.combat`)

Add under the existing `combat` block:
```
squadAggroSharing = false,               -- master gate for P.6.6b
squadAggroConvergeRadiusMeters = 300,    -- how far a squadmate will converge to join
squadAggroTargetTtlSeconds = 8,          -- shared target expiry if not re-refreshed
squadAggroFailedTargetIgnoreSeconds = 10,-- don't re-pick a shared target a member
                                         --   just failed to reach, for this long
```
Parsed with the same explicit per-field clamps as P.6.6 (no blanket zero-preserve).

### 5. Dashboard visibility

**File**: `SimPlayerManager.cpp` (`pvpActivity.combatEngagement`)

Extend the existing combat section with `squadAggroSharing` (on/off),
`convergencesTotal` (members pulled into a squadmate's fight), and per-squad
`sharedTargets` count. `app.js` gets a matching field under `#/warfront`.

## Technical Considerations

- **Pattern Usage**: The shared-aggro set copies the proven `SimPvpFactionContact`
  TTL/`pvpSquadMutex` choreography; convergence reuses the P.6.6 combat lane
  unchanged (no new movement code).
- **Locking & References**: `recordPvpSquadCombatTarget` /
  `getPvpSquadSharedCombatTarget` take `pvpSquadMutex` only, resolve OIDs to
  `ManagedReference` via `ZoneServer::getObject` **outside** the mutex before any
  agent lock — matching every existing squad-state accessor.
- **IDL Impact**: None (plain fields on the in-memory `SimPvpSquad`; not persisted).
- **C++ vs Lua**: Convergence decision per tick → C++; radius/TTL/gate → Lua.
- **Gating & Simulation-Only**: Default-off `squadAggroSharing`; combat stays inside
  the already-approved PvP bot-vs-bot scope; no economy/inventory/persistence
  mutation.
- **Interaction with P.6.6a traversal suppression**: `isInteriorTraversalActive()`
  still short-circuits combat, so a member mid-starport-run finishes the run before
  converging — no regression of the traversal fix.
- **Dashboard Visibility**: `combatEngagement.convergencesTotal` + per-squad
  `sharedTargets` is the verification surface.
- **Live Verification Plan**: enable `squadAggroSharing` at runtime; confirm on the
  dashboard/in-game that when one member engages, squadmates path in and attack the
  same enemy (no clipping), a dying target releases the squad, and no member sits
  idle-healing while a squadmate fights; `convergencesTotal` climbs; churn ≤
  post-P.6.6a baseline.
- **Edge Cases**: shared target dies/leaves zone (pruned → members disengage);
  target flees beyond converge radius (member gives up, resumes follow); leader
  promotion / member death (roster already reconciled each maintenance tick); a
  member converging when its own scan finds a *closer* enemy (prefer the closer/own
  target); friendly-only squads never share across factions (aggro set is the
  squad's own enemies).

## Type Definitions

No IDL/distributed types. New in-memory fields on `SimPvpSquad` (shared enemy OID
set + per-entry refresh ms), new scalar config + getters on `SimPlayerManager`, and
new per-controller fields on `SimPvpBotController`: `combatIsConvergenceTarget`
(bool — widens the approach outer bound to the converge radius),
`lastSquadAggroPublishMs` (keep-alive throttle), and `failedSharedTargetOid` +
`failedSharedTargetIgnoreUntilMs` (don't-immediately-re-pick). No persistence.

## Performance & Cost Impact

- One extra `pvpSquadMutex`-guarded lookup per idle controller-driven bot per tick
  (bounded to ~10–20 bots) — negligible; no new raycasts.
- No new task threads; convergence rides the existing single arrival/tick chain.

## Backward Compatibility

Fully backward compatible: with `squadAggroSharing = false` (shipped default) the
publish/query paths are inert and behavior is identical to P.6.6. Reversible at
runtime.

## Test Impact

- No existing GoogleTest covers the PvP controller; acceptance is live-dashboard +
  in-game (per ARCHI). The `convergencesTotal` / per-squad `sharedTargets` counters
  are the instruments.
- New pure-ish logic worth a focused unit test if cheaply isolatable:
  `getPvpSquadSharedCombatTarget` pruning/eligibility (dead/stale/excluded OIDs) as
  a function of the aggro set + clock — otherwise record in COVERAGE-DEBT.md.
- Regression guard: with the gate off, P.6.6 combat behavior is byte-unchanged;
  with it on, verify the P.6.6a traversal suppression still wins (no convergence
  mid-starport-run).
