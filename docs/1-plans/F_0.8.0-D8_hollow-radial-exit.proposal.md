# F_0.8.0 — D8: Hollow Exit by Radial Scan (mode 2)

**Status**: **Phase 1 IMPLEMENTED and RUN. OPTION D IS REFUTED — Phase 2 must
NOT be built as designed.** The scan works correctly and reports that the
enclosure is solid: `blocked=72/72`. There is no gap for a ray to find.
**Target**: the 11 `exit_not_outdoors` failures — 79% of what remains in the
matrix, and the only defect class no existing strategy touches.

## Why nothing so far has worked

The bot is on a starport landing pad: **cell 0, so it is "outdoors" as far as
every cell-based mechanism is concerned**, but walled in. Consequently:

- `findPathFromCellToWorld` never runs — there is no cell to leave. Retries 1-6,
  including the multi-cell route that just fixed D2, are all unreachable here.
- D7's exit set reads the building's doors, which D1 measured as
  `nodes examined=3 rejectedHollow=3` — they are doors *into the starport from
  the pad*, not doors *out of the pad*.
- D1's Option C escapes by drawing a straight line, which measured
  `crossesGeometry=1 hitAt=0.069` — it leaves by walking through the hull.

The enclosure is not in the starport's portal layout. It is surrounding
geometry, and the ways out are **gaps between collidable objects**, not portals.
No data lookup can find them; they have to be found geometrically.

## Owner domain knowledge (2026-08-24)

- Hollow starports are **all laid out the same**, so whatever is measured on one
  generalises to the template family.
- A hollow has **two doors**.
- **Theed is different**: the bot spawns outside, not in a hollow; reaching the
  ticket collector means entering a *cell*. So Theed combat is a cell problem
  (Retry 6 territory), not a hollow problem, and `theed_starport_hangar`'s
  `target_cell_unresolved` should NOT be folded into D8.

## Option D — radial ray scan

This was proposed in the D1 document §4 and **deliberately not built** at the
time. It is buildable now for a reason that did not hold then: D7 Part 1's
clearance probe is implemented and live-verified, so the ray machinery it needs
already exists and is known to measure correctly.

When a bot is detected inside the hollow (`hollowMissDistance == 0`):

1. Cast N rays outward from the bot, evenly spaced over 360°, each long enough
   to clear the hollow bounds.
2. A ray **escapes** if it reaches a point outside the hollow region without
   intersecting any collidable appearance mesh — the same broad-phase
   `getInRangeObjects` + narrow-phase `getAppearanceIntersection` pair D7 Part 1
   already uses, including the bounding-sphere cull that made it affordable.
3. Cluster contiguous escaping bearings into **openings**. The centre bearing of
   each cluster is a door; its angular width is a confidence measure.
4. Walk to the nearest opening. D7's clearance probe then independently reports
   whether that route is clean — `crossesGeometry == 0` is the acceptance bar
   Option C failed.

If the owner's account is right, a hollow starport should yield **exactly two
openings**, and the same two on every hollow starport.

## Phase 1 — observe only (this slice)

Log what the scan finds and change nothing:

```
ST_HOLLOW scan status=<ok|error> rays=<n> escaped=<n> reachedOutside=<n> blocked=<n>
          rayLength=<m> openings=<n> elapsedUs=<n> building=<oid> template=<path>
ST_HOLLOW opening index=<i> centreBearing=<deg> widthDeg=<deg> escapeDist=<m> target=<x,y,z>
```

**Corrected contract (2026-08-24).** The first run logged only `escaped`, which
is `reachesOutside && !blocked` — so `openings=0` could not distinguish "every
ray hit geometry" from "no endpoint qualified as outside". The second was in
fact likely, because `rayMarginMeters` had been made to do two jobs at once:
how far past the far corner to cast, *and* how far past the bounds an endpoint
must be to count as escaped. Those are measured from different origins and for a
centred bot never line up. A ray now escapes if its endpoint is outside the
hollow at all, and `reachedOutside` / `blocked` / `rayLength` are reported
separately. **`openings=0` alone refutes nothing — the counters have to say
which condition failed.**

Phase 1 answers, before a single bot is moved:

- Does a hollow starport really yield 2 openings?
- Are they the same 2 across Mos Eisley / Corellia / Tatooine hollow starports?
- Is the scan cheap enough to run at egress time?

If it yields 0 openings the premise is wrong and Phase 2 must not be built. If
it yields many, the clustering needs work. Either is worth knowing before
writing movement code.

## What this implies instead

If the pad has no gap, then the owner's "two doors" are **the starport's own
doors**, and a bot leaves the pad by walking **through the building** rather than
around it — in one door, through the interior, out the other side.

That is a **cell traversal**, which is exactly what Retry 6 (`repair=multicell`)
now does for D2: BFS the portal graph, then one floor route per cell. It is
already built, reviewed and live-verified on two planets.

2. Let D7's exit set run for a bot that is outdoors-but-in-hollow.
   `buildCellEgressExitSet` currently returns false unless the bot's parent is a

**Open risk:** whether the starport's doors are on opposite sides (pad-side in,

Phase 2 as written — cluster gaps, walk to an opening — is **cancelled**.

## Residual defect: D9 — controller lifecycle state is not serialized across threads

Surfaced by Codex during the D8 mode-2 code review (2026-08-25). **Pre-existing
in the resume monitor; NOT introduced by this slice**, though the leash work
made one window easier to reach and is why it was noticed.

`scheduleStructureTraversalResumeMonitor()`'s callback checks ownership
(`generation != traversalGeneration || !isTraversalActive()`) and then acts on
that decision non-atomically. Another task-pool thread can activate a
replacement traversal between the check and the action, after which
`onPathFailed()` clears whichever traversal is *currently* active — the
replacement, not the one the monitor owned. Two branches are affected:

- the `resumeAttempts >= resumeAttemptCap` branch (last ownership check, then
  unconditional `recordStructureTraversalResumeFailure()` + `onPathFailed()`);
- the `!resumeStructureTraversalFromCurrentPosition()` branch (revalidates the
  captured generation first, which *narrows* the window but does not close it).

Consequences: a replacement traversal can be cancelled by a stale monitor, and
the resume-failure counter can be charged against work the monitor no longer
owns — so `minerRecovery`/traversal failure telemetry can overstate failures.

**Fix direction (deliberately NOT attempted inside D8):** make failure-and-clear
a single generation-owned operation — e.g. `clearStructureTraversalStateIfGeneration(expected, reason)`
plus a failure entry point that takes the expected generation — and use it in
both branches. This needs a serialization decision (which lock, and whether the
hunter teardown paths hold it) that is larger than D8 and touches released
hunter/PvP lifecycle code, so it belongs in its own slice with its own review.

**Why D8 stopped short:** D8 removed its own contribution to this class by no
longer re-installing the leash-suppression AI map from the resume-monitor
thread. Suppression is now installed only from the controller's own synchronous
walk/enter decision points. Known behavioural cost, accepted and measurable:
after a combat pause the remainder of that door walk runs unsuppressed and can
be leashed again; the next escalation attempt re-arms it.

### D9 addendum — the same root cause reaches `pauseStructureTraversal()`

Raised by Codex in the final review round (2026-08-25) and **accepted as debt,
not fixed**, because it is the same unserialized-lifecycle root cause and not
specific to this slice.

`pauseStructureTraversal()` checks `isTraversalActive()`, then acts. A
preemption on another thread can clear that traversal, advance the generation
and install a replacement in between, after which the stale pause operates on
the replacement: it restores using the replacement's generation (which
therefore matches), clears its movement, and sets it `CombatPaused`.

Capturing the generation immediately after the guard — which is what the code
now does — only shortens the window; it cannot close it. `traversalGeneration`
and `structureTraversalIntent.active` are mutated by teardown/preemption
**without any lock**, so the agent lock used by the suppression helpers does not
serialize against them. The fix is the same generation-owned/serialized
lifecycle primitive described above, applied to the pause transition as well as
to the monitor's failure branches, with the expected generation supplied by the
triggering work rather than re-read.

**Blast radius while this is outstanding:**
- With `hollowDoorEgress.suppressLeash = false` (the committed default) this
  slice contributes nothing to the race — the restore is a no-op.
- With it enabled, the worst case is a replacement traversal losing its leash
  suppression, which degrades to "may be leashed again" and is re-armed at the
  next walk/enter decision. It does **not** strand a bot: restore is
  generation-owned and the map is always handed back to a real tree.
- The phase mutation on a replacement traversal is pre-existing behaviour,
  independent of D8.
