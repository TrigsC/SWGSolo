# Armor Loadout (P.10n) Implementation Plan

**Chunk**: F_0.9.13 (P.10n), ships as **v0.9.14**. Follows F_0.9.12 (weapon loadout, v0.9.13) and
reuses its shape: derived selection, transient copies on the body, SELL protection, the debit-first
bazaar upgrade path. F_0.9.11 (profession allocation) stays next on the roadmap.

**Owner decisions (discovery, 2026-10-17):**

| Question | Decision |
|---|---|
| How worn armor protects a bot | **Player armor math.** Transient copies of the vault pieces go on the body's real wearable slots, and a flagged AI defender takes the stock player mitigation (hit location, armor rating vs armor piercing, per-type resists, PSG, condition damage). |
| When armor goes on / comes off | **Equip buffed, keep worn.** New or better pieces go on only while the bot carries the buffs for every pool the piece encumbers, and only if the stock encumbrance check passes. Worn armor stays through buff expiry and respawn. The worn set lives in memory; after a reboot a bot re-equips at its next buff. |
| Encumbrance | **Apply real encumbrance**, with the stock `PlayerManager::applyEncumbrancies` / `removeEncumbrancies` arithmetic. |
| Scope | **Equip + bazaar upgrades.** Vault equip, SELL protection of worn armor and the best spare per slot, and a default-off sub-gate that buys a clearly better piece through the F_0.9.10/F_0.9.12 upgrade path. |

## Overview

Roster PlayerBots will wear the best usable armor in their vault, one piece per body slot, as
transient copies of the vault items. Combat will mitigate damage against those pieces exactly as it
does for a player. Putting armor on follows the player habit the owner described: a bot dons new
armor only while buffed, because buffs pay for the encumbrance, and it never takes armor off because
buffs ran out. SELL never lists worn armor or the best spare per slot. An optional sub-gate lets a
bot buy a clearly better piece on the bazaar within a share of its spendable credits.

## Problem Statement

1. **Stock combat ignores worn armor on NPCs.** `CombatManager::getArmorReduction`
   (`CombatManager.cpp:2683`) sends every `AiAgent` defender through its template values
   (`getArmorNpcReduction` at `:2588` plus `AiAgent::getArmor()` for piercing, `:2785-2799`) and
   returns before the player PSG and armor blocks (`:2870-2921`). `doObjectDetonation` (`:3061`) does
   the same for blast damage. The novice body template `sim_playerbot_novice.lua` has `armor = 0`
   and `resists = {0,0,0,0,0,0,0,-1,-1}`, so every roster bot fights unarmored whatever it owns.
2. **NPC wearables are not tracked for protection.** `AiAgent` uses the generic
   `ContainerComponent`, so slotting a wearable does not call `addWearableObject`. That call is what
   fills `WearablesDeltaVector::protectionArmorMap`, which `getArmorObject` reads
   (`WearablesDeltaVector.h:107-125`, `CombatManager.cpp:2534`). The stock outfit loader
   (`AiAgentImplementation.cpp:539`) never registers its pieces. The P.7 ranked-Jedi outfit
   (`:1225-1237`) is the precedent that does.
3. **Armor in the vault is dead weight, and SELL would sell it.** No armor rule exists, so a looted
   or bought piece is just a sellable item.
4. **Nothing models encumbrance or the buff habit.** Players lose secondary stats to encumbrance,
   buff to offset it, and keep armor on when buffs lapse. Bots need the same, so armor carries a real
   cost and a bot never sheds armor in the field.

## Solution Architecture

```
vault bag (held armor rows) ──snapshot──► SimBotArmorLoadout (pure)
  └─ per-item lock alone                       │  usable filter (race, faction, certs, coverage)
                                               │  score = expected damage fraction absorbed
                                               │  greedy best-per-slot + hysteresis
                                               ▼
                         desired set D ──diff──► worn set W (memory, per identity)
                                               │
          remove (always allowed) ◄────────────┤
          add / replace (needs: not in combat, │
            buffs for every encumbered pool,   │
            stock encumbrance check)           ▼
                         clone vault item (transient) ─► agent lock: slot + addWearableObject
                         + applyEncumbrancies + wearable skill mods + set AiAgent::simBotWornArmor
                                               │
CombatManager: AI defender with simBotWornArmor ─► shared player armor helper (PSG + armor at hit
                                                   location), per-agent mitigation tally
```

Principles carried over from F_0.9.12 (`tuto_0.9.13.md`):

- **Never move a durable object onto a mortal body.** The vault item stays `held`. The body wears a
  transient clone (`ObjectManager::cloneObject(item, true)`, which copies every serialized field:
  base and special protection, slices, vulnerabilities, condition, encumbrance, skill mods). A
  field-by-field copy, as weapons use, would miss `baseProtection`, `specialProtection`,
  `effectivenessSlice` and `sliced`, which feed `ArmorObjectImplementation::getTypeValue`
  (`:282-304`).
- **Derive what can be derived.** The desired set D is recomputed from the vault, trained skills
  and the body race. The one piece of history the owner's rule requires (W: what the bot has
  already put on, since it was buffed at that time) lives in manager memory only. Losing W at boot
  means the bot re-equips at its next buff, as the owner chose.
- **The roster correction lives in the sim layer, behind a flag only the sim layer sets.** Stock
  NPC outfits include armor objects (`mobile/outfits/*.lua`), so "has armor in a slot" must not
  switch NPCs onto the player path; that would rebalance every stormtrooper. The switch is an
  explicit transient `AiAgent` flag set only by this chunk's equip code and cleared in
  `loadTemplateData`.

## Implementation Details

### 1. Pure policy header

**File**: `MMOCoreORB/src/server/zone/objects/creature/simplayer/SimBotArmorLoadout.h` (new)

No objects, locks or database access, like `SimBotLoadout.h`. Contents:

- `ArmorStats` (snapshot of one piece):
  - template string and CRC, object id, game object type;
  - slot key (sorted, joined slot names of arrangement descriptor 0);
  - hit-location mask (`ArmorObject::getHitLocation`);
  - armor rating;
  - the nine effective resists, read through the getters so condition and slicing are included;
  - vulnerability mask, as read by `isVulnerable` per type;
  - health/action/mind encumbrance (raw, can be negative);
  - allowed player races (template CRCs), faction (neutral, imperial or rebel), wearable
    `certificationsRequired` (skill names), and current/max condition (for inspect).
  - Carries the same empty stream stubs as `WeaponStats`.
- `ArmorScoringConfig`: damage-type weights (kinetic, energy, blast, stun, heat, cold, acid,
  electricity; lightsaber excluded) and `assumedArmorPiercing`.
- `scoreArmor(stats, config)`:
  - Score = weighted expected fraction of damage absorbed, in [0, 1].
  - Per type: zero for a vulnerable type. Otherwise one minus the product of the stock
    piercing factor and the resist term. The piercing factor matches
    `CombatManager::getArmorPiercing`: 0.5^(AR−AP) when AR > AP, 1.25^(AP−AR) otherwise. The resist
    term is (1 − resist/100).
  - A piece with no hit-location coverage scores zero.
- `isUsable(stats, bodyRaceCrc, botFaction, trainedSkills)`:
  - Mirrors `PlayerContainerComponent::canAddObject:24-90`: race list contains the body race;
    neutral wearable for a faction-0 bot; any listed certification held (a single match suffices,
    as stock).
  - Returns a reason code (`OK`, `RACE`, `FACTION`, `CERT`, `NO_COVERAGE`) for counters and inspect.
- `passesEncumbrance(stats, secondaries)`: an exact mirror of
  `PlayerManagerImplementation::checkEncumbrancies` (`:2669-2735`). It passes when all three
  encumbrances are ≤ 0, and fails when any encumbrance is ≥ either matching current secondary.
- `requiredBuffPools(stats)`: the secondary pools a piece encumbers:
  - health encumbrance > 0 → strength, constitution;
  - action encumbrance > 0 → quickness, stamina;
  - mind encumbrance > 0 → focus, willpower.
  - The manager maps pools to tracked buff CRCs with `pveTrackedBuffCrcForAttribute`
    (`SimPlayerManager.cpp:7850`).
- `chooseArmor(candidates, current W source oids, config, minUpgradePercent)` → desired set:
  - Usable pieces in descending score (ties: lower total encumbrance, then lower OID).
  - Greedy pass: a piece is taken if none of its slot names is already claimed.
  - Hysteresis per slot key: a candidate replaces the piece currently worn on that key only if its
    score is ≥ current × (1 + minUpgradePercent/100). An empty key accepts any score > 0.
  - Returns, per chosen piece, whether it is new, held by hysteresis, or kept.
- `protectedSet(candidates, wornOids, …)`: the worn OIDs plus the best usable piece per slot key
  (held armor only).
- `upgradeDecision(listingStats, price, currentScoreForKey, bank, reserved, reserve,
  spendFraction, maxPrice, minUpgradePercent, usability, bodyHamBaseline)`:
  - Returns `BUY`, `NOT_BETTER`, `UNUSABLE`, `TOO_ENCUMBERING`, `OVER_BUDGET` or `UNAFFORDABLE`.
  - `TOO_ENCUMBERING`: any encumbrance ≥ the configured body baseline, which a buff cannot rescue.

### 3. Combat: shared player armor helper and the flagged AI branch

**File**: `MMOCoreORB/src/server/zone/managers/combat/CombatManager.{h,cpp}`

- **Extract the player path.** Extract the player PSG and standard-armor block of
  `getArmorReduction` (`:2870-2921`) into a private const helper, `applyWornArmorReduction(defender,
  hitList, damage, damageType, armorPiercing, hitLocation)`. It returns the post-armor damage and
  the absorbed amount. The player path calls it with **no behavior change**: same order, same
  `Locker` on the PSG and armor piece for condition damage, same `hitList` mitigation fields.
- **Flagged AI branch in `getArmorReduction`.** It sits after the existing jedi mitigation block
  (`:2700-2784`) and before `getArmorNpcReduction`. When the defender is an `AiAgent` with
  `hasSimBotWornArmor()`:
  - call the helper instead of the template armor;
  - add the absorbed amount to the agent's tally;
  - keep `addUnmitigatedDamage`, as the template branch does for non-pets;
  - return.
  - Unflagged agents, pets, vehicles and turrets are untouched.
- **`doObjectDetonation` (`:3061-3110`).** Same split for blast. Extract the player PSG and armor
  blast block into `applyWornArmorBlastReduction`, called by the player branch unchanged and by the
  flagged AI branch. The droid PvP reduction stays outside the helper, player-only.
- **Combat spam:** `sendMitigationCombatSpam` is unchanged. A bot has no client, and the existing
  NPC-to-attacker spam remains under its own flag.
- **Defense skill mods need no combat change.** `getDefenderDefenseModifier` and
  `getDefenderToughnessModifier` (`:2099`, `:2456`) already read `AiAgent::getSkillMod`, which
  includes `WEARABLE` mods added by `applySkillModsTo`.
- **Lock context:** both functions already run with the defender locked. The helper's armor
  `Locker`s are the exact stock lines moved, so the lock choreography is unchanged.

### 4. Manager: snapshot, selection, worn set and equip

**File**: `SimPlayerManager.{h,cpp}`

**State** (all under `progressionMutex`, all memory-only):

- `progressionArmorWorn`: identity → list of `SimBotWornArmorPiece`:
  - source OID, slot key, encumbrance triple;
  - copy OID and the body OID it was put on;
  - an `onBody` bool (false when respawn could not re-wear it unbuffed);
  - a `pendingRemoval` bool, the tombstone set by the item reconcile when the source row leaves
    `held`.
- `progressionArmorChoices`: identity → last desired set, for dashboard and inspect.
- `progressionArmorBlockedReason`: identity → last blocking reason (`unbuffed`, `in_combat`,
  `encumbrance`, `no_body`, …).
- **Dirty marks:** reuse `progressionLoadoutDirtyIds`. Loot, purchase, training and item reconcile
  already mark it (`:12450`, `:13855`, `:15904`, `:17569-17652`, `:21243-21271`). A buff landing
  marks it too (below).

**Functions** (new unless noted):

1. **`snapshotPlayerBotArmorCandidates(identityId, out candidates, out trainedSkills)`:**
   - Same choreography as `snapshotPlayerBotLoadoutCandidates` (`:8792`): manager mutexes for
     identity, plan, held rows and trained skills, all released; then a bag snapshot under the bag
     lock; then each held `isArmorObject()` child under its own lock alone.
   - The PSG (`isPsgArmorObject`, `utility_belt`) is **excluded** in this chunk; see Edge Cases.
2. **`snapshotPlayerBotBodyArmorContext(identityId, out bodyOid, out bodyRaceCrc, out
   secondaries[6], out buffedPools, out inCombat, out wornCopies)`:**
   - Taken under the agent lock **alone**, before any selection.
   - The race comes from the body's appearance template through the Lua `armor.bodyRaces` map. An
     unmapped body fails closed (`skippedRace`, no armor).
   - `buffedPools` reads each tracked buff CRC with `getBuff()`, the same read as
     `SimHunterController::computeBuffNeeds` (`:1063-1100`). A buff only counts as present; the
     refresh threshold does not apply to equipping.
3. **`selectPlayerBotArmor(identity, out choice, bool preview=false)`:**
   - Runs the gate first (gate off and not preview → empty choice). Then snapshots and calls
     `SimBotArmorLoadout::chooseArmor` with W as the current set.
   - Records counters and a `LOADOUT_ARMOR` missiondiag event on change, unless in preview, which
     records nothing (the v0.9.13 inspect lesson).
4. **`reconcilePlayerBotArmorOnLiveBody(identityId, bool respawn)`:**
   - Diffs D against W and the body's actual wearables.
   - **Standalone removals** need no buffs. They apply when a W piece's source is no longer held or
     no longer usable (sold, withdrawn, orphaned, or the race/cert check now fails).
   - **A replacement** (a better piece for an occupied slot key) is atomic in one agent-lock pass:
     the old copy comes off only when the new one goes on, so a slot is never emptied to wait for
     buffs. The slot must be free before the new copy can be slotted, so the pass runs:
     1. detach the old copy: undo its side effects (wearable entry, encumbrance, skill mods) and
        remove it from the slot, but keep the reference and do not destroy it;
     2. try the new copy's addition sequence;
     3. **on failure**, re-slot the old copy and restore its side effects in the addition order, so
        the body is exactly as before, and leave W unchanged with the identity dirty;
     4. **on success**, destroy the old copy with `destroyObjectFromWorld(true)`.
     - W is updated only after the agent lock is released, and only from the pass's actual
       outcome.
   - **Additions and replacements** require:
     - not in combat (`armorReequipsDeferredInCombat`);
     - every pool in `requiredBuffPools` buffed (`armorDeferredUnbuffed`); skipped on the
       `respawn` re-wear of pieces already in W;
     - the stock check (`passesEncumbrance`) against the current secondaries, after the replaced
       piece's encumbrance is removed (`armorDeferredEncumbrance`).
   - **Cloning:** each needed vault item is cloned **before** the agent lock, under its own item
     lock alone. Clones not used are dropped: transient, never in the world.
   - **Removal under the agent lock, per piece:**
     1. `removeWearableObject(copy, true)`;
     2. `PlayerManager::removeEncumbrancies(agent, copy)`;
     3. `removeTemplateSkillMods` / `removeSkillModsFrom`;
     4. `destroyObjectFromWorld(true)`.
   - **Addition under the agent lock plus `Locker(copy, agent)`:**
     1. `transferObject(copy, 4, notify)`;
     2. confirm the parent is the agent;
     3. `addWearableObject(copy, notify)`;
     4. `PlayerManager::applyEncumbrancies(agent, copy)`;
     5. `addTemplateSkillMods` / `applySkillModsTo`.
     - This mirrors `PlayerContainerComponent::notifyObjectInserted` (`:118-150`).
     - `notify` is false before placement (spawn) and true on a live body, as in the ranked-Jedi
       precedent.
   - Finally sets `simBotWornArmor` to "at least one piece on the body", releases the agent lock,
     then updates W, the blocked reason and the dirty mark under `progressionMutex`.
   - A failed transfer leaves W unchanged and the identity dirty (retry next tick).
5. **`collectPlayerBotProtectedArmorOids(identityId, out map)`:**
   - W source OIDs (excluding tombstones), always, including while a gate-off drain is pending;
   - plus `SimBotArmorLoadout::protectedSet` when the armor gate is on.
6. **`playerBotArmorLoadoutGateEnabled(identityId)` and
   `playerBotArmorBazaarUpgradesGateEnabled(identityId)`:**
   - Reference shape (ARCHI §12 F_0.9.5 lesson): master progression first, identity-scoped harness
     override second, configured value last.
   - The armor gate also requires the early-game gate (as the weapon loadout does) and a non-empty
     training plan.
   - The armor gate is **independent of `weaponLoadout`**.
   - The upgrade sub-gate also requires `bazaarBuy` and the armor gate.

**Wiring:**

- **Spawn** (`SimPlayerManager.cpp:~27245-27300`):
  - Before the spawn agent lock, prepare the W re-wear clones and the context.
  - Inside the existing lock, right after `equipPlayerBotWeaponLocked` and before clone wounds,
    re-wear W pieces with `respawn = true`: no buff requirement, but the stock encumbrance check
    against the fresh body.
  - A piece that fails stays in W with `onBody = false` and goes on at the next buffed reconcile
    (`armorRewearDeferred`).
  - New pieces (D − W) are not added at spawn: a fresh body carries no buffs.
- **Slow-tick reconcile** (`:16745-16830`): after the weapon loop, for the same dirty or
  full-sweep identities with a live body, compare D against W (by source OID and `onBody`). Queue
  a mismatch for `reconcilePlayerBotArmorOnLiveBody`, outside every manager mutex as the weapon
  reapply is.
  - A queued mismatch keeps the identity dirty, so a deferred one (unbuffed, combat, encumbrance)
    retries on later ticks.
  - **Bound:** a bot that stays unbuffed would otherwise re-run selection every slow tick. An
    identity whose only blocker is `unbuffed` is therefore dropped from the dirty set and re-marked
    by the buff hook.
- **Buff hook:** `recordPveBuffSource(bodyOid, …)` is called on every real and synthetic buff
  landing (`SimHunterController.cpp:1404-1408`, `:4262-4276`). It resolves the identity and marks it
  dirty, after releasing whatever it holds, so armor goes on right after the bot buffs.
- **Teardown:** body death or drain destroys the transient copies with the body. W keeps the
  source OIDs, and the next spawn re-wears them.
  - Identity retirement, deletion and the reaper drop W. The body is destroyed on those paths, and
    its copies with it.
  - **The item reconcile never erases a W entry directly.** When a W entry's row is no longer
    `held` (sold, orphaned, withdrawn), the reconcile marks the entry `pendingRemoval` (a
    tombstone) and marks the identity dirty.
    - The next armor reconcile removes the copy and its side effects through the W mapping, then
      erases the entry.
    - With no live body, or a copy no longer on the body (a respawn already dropped it), the
      tombstone is erased directly.
    - A tombstoned entry is never re-worn and is not protected (its source is gone).
- **Gate disable drain:**
  - When the armor gate turns off while W is non-empty, whether by a config edit or a harness
    override, each identity with W is queued for a drain. This is detected by the slow tick seeing
    gate off with a non-empty W, so it needs no edge detector.
  - The drain is a forced removal pass: every copy and its side effects come off, the flag clears,
    then W is erased after unlock.
  - It runs even in combat, because a disabled capability must not keep acting. Removing armor
    mid-fight only takes protection away.
  - **SELL keeps protecting W sources while W is non-empty, even with the gate off**, so nothing
    worn can be listed before the drain lands.
  - A bot without a live body is drained by erasing its W entries; its next body is gate-off and
    gets no armor.

### 5. Bazaar: SELL protection and armor upgrades

**File**: `SimPlayerManager.cpp`

- **SELL** (`listPlayerBotItemsAtTerminal` `:12862`, `shouldPlayerBotVisitBazaar` `:12481`):
  - The protected set becomes weapon ∪ armor.
  - The buy-list keep (protected first, then oldest, then OID; the v0.9.13 product fix) counts
    protected armor the same way.
- **Listing cache** (`SimBotBazaarListingTemplate`, `:13380-13410`): add armor fields filled on
  object load: `isArmor`, slot key, score, encumbrance triple, a usability snapshot (races,
  faction, certs). Known mismatches stay free.
- **BUY need:** an `ARMOR_UPGRADE` need. It is added before the early exits when the armor upgrade
  gate is on, the visit is due (`upgradeScanIntervalMinutes`, its own timestamp map) and no upgrade
  of **any** kind is pending.
  - **One pending upgrade, weapon or armor.** The pending check is extended so armor game object
    types (`0x101-0x107`) count beside weapon classes. That keeps two spend-share purchases from
    stacking.
  - **Candidates:** armor listings, any slot. A candidate must be usable for the bot's body race
    and skills and must beat the bot's current best for that slot key (worn or held) by
    `minUpgradePercent`. An empty key accepts any covering piece.
  - **Budget:** `floor((bank − reserved − reserve) × armor.upgradeSpendFraction)`, capped by
    `bazaar.maxPrice`.
  - **Ranking across slots, deterministic:**
    1. improvement over that slot key's current score (candidate − current; an empty key's current
       is 0), descending;
    2. then price ascending;
    3. then auction OID ascending.
    - At most one armor purchase per visit (the one-pending rule).
  - Final recheck under `progressionMutex` before the debit with
    `SimBotArmorLoadout::upgradeDecision`.
  - **Order:** buy-list needs first, then weapon upgrade, then armor upgrade, all through the
    existing need cursor.
  - The purchase, debit, object move, boot resolution and seller payment are the F_0.9.10 pipeline,
    **unchanged**. After commit the identity is marked dirty (already true, `:13855`). The piece
    goes on at the next buffed reconcile.
- **Visit admission:** an armor-upgrade-only visit needs the same spendable-floor test as the weapon
  upgrade (`ceiling ≥ bazaar.minPrice`) and its own scan interval.

- `playerBotProgression.loadout.armor` block:

  - `damageTypeWeights` kinetic 0.5, energy 0.2, blast/stun/heat/cold/acid/electricity 0.05 each;

- All reads clamp. `applyPlayerBotProgressionConfig` (`:9286`) parses them beside the existing

- **Hot-reload contract:** the server re-reads this file at runtime.
  - The whole armor policy (gate values, `minUpgradePercent`, scoring config, race map, spend

    published by one assignment under `progressionMutex`.
  - Every consumer (selection, body-context snapshot, SELL, BUY, inspect) copies the policy under
    `progressionMutex` **before** taking any item or agent lock, and uses only that copy for the
    rest of the operation.
  - A partially parsed policy is never visible. No consumer reads policy fields lock-free. This
    follows the F_0.9.5 lesson about `progressionTrainingPlans` being read lock-free.
- **Harness:** `armor_*` scenarios in `playerBotParityTest`, with `requiresGates` naming

- `luac -p` immediately after every edit. The running server re-reads this file.

## Technical Considerations

- **Pattern usage:**
  - F_0.9.12 weapon loadout: pure header plus manager snapshot plus transient body copy.
  - The P.7 ranked-Jedi outfit, for registering an AI wearable (`addWearableObject` after
    `transferObject(…, 4)`).
  - `PlayerContainerComponent` insert/remove for the exact equip side effects.
  - F_0.9.10 for purchases.
- **Locking and references:**
  - **Order:** manager mutexes released → bag lock snapshot → each item lock alone (snapshot and
    clone) → agent lock alone (context snapshot) → agent lock plus `Locker(copy, agent)` (equip).
    This is the v0.9.13 order, with the body context snapshot added.
  - `progressionMutex` is never held under the agent lock. W updates happen after the agent lock
    is released.
  - The armor policy (`SimBotArmorPolicy`) is copied under `progressionMutex` before any item or
    agent lock (section 6, hot-reload contract).
  - Clones are held as `ManagedReference<ArmorObject*>`.
  - `cloneObject` locks the new clone internally; the source item is locked by us for the read.
  - The combat helper is a pure move of stock lines, including their `Locker(armor)`.
  - The buff hook marks dirty under `progressionMutex` only, after resolving the identity under
    `pveMutex`, one at a time.
  - The F_0.8.1 post-lock lifecycle recheck (`agent->getZone() != nullptr` after acquiring the
    lock) is required in `reconcilePlayerBotArmorOnLiveBody`.
- **IDL impact:** `AiAgent.idl` gains two transient fields and accessors. Autogen regenerates; no
  `.idl` persistence change and no SQL migration. `CombatManager` is plain C++.
- **C++ vs Lua placement:** selection, equip and combat are C++ (hot path, locks). Weights,
  thresholds, race map and gates are Lua.
- **Gating and simulation-only:** P.10 roster-only real mutation (ARCHI §12). `armorLoadout` and
  `loadout.armor.bazaarUpgrades` ship **false**. Gate off means no snapshot, no flag, no combat
  change, no SELL change. Miners, PvP bots and non-roster NPCs never get the flag. Purchases are
  real credit mutations through the already-approved F_0.9.10 path.
- **Parity notes (documented in the plan and the tutorial):**
  - **Condition:** the copy takes stock condition damage in combat and can break within a life. The
    vault item does not decay, and a respawn restores the copy from it. Accepted debt until a
    repair economy exists; weapons have the same gap.
  - **The PSG is excluded:** it is a utility-belt item with its own rules. A later chunk can add it
    through the same helper, since the helper already handles PSG.
- **Dashboard visibility:** section 8 above.
- **Live verification plan:** see Test Impact. The harness proves equip, the buff rule,
  encumbrance, mitigation, SELL and the upgrade. The production stage needs a production bot that
  holds or can buy armor. No bot holds wearable armor today; the vault has only a Chitin Armor
  Segment, a component. If none is observed, the owner may approve a fair-priced harness-seller
  listing for a real bot to buy with its own credits. Otherwise production equip is reported as not
  observed and the receipt rests on the harness.
- **Edge cases:**
  - Two pieces whose slot sets overlap (greedy best-first resolves).
  - A piece covering no hit location: score 0, never worn, never protected. (Verification note:
    stock `ArmorObjectImplementation` derives coverage from slots when the template sets none, so
    gloves cover the arms and shoes the legs; a stock piece with no coverage is rare.)
  - Negative encumbrance on crafted armor: the stock check passes and apply clamps at 0, as stock.
  - The bot dies mid-reconcile: the post-lock recheck returns.
  - A piece sold or withdrawn while worn: the item reconcile tombstones its W entry
    (`pendingRemoval`). The next armor reconcile removes the copy and its side effects through
    that entry, and only then erases it.
  - A buff lapses while a replacement is pending: the removal half still runs only when the
    replacement is equipped. Never strip a worn piece to wait for buffs.
  - **Secondaries near zero after buffs lapse:** the same as a player. A respawn re-wear runs the
    stock check unbuffed and defers on failure, so a fresh body never goes negative.
  - An unmapped body race: fail closed.
  - Faction armor on a neutral bot: refused.
  - A harness body exempt from `bodyHam`: the race map must cover harness appearance templates, or
    the scenario sets them up.
  - A reboot loses W: by design, the bot re-equips at its next buff.

## Amendment A — visible armor (owner decision 2026-10-18)

**Found in-client after live verification:** armor works on the server (slot, wearables list,
protection map, mitigation, encumbrance), but it never shows on a bot. The novice bodies use stock
`object/mobile/dressed_commoner_*.iff` templates whose client data file (`.cdf`) bakes clothing; the
client draws that clothing and masks a server-sent chest piece. Weapons are not masked, which is why
Castu's knuckler shows. P.7 hit the same wall with robes and solved it with clothing-free vendor
bodies (`bin/scripts/object/mobile/ranked_jedi_bodies.lua`, `object_mobile_vendor_shared_human_*`,
`clientDataFile = ""`); its dress group requires an in-client check before adding a body.

**Owner decision:** bare bodies plus server-sent clothing, and armor that swaps clothing off its
slots like a player and puts it back when the armor comes off.

### A.1 Bodies, species and a fixed look per bot

**Owner request (2026-10-18):** a bot keeps the same appearance across respawns, so it can be
picked out in a crowd like a player, and roster bots come in different species, like the P.7 Jedi.

- **Bodies (Lua):** new `bin/scripts/object/mobile/sim_playerbot_bodies.lua`, included from
  `object/mobile/serverobjects.lua` beside `ranked_jedi_bodies.lua`. It defines 20 bodies,
  `object/mobile/sim_playerbot_<species>_<gender>.iff`, for the ten P.7 species (human, bothan,
  ithorian, moncal, rodian, sullustan, trandoshan, twilek, wookiee, zabrak) × male/female, each a
  one-line subclass of `object_mobile_vendor_shared_<species>_<gender>` (empty `clientDataFile`, so
  nothing baked masks a wearable). `sim_playerbot_novice.lua` lists these 20 in `templates`, has
  **no** `outfit` field (dressing moves to the sim layer, below). Its comment says entries are
  keyed by template string, so editing the list moves only the bots a change touches.
- **Pure chooser (C++):** new `SimBotAppearance.h`, with no locks or objects.
  - **Bodies and outfit variants use rendezvous (highest-random-weight) hashing:** each candidate
    scores `splitmix64(identityId ^ hash(key) ^ salt)` and the highest wins. The key is stable and
    content-based: the body template string, or for an outfit variant, its object templates
    joined in order, each with its customization variable/value pairs sorted by name (the
    variant's full content, not its position). Exact-duplicate variants are rejected at load with a
    log line, and any remaining score tie breaks on the key string.
    - **Stability:** removing or reordering entries never moves a bot whose winner remains.
      Appending moves only the bots the new entry wins (about 1 in n+1).
  - **Features use a seeded generator** (splitmix64 from the identity ID and a per-purpose salt)
    to pick each customization value, the morph side, scale and hair from the stock vendor
    profile. Those profiles are fixed client data.
  - **Same identity, same answers; different identities spread evenly.** Gtests pin determinism,
    spread, the append bound and morph-pair exclusivity.
- **Applying the look (C++, sim layer):** `applyPlayerBotAppearanceLocked(agent, identityId,
  bodyTemplate)` runs in the spawn's existing agent lock, after `loadTemplateData` and before the
  weapon equip, for planned novice bodies only. Harness bodies are included so the matrix
  exercises it.
  - **Body:** `spawnPveIdentityBody` chooses the body from the novice template's list by the seeded
    index, instead of `CreatureManager::getTemplateToSpawn`'s random pick, and creates the creature
    from it.
  - **Features:** the vendor profile is `object/mobile/vendor/<species>_<gender>.iff` (the P.7
    mapping). Customization variables, morph pairs, scale and hair follow P.7's
    `randomizeRankedJediAppearance` (`AiAgentImplementation.cpp:812`), with the seeded generator
    in place of `System::random`. The shared Jedi function is not changed.
  - **Clothing:** one outfit group per species family, chosen by the seeded index from
    `CreatureTemplateManager::getMobileOutfitGroup`:
    - `sim_playerbot_outfit_humanoid` for most species;
    - `sim_playerbot_outfit_wookiee` (wookiee garments);
    - `sim_playerbot_outfit_ithorian` (ithorian garments).
  - Pieces are created and slotted exactly as the stock outfit loader does (`createObject` with the
    agent's persistence, which is transient for bot bodies, then `transferObject(tano, 4, false)`).
    A piece that fails is destroyed, as stock.
- **Stability limits:** the look depends on the identity ID, the set of bodies and outfit
  variants, and the stock vendor profiles. Appending a body or variant re-rolls about 1 in n+1
  bots; nothing else does. Existing bots change look once, at their next respawn, then keep it.
- **Species change and worn armor:** the first respawn on a new body can change a bot's species.
  Spawn re-wear therefore checks each W piece's usability (race and faction) against the new
  body's race before slotting it, not only encumbrance.
  - An incompatible piece stays off-body (`onBody = false`) and the identity is marked
    armor-dirty.
  - The next reconcile drops it, since an unusable piece is never desired, and selects
    compatible armor.
- **Armor by species:** the armor race filter already uses each piece's player-race list, so a
  Wookiee or Ithorian bot only wears armor its species can, as a player.

### A.2 Clothing swap on equip (C++)

- **Stash:** a leaf-mutex map `armorStowedClothing` (body OID → stowed pieces, each a
  `ManagedReference<SceneObject*>` plus its slot names), guarded by its own `armorClothingMutex`,
  which is never held while taking any other lock. It may be taken under the agent lock, like the
  existing leaf mutexes (`SimEarlyGameDeathLog`).
- **Which slotted objects are armor copies:** the reconcile already snapshots W before taking the
  agent lock; it passes the set of W copy OIDs (plus the copies prepared for this pass) into the
  equip and remove helpers. Nothing under the agent lock reads W or takes `progressionMutex`.
- **Equip** (`equipPlayerBotArmorCopyLocked`, agent locked): before `transferObject`, every object
  slotted in any of the copy's arrangement slots that is not in that copy-OID set is detached with
  `removeObject(piece, nullptr, notify, true)` and stashed. Then the existing sequence runs. If the
  transfer fails, the detached pieces are re-slotted at once, so a failed equip leaves the body
  exactly as it was. That also preserves the replacement-failure restore.
- **Remove** (`removePlayerBotArmorCopyLocked`): after the copy leaves its slots, every stashed piece
  of that body whose slots are now all free goes back with `transferObject(piece, 4, notify)`.
  Stock outfit pieces are slotted only, not added to the wearables list, so the restore does the
  same.
- **Body teardown:** the slow tick drops stash entries whose body OID no longer belongs to any live
  identity body. The pieces are transient and simply released.
- **Race map:** `loadout.armor.bodyRaces` becomes a list of `{body = "...", race = "..."}` pairs,
  parsed by array index, replacing the four hard-coded keys. Each of the 20 new bodies maps to
  `object/creature/player/<species>_<gender>.iff`. The four `dressed_commoner_*` entries stay for
  any body not yet respawned.

### A.3 Also fixed in this amendment

- **Copy persistence:** `cloneObject(item, true)` restores the source's persistence level when it
  reads the serialized fields, so copies were `persistenceLevel 1`. The clone is now set
  `setPersistent(0)` right after cloning, and `destroyPlayerBotArmorCopy` also calls
  `destroyObjectFromDatabase(true)`.
- **Dashboard:** `gates.armorBazaarUpgrades` and `armor.bazaarUpgrades` report the configured chain
  (armor gate, BUY gate, `loadout.armor.bazaarUpgrades`) instead of the per-identity gate for
  identity 0, which is always false.
