# F_0.9.3 — Loot from kills and the hive item vault (P.10d) Implementation Plan

**Status:** RELEASED as v0.9.10 (2026-10-14). Plan approved by owner 2026-10-14 (Codex plan review: 7 rounds); code review APPROVED (17 rounds); live receipt 23/23
**Branch (at implementation):** `feat/p10d-loot-vault`
**Gate:** `playerBotProgression.lootEnabled`, default off
**Schema:** 1015 (`simbot_items`)
**Release version:** decided at TRIP-3 (next free number after v0.9.9)

## Overview

When a roster PlayerBot earns a kill, the corpse gets stock loot and cash exactly as
it would for a player. The bot then walks to the corpse and loots it. Cash goes to
the bot's cash balance in the progression store, and items move into the bot's own
bag inside a persistent **hive item vault** owned by `AiEconomyManager`. One
`simbot_items` row per item records which roster identity owns it and in what state. Every item and cash change
writes a `simbot_ledger` row. This is the first real object movement in the P.10
line and the second kind of holding after credits.

Owner decisions (2026-10-13):

| Question | Decision |
|---|---|
| Loot step | The bot walks to the corpse after the fight and loots it like a player. A death or a new fight before then leaves the corpse lootable until it despawns |
| Equipping looted gear | Not in this chunk. Items are stored and journaled only. The `equipped` state name is reserved for the later equip chunk |
| Vault growth before the bazaar exists | A per-bot item cap in Lua. A bot at its cap takes the cash and leaves the items on the corpse, and the skip is counted |
| Ghost (`PlayerObject`) for bots | Spike it first, with the long-term scenario in mind: bots joining a player guild and a player giving a bot a vibro knuckler. Outcome below: **keep the vault** |

## Ghost spike: should bots have had a PlayerObject?

The roadmap (§5b.5) asked for this to be re-examined before the loot plan, because a
real player inventory would replace the vault. The owner added two future scenarios
to test it against: a bot in a player guild, and a player handing a bot an item.

**Finding 1: a ghost does not make a bot a player.** `isPlayerCreature()` is decided
by the object's template type (`CreatureObjectImplementation.cpp:4297` returns
`templateObject->isPlayerCreatureTemplate()`), not by having a `PlayerObject`. An
`AiAgent` with a ghost would still fail the roughly 900 `isPlayerCreature()` checks
that fence loot, missions, guild lists and trade. Becoming a real player type means
leaving `AiAgent`, and with it the behaviour trees, the controller-driven movement,
the combat sockets and the whole P.4 to P.10 stack.

**Finding 2: a ghost does not give a bot a client.** Secure trade is a two-client
handshake (`ItemDropTradeCallback.h:60-150`: each side must target the other, then
both accept and verify). Guild sponsoring, joining and leadership go through SUI
windows (`GuildManagerImplementation.cpp`, e.g. `:484-494`, `:1067-1131`). Neither
works without a client on the bot's side, ghost or not. Either design needs a
simulated bot side for these interactions.

**Finding 3: a ghost would cost a lot.** A ghost with no client is unloaded as
link-dead (`PlayerObjectImplementation::doRecovery`, `:2306-2318`). Players expect
an account and a `characters` row, appear in who-lists and player counts, and die
by cloning rather than having the body rebuilt. Each of these would need changing.

**Scenario: a bot in a player guild.** `GuildObject` membership is keyed by the
member's creature OID, and member lists drop anyone who is not `isPlayerCreature()`
(`GuildManagerImplementation.cpp:429`, `:1087`). A bot body gets a new OID every time
it dies. So guild membership has to be an identity attribute that the spawn path
re-applies, the way trained skills are, plus a roster-aware member-list branch. A
ghost would not avoid this. The vault does not make it harder.

**Scenario: a player gives a bot a vibro knuckler.** Stock already has a "give an
item to an NPC" path: `GiveItemCommand.h:111-140` accepts a wearable or weapon
dropped on a vendor or event-perk NPC. A future branch there for a roster bot would
call the same vault deposit API this chunk builds, with `source = player_gift` and
`ref = giver OID`. Secure trade could later get a simulated bot side that settles
into the vault the same way.

**Verdict: keep the vault.** It matches the holdings model approved in v0.9.9. This
chunk makes the deposit API generic (it takes a source and a reference) so that loot
is only its first caller, and reserves the `equipped` state so that gifts, the
bazaar and equipping all land on the same record.

## Item stats are part of the object

A looted item's stats are rolled once, when stock `LootManager` creates it on the
corpse (`updateCraftingValues`, `LootManagerImplementation.cpp:316`), and stored on
the object itself. A rare Acklay bone (`acklay_bones_rare`,
`object/tangible/component/weapon/acklay_bone_reinforcement_core.iff`, rolling
`mindamage` and `maxdamage` 65 to 130 and `useCount` 1 to 11) keeps the two damage
values in `Component.attributeMap`, a persisted field (`Component.idl:19-32`), and
its use count in `TangibleObject`'s own `useCount` field (component creation keeps
`useCount` out of the attribute map). The loot step
moves **that same object**: the same OID, never a copy, never a re-roll, and the
stats are never converted into MySQL numbers. The `simbot_items` row only points at
the OID, so the object stays the single authority for what the item is.

The stats survive restarts and bot deaths for the same reason a player's inventory
does: the object is persistent (loot is created at persistence level 2,
`LootManagerImplementation.cpp:381`) and lives in a persistent bag. Scenarios 1 and
11 assert this directly.

Ways an item can still be lost, all deliberate or identical to player behaviour:
the reaper destroys a deleted bot's items (holdings rule 9); an item over the cap is
left on the corpse; and a crash before the next object-store save loses a fresh
item, exactly as it would for a player (reconciliation then reports the row as
`orphaned`).

## Problem Statement

1. **A bot kill produces an empty corpse.** `CreatureManagerImplementation.cpp:684`
   creates loot and cash only when the highest-damage group leader is
   `isPlayerCreature()`. A bot's corpse gets nothing and despawns in 10 s
   (`PlayerManagerImplementation::shouldRescheduleCorpseDestruction`, `:6673`).
2. **A bot has nowhere durable to keep an object.** Its body is destroyed on death
   and rebuilt, so anything in its inventory is lost. Holdings model rule 2 forbids
   using the body anyway.
3. **There is no item record.** Nothing says which identity owns which object, so
   a restart, death or reaper run could not be checked.

Expected yield is modest, and that is correct parity rather than a defect. Stock gives
cash only to humanoid NPC corpses (`calculateLootCredits` is gated on
`isNonPlayerCreatureObject()`). About half of the creature templates have an empty
`lootGroups` table (154 of 305 on Tatooine, 141 of 234 on Naboo). Novices grinding
fauna will loot rarely. Mission lairs and humanoid targets will produce most of the
items.

## Solution Architecture

```
kill (notifyDestruction, corpse locked)
  └─ bot branch: winner is a roster bot with a record, gate on, vault available
       ├─ cash + createLoot into the corpse (stock calls), owner = bot body OID
       ├─ corpse kept 300 s if it has loot or cash, else 10 s
       └─ queue a LootClaim {identity, corpse OID, zone, position, expiry}
controller (runActiveTick, out of combat)
  └─ loot step: take the nearest claim → walk ≤ lootArriveMeters → lootPlayerBotCorpse
manager lootPlayerBotCorpse (lock chain body → corpse → corpse inventory → item → bot's bag)
  ├─ per item while under cap: transfer into the identity's bag → row held
  │    └─ journal: simbot_ledger kind=item, +1, balance_after = items held
  └─ after the locks: cash → grantPlayerBotCredits(cash, source=loot, ref=corpse OID)
maintenance lane: flush rows; at boot, reconcile rows against bag containment
reaper: destroy a reaped identity's items and its bag before deleting it
```

Four principles:

- **Stock where possible.** Loot and cash come from the same `LootManager` calls a
  player kill uses, at the same chokepoint. Only who owns the corpse differs.
- **One authority per kind.** The `simbot_items` row says who owns an object, and
  the object being in the vault is checked against it. Credits keep the balance
  column as the authority (F_0.9.2).
- **The vault is the inventory.** No item ever sits on a bot body. The vault is one
  manager-owned container, never in the world, holding one **bag** (a child
  container) per identity. The row is the authority on ownership; the bag is the
  durable recovery source when a row was not flushed, because moving an item into
  a bag records its owner in the same object save as the move itself.
- **Fail closed.** If the vault did not load, the loot gate reads as off and the
  stock path runs unchanged.

## Holdings model — what this chunk adds

The F_0.9.2 rules apply unchanged. This chunk builds the item column:

| # | Rule | How items meet it here |
|---|---|---|
| 1 | Owner is the roster identity id | `simbot_items.identity_id` |
| 2 | Nothing durable on the body | The object is in the vault from the moment it leaves the corpse |
| 3 | One authority per kind | The `simbot_items` row; vault containment is checked against it at boot |
| 4 | One manager API per kind | `depositPlayerBotItem` and `removePlayerBotItemsForReap` are the only writers |
| 5 | Source, reference, journal row | `source = loot`, `ref = corpse OID`; ledger `kind = item`, `ref_id = object OID`, `detail` = template short name |
| 6 | Reserve → commit or release | Loot is one atomic object move into the owner's bag, so it needs no reserve step: the bag is the write-ahead record and the `held` row follows. A failed transfer writes nothing. `pending` stays reserved for multi-step flows (the bazaar) |
| 7 | No record, no holding | No progression record ⇒ no loot is created for that bot's kill, and the miss is counted |
| 8 | Death, respawn, restart lose nothing beyond the unflushed window | Items are in the vault. Boot reconciliation classifies anything else |
| 9 | The reaper removes every holding | Item teardown runs before the identity delete |
| 10 | Visible per bot | Item count and a bounded item list per identity |

## Implementation Details

### 0. Schema 1015: `simbot_items`

**Files**: `src/server/db/ServerDatabase.cpp`, `MMOCoreORB/sql/swgemu.sql`

`alterDatabase(1015, CREATE TABLE IF NOT EXISTS simbot_items …)`, MyISAM like the
other `simbot_*` tables. The table holds **current state**, one row per object. Its
history is in `simbot_ledger`.

- `object_id` BIGINT primary key (an OID is never reused)
- `identity_id` BIGINT NULL (NULL for the system-owned states `lost` and `orphaned`)
- `state` VARCHAR(12). This chunk writes only `held` and `orphaned`. `pending`,
  `lost` and `consumed` (multi-step flows, F_0.9.9), `listed` (F_0.9.9) and
  `equipped` (the equip chunk) are reserved: reconciliation recognises them but
  nothing here writes them
- `template_crc` INT UNSIGNED, `display_name` VARCHAR(64) (for the dashboard,
  captured at deposit)
- `source` VARCHAR(32), `ref_id` BIGINT
- `acquired_at`, `updated_at` DATETIME
- Indexes on `(identity_id, state)` and `(state)`

Using `object_id` as the primary key makes every state change an UPDATE of one row.
This departs on purpose from the roadmap's wording "a consumed object still in the
vault gets a **new** orphaned row": here the existing row moves to `orphaned` instead,
and the ledger keeps the history. It also departs from the roadmap's `pending → held`
loot protocol, for the reason in rule 6 above: a row that is flushed asynchronously
cannot act as a write-ahead record (a flush can snapshot `pending` just before the
transfer fails), but the bag can, because the move and the owner are one BDB write.

`simbot_ledger.identity_id` stays NOT NULL. Ledger rows are written only for changes
to an identity's holdings; system-owned discoveries (an object with no owner) are
counted on the dashboard, not journaled.

### 1. The hive item vault

**Files**: `src/server/zone/managers/aieconomy/AiEconomyData.idl`,
`AiEconomyManager.{h,cpp}`

**Current state**: `AiEconomyManager` loads or creates the single `AiEconomyData`
object from its own object database (`AiEconomyManager.cpp:1555-1622`). It has no
vault.

**Modifications**:

- `AiEconomyData.idl`: add `protected unsigned long itemVaultOid` with a `@read
  @preLocked` getter and a `@dirty @preLocked` setter; add `@dereferenced protected
  VectorMap<unsigned long, unsigned long> itemBagOids` (identity id → bag OID) with
  `@read @preLocked` lookup and `@dirty @preLocked` put and drop methods; and add a
  `@dirty @preLocked setSchemaVersion(int)`, since `schemaVersion` has only a getter
  today. Bump `CURRENT_SCHEMA_VERSION` to 2 and make `validateEconomyData` accept
  version 1 (an older object reads `itemVaultOid = 0` and an empty bag map) and
  upgrade it to 2 under the data object's lock. `src/autogen/` regenerates and is
  never edited by hand.
- **Bags.** `AiEconomyManager::getOrCreateItemBag(identityId)` returns the
  identity's bag. On first deposit it creates a persistent container
  (`createObject(<vault template>, 1)`), transfers it into the vault under `Locker
  bagLock(bag)` then `Locker vaultLock(vault, bag)` (object before the container
  it enters, as everywhere), and records it in `itemBagOids` (data object lock only), in that order and
  **before** any item moves into it. A crash between those steps leaves an empty,
  unmapped bag, which reconciliation counts and destroys. Callers never hold a
  manager mutex here.
- `AiEconomyManager::ensureItemVault()`, run once after the economy data loads. If
  `itemVaultOid` resolves through `zoneServer->getObject` to a container, use it.
  If it is 0, create one with `zoneServer->createObject(<vault template>, 1)`
  (persistent), give it no zone and no parent, store its OID with the setter, and
  count `vault.created`. If the OID is set but does not resolve, **do not create a
  replacement**. Mark the vault unavailable (`vault.loadFailed`) so the gate fails
  closed and the owner sees it. A silent second vault would orphan every item in
  the first.
- Vault template: a plain volume container with no slots. The implementer confirms
  that `object/tangible/inventory/creature_inventory.iff`, which
  `CreatureManagerImplementation.cpp:548` already creates for every creature, has
  `ContainerType::VOLUME`, and chooses a different one if it does not. The
  container's owner id stays 0, so no creature passes `checkContainerPermission` on
  it. Transfers into the vault use `transferObject(item, -1, false, true)`
  (`allowOverflow`, `SceneObject.idl:357`) because the volume limit is meant for
  one character. The per-bot cap is enforced from the rows, not by the container.
- Accessors: `getItemVault()` and `getItemBag(identityId)` return a
  `ManagedReference<SceneObject*>` or null, plus `isItemVaultAvailable()`,
  `getItemBagMapSnapshot()` (a copy, for reconciliation) and `dropItemBag(identityId)`.

### 3. Bot branch at the loot chokepoint

**File**: `src/server/zone/managers/creature/CreatureManagerImplementation.cpp`
(around `:679-703`)

**Current state**: the loot block runs only if `player->isPlayerCreature()`.

**Modifications**: an `else if` after the stock block. The stock block's condition
and body are untouched.

- Cheap pre-filter: `player` is non-null, not `isPlayerCreature()`, is an `AiAgent`
  with `getSimPlayerBot()`, the destructed object is not an event mob, and the
  creature inventory exists. As in F_0.9.1, the flag is a cost filter only.
- Authority: `SimPlayerManager::resolvePlayerBotLootOwner(bodyOid)` returns an
  identity id or 0, in three separate, unnested steps: resolve the body under
  `pveMutex`; evaluate `playerBotLootGateEnabled(identityId)` with **no** manager
  mutex held (it takes `playerBotParityTestMutex`, which must never nest inside
  `progressionMutex`, `SimPlayerManager.h:2856-2860`); then check only that the
  record exists under `progressionMutex`. All three are leaf mutexes, never held
  while locking an object (`SimPlayerManager.h:2288-2302`), so taking them here
  under the corpse lock is the permitted direction. A 0 is counted
  (`loot.notCreated.{noIdentity,noRecord,gateOff}`) and the corpse keeps legacy
  behaviour.
- With an identity: the same cash and `createLoot` calls as the stock block, using
  the same `TransactionLog` codes, with `ownerID = player->getObjectID()` (no
  grouping for bots in this chunk; F_0.9.4 adds it). The container owner is the bot
  body, so a passing player cannot loot it.
- Despawn: a bot-branch flag makes the corpse keep 300 s when it holds loot or
  cash, else 10 s. `shouldRescheduleCorpseDestruction` is not called for the bot
  branch, because for a non-player it always answers 10 s.
- Claim: `SimPlayerManager::queuePlayerBotLootClaim(identityId, corpseOid, zone
  name, position)`. It is a value copy into a per-identity bounded deque under a
  new leaf `lootMutex` (`maxClaimsPerBot`, oldest evicted and counted), with
  `expiresAtMs = now + claimTtlSeconds`. No object reference is stored.

### 4. Loot step in the controller

**Files**: `SimHunterController.{h,cpp}`

**Current state**: kills happen in three places: the early-game `EARLY_ENGAGE`,
`HUNTING` at a mission lair, and travel-combat self-defence. After a kill the bot
moves straight on.

**Modifications**: one shared loot sub-step, owned by `runActiveTick` under the
single-writer rule. It is not a new top-level phase, because kills happen in several
phases.

- Entry: at a safe point (no live attacker from `selectActiveCombatAttacker`, not
  fleeing or resting, not mid-traversal), the bot asks
  `takeNearestPlayerBotLootClaim(identityId, zone, position, maxDetourMeters)`. Safe
  points are the early-game tick before `EARLY_SELECT_TARGET`, the `HUNTING` tick
  between waves and after the lair falls, and travel combat's return to MOVE.
- Walk: `moveTo` the claim position, with the same reschedule guard ARCHI §12
  requires (read `activeTickGeneration` before, `scheduleActiveTick` if unchanged).
- Arrive (within `arriveMeters`): call `lootPlayerBotCorpse`, then return to the
  phase that was interrupted.
- Exit without looting, each counted under `loot.abandoned.*`: a new attacker
  (combat wins; the claim goes back to the queue if it has not expired), claim
  expired, corpse gone, `stepTimeoutSeconds` exceeded, or bot death. A body teardown
  drops nothing durable, because nothing was written yet.
- The step stays a pure decision in a new header,
  `SimBotLootStep.h` (claim selection by distance and expiry, and the exit
  decision), so it can be unit-tested.

### 5. Looting a corpse

**Files**: `SimPlayerManager.{h,cpp}`

`lootPlayerBotCorpse(identityId, body, corpseOid)` returns a disposition enum
(`LOOTED`, `PARTIAL_CAP`, `NOTHING`, `CORPSE_GONE`, `NOT_OWNER`, `TOO_FAR`,
`TRANSFER_FAILED`, `GATE_OFF`) for the counters and the diag log.

Choreography, mirroring `PlayerManagerImplementation::lootAll` (`:4601-4660`) and
`TransferItemMiscCommand::doTransferItemMisc` (`:105-380`):

Before any lock: read the identity's `held` count under `progressionMutex` and
release it; get or create the identity's bag (section 1). Both happen with no object
locked.

**Lock chain**, the same everywhere items move: **world objects before vault
objects, and an item before the container it enters.** Each `Locker` crosses the
one before it, so every cross-lock precondition holds.

1. `Locker bodyLock(body)`. `runActiveTick` holds no body lock at this point
   (`SimHunterController.cpp:3979`), and `lootAll` is entered with the player
   already locked. Recheck after locking that the body is alive and in a zone (the
   ARCHI §12 post-lock lifecycle rule).
2. Resolve the corpse with `zoneServer->getObject`, then `Locker
   corpseLock(corpse, body)`, `lootAll`'s order. Recheck: the corpse is dead, the
   corpse inventory's owner id equals the body OID, and the distance is at most
   16.5 m (`doTransferItemMisc`'s limit).
3. Cash: read and clear the corpse's cash under these locks. The grant happens
   after all locks are released (step 5).
4. Items, newest first as `lootAll` does, while `held + moved in this call` is
   under `maxItemsPerBot`. First `Locker invLock(corpseInventory, corpse)`: the
   source parent, which the stock transfer locks explicitly
   (`TransferItemMiscCommand.h:357`). For each item: `Locker itemLock(item,
   corpseInventory)`, then `Locker bagLock(bag, item)` (`transferObject`'s
   precondition is that both the destination and the object are locked,
   `SceneObject.idl:348-357`), then
   `bag->transferObject(item, -1, false, true)`. Release the item and bag lockers
   before the next item.
   - On failure the item stays on the corpse, nothing is written, and
     `loot.transferFailed` is counted. The engine's `ObjectController`
     convention of putting the item back into its old parent is followed if the
     destination refused it.
   - On success, the moved OID and its template and name are recorded in a local
     list.
   - Items over the cap stay on the corpse and are counted
     (`loot.skippedVaultFull`).
5. Still holding the body and corpse locks: if the corpse inventory is now empty,
   reschedule its despawn the way `rescheduleCorpseDestruction` does (1 s). Then
   release every lock.
6. With no object locked: `depositPlayerBotItem` takes `progressionMutex`, writes
   one `held` row per moved object with one ledger row each (`kind = item`,
   `delta = +1`, `balance_after` = items held, `source = loot`, `ref_id` = object
   OID, `detail` = template short name), and **releases it**. If the record
   vanished meanwhile (reaped mid-step), no rows are written and the objects stay
   in the bag for reconciliation (`loot.depositNoRecord`).
7. Then, with no manager mutex held, one call grants the cash:
   `grantPlayerBotCredits(identityId, cash, bank = false, source = loot, ref =
   corpse OID)`. That function evaluates the parity gate before taking its own
   `progressionMutex` (`SimPlayerManager.cpp:11316`), so it must never be called
   with `progressionMutex` held. If it fails, the cash is lost and counted
   (`loot.cashDropped`), not put back on the corpse.

Not ported, on purpose: the `LOOTCREATURE` and `ITEMLOOTED` observer notifications
(screenplay observers expect a player), `force_luck` (bots have none), and the
player system messages.

`depositPlayerBotItem(identityId, objects, source, refId)` and
`removePlayerBotItemsForReap(identityId)` are the only writers of item rows, as rule
4 requires; reconciliation writes through the same internal row setter. The deposit
takes objects that are already in the identity's bag, so any future source (a gift
through `GiveItemCommand`, a bazaar purchase) moves the object into the bag under
the same lock chain and then calls it. Loot is the first caller.

### 6. Store load, flush and reconciliation

**Files**: `SimPlayerManager.{h,cpp}`

- In memory: `progressionItems`, a `VectorMap<uint64 objectId, SimBotItemRow>`
  under `progressionMutex`, with a per-identity held count kept alongside. Each row
  carries a `version` bumped on every change. Dirty rows join the existing
  atomic-swap flush as copies; on failure a copy is merged back only if the live
  row's version still equals the copy's, so a newer change is never overwritten by
  a stale retry. Rows are written with `INSERT … ON DUPLICATE KEY UPDATE` keyed by
  `object_id`, so a re-flush is idempotent. Ledger rows go first, as in F_0.9.2.
  Item rows are deleted only by the reaper, which runs on the same lane and
  removes in-memory rows and dirty copies before issuing its DELETE, as the
  existing `progressionDirtyIds` clear-before-delete does.
- Load: `loadPlayerBotProgressionStore` also reads `simbot_items`.
- Reconciliation runs once per boot on the maintenance lane, after the store load
  **and** once the vault is available (`AiEconomyManager` loads earlier; if it has
  not, retry on the next tick). It takes a snapshot of the bag map, then locks each
  bag on its own (no mutex held), copies its child OIDs and releases it, and also
  copies the vault's direct children. Only then does it take `progressionMutex` to
  compare. The decision is a pure function in `SimBotItemReconcile.h`:

  | Row | Where the object is | Result | Ledger row |
  |---|---|---|---|
  | `held` for X | in X's bag | unchanged | none |
  | `held` for X | missing, or anywhere else | → `orphaned`, identity NULL | X: −1, `source = reconcile` |
  | `pending` or `consumed` for X (reserved; not written by this chunk) | in X's bag | → `orphaned`, identity NULL | X: −1 if it was counted as held, else none |
  | `pending` for X | missing | → `lost`, identity NULL | none |
  | `consumed` | in any bag | → `orphaned`, identity NULL | none |
| `consumed` | missing | unchanged | none |
| `lost` or `orphaned` | anywhere | unchanged | none |
  | none | in X's bag, X has a record | new `held` row for X (recovers an unflushed deposit) | X: +1, `source = reconcile` |
  | none | in X's bag, X has no record | new `orphaned` row | none (counted) |
  | none | directly in the vault, or in an unmapped bag | new `orphaned` row | none (counted) |

  Every change bumps `vault.reconcile.*`. `orphaned` and `lost` never block
  reaping. Orphaned objects stay where they are for inspection; there is no
  automatic delete in this chunk. An unmapped bag that is empty is destroyed.

### 7. Reaper teardown

**Files**: `SimPlayerManager.cpp` (`runPlayerBotProgressionReaper`, the harness
`deleteIdentity` path, and retirement)

The two existing teardown paths, the reaper (`SimPlayerManager.cpp:12666`) and
retirement (`:18228`), already delete every ledger row of the identity: holdings
model rule 9 removes the history with the identity. Item teardown follows the same
rule, so no `reap` or `consumed` audit row survives the identity.

Before an identity's rows are deleted, for each object in its bag (the bag's
contents, not just its `held` rows, so an unflushed deposit is removed too): `Locker
itemLock(item)`, then `Locker bagLock(bag, item)`, the same item-before-container
order as looting; remove the item from the bag (the implementer confirms whether
`destroyObjectFromWorld(true)` unlinks a zoneless container child, or uses
`bag->removeObject`); release the bag; then `item->destroyObjectFromDatabase(true)`
with the item still locked (`SceneObjectImplementation.cpp:295` requires that, and
by itself only marks the object for deletion, which is why the unlink comes
first). Then the bag itself is destroyed the same way from the vault and dropped
from `itemBagOids`. Only then do the item rows go, with the ledger rows, in the
existing delete statements. A failed destroy leaves the identity for the next run
and is counted (`vault.reapDestroyFailed`). This matters at once on the live
server, where `retireLegacyHunters` is on. `listed` (F_0.9.9) will block reaping
instead.

## Technical Considerations

- **Pattern usage**: the loot branch mirrors F_0.9.1's kill-XP branch (a bot
  branch at a stock chokepoint, with the flag as a cost filter only). The loot
  transfer mirrors `lootAll` and `doTransferItemMisc`. The store work extends the
  F_0.9.2 journal and atomic-swap flush. The vault creation follows
  `AiEconomyManager`'s own load-or-create.
- **Locking and references**:
  - In `notifyDestruction` the corpse is locked and the destructor unlocked
    (`:603-605`). The new code takes only leaf mutexes, one at a time and never
    nested: `pveMutex`, then the gate's `playerBotParityTestMutex` (inside the gate
    function), then `progressionMutex`, then `lootMutex`.
  - Loot step order: body → corpse → corpse inventory → item → bag (section 5). No manager mutex is
    held while any object lock is acquired; `progressionMutex` is taken only
    before the chain or after it.
  - Bag creation locks bag → vault (object before the container it enters), releases
    both, then locks the economy data object alone to record the mapping.
  - Reconciliation locks one bag at a time to copy OIDs; the reaper locks item →
    bag. Neither holds a mutex while locking, and both copy rows out first.
  - Claims hold an OID, never a `ManagedReference`, so a queued claim cannot keep a
    corpse alive.
- **IDL impact**: `AiEconomyData.idl` gains one field and two accessors. Autogen is
  regenerated and never hand-edited. The object's schema version goes from 1 to 2,
  with version 1 still accepted.
- **C++ vs Lua**: the mechanics are C++. The gate, the cap and the distances and
  timeouts are Lua.
- **Gating**: everything is behind `lootEnabled`, default off. With the gate off,
  the chokepoint, despawn timing and controller are byte-for-byte legacy, because
  the bot branch sits in an `else if` the gate never reaches.
- **Dashboard**: section 8.
- **Live verification**: arm `lootEnabled` on the live server and run 60 to 90
  minutes. Assert from the dashboard and MySQL: every corpse claim either ends in a
  loot or an abandonment counted by reason; vault `bagItemCount` (items inside
  bags, bags themselves excluded) equals `held` rows, and per bag equals that
  identity's `held` rows;
  each bot's `items[]` matches its rows; each cash ledger row matches its balance
  change; restart reconciliation reports only expected states; no new BDB, crash or
  lock signatures.
- **Edge cases**: a corpse that despawns early (claim expires, counted); two claims
  in one fight (nearest first); a bot at its cap (cash only); the vault failing to
  load (gate off, visible); a player killing the bot mid-step (no write); an item
  that is itself a container (it moves whole, as for a player); `listed` and
  `equipped` are never written.

## Safety analysis

| Risk | Mitigation |
|---|---|
| Deadlock in `notifyDestruction` | Only leaf mutexes, never nested, under the corpse lock: the direction the existing mutex contracts allow. No new object lock in that function |
| Item lost between corpse and vault | The move into the owner's bag is one atomic object change that also records the owner. A failed transfer writes nothing and the item stays on the corpse. A crash before the row flush is recovered from the bag at boot |
| Lock-order deadlock in the loot chain | One order everywhere: body → corpse → corpse inventory → item → bag → vault, each `Locker` crossing the previous; the reaper locks item → bag, then bag → vault to remove the bag; reconciliation locks one bag (or the vault) at a time to copy OIDs; no manager mutex is held while any object is locked |
| A second vault orphaning the first | A set but unresolvable vault OID fails closed and is never replaced automatically |
| Players looting a bot's corpse | Container owner is the bot body OID, as for a player kill |
| Unbounded BDB growth | Per-bot cap (80) and the reaper teardown |
| A wild creature with a leaked bot flag | The pre-filter is cost only. Authority is roster resolution plus a record, so a leaked flag resolves to 0 |
| Live config reload | Gate default off; `luac -p` straight after any edit |

## Performance & Cost Impact

The chokepoint adds one cost filter and, for bot kills only, three short leaf-mutex
sections. The loot step is one walk and one locked transfer per item. Reconciliation
is once per boot and linear in rows. The vault holds at most `maxItemsPerBot` × the
roster (about 80 × 30 today).

## Backward Compatibility

Schema 1015 is additive. `AiEconomyData` version 1 objects load and are upgraded. A
server with the gate off behaves exactly as v0.9.9. Before the first armed run, the
vault is created once at boot whether or not the gate is on (an empty container).
