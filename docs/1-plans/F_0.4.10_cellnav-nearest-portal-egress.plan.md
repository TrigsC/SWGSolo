# Cell-Egress Nearest-Exterior-Portal Waypoint (Pass 4) Implementation Plan

## Overview

The Pass-3 cell-egress leg (`F_0.4.9`) gets a bot out of a building by walking it to
the building's exterior exit point, computed via the engine's native
`BuildingObject::getEjectionPoint()`. That works for a simple one-door building (the
cantina), but the live starport diagnostic showed it is wrong for a multi-portal
building: `getEjectionPoint()` returns a **single** template-defined point, and for
`starport_tatooine.iff` that point is on the **landing-pad side** — the opposite end
from the front entrance the bot came in. The egress then marched the bot through the
**entire** starport (six cells) to pop out the wrong (dead-end) side, then wander
overland from there.

Pass 4 replaces the egress waypoint with the **nearest exterior portal**: enumerate
the building's exterior doorways from its `PortalLayout` and egress through the one
closest to the bot. A bot in the front hall then leaves via the **front** door (a
short portal path back to the world), instead of trekking to a far/dead-end exit.
Owner decision: **nearest exterior portal** (waypoint keyed to the bot's position).

This modifies only the egress **waypoint** inside `F_0.4.9`; the egress leg
mechanics, resume, failure handling, and the entry fix are unchanged. It ships in the
same release train (`F_0.4.8` + `F_0.4.9` + `F_0.4.10`).

## Problem Statement

From the live starport trace (`cellnav.log`, building `1106368` =
`starport_tatooine.iff`, interior `cell 1106372`/"foyer4"):

- Enter worked — the resolver found the interior cell and the bot walked in.
- `CELL_EGRESS_BEGIN ... ejection=(3608.21,-4751.52)` — `getEjectionPoint()` returned
  the **landing-pad side** (NE), far from the front entrance `~3527,-4803` (SW) the
  bot used.
- The egress `findPath` therefore routed the bot through **six** cells
  (`1106372 → 1106373 → 1106374 → 1106375 → 1106381 → 6595536 → cell 0`) to reach that
  far exit, then overland from the landing pad — the observed "really strange" path.

Root cause: `getEjectionPoint()` is a single template point, unsuitable as a
"nearest way out" for a multi-door building. Its own portal-geometry fallback
(`BuildingObjectImplementation.cpp:236-284`) is also **buggy** — it loops
`for (i…getNumberOfPortals())` but reads `cell->getPortal(0)` every iteration, so it
only ever considers the first portal even when the exterior cell has several.

## Solution Architecture

Add a building method that returns the exterior portal doorway **nearest a given
world point**, and use it as the egress waypoint:

1. **New native `BuildingObject::getNearestExteriorPortalPoint(Vector3 fromWorld)`**
   — enumerate the exterior cell's portals (`PortalLayout::getCellProperties().get(0)`,
   then `getPortal(i)` for `i` in `0..getNumberOfPortals()-1` — fixing the
   `getPortal(0)` bug), compute each portal's exterior world point using the **same**
   geometry→normal→floor+`getEjectDistance()`→world-transform→ground-snap math as the
   `getEjectionPoint()` fallback, and return the point closest to `fromWorld`. If the
   building has no portal layout / no exterior portals, return the (0,0) sentinel so
   the caller can fall back.
2. **`beginCellEgressIfNeeded` uses it** — compute
   `building->getNearestExteriorPortalPoint(agent->getWorldPosition())` as the egress
   waypoint (bot-keyed, so a front-hall bot picks the front door). If it returns the
   sentinel, fall back to `getEjectionPoint()` (preserves the cantina behavior and
   covers buildings whose portal layout can't be read).

Everything else in the egress leg (portal-following `findPath`, outdoors-gated
arrival, resume, bounded failure) is unchanged and already verified.

## Implementation Details

### 1. New building method: nearest exterior portal point

**Files**: `src/server/zone/objects/building/BuildingObject.idl` (declare native
method) + `BuildingObjectImplementation.cpp` (implement). Note: there is **no**
`BuildingObjectImplementation.h` — the implementation class header is generated as
`src/autogen/.../BuildingObject.h` and must never be hand-edited.

**Current state**: `getEjectionPoint()` (`BuildingObjectImplementation.cpp:211`)
computes a single exterior point — either the template ejection offset, or (fallback)
a point derived from **portal 0** of the exterior cell.

**Modifications**:
- Add the native method to `BuildingObject.idl` mirroring the `getEjectionPoint`
  sibling's annotations (`:185-188`), with the parameter dereferenced:
  ```
  @local
  @dereferenced
  @dirty
  public native Vector3 getNearestExteriorPortalPoint(@dereferenced final Vector3 fromWorld);
  ```
  Rebuild (`BUILD_IDL`) regenerates the autogen stubs/adapter (never hand-edited).
- Implement in `BuildingObjectImplementation.cpp`:
  - Resolve `SharedBuildingObjectTemplate` → `PortalLayout` (guard nulls; return
    `Vector3(0,0,0)` sentinel if absent).
  - `const CellProperty* exterior = portalLayout->getCellProperties().get(0);` (index
    0 is the exterior cell).
  - For `i` in `0 .. exterior->getNumberOfPortals()-1`: `const CellPortal* portal =
    exterior->getPortal(i);` (the **`i`** fix), compute the portal's exterior world
    point with the existing fallback math (`getPortalGeometry`/`getPortalBounds`,
    winding-aware `normal`, `box.center() - (0,extentsY,0)`, `+= normal *
    getEjectDistance()`, the building `direction.toMatrix3()` + translation +
    transpose transform, then `CollisionManager::getWorldFloorCollision(x, z, y,
    zone, false)` for Z). Factor this per-portal computation into a **file-local
    `static` helper function in `BuildingObjectImplementation.cpp`** (not a class
    method — there is no editable impl header) that takes the portal + template +
    building transform inputs and returns the exterior world point, so both
    `getEjectionPoint()`'s fallback and this method can call it with index `i`.
  - Track the candidate with the smallest horizontal distance to `fromWorld`; return
    it. If no portal produced a valid point, return the sentinel.
- Optionally, fix `getEjectionPoint()`'s fallback loop to use the shared helper too
  (so its latent `getPortal(0)` bug is corrected), but scope that minimally — the
  primary consumer is the new method.

### 2. Egress uses the nearest exterior portal

(`beginCellEgressIfNeeded`).

**Current state**: reads `ejection = building->getEjectionPoint()` under a short

**Modifications**:
- Replace the waypoint computation with
  `Vector3 exit = building->getNearestExteriorPortalPoint(agent->getWorldPosition());`

  `building->getEjectionPoint()` (cantina-style buildings unaffected).
- Keep the existing validation (within zone boundaries, not (0,0)) and the rest of
  the egress leg exactly as-is.

## Technical Considerations

- **Pattern Usage**: `getNearestExteriorPortalPoint` mirrors `getEjectionPoint` (same
  file, same portal-geometry math, same native-method shape) — the nearest analogous
  primitive. The egress caller change is a one-line waypoint swap plus a fallback.
- **Locking & References**: The new method reads template/portal-layout data and calls
  `getZone()`/`getWorldFloorCollision` like `getEjectionPoint`; call it under the same
  short building `Locker` the egress already takes, released before the async
  `findPath`. No new lock, no ordering change.
- **IDL Impact**: One new `native` method on `BuildingObject.idl`; `src/autogen` is
  regenerated by the build (never hand-edited). Hand-written logic lives in
  `BuildingObjectImplementation.cpp`. No fields/persistence change.
- **C++ vs Lua Placement**: Portal geometry + building method are C++ (engine data);
  no new Lua beyond the transient diagnostic config already present.
- **Gating & Simulation-Only**: Movement-only; no inventory/credit/market mutation.
  The new building method is a pure read/compute (usable by anything later, but only
  the gated egress calls it now).
- **Nearest-to-bot vs nearest-to-destination (design note)**: This plan keys the
  waypoint to the **bot's** position, so a front-hall bot exits the front. That is
  correct for the realistic case (bots operate from the entrance/ticket-collector
  hall). Caveat: it does not model that a landing-pad-side portal is a **dead end** —
  a bot that were deep on that side could still pick it. Excluding dead-end/enclosed
  portals (or keying to the destination direction) is a possible future refinement;
  called out here, not implemented, to keep the change minimal.
- **Dashboard Visibility**: None; verification is `cellnav.log` (pre-strip) +
  in-game (a bot leaving a starport via the front).
- **Live Verification Plan**: §3 — starport egress now exits the front with a short
  path; cantina still works; and a **real** bot (PvP squad / PvE hunter that uses a
  starport or building) leaves via the front and continues its route. Gates the strip.
- **Edge Cases**: building with no portal layout (sentinel → `getEjectionPoint`
  fallback); exterior cell with a single portal (nearest = that one; same as today but
  correct); portal geometry missing for an index (skip, per existing fallback guards);
  ground-snap returning 0 (validated as before); bot equidistant from two portals
  (deterministic first-min pick).

## Type Definitions (if applicable)

No new types. One new native method returning `Vector3` (the (0,0) vector doubles as
the "no exterior portal" sentinel, matching `getEjectionPoint`'s own convention).

## Performance & Cost Impact

Negligible: the portal enumeration runs once per cell-exit event (rare, event-driven),
over a handful of exterior portals, reusing existing geometry accessors. No per-tick or
population-wide cost.

## Backward Compatibility

Fully compatible: additive native method; the egress waypoint swap only changes which
outdoor point a cell-exiting bot heads to (and only when a portal layout is readable —
else it falls back to today's `getEjectionPoint`). No schema/persistence/IDL-field
changes. Single-door buildings behave as before.

## Test Impact

- No new unit tests: engine portal-geometry + movement behavior, verified live per
  project norm (mocking a full `PortalLayout` exceeds the mock-pain tripwire). Record
  any deferral in `docs/4-unit-tests/COVERAGE-DEBT.md`.
- Release code review must cover the new `BuildingObject` method (shared with the
  `getEjectionPoint` fallback) and the egress caller change; live check includes a real
  bot leaving a starport via the front.
