# F_0.9.5 — Skill training, novice PlayerBots, and the neutral body template (P.10f)

**Line**: P.10 (`docs/1-plans/ROADMAP_p10-playerbot-parity.md`, chunk F_0.9.5 + §5b.1/§5b.2/§5b.3/§5b.3a)
**Version**: 0.9.5
**Branch**: `feat/p10f-skill-training`
**Written**: 2026-09-04 (project week 8), revised after Codex round 1
**Predecessor**: F_0.9.1 (v0.9.1, kill XP) — shipped, live-verified, released.

## Overview

F_0.9.1 gave roster PlayerBots real XP. This chunk turns that XP into
**progression**: a bot spends it on skill boxes, the boxes grant real skill mods
that `CombatManager` reads, and the bot is **minted as a novice with a
profession** on a purpose-built neutral body template instead of inheriting a
level-178 combat mob. The proving vehicle is the owner's chosen first target — a
single unarmed brawler climbing `combat_brawler_novice` → `combat_unarmed_master`
— because unarmed needs no weapon-equip code and already credits the correct XP
type through the shipped F_0.9.1 path.

The chunk is sized for the owner's stated scale bar of **2000+ identities**. The
training decision is event-driven, not a per-tick roster scan.

## Problem Statement

Seven concrete gaps, each verified against the current tree:

1. **No training exists.** `SimBotProgression` already carries `skills` and
   `skillPointsSpent` (`SimPlayerManager.h:134/:139`) and `simbot_skills` already
   exists (schema 1012, `ServerDatabase.cpp:191`), but nothing writes them.
   `SkillManager::awardSkill` cannot be reused: `fulfillsSkillPrerequisites`
   rejects every ghostless creature at `SkillManager.cpp:942-944`, and XP
   withdrawal, skill points, abilities and schematics are all ghost operations.
2. **The shipped XP ceiling strands progression.** `grantPlayerBotExperience`
   caps on `SkillManager::getDefaultXpLimit` with a 2000 fallback
   (`SimPlayerManager.cpp:9173-9181`). The stock rule
   (`SkillManager::updateXpLimits`, `:802-824`) takes `max(Skill::getXpCap())`
   over the character's trained skills. A brawler saturates
   `combat_meleespecialize_unarmed` at the default long before master. This is a
   defect in already-released code.
3. **The per-kill XP cap and hunt eligibility are frozen at mint.**
   `levelCap = skillTier * 300.f` (`SimPlayerManager.cpp:9381`, mirrored at
   `:10227`) and species eligibility (`identity.skillTier < species.minSkillTier`
   at `:15618`, `:15624`, `:15845`, `:15851`, plus a `< 1` validity guard at
   `:15338`) all read
   `identity.skillTier`, which is set once from the static `pveSkillTier` config
   (`:12186`, clamped 1-5 at `:8233`) and never updated. A trained master would
   remain capped and matched as a tier-1 bot. Fixing only the lifetime ceiling
   (gap 2) is therefore insufficient.
4. **Profession is a hard filter on every PvE path.** Population governance
   (`:12269`), body spawning (`:12752`) and hunt dispatch (`:15259`) all test
   `profession == "hunter"` exactly. A `brawler` identity would be minted and
   then never spawn, never hunt, and never be counted.
5. **Nothing mints a novice.** `mintPveIdentity` (`:12161`) persists a profession
   string but every caller passes `"hunter"` or `"harness"`, and no box is
   granted at mint.
6. **The body and its weapon path are wrong.** `pveConfig.bodyTemplates =
   { "death_watch_wraith" }` (`sim_player_manager.lua:1449`) is a level-178
   factioned combat mob. Worse, the spawn path cannot express "no weapon":
   `spawnPveIdentityBody` always selects from `pveHunterTemplates` (`:12356`),
   unconditionally calls `createObject(weaponTemplate…)` and **destroys the body**
   when that returns null (`:12403-12410`), and destroys it again when
   `equipped == false` (`:12478-12484`). Simply skipping the equip block would
   delete every novice.
7. **Trained mods would silently make a bot worse.**
   `AiAgentImplementation::getSkillMod` (`:624-664`) returns the creature
   skill-mod list value whenever it is nonzero and only then falls back to
   `npcTemplate->getStatistic`. A raw trained delta *replaces* the baseline.

## Solution Architecture

### A. Derived spend — training is a single-row mutation

**This is the central design decision and it removes the need for a write-ahead
journal.** MyISAM has no transactions, so any design that debits XP in one table
and inserts a skill in another can be torn by a crash.

Instead, nothing is ever debited:

- `simbot_experience.amount` means **lifetime earned** XP per type. This is
  already exactly what F_0.9.1 writes — `grantPlayerBotExperience` only ever
  adds (`:9197`). No writer changes.
- **Available XP** for a type = `earned − Σ getXpCost()` over trained boxes of
  that XP type. Derived, never stored.
- `skill_points_spent` becomes **derived** from `simbot_skills` as
  `Σ getSkillPointsRequired()`. The existing column is retained as a cached
  mirror for the dashboard and is recomputed at load and after each train; it is
  never authoritative.

Training therefore mutates exactly **one durable row**: an `INSERT` into
`simbot_skills`. That single insert is atomic under MyISAM, so no phase protocol,
journal, or crash-boundary replay is required. A crash can only lose an
in-flight *earned* XP flush — the pre-existing F_0.9.1 behaviour, unchanged — and
can never produce a half-trained identity. Boot reconciliation is inherent:
recomputing available XP and spent points from `simbot_skills` is self-healing.

The XP ceiling (B) applies to **available** XP, which matches the player
experience of being capped while holding XP.

### B. Effective XP cap and derived combat tier

Two corrections to F_0.9.1, both no-ops for an untrained identity:

- `effectivePlayerBotXpCap` mirrors `SkillManager::updateXpLimits`
  (`:802-824`): the max `Skill::getXpCap()` over trained skills matching the XP
  type and having a nonzero cap, else `getDefaultXpLimit`, else 2000, with
  `prestige_` uncapped. Replaces `SimPlayerManager.cpp:9173-9181`.
- Tier follows the **stock player formula**, not a heuristic.
  `PlayerManagerImplementation::calculatePlayerLevel` computes
  `min(25, getSkillMod("private_" + weaponType + "_combat_difficulty") / 100 + 1)`,
  with the XP-type-scoped variant mapping the XP type to a weapon type by
  substring (`onehand`, `polearm`, `twohand`, `unarmed`, `carbine`, `pistol`,
  `rifle`, else `heavyweapon`) at `:4655-4679`. It is reproduced against the
  identity's **accumulated trained skill-mod deltas**, which is real parity
  rather than a proxy: the SKILLBOX overlay (F) means a trained brawler genuinely
  carries `private_unarmed_combat_difficulty`.
- **Two consumers, and only one of them has an XP type in scope**, so the API is
  split rather than generalised:
  - **Per-kill cap** (`:9381`, `:10227`) — the kill-XP path knows the attacking
    weapon's XP type, so it calls
    `int playerBotKillXpTier(const SimBotProgression&, const String& xpType, int fallbackTier)`,
    reproducing the XP-type-scoped variant (`:4655-4679`).
  - **Hunt dispatch** — the species comparisons are
    `identity.skillTier < species.minSkillTier` at **`:15618`, `:15624`,
    `:15845`, `:15851`** (two branches in each of two functions), plus a
    `skillTier < 1` validity guard at `:15338`. None of these has an XP type or
    an equipped weapon in scope. **They are therefore left completely
    unchanged**, and instead `identity.skillTier` is recomputed and persisted on
    every successful train, from the training plan's own weapon type (which the
    plan already declares — `unarmed` for the brawler), using the same formula.
    Hunt dispatch keeps reading one field that is simply kept current.
- **That makes `skill_tier` a derived cache, so it must persist and self-heal.**
  Two gaps close here. First, the roster `UPDATE` at `:12305-12313` does **not**
  currently include `skill_tier`, so a recomputed tier would never reach the
  database — the column is added to that statement. Second, because the roster
  and the progression store flush independently, a crash between them could
  persist a tier without its skill or a skill without its tier, and nothing would
  ever correct it. So `reconcileIdentityTiers()` runs **after the progression
  store loads and before body governance**: it recomputes every planned
  identity's tier from its durable trained skills, and where the recomputed value
  differs from the persisted one it corrects the in-memory roster and marks the
  identity dirty. The durable skills are the authority; the tier is only ever a
  cache of them.
- This is deliberately not the unscoped `calculatePlayerLevel(player)` variant
  (`:4643-4650`): that reads the *equipped* weapon off a live body, which is not
  available on the dispatch path and would be wrong for an identity with no body
  spawned.
- The fallback must be passed in — `SimBotProgression` has no tier field, so the
  function cannot reach `identity.skillTier` on its own. When no trained box
  contributes the relevant difficulty mod it returns `fallbackTier`, i.e. the
  persisted `identity.skillTier`, which is exactly today's behaviour.

### C. `trainPlayerBotSkill` — the single training entry point

One function, mirroring F_0.9.0's one-creation-function invariant:

1. gate `playerBotProgression.trainingEnabled` (see H for the mint exception);
2. **train-requires-record** — a missing record is counted and skipped, never
   created;
3. the skill resolves in `skillMap` and is not already trained;
4. prerequisites: every `getSkillsRequired()` entry present in
   `progression.skills` — deliberately **not**
   `SkillManager::fulfillsSkillPrerequisites`, which rejects ghostless creatures;
5. preclusions: no `getPreclusionSkills()` entry trained;
6. skill points: `derivedSpent + getSkillPointsRequired() <= 250`;
7. available XP (per A) `>= getXpCost()`.

On success it appends the skill, recomputes derived spend and tier, and marks the
record dirty. It **never touches a body**, so training is correct when the
identity has no body spawned.

`freeGrant` skips only step 7, for the novice grant at mint.

### D. Training plans — goal in Lua, order derived from the skill graph

Lua names only the terminal box. C++ walks `getSkillsRequired()` transitively
from that goal at config load, produces a topological order (prerequisites
first), and breaks ties by ascending `getXpCost()` then skill name for
determinism. Derived plans are immutable after load, so the hot path reads them
without a lock.

No external grind-guide research is required: the prerequisite graph, XP costs,
point costs and skill mods are all in `skillMap`, parsed from
`datatables/skill/skills.iff` by `SkillManager::loadClientData` (`:68-108`).
Adding marksman, artisan or a crafting line later is one Lua line each.

Load-time validation surfaced on the dashboard, not thrown: every referenced
skill resolves; the graph is acyclic; total `getSkillPointsRequired()` is
reported against the 250 budget (over-budget is a legal plan that stalls at the
budget — correct behaviour, but it must be visible).

### E. Event-driven evaluation with a bounded repair sweep

Training events are inherently rare — a box costs thousands of XP and a bot earns
~85 per kill, so an active bot trains on the order of once an hour.

- Each identity caches its next box: skill name, XP type, and a **lifetime-earned
  threshold**. Because A makes `simbot_experience` cumulative, the threshold is
  `Σ getXpCost() over already-trained boxes of that XP type + next box cost`,
  **not** the next box's cost alone — comparing a lifetime-earned total against a
  bare cost would fire on every award once the first box was trained.
- Inside `grantPlayerBotExperience`, already holding `progressionMutex`, the
  check is one string compare and one integer compare against that threshold. On
  a crossing the identity id is pushed to a pending set — **no training work and
  no SQL on the award path**.
- After a successful train the threshold is recomputed immediately. If the
  remaining available XP already affords the successor box, the identity is
  requeued rather than waiting for its next kill — but it re-enters the queue
  behind the others and still consumes one `trainingMaxPerTick` slot per box, so
  a bot that banked a large surplus catches up over several ticks instead of
  monopolising one.
- The PvE maintenance task drains the pending set, bounded by
  `trainingMaxPerTick`, keeping every write on the one existing SQL lane.
- A round-robin repair sweep recomputes `trainingSweepBatch` identities per tick
  to catch plan assignment, gate flips and database recovery.

**Cost at 2000 identities**: O(1) per XP award, O(`trainingSweepBatch`) per tick,
zero idle SQL. Nothing is O(roster) per tick. A full sweep completes in ~16
minutes at the shipped 30 s tick with a batch of 64.

### F. `applyProgressionToBody` — the skill-mod overlay

**Signature and locking contract** (corrects the round-1 contradiction):

```
void applyProgressionToBody(AiAgent* agent, const SimBotBodyProgression& snapshot)
```

`SimBotBodyProgression` is a plain POD — trained skill names plus a
`VectorMap<String,int>` of accumulated mod deltas — built by
`buildBodyProgressionSnapshot(identityId)` under `progressionMutex`, which is
released before the caller takes any agent lock. `applyProgressionToBody` itself
takes **no manager mutex** and requires the agent lock to be **already held** by
the caller. No manager mutex is ever held across an agent lock.

The desired value per mod is `npcTemplate->getStatistic(mod) + trained delta`,
matching the precedent at `AiAgentImplementation.cpp:972-977`
(`applyArchetypeMod`).

Application is a **full reconcile of the `SKILLBOX` group**:
`removeAllSkillModsOfType(SkillModManager::SKILLBOX, false)` then one
`addSkillMod(SKILLBOX, mod, desired, false)` per touched mod. Safe and idempotent
because `SKILLBOX` is written only by `SkillManager::awardSkill` (`:380`) and
cleared by `surrenderSkill` (`:582`, `:726`) — ghost-gated player paths a
PlayerBot body never reaches. It needs no per-body bookkeeping and behaves
identically on a fresh respawn and a mid-life train, leaving the `TEMPLATE` group
untouched so the Jedi archetype path cannot double-count.

Trained skills are also added with `agent->addSkill(name, false)` so `hasSkill`
reflects the store.

Call sites: inside the existing `Locker agentLock(agent)` block in
`spawnPveIdentityBody` after `loadTemplateData` (`:12419`), and after a
successful mid-life train when a body is live — the latter re-resolving the body
and applying the F_0.8.1 post-lock lifecycle recheck.

### G. PvE eligibility replaces the profession hard-filter

A single predicate `isPveHuntEligible(const SimBotIdentity&)` returns true when
the profession is in the Lua-configured `pveConfig.huntingProfessions` set
(shipped `{"hunter", "brawler"}`) and is not `"harness"`. It replaces all three
hard-filters at `:12269`, `:12752` and `:15259`, so eligibility is defined in one
place and future professions are a config change.

Novice identities are hunt-eligible and share the `pveMaxHunters` budget — but
**eligibility alone does not get a brawler spawned, and reordering candidates is
not sufficient either.**

`governPvePopulation` (`:12727`) skips any identity that already has a live body
**before** it counts toward the budget (`:12752-12756`, the
`pveIdentityBodyOids.contains(identityId) → continue` branch sitting inside the
`candidates.size() < pveMaxHunters` loop). `pveMaxHunters` is therefore a
**spawn-batch cap, not a population cap**: with six live hunters, a brawler with
no body is the only candidate and is spawned as a **seventh** body. Nothing in
the current governor ever detaches a live hunter, so no ordering change alone can
produce displacement.

The governor is therefore restructured into a **desired-active-set** model:

1. compute the desired set — at most `pveMaxHunters` identities drawn from **all**
   eligible identities, live-bodied or not, filled distribution-first (a reserved
   slot per profession) and then from the general eligible pool;
2. **drain** live bodies whose identity is not in that set, using the established
   teardown choreography from `drainSimPresenceBodies` (`:12523-12580`) — detach
   the identity maps, drop the controller, destroy under the agent lock, then
   `removeSimPresenceMemberAfterWorldExit`. This is a **body drain, not
   retirement**: the identity stays on the roster with its progression intact and
   simply loses its body. Bounded to one drain per tick, preferring an idle body
   over one mid-hunt, so a distribution change cannot churn the whole population
   in a single pass;
3. spawn desired identities that lack a body — but **at most
   `pveMaxHunters − currentLiveBodyCount`** of them, recounted after the drain.
   The bound is not symmetric with step 2 by accident: draining is capped at one
   per tick while the desired set may call for several replacements at once, so
   an unbounded spawn loop would drain one body and spawn N, transiently
   exceeding the cap. Deferred replacements simply wait for later ticks, and the
   population converges one swap per tick instead of overshooting.

**Semantic change worth flagging**: this makes `pveMaxHunters` a true population
cap. For the current deployment (six hunters, `maxHunters = 6`) observable
behaviour is unchanged, because the desired set is already the live set. It bites
only when the roster exceeds the budget — precisely the case novice minting
introduces.

The harness asserts the strong form: after minting a brawler against six live
hunters there are **exactly six** live bodies, the brawler is one of them, the
drained hunter keeps its roster row and progression, and the brawler actually
receives a hunt order.

**Open risk, explicitly scoped**: an unarmed novice has empty attack maps and
only auto-attack. Its ability to actually kill lair spawns is unproven. Phase 4
proves the narrow case (a `dwarf_nuna`) and the template's damage band is
Lua-tunable; if it proves unable to complete real hunts, the fallback is a
tuning change plus deferring novice hunt-eligibility to a later chunk, not new
C++ in this one.

### H. Novice minting, the neutral template, and the weapon branch

- `pveConfig.novice` declares a profession distribution (profession → training
  plan → count) and the shipped body template. F_0.9.8's allocator later replaces
  the static distribution; the plumbing is identical.
- **The mint loop itself must change.** `mintPveIdentitiesIfNeeded` currently
  counts only `profession == "hunter"` (`:12269`) and then runs
  `while (rosterSize < pveMaxHunters) mintPveIdentity("hunter", identity)`
  (`:12274-12277`) — a hardcoded profession that would refill hunters forever and
  never mint a brawler. It is replaced by a **per-profession deficit** pass: for
  each distribution entry, count live identities of that profession excluding any
  in the retiring set, and mint the shortfall with that entry's plan. Hunters
  become one distribution entry like any other, and when `retireLegacyHunters`
  is enabled their target is zero, so retirement can never race a refill.
- `simbot_identities` gains `training_plan VARCHAR(64) DEFAULT NULL` at
  **schema 1013**. Identities without a plan never train, so production training
  cannot pre-empt F_0.9.8's allocation.
- New authored template `bin/scripts/mobile/misc/sim_playerbot_novice.lua`: low
  level, `primaryWeapon = "unarmed"`, `secondaryWeapon = "none"`, empty attack
  maps, no loot groups, empty meat/hide/bone so a PlayerBot corpse is not
  harvestable. Every stock humanoid is level 100+ (`misc/chiss_male.lua:5`), so
  this must be authored rather than chosen.
- **Template selection** in `spawnPveIdentityBody` becomes explicit: an identity
  with a training plan uses `pveConfig.novice.bodyTemplate`; otherwise the
  existing `pveHunterTemplates` rotation (`:12352-12358`). Both are read under
  the same `pveMutex` copy-out that exists today.
- **The weapon branch is restructured, not skipped.** When the plan's
  `weaponTemplate` is empty:
  - `createObject` is **not called at all**, so the null-weapon destroy at
    `:12403-12410` is unreachable rather than triggered;
  - the stock `default_weapon` is **created by `loadTemplateData`, not by
    `createCreature`** — the existing comment at `:12415-12418` is explicit that
    `createCreature()` alone leaves the agent uninitialized and that the mobile
    template load is what populates weapons. Empty-loadout validation therefore
    happens *inside* the agent-lock block **after** `loadTemplateData(creoTempl)`
    (`:12419`); validating earlier would read a null weapon and destroy every
    novice for the opposite reason. The weapon is retained,
    validated non-null and castable to `WeaponObject*`, and aligned across
    `setPrimaryWeapon` / `setDefaultWeapon` / the AI weapon slots the way the
    rifle branch does at `:12437-12450`;
  - `equipped` is set true only after that validation, so the `!equipped`
    invariant at `:12478-12484` still holds and still destroys a body combat
    cannot arm.

  The `weaponTemplate` non-empty path is byte-for-byte the existing behaviour.

- **`freeGrant` and the gates** (round-1 P2): the mint-time novice grant requires
  `playerBotProgression.enabled` and `pveConfig.novice.enabled` but deliberately
  **bypasses `trainingEnabled`**. Rationale: the novice box is part of identity
  creation, not progression. Minting a "novice brawler" that has a plan but no
  profession box would be a worse state than either gate implies, and would make
  the first training step's prerequisites unsatisfiable. This is documented at
  the call site and asserted by a harness scenario that mints with
  `trainingEnabled = false` and checks the box is present while no further
  training occurs.
- **Mint is crash-torn without a repair pass.** The roster row and the
  progression record are persisted synchronously, but the novice box reaches
  `simbot_skills` only through the later dirty flush. A crash in between leaves a
  planned identity with no profession box, and because the ordinary sweep is
  behind `trainingEnabled` it cannot repair that. `reconcileNoviceGrants()`
  therefore runs on the maintenance lane **before body governance**: for every
  identity that has a `training_plan` and no trained skills, it free-grants the
  plan's first box. It is idempotent by construction — `trainPlayerBotSkill`
  already refuses an already-trained box — and it bypasses `trainingEnabled` for
  the same reason the mint-time grant does. Restart-probe scenarios cover each
  mint boundary.
- **Repair can legitimately fail** — a missing progression record, an invalid or
  unresolvable plan — and running before governance does not by itself stop an
  unskilled body from spawning. So body governance additionally **requires** the
  plan's novice box.
  The precondition is specifically that `progression.skills` contains
  `plan.orderedSkills[0]`, **not** the weaker "has no trained skills": those are
  not equivalent once a plan is reassigned, which this chunk explicitly supports
  and which retains previously-trained boxes. An identity carrying old skills but
  missing its current plan's novice box must still be refused.
  It stays unspawned with the refusal counted and named on the dashboard, which
  is strictly better than a novice brawler walking around with no profession and
  silently earning XP it can never spend.
- **Lock order**: the readiness test reads progression state while candidate
  selection runs under `pveMutex`. The set of plan-ready identity ids is
  therefore copied out under `progressionMutex` **before** selection takes
  `pveMutex`, preserving the never-nested contract that governs the rest of this
  chunk.

### I. Retirement — a production path, not the harness one

The existing `DeleteIdentity` handler (`:9858-9887`) is harness-specific: it
destroys only registered harness bodies via `destroyPlayerBotParityBody` and
deletes only the `simbot_identities` row. It is not reusable for a live hunter
with a controller, world presence and progression rows.

`retirePveIdentity(identityId)` mirrors the authoritative production teardown in
`drainSimPresenceBodies` (`:12523-12580`) exactly:

0. mark the id as retiring in **two independently-guarded places**, because the
   readers live under different mutexes and nesting them is forbidden:
   `pveRetiringIdentityIds` under `pveMutex` (read by body governance, the
   distribution mint pass and training), and `progressionRetiringIds` under
   **`progressionMutex`** (read by every progression dirty writer). A single
   `pveMutex`-guarded set would not close the race: the four
   `progressionDirtyIds.put(identityId, true)` sites (`:9201`, `:9236`, `:9271`,
   `:9305`) all run under `progressionMutex`, so a writer could pass a
   `pveMutex`-side check and then re-dirty the record after step 5 had cleared
   it. Each dirty writer consults the progression-side flag under the mutex it
   already holds and skips the dirty mark. Both flags are cleared only on
   successful completion, so an interrupted retirement resumes rather than
   leaving a half-torn identity eligible for anything;
1. under `pveMutex`, detach `pveBodyIdentityIds`, `pveIdentityBodyOids`,
   `pveRespawnDueAtMs` and `pveTerminalVisitEpoch`, plus this chunk's training
   caches and pending-set entry — **without** revoking presence membership yet
   (the disable=drain ordering contract);
2. `controllers.drop(bodyOid)`;
3. resolve the body and, under `Locker agentLock(agent)` with the F_0.8.1
   post-lock lifecycle recheck, `destroyObjectFromWorld(true)` +
   `destroyObjectFromDatabase(true)`;
4. `removeSimPresenceMemberAfterWorldExit(oid, nowMs)` only after world removal
   returns;
5. under `progressionMutex`, clear `progressionDirtyIds` for the id **before**
   any row delete — with `progressionRetiringIds` already set in step 0, no
   writer can re-dirty it afterwards. Without both halves a dirty flush landing
   mid-teardown would recreate the child rows that were just deleted;
6. delete rows in dependency order — `simbot_skills` → `simbot_experience` →
   `simbot_progression` → `simbot_identities`. Each delete is idempotent, so a
   crash mid-sequence simply resumes on a later tick;
7. only after the final delete succeeds: under `progressionMutex` drop
   `progressionRecords` and `progressionDirtyIds` for the id
   (`SimPlayerManager.h:1886-1887`), then under `pveMutex` drop it from
   `pveIdentities`, then remove it from `pveRetiringIdentityIds`. Clearing the
   in-memory progression record is not optional: leaving it behind would make the
   very next `reconcilePlayerBotProgression()` report the retired identity as an
   `orphanRecords` entry;
8. `reconcilePlayerBotProgression()` to assert `orphanRecords` stays zero.

One identity per maintenance tick, gated and default-off.

## Schema ordering — renumbering, and why it is safe

`alterDatabase` skips any version at or below the deployed one. The deployed
schema is **1012**; `ServerDatabase.cpp` currently ends at 1012. The roadmap
reserved 1013 for F_0.9.3 (loot) and 1014 for this chunk, which would have forced
F_0.9.3 to ship first for no design reason.

Nothing above 1012 has shipped, so the numbers are free. **F_0.9.5 takes 1013 and
F_0.9.3 moves to 1014.**

## Technical Considerations

- **Pattern usage**: F_0.9.0's store discipline — one SQL lane on the PvE
  maintenance task, requests enqueued rather than issued inline, dirty-batch
  atomic swap on flush. Training adds no new writer.
- **Atomicity**: derived spend (A) reduces training to one row insert, which is
  atomic under MyISAM. No journal is required; a journal is still the right tool
  for F_0.9.6's bazaar, where value is human-visible and multi-party.
- **Locking**: `pveMutex` then `progressionMutex`, never nested, never held
  across an agent lock. Body snapshots are copied out before any agent lock.
  `addSkillMod` takes the creature's own `skillModMutex`
  (`CreatureObjectImplementation.cpp:1534`), so the agent lock must already be
  held — it is, at both call sites. Retirement mirrors `drainSimPresenceBodies`
  (`:12523-12580`) exactly.
- **IDL impact**: none. No `.idl` change, no `src/autogen` regeneration, no
  build fan-out.
- **C++ vs Lua**: derivation, checks and persistence in C++; gates, quotas, plan
  goals, tier mapping, eligibility set, distribution and body template in Lua.
- **Gating**: `trainingEnabled`, `novice.enabled` and `retireLegacyHunters`
  default off and are independently reversible. With all three off the tree
  behaves as v0.9.1 except for the cap and tier corrections, which are no-ops for
  untrained identities.
- **Scale**: O(1) per XP award, O(`trainingSweepBatch`) per tick, no idle SQL;
  asserted by a synthetic 2000-identity harness scenario, not extrapolated.
- **Edge cases**: goal skill absent; cyclic prerequisites; plan over 250 points;
  XP type with neither default limit nor capped box; plan reassigned after
  partial training (already-trained boxes are retained, never surrendered —
  surrender is out of scope); training with no body spawned; body destroyed
  between snapshot and agent lock; concurrent award and train on one identity;
  database unavailable mid-train; retirement interrupted mid-delete;
  `maxHunters` pressure between novices and hunters.

## Performance & Cost Impact

- Gate off: one boolean test on the award path.
- Per XP award: one string and one integer compare under a mutex already held.
- Per maintenance tick: ≤ `trainingMaxPerTick` trainings plus
  `trainingSweepBatch` cache recomputes, plus at most one retirement.
- Per body spawn: one `removeAllSkillModsOfType` plus one `addSkillMod` per
  touched mod, bounded by the ~26 boxes of a full profession.
- Plan derivation once at config load. No new SQL statement types.

- Existing hunters have no plan, never train, and derive tier 1 — identical to
  today.
- Eligibility ships as `{"hunter","brawler"}`; with novice minting off, only
  hunters exist, so all three replaced call sites behave as before.
