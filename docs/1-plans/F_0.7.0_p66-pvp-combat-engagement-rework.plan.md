# P.6.6 PvP Controller-Driven Combat Engagement Rework Implementation Plan

## Overview

Move all in-combat movement for AI PvP squads out of the stock SWG combat
behavior tree and into `SimPvPController`, mirroring the proven
`SimHunterController` engage/approach split. Bots scan a wide radius-only bubble
(~100 m, no LOS needed for *detection*), path to a spotted enemy with
**navmesh + cell-aware** movement so they never clip through starports or
buildings, gate the actual *damage* on real line-of-sight plus the equipped
weapon's own range, and hold at each weapon's stock range band (rifles stand off
~64 m, melee close in) so they stop stacking on top of each other. In-cell
convergence becomes legal. Combat firing stays with `CombatManager` /
`activateAiBehavior` — the controller owns *movement and gating* only. All new
behavior is gated behind a new default-off `pvpConfig.combat` block.

## Problem Statement

Verified against current code and the live-soak history (memory
`pvp-gameplay-project`, doc §15.2):

1. **All combat movement is ceded to the stock tree.** `simPvp.lua` overrides
   only IDLE; on a scan hit `SimPvpBotController::scanForTargets`
   (`SimPvPController.cpp:299-318`) just does
   `setTargetObject`/`addDefender`/`setCombatState` + `state = IDLE` and lets the
   engine's combat tree move the bot. Off-navmesh (and inside starports) that
   movement degrades to straight-line "direct fallback" → **bots clip through
   starports and get stuck in weird places.**
2. **No LOS gate and no per-weapon spacing.** The stock tree closes to its
   weapon's min band, so melee bots pile into ~2 m of shared space ("10 jedi in
   2 m") and there is no controller-level control of where they stop.
3. **In-cell enemies are never engaged.** `scanForTargets` hard-skips any target
   with `getParent() != nullptr` (`SimPvPController.cpp:251-252`), so squads that
   converge at an indoor collector cannot actually fight there.
4. **Convergence is "strange."** Manager-level gank convergence gets two squads
   to the same city, but the final "paths meet → fight" step is entirely
   stock-tree movement with a single fixed 64 m engage radius
   (`scanRadiusMeters`), so the meeting looks erratic and stalemate-prone
   (the P.6.5e stalemate-break exists precisely because of this).
5. **Uncertainty flagged by owner:** scouts run starports correctly, but it is
   unconfirmed whether full squads traverse starport interiors the same way. This
   plan adds a diagnostic to answer that on the dashboard rather than assuming.

## Solution Architecture

Adopt the `SimHunterController` combat model, which is already proven live for
PvE, and specialise it for PvP:

- **Single-threaded combat lane.** Keep everything on the existing
  `SimPvpBotController::onTick` chain (which already runs the phantom-combat
  guard, stalemate tracker, and `scanForTargets`). Do **not** add a second
  active-tick task — that would reintroduce the exact `onTick` vs `runActiveTick`
  single-writer/atomic-generation concurrency hazards the hunter had to fix
  (ARCHI §12). **Cadence (Codex P1-2 fix):** `onTick` must **not** schedule its
  own task — `checkArrival()` calls `onTick()` and then independently schedules
  the next `ArrivalCheckTask` (`SimPlayerController.cpp:994` then the `:1061`/
  `:1075`/`:1143` etc. `schedule(1000)`/`schedule(500)` sites). Self-scheduling
  inside `onTick` would fork duplicate chains. Instead add a virtual
  `nextArrivalDelayMillis()` hook on `SimPlayerController` (base returns today's
  hard-coded value at each site) that `checkArrival`'s reschedule consults; the
  PvP combat lane overrides it to return `combatTickMillis` while a controller
  target is active, so the *existing* single chain simply ticks faster.
- **Dual-driver suppression via a *dynamically-swapped* combat AI map
  (Codex P1-1 + round-2 P1 fix).** This is the critical correction. `startCombat`
  sets the defender, which puts the agent in `FOLLOWING`
  (`AiAgentImplementation.cpp:3699`); `rootDefault` then runs its
  `TreeSocket(slot=MOVE)` (`default.lua:293`, gated on *not* PATROLLING) and the
  stock tree *keeps closing on the target*, fighting the controller's
  range-holding. A custom-map slot override is **static** for as long as the map
  is installed (`AiMap.h:313`), so baking a MOVE no-op into the existing `simPvp`
  map — or assigning it to members at spawn — would change behavior while the
  feature is *off* and would break members' out-of-combat FOLLOW (which relies on
  the stock MOVE socket). Instead define a **separate** `simPvpCombat` map
  (`{IDLE→idleSimPvp}, {MOVE→moveNoopSimPvp}`) and **swap it in only while
  engaged** via the proven runtime choreography — `setCustomAiMap(hash)` **plus
  `setAITemplate()`** (the field-set alone does not rebuild the trees; both are
  required, exactly as `SimPlayerManager.cpp:31075-31088` does), with the member
  `formationOffset` captured before and re-written after because `setAITemplate()`
  clears the blackboard (round-3 P1; see Implementation §2b): on target
  acquisition install `simPvpCombat` (controller becomes sole mover; weapon still
  fires via the untouched ATTACK/TARGET sockets); on teardown restore the base map
  (leader → `simPvp`, member → `0`). This makes the no-op genuinely combat-scoped,
  keeps the feature-off path byte-identical, and — because teardown restores the
  map — is also the missing piece of the runtime-disable rollback (round-1 P1-5).
  Both runtime edges are handled: false→true installs the combat map on the next
  engagement; true→false teardown restores the base map on **all** live bots.
- **Two-radius model.**
  - *Detection radius* (`combatApproachRadiusMeters`, default 100): pure distance
    filter, no LOS — this is the "PvP bots don't worry about LOS like regular
    NPCs" part. Replaces the fixed 64 m engage radius as the scan gate.
  - *Engage band* (per weapon): read the equipped weapon's own
    `getMaxRange()`/`getIdealRange()` (`WeaponObject.idl:250-270`,
    `CreatureObject::getWeapon()` `CreatureObject.idl:1822`). The bot **holds at
    `getMaxRange()`** — ranged bots naturally sit ~64 m apart (no stacking) and
    melee weapons, whose `getMaxRange` is a few metres, close in. This is the
    owner's chosen "weapon stock band" spacing. There is deliberately **no
    separate "stop short of max range" buffer** (round-2 P2): engagement fires as
    soon as `dist <= getMaxRange()` and movement stops, so a stop-short distance
    would never be reached and would be dead config. Thrash is prevented instead
    by a **re-approach hysteresis**: once holding, the bot only resumes approach if
    the target drifts beyond `getMaxRange()` by `reapproachHysteresisMeters`
    (mirrors the hunter's ½-range move-throttle at `SimHunterController.cpp:2724`).
    **Effective-range clamp (Codex round-1 P2 fix):** the base mover declares
    arrival at a fixed 4 m (`distSq < 16` at `SimPlayerController.cpp:1178`), so a
    weapon whose `getMaxRange()` is below 4 m (unarmed ≈ 3 m) could have the mover
    arrive at 4 m and never satisfy a `<= 3 m` engage test. Clamp the effective
    engage range to `max(getMaxRange(), arrivalToleranceMeters)` so short-range
    combatants engage on arrival. 5 m sabers engage at ≤ 5 m (mover arrives at
    4 m < 5 m — fine).
- **Engage/approach split** (mirrors `SimHunterController::runActiveTick`
  `SimHunterController.cpp:2323-2333`, `moveToTarget` `:2706`, `engageTarget`
  `:2864`):
  - target beyond weapon max range → **approach**: navmesh/cell-aware `moveTo`
    toward the target, re-issued only when the target moves ≥ ½ weapon range
    (the hunter's anti-thrash throttle, `:2724-2737`);
  - target within weapon max range **and** LOS clear
    (`CollisionManager::checkLineOfSight`, `CollisionManager.h:61`; in-cell uses
    `checkLineOfSightInBuilding`/`WorldToCell`, `:60,62`) → **engage**:
    `CombatManager::startCombat` + `setTargetObject` + `activateAiBehavior(true)`,
    then `state = IDLE` so the controller stops moving and lets the stock attack
    socket fire from the held position;
  - within range but **no LOS** → keep approaching (moving toward the target
    naturally rounds the obstacle / enters the cell and re-establishes LOS).
- **Anti-clip everywhere via a combat-scoped hybrid latch.** PvP travel legs
  (routed starport/collector runs) are verified-good and must stay byte-identical,
  so we do **not** flip global `usesNavmeshHybridMovement()`. Instead the combat
  approach leg sets a leg-scoped latch (same idea as the hunter's leg-scoped
  non-hybrid buff latch and `SimPlayerController.h:328 interiorApproachLeg`) that
  makes *only the approach `moveTo`* navmesh + cell-aware, reusing the existing
  P.6.5b cell-aware `moveTo` and F_0.4.7–F_0.4.11 cell entry/egress
  (`beginCellEgressIfNeeded`, `getNearestExteriorPortalPoint`). This is what stops
  the clipping and lets in-cell convergence work.
- **In-cell engagement.** Drop the outdoor-only guard in `scanForTargets`, gated
  by `combat.allowInCellEngage`; when the target is in a cell the approach uses
  the cell-aware path so bots enter through the portal, never through a wall.
- **Members participate (Codex P1-3 fix).** `SimPvpMemberController::assertFollow`
  bails on `isInCombat()` (`SimPvPController.cpp:1353`), but the **approach leg
  clears combat** before `moveTo` (movement and combat are mutually exclusive on
  the shared base), so `isInCombat()` alone would let `assertFollow` re-assert
  FOLLOW mid-approach and overwrite the member's own path. Suppress FOLLOW on a
  broader condition: a `combatEngageActive` latch that is true whenever the member
  holds a controller combat target **or** is mid-approach (not merely
  `isInCombat()`), cleared only on target teardown. `assertFollow` must early-out
  on that latch; FOLLOW resumes only after teardown. The member also needs the
  combat MOVE-slot no-op map (above) so its stock tree never closes.
- **Approach lane bounding (Codex P1-4 fix).** The existing `combatLeashMeters`
  (72 m) and P.6.5e stalemate break run **only while `isInCombat()`**
  (`SimPvPController.cpp:103`), so they cannot bound the approach leg (which
  clears combat). Add an **approach-specific** abandon rule on the controller-held
  target: give up the approach and resume the route if the target leaves
  `combatApproachRadiusMeters` **or** the approach exceeds `approachTimeoutMillis`.
  Constrain config so `combatApproachRadiusMeters >= currentWeaponEngageRange` for
  every weapon (i.e. detection radius must be ≥ the largest engage band) — a bot
  must be able to approach from beyond its own weapon range. The in-combat leash
  and stalemate break continue to bound the *holding/firing* phase unchanged.
- **Runtime-disable teardown (Codex P1-5 fix).** Flipping
  `controllerDrivenEngage` true→false at runtime must not strand a bot mid-combat.
  Detect the enabled→disabled edge in the config refresh and run a one-shot
  teardown per bot: clear the controller combat target, cancel the approach path
  and hybrid latch, clear the `combatEngageActive` latch, **restore the base AI map
  via the full `setCustomAiMap`+`setAITemplate` swap helper (blackboard preserved)
  if `simPvpCombat` was installed**, and hand control back to the role's normal flow
  (leader resumes its route leg; member resumes FOLLOW via `assertFollow`). Only
  then is "exact current behavior when disabled" actually
  true.
- **Convergence falls out for free.** With both squads scanning 100 m and pathing
  to the nearest enemy, "when the paths meet / when they're in range, the fight
  begins" is an emergent result of the local approach lane — no new manager
  convergence code is required. Existing `dispatchPvpConvergence` still handles
  getting squads into the same city.

## Implementation Details

### 1. Combat engage/approach lane on the bot controller

**File**: `src/server/zone/objects/creature/simplayer/SimPvPController.{h,cpp}`

**Current state**: `SimPvpBotController::scanForTargets` engages by setting combat
state + `state = IDLE` and defers movement to the stock tree; there is no
controller-side approach, LOS, or range logic. `onTick` runs the phantom-combat
guard, stalemate tracker, and `scanForTargets`.

**Modifications**:
- Add helpers on `SimPvpBotController` modelled on the hunter:
  - `float currentWeaponEngageRange()` — resolves `agent->getWeapon()`, returns
    `max(getMaxRange(), arrivalToleranceMeters)` (or `fallbackWeaponRangeMeters` if
    no weapon). There is **no** stop-short buffer — the bot engages/holds at this
    range directly; re-approach uses `reapproachHysteresisMeters` past it.
  - `bool hasCombatLineOfSight(target)` — `checkLineOfSight`, dispatching to the
    in-building/world-to-cell variant when either party is in a cell.
  - `void approachTarget(target)` — combat-scoped hybrid latch + cell-aware
    `moveTo` toward the target, throttled by ½-range movement (anti-thrash), with
    `disengageTarget`-style clearing of combat/movement before `moveTo` (movement
    and combat are mutually exclusive on the shared base — see
    `SimHunterController.cpp:2739-2744`).
  - `void engageHeldTarget(target)` — `startCombat` + `setTargetObject` +
    `activateAiBehavior(true)` + `state = IDLE`; only when in range **and** LOS.
  - `void driveCombatMovement()` — the per-tick decision: no target → scan;
    target dead/gone → clear; dist > range || no LOS → `approachTarget`; else
    `engageHeldTarget`.
- `scanForTargets`: change the distance gate from the fixed engage radius to
  `combatApproachRadiusMeters`; on a hit, record the target and hand control to
  `driveCombatMovement` instead of immediately `setCombatState`. Remove the
  `getParent() != nullptr` skip when `allowInCellEngage` is true (keep it as the
  default-off safety otherwise).
- `onTick`: after the phantom-combat/stalemate/posture handling, if a combat
  target is active call `driveCombatMovement()` and reschedule at the faster
  `combatTickMillis`; otherwise fall through to the existing scan + normal
  cadence. Keep the existing `combatLeashMeters` disengage and P.6.5e stalemate
  break intact — but note these run **only while `isInCombat()`**, so they bound
  the *holding/firing* phase only. The combat-cleared **approach** leg is bounded
  separately by the approach-specific abandon rule (radius + `approachTimeoutMillis`,
  see the "Approach lane bounding" architecture bullet), not by the in-combat leash.

### 2. Member controller combat participation

**File**: `SimPvPController.cpp` (`SimPvPMemberController::onTick`)

**Current state**: member `onTick` calls the base scan + `assertFollow`; the
member "never calls `moveTo`" (`SimPvPController.h:252`) and the stock tree drives
it in combat.

**Modifications**: in `onTick`, when the member has/acquires a combat target,
call the shared `driveCombatMovement()` (approach/engage against its own target)
before `assertFollow`. Add a `combatEngageActive` latch (true from acquisition
through teardown, spanning the combat-cleared approach leg) and make
`assertFollow` early-out on it (Codex P1-3) — the `isInCombat()` guard alone is
insufficient because approach clears combat. FOLLOW resumes only after teardown.
Optional spacing refinement: when multiple squadmates target the same enemy, fan
their stop points by `memberIndex` around the target (reuse the P.6.2c
`pvpFormationOffset` helper) so melee attackers ring the enemy instead of
stacking — include only if it stays trivial.

### 2b. Dynamically-swapped combat AI map (dual-driver suppression)

**Files**: `bin/scripts/ai/simPvp.lua` (modify — add the no-op MOVE tree),
`bin/scripts/ai/templates.lua` (modify — register the new `simPvpCombat` map and
bind its MOVE slot), and the runtime swap in `SimPvPController.cpp` /
`SimPlayerManager.cpp`.

**Current state**: `templates.lua:51` registers `simPvp = {IDLE→idleSimPvp}`;
custom-map slots override statically for as long as the map is installed
(`AiMap.h:313`). Leaders run `simPvp`; members run `customAiMap 0` + FOLLOW
bitmask. In combat the stock `rootDefault` MOVE socket closes on the defender
(`default.lua:293`).

**Modifications**:
- Define `moveNoopSimPvp` (a trivial `AlwaysSucceed`/`Wait` tree) in `simPvp.lua`.
- Register a **new** map in `templates.lua`:
  `{ "simPvpCombat", { {IDLE, "idleSimPvp"}, {MOVE, "moveNoopSimPvp"} } }`. This is
  used *only while engaged*, so the existing `simPvp` map and member map `0` are
  byte-unchanged when the feature is off (fixes the round-2 static-override P1).
- **Swap requires BOTH `setCustomAiMap` and `setAITemplate` (round-3 P1).**
  `setCustomAiMap()` only assigns the field (`AiAgent.idl:1704`); the behavior
  trees are not rebuilt until `setAITemplate()` runs (`AiAgentImplementation.cpp:5213`),
  which is exactly why the proven spawn code at `SimPlayerManager.cpp:31075-31088`
  calls **both** (plus `clearPatrolPoints`). Reuse that exact choreography. But
  `setAITemplate()` does `blackboard.removeAll()` (`:5215`), so the swap **wipes
  the blackboard** — including the member `formationOffset` that the spawn code
  re-writes right after. Therefore the swap helper must, on each transition:
  capture the required PvP blackboard values first (member `formationOffset`; audit
  for any other PvP keys the controllers read), call
  `setCustomAiMap(hash) + setAITemplate()`, then **re-write** the captured values —
  mirroring `SimPlayerManager.cpp:31075-31088` precisely. Do **not** call
  `clearPatrolPoints` on the combat-acquire swap (the controller may hold an
  approach path); do clear as appropriate on teardown to match the base flow.
- On combat acquisition (leader **and** member) swap to `simPvpCombat`; on
  teardown restore the base map (`"simPvp"` for a leader, `0` for a member) via the
  same both-calls-plus-blackboard-restore helper. This makes the MOVE no-op
  genuinely combat-scoped and the controller the sole mover in combat.
- **Churn is bounded to combat enter/exit transitions only** (not per tick). Note
  this on the verification checklist — watch for any instability from the extra
  `setAITemplate` rebuilds under heavy bot-vs-bot churn; if problematic, fall back
  to a conditional blackboard-gated MOVE tree (no rebuild) as a follow-up.
- Handle **both runtime edges** for all live bots: false→true means the acquire
  swap simply happens at the next engagement; true→false teardown restores each
  live bot's base map (via the same helper, blackboard preserved) — shared with the
  disable-teardown edge in Implementation §4.
- Verify the no-op MOVE does not affect the controller's own
  `findNextPosition`/travel movement (it does not for `simMiner`, which no-op'd
  the entire root) — required build/live check.

### 2c. Virtual tick-cadence hook on the base controller

**File**: `SimPlayerController.{h,cpp}`

**Current state**: `checkArrival()` calls `onTick()` then schedules the next
`ArrivalCheckTask` with hard-coded `schedule(1000)`/`schedule(500)` at several
sites (`:1063,:1077,:1145,:1161,:1297,:1391`).

**Modifications**: add `virtual uint32 nextArrivalDelayMillis(uint32 defaultMs)`
returning `defaultMs` in the base; replace the hard-coded reschedule constants
with `nextArrivalDelayMillis(1000)` (etc.) so behavior is byte-identical for all
existing controllers. `SimPvpBotController` overrides it to return
`combatTickMillis` while a controller combat target is active. This gives the PvP
combat lane a faster cadence on the **existing single chain** with no duplicate
tasks (Codex P1-2).

### 3. Config surface (Lua, default-off)

**File**: `bin/scripts/managers/sim_player_manager.lua` (`pvpConfig`)

Add a new nested block (all C++ defaults off / conservative):
```
combat = {
    controllerDrivenEngage = false,   -- master gate for the whole rework
    approachRadiusMeters   = 100,     -- radius-only detection + approach start
                                      --   (clamped up to >= largest engage band)
    reapproachHysteresisMeters = 8,   -- resume approach only if target drifts this
                                      --   far past maxRange (anti-thrash)
    arrivalToleranceMeters = 4,       -- effective engage range floor (>= base 4m
                                      --   mover) so sub-4m weapons engage (P2)
    approachTimeoutMillis  = 15000,   -- abandon approach if not closed in time (P1-4)
    losGateDamage          = true,    -- require LOS before startCombat
    allowInCellEngage      = true,    -- drop the outdoor-only scan guard
    combatTickMillis       = 500,     -- faster tick cadence while engaging (P1-2)
    fallbackWeaponRangeMeters = 64,   -- used if getWeapon() is null
    logCombatMovement      = false,   -- verbose approach/engage/LOS logging
},
```
**Per-field zero semantics (round-2 P2).** The project's zero-preserving parse
("raw 0 = off") is *not* blanket-applied here — each field's zero is defined and
clamped explicitly: `combatTickMillis = 0` means "use the normal arrival cadence"
(the override is skipped, never a 0 ms schedule), and any positive value is
floored to a safe minimum (e.g. 100 ms); `approachRadiusMeters` and
`arrivalToleranceMeters` are clamped to positive minimums (a 0 there is invalid,
not "off") with `approachRadiusMeters` additionally raised to at least the largest
weapon engage band; `approachTimeoutMillis`/`reapproachHysteresisMeters` treat 0
as "disabled" for that specific guard. The only true master gate is
`controllerDrivenEngage`.

Refreshed every `maintenanceIntervalSeconds` like the rest of `pvpConfig`, so
every knob applies at runtime without a restart. When
`controllerDrivenEngage = false` the controller keeps the exact current behavior
(fixed engage radius, stock-tree movement, outdoor-only) — the whole feature is
inert until flipped.

## Technical Considerations

- **Pattern Usage**: This is a direct specialisation of the live-proven
  `SimHunterController` combat model — `runActiveTick`'s in-range→engage /
  out-of-range→moveToTarget split, the ½-range anti-thrash throttle, the
  `startCombat` + `activateAiBehavior(true)` firing handoff, and the leg-scoped
  hybrid latch. Reuse, do not reinvent.
- **Locking & References**: Match the existing PvP choreography exactly. Engage
  takes `Locker(agent)` then `Locker cross(target, agent)` (already the shape at
  `SimPvPController.cpp:300-301`); `startCombat` under `Locker(agent)` as the
  hunter does (`:2886`). Targets held via `ManagedReference`, resolved through
  `ZoneServer::getObject` before use (hunter `targetIsLive` pattern). Never hold
  `pvpSquadMutex` while locking an agent. **Single-threaded onTick lane
  specifically avoids the cross-thread target-state hazard** (ARCHI §12 hunter
  single-writer rule) — there is no second combat thread to race.
- **IDL Impact**: None. `getWeapon()`, `WeaponObject::getMaxRange/getIdealRange`,
  and `CollisionManager::checkLineOfSight*` are all existing native APIs; no
  `.idl` changes, no `src/autogen/` regen.
- **C++ vs Lua Placement**: Movement/LOS/range decisions are per-tick and
  perf-sensitive → C++ in the controller. All thresholds and gates → Lua
  `pvpConfig.combat`, default-off, per project standard.
- **Gating & Simulation-Only**: Whole feature gated behind
  `combat.controllerDrivenEngage = false`. PvP bot-vs-bot combat is *already*
  real `CombatManager` combat within the owner-approved PvP scope; this plan
  changes **movement and engagement gating only** and mutates **no**
  inventory/credit/market/persistence state — it stays inside the existing
  approved PvP combat boundary.
- **Dashboard Visibility**: New `pvpActivity.combatEngagement` section (item 5) is
  the primary verification surface; the starport diagnostic (item 6) answers the
  open scout-vs-squad question.
- **Live Verification Plan**: Restart (owner's call), flip
  `controllerDrivenEngage = true` at runtime, then on the live dashboard confirm:
  ranged squads hold ~weapon-max-range apart (no 2 m stacks), `losBlockedAttacks`
  is non-zero only transiently (bots reposition and it clears),
  `inCellEngagements` climbs when squads meet at an indoor collector with **zero**
  clip-through (spot-check positions via `/v1/object/{oid}`), two converging
  squads produce a clean "paths meet → fight" without the old stalemate statues,
  and the starport diagnostic shows full squads traversing interiors like scouts.
  Watch death/reform churn vs the P.6.5e baseline.
- **Edge Cases**: no equipped weapon (`getWeapon()` null → fallback range); target
  leaves the 100 m bubble mid-approach (**approach-specific** abandon —
  `approachRadiusMeters` + `approachTimeoutMillis` — then route resume; the
  in-combat leash does not apply during the combat-cleared approach); target enters
  a cell the bot cannot path into (cell-egress bounded retry + safe outdoor
  recovery, already present); LOS never establishes so combat never starts
  (approach-timeout abandons it) vs LOS lost mid-fight while already engaged
  (in-combat `combatLeashMeters` + P.6.5e stalemate break bound the holding phase);
  member's target dies while leader's lives (per-bot independent target state); a
  bot knocked down (existing posture reset at `:203`).

## Type Definitions

No new IDL/distributed-object types. New plain C++ members on the controllers

## Performance & Cost Impact

- LOS raycasts (`checkLineOfSight`) run only for a bot's *single active target*
  and only when it is already within weapon range — bounded to ~O(active
  combatants), not O(close objects). With the current ~20–30 PvP bots this is
  negligible.
- Faster `combatTickMillis` cadence applies only while a bot is actively engaged,
  not squad-wide idle time.
- The ½-range moveTo anti-thrash throttle (hunter's proven fix) prevents per-tick
  path re-issue under pathfinder latency.

## Backward Compatibility

Fully backward compatible. With `controllerDrivenEngage = false` (the shipped
default) every code path keeps the current behavior: fixed engage radius,
stock-tree combat movement, outdoor-only targeting, members on plain
FOLLOW/`customAiMap 0`, and base `nextArrivalDelayMillis` returning today's
constants byte-for-byte. No migration, no persisted state change. Runtime
reversibility is *explicit*, not incidental: the enabled→disabled edge triggers
the one-shot per-bot teardown (clear combat target, cancel approach + hybrid
latch + `combatEngageActive`, resume route/FOLLOW) so a flip-off never leaves a
bot mid-approach (Codex P1-5).
