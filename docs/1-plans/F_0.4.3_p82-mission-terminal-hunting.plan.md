# P.8.2 PvE Mission-Terminal Hunting (Player-Mimetic Reliable Spawns) Implementation Plan

## Overview

Live verification of P.8.1c/d proved hunters now dispatch and travel, but they
never complete a kill: they reach the hunt ground and rely on **static city
spawns**, which are unreliable and too far (observed: nearest womprat ~100m vs
the 96m scan radius), so `scanForTarget` never locks. This slice makes hunting
**player-mimetic and reliable**: a hunter runs to a real **mission terminal**,
the manager constructs a **bot destroy-mission** for the hunter's species and
spawns a **real lair/creature pack** (via `CreatureManager::spawnLair`) at a
mission point, the hunter runs out to it and **pulls one creature at a time**
(respecting social/pack aggro), kills, harvests (sim loot), and the lair is
cleaned up. It spawns a genuine SWG **lair** (`CreatureManager::spawnLair`, the
same real creature packs the world uses) without giving `AiAgent` bodies player
`mission_bag`/`datapad` slots or dragging a persistent mission graph.

## Problem Statement

- `SimHunterController::HUNTING` scans `getCloseObjects()` for a species-matching,
  attackable creature within `scanRadiusMeters` (96m). Static presence spawns
  scatter creatures beyond that and the kreetle ground produced **0** spawns —
  so hunters patrol without ever locking (`targetOid=0` for 12+ min, verified
  live 2026-07-17).
- The real player path (`MissionManager::handleMissionAccept`) requires
  `mission_bag` + `datapad` slots that `AiAgent` hunter bodies don't have, so a
  literal player mission flow is not directly usable.

## Solution Architecture

Owner decisions (2026-07-17): **bot-mission-spawn** reusing the real lair (spawn
the genuine SWG lair pack directly via `CreatureManager::spawnLair`), **with an
observable terminal-visit leg** (the hunter physically runs to a real in-city
mission terminal first, so the whole player-mimetic loop is watchable in-game).
Real combat vs real creatures, **simulated loot** (same posture as Phase 2).

New hunter phase flow (extends the existing `SimHunterController` machine):
`IDLE_HOME → ANNOUNCE_JOB → BUFF_UP → TRAVEL_TO_TERMINAL` (run to the nearest
city mission terminal) `→ ACCEPT_MISSION` (dwell at the terminal; manager spawns
the species lair at a mission point in nearby wilderness) `→
TRAVEL_TO_LAIR` (run to the lair) `→ HUNTING` (scan the now-close pack, pull one
at a time) `⇄ RETREAT` (existing) `→ DELIVER/harvest → MISSION_CLEANUP` (despawn
the lair) `→` repeat or `TRAVEL_HOME`. Death → existing `CLONE_HOME`.

Species→lair mapping is config: each `pveConfig.species` entry gains a
`lairTemplate` (e.g. womprat → `tatooine_womprat_lair_neutral_small`, kreetle →
`tatooine_kreetle_lair_neutral_small`), so the manager spawns exactly the
target creature — this also **fixes the kreetle 0-spawn issue** (reliable lair
instead of static spawns).

The lair is spawned **directly** via `CreatureManager::spawnLair(lairTemplateCrc,
difficulty, buildingLevel, x, z, y, size)` (returns the `LairObject`, exact
placement, persistence-level-0/non-persistent) at a chosen mission point — no
`MissionObject`/`DestroyMissionObjective`/`MissionSpawnActiveArea` and thus no
player-gated area-enter and no persistent mission graph to own (see §2, which
also resolves why the objective path is unsuitable for a bot). The "mission"
framing is the *observable* behavior (the hunter visits a real terminal); the
spawn itself is the genuine lair pack placed deterministically.

Everything is **gated** behind a new `pveConfig.missionHunt.enabled` flag
(default **false**, its own gate — see §4) and is **simulation-only** for loot.

## Implementation Details

### 1. Mission-terminal resolver (nearest terminal per city)

**File**: `SimPlayerManager.{h,cpp}`

**Current state**: `allShuttleports` is loaded at boot (`~:6533`) by scanning
travel points; there is no mission-terminal registry.

**Modifications**:

- Enumerate **mission terminals** (`isMissionTerminal()` tangibles) per
  city/planet into an `allMissionTerminals` registry (planet, city, world
  position). **Populate lazily on a post-load maintenance pass with PER-CITY
  retry (Codex P2)** — world objects may not exist yet at Lua-config load, and
  cities load at different times, so retrying only until the *global* registry is
  non-empty would stop after the first city resolves and leave the rest
  permanently unresolved. Track a **per-configured-city resolution state**
  `pending | resolved | absent` (a `VectorMap<cityKey, state>`): `pending` until
  the city's zone/region is ready and scanned; `resolved` once ≥1 terminal is
  found (stored in `allMissionTerminals`); `absent` if, after the city IS ready
  and scanned, no `isMissionTerminal()` exists (stop retrying it). Re-attempt
  each maintenance tick only for `pending` cities (readiness-guarded).
- **Shared state transitions only via scan** (Codex): the shared
  `missionTerminalCityState` moves `pending → resolved` (≥1 terminal found) or
  `pending → absent` (city ready AND scanned, none found). **A hunter's wait
  timeout never mutates the shared state** — otherwise a merely-slow city would
  be marked `absent` permanently and discovery would stop.
- **Lookup + one fallback per state** (city-scoped
  `getNearestMissionTerminal(planet, city, fromPos)`): `resolved` → return the
  city's nearest terminal; `pending` → the hunter **defers** in a pre-terminal
  wait, and only **that hunt** (after `terminalResolveWaitCycles`) takes the
  adjacent-spawn fallback while the shared city stays `pending` (still retried);
  `absent` → **skip the terminal leg** and spawn the lair at a hunt-ground-
  adjacent mission point. Adjacent-spawn is the single documented no-terminal
  fallback (no nearest-on-planet variant) — Edge Cases agrees.
- Held via `Reference` (not `ManagedReference`) like the PlanetTravelPoint
  registry, snapshot under the existing config mutex.

### 2. Bot lair spawn via `CreatureManager::spawnLair` (no mission-object graph)

**File**: `SimPlayerManager.cpp` (new helper `spawnPveHuntLair(...)`) reusing
`CreatureManager::spawnLair`.

**Current state (why the direct API, Codex P1×3)**: the `DestroyMissionObjective`
path is unsuitable for a bot: `spawnLair()` returns `void`, randomizes the final
position, and exposes neither the lair nor the spawn area; and a real
destroy-mission drags a **persistent** object graph (mission + waypoint +
`MissionSpawnActiveArea` + observer) whose enter-trigger is player-gated. Instead
use the lower-level `CreatureManager::spawnLair(uint32 lairTemplateCrc, int
difficultyLevel, int lairBuildingLevel, float x, float z, float y, float size)`
(`CreatureManager.idl:59`, impl `:86`) which **returns the `LairObject`**, places
it at an **exact** position, and creates it at **persistence level 0
(non-persistent)** — so we get the lair OID/position, control placement, and
nothing survives a restart to orphan.

**Modifications**:

- Add `spawnPveHuntLair(bodyOid, species, missionPos)`: resolve
  `species.lairTemplate` → hashcode; call `CreatureManager::spawnLair(crc,
  species.missionDifficulty, species.lairBuildingLevel, missionPos.x,
  missionPos.z /*height*/, missionPos.y /*north*/, species.lairSize)` (note the
  API's `(x, z, y)` order — z is height, y is north). Capture the returned
  `LairObject*`.
- **Manager owns the lair's lifecycle (Codex P2):** `spawnLair` sets
  `setDespawnOnNoPlayersInRange(true)` (`CreatureManagerImplementation.cpp:~148`),
  and hunters are not player creatures — so a human observer entering then
  leaving could trigger the stock 5-minute despawn and vanish the lair out from
  under the manager. Immediately after spawn, **lock the returned lair and
  `setDespawnOnNoPlayersInRange(false)`** so only the P.8.2 cleanup/janitor (§5)
  destroys it.
- Record a `PveHuntLair` (identityId, bodyOid, **lairOid**, speciesKey, planet,
  x/y/z, spawnedAtMs, alive) in a `pveMutex`-guarded registry; **one active lair
  per hunter**, global cap `maxActiveLairs`. No `MissionObject`/waypoint/spawn
  area is created, so there is no extra persistent graph to own.
- `missionPos`: a point a short run from the terminal/hunt ground (config
  `missionSpawnDistanceMeters`), chosen with a **proper spawnability check**
  (§2a below), not just water/boundary.

**2a. Spawnable-point selection (Codex P2)**: pick `missionPos` via bounded
candidate retries (config `maxSpawnPointTries`), each validated by
`PlanetManager::isSpawningPermittedAt` (world-region/no-build/city exclusion),
**outside city regions** (a lair must not spawn inside the city around the
terminal), on land (the existing `isOverlandPointInWater`/terrain-height guards),
with basic collision clearance. If no candidate qualifies, skip the spawn this
cycle and log (hunter re-tries next cycle).

### 3. Hunter phase machine: terminal + lair legs

**File**: `SimHunterController.{h,cpp}`

**Current state**: phase machine `IDLE_HOME→ANNOUNCE_JOB→BUFF_UP→TRAVEL_OUT→
HUNTING⇄RETREAT→…`; `HUNTING` scans `getCloseObjects()` (`:612`) and
`moveToPatrolPoint`s when no target.

**Modifications**:

- Add phases `TRAVEL_TO_TERMINAL`, `ACCEPT_MISSION`, `TRAVEL_TO_LAIR`,
  `MISSION_CLEANUP`. `TRAVEL_OUT` is replaced/retargeted: instead of walking to
  the static hunt ground, the hunter routes to the nearest mission terminal
  (§1), dwells briefly ("accept"), the manager spawns the lair (§2), then it
  routes to the lair position and enters `HUNTING`.
- `HUNTING` now scans near the **lair** (targets are close and reliable, so the
  existing `scanForTarget`+`moveToTarget`+`engageTarget` works). **Pull-one-at-
  a-time**: acquire/engage a single creature and hold until it dies before
  scanning for the next; do not body-pull the whole lair. **Social/pack aggro
  (Codex P2):** detect a herd/pack target via the target `AiAgent`'s
  `getSocialGroup()` (a `String` — nonempty ⇒ social) or its
  `getCreatureTemplate()->isHerd()`; count `adds` = the hunter's
  `getDefenderList()` size. If `adds > maxSimultaneousAdds`, take the **existing
  RETREAT path** (break off, heal HAM); if adds stay over the cap for
  `addsAbandonCycles`, **abandon** the lair (§5 cleanup + re-mission) rather than
  dying to the pack.
- Remove the temporary non-functional `scanForTarget` agent-logger diagnostic;
  route any retained controller diagnostics through
  `SimPlayerManager::instance()->info(...)` (confirmed to reach `core3.log`;
  `AiAgent->info` does not).
- Reuse existing travel primitives (`moveTo`/overland) and the active-tick
  cadence.

### 4. Species config (lair mapping + tuning)

**File**: `MMOCoreORB/bin/scripts/managers/sim_player_manager.lua`

- Each `pveConfig.species` entry gains `lairTemplate` (e.g.
  `tatooine_womprat_lair_neutral_small`, `tatooine_kreetle_lair_neutral_small`),
  `missionDifficulty`, `lairBuildingLevel`, and `lairSize` (the `spawnLair` size
  arg; validated to a sane range, default 20 as the API default). New
  `pveConfig.missionHunt`
  block: **`enabled = false`** (its OWN gate; both the Lua default and the C++
  default are explicitly `false` — Codex P2), `missionSpawnDistanceMeters`,
  `maxSpawnPointTries`, `maxSimultaneousAdds`, `addsAbandonCycles`,
  `terminalDwellSeconds`, `terminalResolveWaitCycles` (default e.g. 10 — how long
  a hunt waits on a `pending` city before the adjacent-spawn fallback),
  `lairTimeoutSeconds`, `maxActiveLairs`.
- **Gate contract:** mission-terminal hunting is active iff
  `missionHunt.enabled` (independent of, and additional to, the PvE hunter
  enablement that already dispatches hunters). Off ⇒ no terminal legs, no lair
  spawns, hunters keep today's behavior.

### 5. Lair lifecycle / cleanup

**File**: `SimPlayerManager.cpp`

- On hunt completion (kill quota met), hunter death/abandon, or lair timeout,
  **destroy the lair** via a queued task: resolve `lairOid` →
  `lair->destroyObjectFromWorld(true)` (the lair despawns its own child
  creatures), then drop the `PveHuntLair` record. Because the lair is
  **persistence-level-0 (non-persistent)** there is no `destroyObjectFromDatabase`
  needed and no cross-restart orphan — a restart simply loses the transient
  lairs. A bounded in-memory janitor (miner-recovery pattern) still sweeps
  timed-out/records-without-live-lair each maintenance tick so nothing lingers
  in-session; `maxActiveLairs` caps concurrent spawns. Destruction runs off the
  hunter tick, never holding `pveMutex` across the zone mutation.

### 6. Dashboard visibility

**File**: `SimPlayerManager.cpp` `pveActivity`

- Extend the roster/hunt rows with the mission-hunt state: current phase
  (incl. new phases), terminal target (planet/pos), lair position + lair OID +
  lair alive?, adds engaged, and counters `missionLairsSpawned`,
  `missionLairsCleaned`, `hunterKillsTotal` (existing). Keep the live body
  position (P.8.1d) so the owner can watch each leg.

## Technical Considerations

- **Pattern Usage**: reuse `CreatureManager::spawnLair` + `LairTemplate`
  (genuine lair spawn), the shuttleport/ticket-collector resolver pattern (PvP
  squads) for terminals, and the existing `SimHunterController`
  travel/combat/harvest loop.
- **Locking & References**: `spawnLair` locks the created lair internally
  (`Locker blocker(building)`); the manager captures the returned `LairObject`
  reference and, for teardown, locks the lair and `destroyObjectFromWorld(true)`
  off the hunter tick via a queued task — never holding `pveMutex` across the
  zone/object mutation. This is the P.4.4-class risk area (ARCHI.md §5), so the
  spawn/cleanup sequence mirrors existing `spawnLair` callers exactly and the
  `PveHuntLair` registry mutation stays under `pveMutex` separately from the
  object mutation.
- **IDL Impact**: none — `CreatureManager::spawnLair` (`CreatureManager.idl:59`)
  and `LairObject` already exist; we call the existing native method, add no IDL
  fields, and create no persistent object graph.
- **C++ vs Lua Placement**: spawn/terminal/lifecycle logic in C++ (object
  lifecycle, perf); species→lair mapping and all tuning in Lua.
- **Gating & Simulation-Only**: gated behind `pveConfig.missionHunt.enabled`
  (its own flag, default **false** in both C++ and Lua); off ⇒ hunters keep
  today's (non-killing) behavior.
  Loot stays simulated (typed `pve_hunter` harvest from P.8.1d); real creatures
  are really killed (that is the point), but no real loot/credit/inventory
  mutation.
- **Dashboard Visibility**: new mission-hunt fields under `pveActivity` are the
  acceptance surface.
- **Live Verification Plan**: with the gate on, restart and watch (dashboard +
  in-game at the live `posX/posY`): (1) hunter routes to a real mission terminal;
  (2) a species lair spawns at the mission point (`missionLairsSpawned`↑, lair
  OID + pos on dashboard); (3) hunter runs to it, **pulls one creature**, kills
  (`hunterKillsTotal`↑), harvests (`hunterHarvestUnitsTotal`↑ as `pve_hunter`,
  `familySupply(meat)` climbs); (4) lair cleaned on completion
  (`missionLairsCleaned`↑, no orphans); (5) kreetle hunter now also spawns+kills
  (0-spawn issue fixed); (6) `familySupply(meat)` self-limits at the ceiling
  (P.8.1c/d loop closes end-to-end).
- **Edge Cases**: city `absent` (no terminal after ready+scanned) → skip
  terminal leg, hunt-ground-adjacent spawn (log); city `pending` → hunter defers
  up to `terminalResolveWaitCycles` then THAT hunt takes the adjacent-spawn
  fallback while the shared city stays `pending` (keeps retrying — a slow city is
  never marked absent by a hunter timeout); lair spawn position in water/out-of-bounds
  (retry via terrain guard, else skip); social/pack aggro pulling multiple adds
  (retreat when HAM<threshold; `maxSimultaneousAdds`); hunter dies mid-lair
  (clone path + lair cleanup); server restart with a live lair (no persistent
  orphans — level-0/non-persistent lairs are simply gone after restart, registry
  starts empty); `maxActiveLairs` reached (defer new spawns); observer-driven
  despawn suppressed via `setDespawnOnNoPlayersInRange(false)` (§2).

- New `SimHunterController` phase enum values: `TRAVEL_TO_TERMINAL`,
  `ACCEPT_MISSION`, `TRAVEL_TO_LAIR`, `MISSION_CLEANUP`.
- `MissionTravelLocation`-style `struct` for `allMissionTerminals` (planet, city,

## Performance & Cost Impact

- Terminal enumeration is a post-load per-city retry (bounded, only for
  `pending` cities, then it stops). Per hunter: at most
  one active lair (real spawn cost, bounded by `maxActiveLairs` ≤ hunter count);
  the lair's own creatures use the stock AI already budgeted for wildlife.
  Spawn/cleanup are queued off-tick, O(1) per transition. No new per-tick
  population-scale work.

## Backward Compatibility

- Gated by `pveConfig.missionHunt.enabled`; off ⇒ hunters keep the current
  (dispatch-but-don't-kill) behavior and no lairs spawn. No IDL/schema change.
  Lairs are runtime-only (persistence level 0) — nothing persists across a
  restart, so there is no boot reconciliation to do; the in-session janitor only
  sweeps timed-out records. P.8.1c/d unaffected (fold into the same release).
