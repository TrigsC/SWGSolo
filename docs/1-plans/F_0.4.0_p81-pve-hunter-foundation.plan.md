# P.8.1 PvE PlayerBot Foundation — Identity Roster + Solo Hunt Loop

## Overview

First slice of P.8, the PvE PlayerBot program (owner vision 2026-07-15):
persistent, named, profession-bearing bots whose activity is driven by the
real economy but expressed as *individual* agency — a lived-in world instead
of squads walking A→B. This plan ships the foundation: (1) a **persistent
identity roster** so players see the same named bots across restarts; (2) a
**solo hunt loop** — a hunter bot takes a creature-resource job generated
from real economy demand, gets buffed at its home city's cantina/med
center, travels to hunt grounds, kills real creatures, ledgers a simulated
harvest, and comes home announcing its results; (3) a **P.8.0 combat spike**
(diagnostics-only, ships first inside this release) proving a sim bot can
engage wild creatures before any behavior depends on it. Group content
(ask-for-group at hubs, boss hunts), doctor/entertainer service bots, and
deeper player interaction are P.8.2+ — mapped in a new design doc this plan
creates. PvP squads are untouched.

Owner decisions (2026-07-15 discovery):
- **V1 slice**: identity + solo hunt loop; groups are P.8.2.
- **Persistence**: lightweight identity roster (bodies respawn and reattach),
  not full object persistence.
- **Coordination**: manager as matchmaker, every handshake acted out
  in-world with real timing (players can overhear and interject) — no
  pretend message-passing purity, no invisible hive teleports of knowledge.
- **Realism**: real combat against real creatures (PvP bots and Jedi already
  fight for real); loot/rewards stay simulation-only per standing policy.

## Problem Statement

- Sim bots today are **transient**: reforms/respawns mint fresh names every
  few minutes (12.3h soak: 71 reforms). No identity survives a restart, so
  the world can never feel populated by *people*.
- All purposeful behavior is either resource mining (miners) or faction
  patrol (PvP squads). Nothing hunts, nothing consumes the buff economy,
  nothing expresses the crafting economy's demand for **creature resources**
  (hide, bone, meat — the classes the P.5 hive/demand layer already tracks
  but nothing gathers).
- The hive is visible: coordination happens instantly and invisibly.
  Owner wants decision-making expressed through in-world, observable acts.
- Unknown engine fact (must be proven before building on it): can a
  SimPlayer AiAgent initiate and sustain combat against a wild creature
  AiAgent (aggro back, damage both ways, death/loot paths sane)? PvP bots
  fight bots/players via faction+OVERT; creature targets are a different
  attackability path.

## Solution Architecture

### P.8 phase map (recorded in the new design doc; this plan = P.8.0 + P.8.1)

- **P.8.0** — PvE combat spike (diagnostics-only, in this release).
- **P.8.1** — identity roster + solo hunt loop (this plan).
- **P.8.2** — group content: in-world ask-for-group at hub cities, group
  assembly via the P.6.3c mechanics, boss-class hunts (geo cave, krayt,
  nightsisters), shared-reward ledger.
- **P.8.3** — service professions: doctor/entertainer bots giving REAL buffs
  at med centers/cantinas (replacing P.8.1's self-applied buff package),
  paid via simulated tips.
- **P.8.4** — player interaction depth: trade windows, richer chat, bots
  answering player asks.
- **P.8.5** — miner identity migration (miners join the roster; same names
  forever) + population scale-up.

### P.8.0b — PlayerBot world presence (flag-gated core patches; OWNER
DECISION 2026-07-15 after spike v1)

Spike v1 ran and returned FAIL/timeout with `targetOid=0` — proving the
foundational world fact cheaply: **Core3's wilderness is empty without
players.** Spawn areas populate on player movement, creature AI wakes on
player proximity, and spawned agents despawn without players in range. The
owner's direction: bots must BE players to these systems ("things should
spawn around this entity as if it is a player... These should basically be
players, just PlayerBots") — a nightsister hunt must cause nightsisters,
with no stage-managed lairs. Three surgical, flag-gated core patches
(P.6.3c precedent — guarded relaxations at the exact check sites, inert
when off):

1. **`SpawnAreaImplementation::notifyPositionUpdate/notifyEnter/notifyExit`**
   (:30/:61/:75): accept a "sim presence" creature wherever
   `isPlayerCreature()` is required. Predicate (ordered for hot-path cost,
   and NOTE the `ObjectFlag::PLAYER` bit alone cannot express per-class
   opt-in — every sim bot carries it): `isPlayerCreature()` short-circuits
   real players first; otherwise require the feature flag AND the PLAYER
   presentation bit (cheap pre-filters that exclude every wild creature)
   AND membership in the manager's **presence-OID set** — a small
   manager-owned set containing ONLY opted-in bodies (v1: hunter bodies +
   the spike bot), mutated under `pveMutex` at spawn/despawn and READ via a
   published immutable snapshot swapped on mutation, so zone threads never
   take a manager mutex. Only PLAYER-flagged AiAgents (our ~dozens of
   bots) ever reach the set lookup.
   `tryToSpawn(player)` internals get a ghost-null audit first (P.6.3c
   crash lesson: player-centric paths deref the ghost — every such site on
   this path needs the same null-guard the chat room fix got).
2. **`AiAgentImplementation` players-in-range accounting** (~:4228 increment
   / ~:4416 decrement): presence bots count toward
   `numberOfPlayersInRange` and trigger `activateAiBehavior()` — spawned
   creatures wake up for bots and stop insta-despawning around them.
3. **Presence assignment**: opt-in per bot class via the manager's
   presence-OID set (v1: hunter bodies + the spike bot only; miners/PvP
   squads keep presence OFF until separately approved — density around
   cities is a tuning decision, and the master flag kills everything at
   runtime).
4. **Presence lifecycle balance (increment/decrement symmetry)**: area
   exits and disappear notifications are QUEUED tasks
   (GroundZoneComponent.cpp:443 → ActiveAreaEvent), so eligibility must be
   STABLE across a counted body's whole world lifetime or counts leak
   (an exit evaluating after membership revocation skips its decrement and
   pins the area/creature at players-present forever). Contract:
   (a) membership is published BEFORE the body is inserted into the world;
   (b) membership removal happens only AFTER world removal, and entries
   carry a REMOVAL GRACE (~10s) during which the predicate still accepts
   them — queued exit/disappear events evaluate inside it; (c) runtime
   disable is a DRAIN: despawn all presence bodies first (exits fire while
   still members), then clear membership after the grace — the existing
   disable-despawn path gains this ordering; the master flag is consulted
   only through the published snapshot so flag flips cannot desync
   individual evaluations.
5. **Spawn attribution**: `tryToSpawn` on a SUCCESSFUL lair spawn whose
   triggering creature is a presence bot calls a manager hook
   (`recordSimPresenceSpawn(oid)`) incrementing a per-OID counter map
   (under `pveMutex`) plus a global total — dashboard-visible, and the
   spike consumes it as a DELTA scoped to its own bot's OID (baseline
   snapshotted at AWAITING_WORLD entry), so unrelated player activity can
   never falsely prove bot-triggered spawning.

Density note (recorded, not solved here): every presence bot carries a
player's spawn-trigger cost. v1's 6 hunters are negligible; the
thousand-bot future needs its own density budget pass (dashboard counters
for spawns-triggered-by-bots ship now so that conversation has data).

### P.8.0 — combat spike (diagnostics-only, gated; v2 after the owner's presence decision)

Mirrors P.6.5-0's instrument-first pattern, but combat is ASYNCHRONOUS, so
the spike is a small persisted state machine, not a synchronous one-shot.
`PveSpikeState` (manager member under `pveMutex`): phase
SPAWNING → AWAITING_WORLD → ENGAGING → OBSERVING → DONE; spawn timestamp;
`spawnBaselineCount` + `spawnsTriggeredNearby` (the OID-scoped delta per
§P.8.0b item 4); TWO timeouts — `worldWaitTimeoutSeconds` (AWAITING_WORLD,
default 300; spawn rolls are probabilistic on movement, so the spike bot
paces a small patrol loop while waiting) and `combatTimeoutSeconds`
(ENGAGING/OBSERVING, default 180), both in Lua; observed flags
(attackAccepted, aggroBack, damageDealtToTarget, damageTakenBySpike,
targetDied, spikeBotDied) plus the observer-proof fields the PASS
predicate consumes: `destructionObserverFireCount` and
`observerParticipantVerified`. (Both phase deadlines are the two timeouts
declared above — there is no single combined hard timeout.) The maintenance
tick advances it (v2): spawn ONE disposable PRESENCE-ENABLED hunter bot
inside a real configured spawn area and let the world react — the spike
now proves the whole PlayerBot chain, not just combat: (phase
SPAWNING → AWAITING_WORLD → ENGAGING → OBSERVING → DONE) first OBSERVE
that the spawn system populates around the bot (`spawnsTriggeredNearby`
via the new presence counters; AWAITING_WORLD timeout separate from the
combat timeout), then command the attack on the nearest spawned creature
and OBSERVE combat each tick by reading both creatures' combat/HAM/posture
state (read-only, the phantom-guard read pattern) until a terminal
condition or timeout. The
spike registers the SAME one-shot `OBJECTDESTRUCTION` observer machinery
the hunt loop will use (attacker-participation check included) — the spike
exists to prove the exact kill path Phase 2 depends on, not a lookalike.
Terminal verdict: **PASS requires spawnsTriggeredNearby > 0 &&
attackAccepted && damageDealtToTarget && targetDied && the destruction
observer fired exactly once with the spike bot verified as participant**
(the presence patches AND the kill path proven together); anything weaker (fought but timed out,
mutual damage without a kill, observer never fired) is PARTIAL with the
failing flag named, and FAIL when the attack was never accepted. Only PASS
unlocks Phase 2. Cleanup ALWAYS runs at DONE (despawn the disposable bot
and, if the target survived, leave it untouched). Results land in a `pveSpike`
dashboard section + `SimPveSpike` log lines. **Phase 2's hunt loop stays
config-locked until the dashboard shows verdict=PASS** — if attackability
needs a flag (pvpStatusBitmask/faction arrangement), the spike tells us
with zero behavioral blast radius, and the flag decision goes to the
owner.

### P.8.1a — identity roster

- **Storage**: new MySQL table (versioned block in
  `ServerDatabase::updateDatabaseSchema()` + `sql/swgemu.sql` for fresh
  installs — see §1), loaded once at boot,
  written back on the maintenance thread only (event write-through for
  creations/name-grants; periodic flush for counters). MySQL over BDB
  because the roster is plain relational data the owner can inspect/edit
  with the mysql client, and it keeps us out of the object store's
  lifecycle.
- **Identity** = { id, firstName/lastName (NameManager-minted once, then
  fixed forever), profession (v1: `hunter`), homePlanet/homeCity, skillTier,
  createdAt, lastSeenAt, lifetime stats (hunts, kills, deaths,
  harvestUnits), currentAssignment }.
- **Attachment**: at boot (and on body death → respawn), the manager spawns
  a body per active identity at its home city (existing spawn plumbing) and
  binds identity→controller. The BODY is transient exactly as today; the
  IDENTITY is what persists. Name applied from the roster, not re-minted.
  Population = roster size, governed by config (`maxHunters`); new
  identities are minted only when the roster is below target.
- **Registry** lives in `SimPlayerManager` (new `pveMutex` guarding roster
  maps, same never-held-while-locking-agents rule as `pvpSquadMutex`).

### P.8.1b — solo hunt loop (new `SimHunterController`)

> **AMENDED 2026-07-16 after the P.8.0 spike (design doc §Spike / §Phase 2
> combat).** The original HUNTING bullet said "engage per spike verdict" — a
> placeholder. The spike proved the combat approach concretely: a few
> manager-side setter calls do NOT drive AiAgent combat. Real hunting needs
> (1) a **neutral** body, (2) an **explicitly equipped** weapon, (3)
> **controller-driven move-to-target**, (4) sustained combat via the
> `simPvp`-style AI map, (5) a **~2s active tick**. Those requirements are
> folded into the Body-spawn and HUNTING/RETREAT bullets below; the
> matchmaker / travel / buff / harvest design is unchanged.

Sibling of `SimMinerController`/`SimPvPController` on the shared
`SimPlayerController` base (movement, watchdogs, halt choreography, cell
support all inherited). Phase machine:

`IDLE_HOME → ANNOUNCE_JOB → BUFF_UP → TRAVEL_OUT → HUNTING ⇄ (RETREAT/heal) →
TRAVEL_HOME → DELIVER → IDLE_HOME`  (death → CLONE_HOME → BUFF_UP)

- **Hunter body spawn (NEW, spike-derived).** Hunter identity bodies are
  spawned player-mimetic: (a) **neutral faction** — `setFaction(0)` after
  `loadTemplateData` (the spike rule: `AiAgentImplementation::isAttackableBy`
  refuses a factioned AI attacking a faction-0 wild creature, so a factioned
  hunter can't touch wildlife); (b) **explicitly equipped weapon** — v1 a
  standard **ranged rifle** weapon object created and transferred into the
  weapon slot (the create/place path does NOT equip a mob template's weapon;
  the spike bot was unarmed). Owner gear decision (2026-07-16): v1 uses a
  functional neutral appearance + our explicitly-equipped weapon; a custom
  styled template and buy-your-gear swapping (weapon/armor by persona
  purchase, gear held on the identity) is a later pass. Weapon config in
  Lua (`pveConfig.hunterLoadout`) so it is tunable and the future
  per-profession/skillTier table drops in here. Bodies carry `ObjectFlag::
  PLAYER` + presence membership (already Phase 1b) and the **`simHunter`**
  AI map (a `simPvp` clone: IDLE-only override so combat slots default and
  the body fights, movement stays controller-owned — the dual-driver
  lesson; a PvE-owned map keeps the two verticals independent).

- **Job generation (matchmaker)**: a maintenance step reads unmet
  creature-resource demand from the existing demand layer at RESOURCE-TYPE
  fidelity and matches it against a Lua **species table** (species → planet
  + hunt-ground coordinates + harvest kinds {hide/bone/meat} + per-kill
  unit estimates + soloable flag + min skillTier). An order carries
  `requestedResourceType` and `harvestKind`, not just a species — and at
  hunt time each kill resolves the corpse's ACTUAL current spawn identity
  (creature template `getHideType`/`getBoneType`/`getMeatType` →
  `ResourceManager` current-spawn lookup) so the ledger deposit records the
  real `ResourceSpawn` metadata, type-correct exactly like miner
  acquisitions feed the P.5 hive. The matchmaker validates species
  compatibility (species must yield the requested kind) before assigning.
  Soloable species only in v1 (peko peko, generic huntables); group-tier
  rows (acklay, krayt, geo, nightsisters) are DATA now, consumed by P.8.2.
  Orders are assigned to idle hunter identities; assignment stamped on the
  identity (v1 restart policy: abandon at boot and regenerate).
- **In-world theater**: on taking a job the hunter announces it in spatial
  at its home hub ("Taking a contract: bone harvesting out past the
  ridge.") via a new PvE announcer (own line pools + cooldowns, reusing the
  `announcePvpEvent` pattern — NOT the PvP announcer's cooldown state, so
  the two verticals can't starve each other; the 0.2.1 same-call-stack
  lesson is a named constraint: announce sites separated by gameplay time).
- **BUFF_UP**: v1 self-contained realism — dwell at the home city's cantina
  (already resolved per-city by P.6.5d's cantina cache) then med center
  (new per-city resolved location, same resolver pattern + fallback), and
  apply a REAL standard buff package directly to the bot via the engine's
  existing `Buff` API (HAM buffs; visible to inspecting players). Real
  doctor/entertainer BOT providers replace this in P.8.3. Buff application
  to our own NPC mutates no economy/player state.
- **TRAVEL_OUT/HOME — same-planet only in v1 (explicit non-goal:
  cross-planet contracts).** The routed multi-leg system is squad-private
  state (`pendingRoute` on `SimPvpSquad`, `boardPvpSquad`, shuttle-wait
  tasks) and is NOT lifted in this plan; hunters use only the shared-base
  primitives miners already prove daily: direct overland `moveTo` under the
  `directOverland` trust rules from home city to hunt ground. The
  matchmaker enforces two bounds: (a) each species row lists explicit
  `eligibleHomeCities` (data-driven — planet equality alone is useless when
  home cities on one planet sit thousands of meters apart), and an order
  is only assignable to an identity homed in one of them; (b) a global
  `maxHuntDistanceMeters` (Lua, default ~1500) between the home city and
  the hunt ground, checked at CONFIG LOAD so a bad row is rejected loudly
  once, not per-assignment. Note `directOverland` VALIDATION is
  miner-manager logic, not something `SimPlayerController::moveTo`
  inherits — so each species' hunt ground is validated ONCE at config load
  through the existing P.4.1 overland guards (`isOverlandPointInWater` /
  bounds checks, manager members already callable) with failures surfaced
  on the dashboard as unusable rows, mirroring the collector z-sanity
  precedent. Hunters are minted with homes distributed across the
  eligible cities so every v1 species has local hunters. Cross-planet
  contracts — and any shared travel-component extraction — are P.8.2
  scope, where group journeys need routing anyway.
- **HUNTING (spike-derived combat drive).** The hunter is a PRESENCE bot,
  so the world populates around it like a player (P.8.0b): walk the hunt
  ground, let the spawn system produce lairs/creatures, then scan-radius
  acquisition of wild creature AiAgents matching the species' template
  filter. No manager-spawned quarry, no stage props — a nightsister hunt
  causes nightsisters because a player-shaped thing walked into nightsister
  territory. **Combat is controller-driven, not a setter shortcut** (the
  spike proved `setTargetObject`+`addDefender`+`setCombatState` alone leaves
  the bot idle/unarmed/not-closing): on target select the controller
  (a) `moveTo` the creature via the shared `SimPlayerController` movement
  pipeline to close to weapon range (~within the equipped rifle's range),
  then (b) sets the target/defender/combat state so the `simHunter` AI
  map's default combat slots drive real swings with the equipped weapon. A **~2s
  active tick** (the spike's adaptive-reschedule pattern — the 30s roster
  cadence is far too coarse for live combat) re-pursues if the creature
  moves and re-selects if the target dies/vanishes before the quota is met.
  **Kill attribution is observer-based, not polled**: Core3 emits
  `KILLEDCREATURE` only to PLAYER attackers, so the controller registers a
  one-shot `ObserverEventType::OBJECTDESTRUCTION` observer on the engaged
  target (the exact machinery the spike wired), verifies the hunter
  participated, fires `onHuntKill` EXACTLY once, deregisters, and hands the
  harvest off via a queued task OUTSIDE the target's lock. **One observer
  handle per hunter, dropped on any target change** — `dropObserver` on
  target switch, retreat-to-a-fresh-target, timeout, contract abandonment,
  death, and controller teardown; retained ONLY when resuming the exact
  same target. Without this, an abandoned target dying later would falsely
  credit this hunter (its participation record would still verify). Per-kill
  simulated harvest credits the identity ledger and the hive with the
  resolved real ResourceSpawn (above); quota or timeout ends the hunt.
- **RETREAT/heal ⇄ HUNTING (player-mimetic, owner 2026-07-16).** Losing but
  alive (the MINIMUM current/max ratio across Health/Action/Mind falls below
  `retreatHamPct`, e.g. 30% — any pool bottoming out triggers retreat) →
  break off: disengage combat (per the choreography above) and `moveTo`
  `retreatRangeMeters` away from the creature, stop, and
  **let HAM regen** (real regen, no combat); once HAM recovers above
  `resumeHamPct` (e.g. 70%) and the hunt quota/timeout still allows,
  RE-ENGAGE the same or a fresh nearby target. Abandon the contract only
  after `maxRetreatCycles` or the hunt timeout — a hunter tries, backs off,
  heals, and tries again like a player, not one-and-done.
- **DEATH → CLONE_HOME → BUFF_UP (player-mimetic).** Bot death: the identity
  KEEPS its lifetime stats; the body respawns at its home city "cloner"
  **with wounds** — v1 applies an explicit wound amount per pool via
  `addWounds(pool, cloneWoundAmount)` (config; a fresh clone isn't
  battle-ready). The normal IDLE_HOME → BUFF_UP cycle heals them: at the med
  center the controller **explicitly heals wounds** via `setWounds(pool, 0)`
  (buff activation restores current HAM but does NOT clear wounds —
  BuffImplementation.cpp:294; a med-center dwell must call the wound API),
  THEN applies the buff package. Real doctor/entertainer BOT healers arrive
  in P.8.3; v1 the med-center dwell IS the healing. The in-progress contract
  is abandoned and requeued. Counter `hunterDeathsTotal`.
- **DELIVER**: return announce at home hub ("Back with a full pack of
  ridge-cat hides.") + ledger delivery into the hive stockpile
  (simulation-only), assignment cleared.

### 4. SimHunterController.{h,cpp} (new files)

**Files**: `MMOCoreORB/src/server/zone/objects/creature/simplayer/SimHunterController.{h,cpp}`

- Extends `SimPlayerController` (miner/PvP precedent; no CMake edit —
  zone sources are recursively globbed, the reconfigure picks the files up). Phase machine per §P.8.1b;
  every phase TTL-guarded (stateTtl pattern), movement via inherited
  moveTo/watchdogs, halts via prepareForRelocation choreography at every
  teleport.
- **Body setup (spike-derived)**: after `loadTemplateData`, `setFaction(0)`
  (neutral — else wildlife rejects the attack) and equip the configured
  rifle explicitly, mirroring the stock NPC-arming path
  (`CreatureManagerImplementation.cpp:530`): create the weapon object
  (`ObjectManager::createObject` of the weapon template CRC),
  `transferObject(weapon, 4)` into the weapon slot, then BOTH
  `agent->setDefaultWeapon(weapon)` AND `agent->setCurrentWeapon(weapon)` —
  combat leaf actions read `getCurrentWeapon()` (SimpleActions.h:250), so
  setDefaultWeapon alone leaves the bot effectively unarmed. Verify both
  pointers are non-null before the controller is allowed to enter HUNTING;
  a failed equip aborts the body (never hunt unarmed). The create/place
  path does NOT auto-equip a mob weapon (the spike bot was
  `unarmed_default`).
- **HUNTING engage (controller-driven)**: scan via `getInRangeObjects`
  filtering creature AiAgents by the species template filter + neutral-
  attackable check (`isAttackableBy`). **Disengage-move-reengage state
  machine (required — `SimPlayerController::moveTo` sets state=IDLE and
  refuses to path a combat-state agent, and `onPathFound` discards a combat
  agent's path; movement and combat are mutually exclusive on this base):**
  out of weapon range → `clearCombatState`, drop the target as defender +
  remove self from the target's defender list, clear follow/queued actions,
  THEN `moveTo` the creature (inherited movement pursues); on arrival in
  weapon range → set target/defender/combat state so the `simHunter` AI
  map's default combat slots drive real swings (override IDLE only — PvP
  precedent). The ~2s hunt sub-tick (adaptive reschedule; the 30s cadence
  is far too coarse — spike lesson) drives this: re-close when the creature
  walks out of range, re-select on kill/vanish. Stalemate/phantom-combat
  guards: reuse `SimPvpBotController`'s two guards by lifting them into the
  shared base ONLY if trivially liftable, else duplicate locally with a
  comment — whichever keeps the PvP path byte-identical (reviewer checks).
  Kill via the one-shot OBJECTDESTRUCTION observer (§3 hook, the exact
  machinery the spike wired; one handle per hunter, dropped on any target
  change per §P.8.1b).
- Buff phase applies the configured buff package via the engine `Buff`
  API following the existing `PlayerManager` buff-construction pattern
  EXACTLY, including its lock contract: `Buff::setAttributeModifier` is
  `@preLocked`, so the sequence is — agent `Locker`, construct
  `new Buff(creature, buffCRC, durationSeconds, BuffType::MEDICAL)` (or
  PERFORMANCE for the cantina row), take a `Locker` ON THE BUFF, set the
  modifiers, and call `creature->addBuff(buff)` WITH THE BUFF LOCKER STILL
  HELD — activation inside addBuff is itself `@preLocked` on the buff
  (this is exactly the PlayerManager scope shape; releasing before addBuff
  would violate it).
  Re-application with the same CRC refreshes (engine replace semantics),
  so repeated BUFF_UP phases stack correctly by construction. Lua schema:
  `buffs = { { name, type = "medical"|"performance", durationSeconds,
  modifiers = { { attribute = "health"|"action"|"mind"|..., amount } } } }`.

## Technical Considerations

- **Pattern Usage**: identity registry mirrors the squad-roster pattern
  (mutex-guarded VectorMap in the manager); controller mirrors
  SimMinerController's lifecycle + SimPvPController's combat presence;
  spike mirrors P.6.5-0; resolvers extend the P.6.5d city-locations cache;
  announcer mirrors announcePvpEvent with independent cooldown state.
- **Locking & References**: new `pveMutex` follows the pvpSquadMutex
  contract exactly (never held while locking agents; world scans outside,
  publish under). SQL only on the maintenance thread. Buff application =
  agent Locker + buff Locker held through addBuff (the PlayerManager
  pattern; Buff methods are @preLocked). No cross-mutex ordering with
  pvpSquadMutex (never hold both).
- **IDL Impact**: none — controllers/manager are non-IDL classes (per all
  prior sim work). The MySQL table is schema, not object store.
- **C++ vs Lua Placement**: species/hunt-ground data, all thresholds, and
  gates in Lua; phase machinery, roster, SQL in C++.
- **Gating & Simulation-Only**: C++ defaults off for everything (spike
  included). Real combat + real self-buffs are explicitly approved above;
  harvest/rewards are conceptual-ledger only (miner acquisition precedent);
  the roster table is new, isolated persistence (no object-store or
  character-table contact).
- **Dashboard Visibility**: new `pveActivity` + `pveSpike` sections;
  per-identity rows are the primary live-verification instrument.
- **Live Verification Plan**: staged — (0) spike verdict rows before
  enabling the loop; (1) roster survives a restart with identical names;
  (2) a full solo hunt observed end-to-end in-game (announce → cantina/med
  dwell → travel → kills → return announce) + counters climbing; (3) miner
  and PvP baselines unchanged.
- **Edge Cases**:
  - Spike says creatures aren't attackable by sim bots without a flag →
    STOP: Phase 2 blocked pending an owner decision on the flag (the spike
    exists to catch this cheaply).
  - Species extinct/unspawned at the hunt ground (nothing to scan) → hunt
    TTL fires → RETURN with partial/zero harvest, order requeued with a
    cooldown, `emptyHuntsTotal` counter (visibility, not a wedge).
  - Hunter killed by the creature → death path per PvP precedent (report
    once, corpse cleanup, respawn at home as the same identity).
  - Name collision on mint (roster vs NameManager) → re-mint with
    uniqueness check against the table (DB unique index is the backstop).
  - DB unavailable at boot → hunter subsystem stays down (log + dashboard
    flag), everything else unaffected; no in-memory-only identities (they'd
    violate the persistence promise).
  - Restart mid-hunt → assignment abandoned at boot (stamped stale),
    regenerated naturally.
  - Player attacks a hunter → it's a normal attackable NPC; death path as
    above (revenge/flee behavior is future polish).
