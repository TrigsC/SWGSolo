# F_0.9.7 P.10h — Skill-Derived Combat Abilities, SimBot Inspection Implementation Plan

## Overview

Roster PlayerBots train real skill boxes (F_0.9.5) and grind with them (F_0.9.6),
but they still fight with auto-attack only: the novice body template
`sim_playerbot_novice` ships `primaryAttacks = {}` / `secondaryAttacks = {}`, so
training a box changes skill mods but never adds an ability. This chunk builds each
bot's attack list from its **trained boxes** (the `commands` column the server already
loads from `skills.iff` — no TRE change), keeps only the **highest tier** of each
ability chain, and feeds that list into the existing state-aware NPC special-attack
scorer with a sim-bot–specific special chance and a HAM reserve. It also makes a
SimBot inspectable: admin `/server playerinfo` on a targeted SimBot, and a
click-a-name drawer on the dashboard backed by a new on-demand per-bot API endpoint
that explains the bot's templates in plain terms.

## Problem Statement

1. **No abilities.** `SimPlayerManager::applyProgressionToBody` (`SimPlayerManager.cpp:~8083`)
   applies `addSkill` + SKILLBOX mods, but `AiAgentImplementation::setupAttackMaps`
   (`AiAgentImplementation.cpp:~2248-2400`) builds attack maps only from
   `npcTemplate->getPrimaryAttacks()/getSecondaryAttacks()`. A novice brawler who has
   `combat_brawler_novice` (which grants `intimidate1`, a zero-cost command —
   `bin/scripts/commands/intimidate1.lua:49-51`) never uses it.
2. **Tier duplication.** Nothing collapses ability tiers, so once maps are skill-derived a
   bot with `…hit1` and `…hit2` would carry both and could pick the weaker one. Owner
   decision: **highest tier only** — lower tiers are removed from the list entirely.
3. **Special spam once maps are non-empty.** The stock `SelectAttack` leaf
   (`bt/leaf/SimpleActions.h:250-302`) calls `selectSpecialAttack(-1)` whenever the
   blackboard carries no `attackType`, i.e. **every** swing, and
   `selectDefaultAttack` (`AiAgentImplementation.cpp:~3405`) — when the template default
   is unset — picks a "priority"/"heuristic" special from the maps instead of a plain
   auto-attack. Installing abilities without a sim-specific policy would make a bot use
   a special every swing and drain its pools.
4. **Specials can trigger flee.** `SimHunterController::isBelowEarlyGameHam`
   (`SimHunterController.cpp:2530`) flees on the **minimum** of Health/Action/Mind
   below `fleeHamFraction`. Specials spend Action/Mind, so an unbounded special policy
   can make a winning bot flee by spending its own Action.
5. **SimBots are opaque to admins.** `PlayerInfoCommand` (`commands/PlayerInfoCommand.h:25`)
   falls back to the *admin's own* record when the target is not `isPlayerCreature()`,
   which every AiAgent body fails.
6. **Dashboard shows rows, not a bot.** WILDS shows roster/progression tables; there is
   no single place that explains what a bot *is* (body template, weapon, plan, boxes by
   profession, mods, abilities) and adding it to the ~500 KB snapshot would bloat every
   poll.

## Solution Architecture

Three layers, each following an existing pattern:

**A. Derivation (manager, no agent lock).** `buildBodyProgressionSnapshot` already walks
trained skills under `progressionMutex` and reads `SkillManager::getSkill(name)`. It
additionally collects each skill's `getAbilities()` (the accessor for the `commands` column, `Skill.h:273`), keeps only names that resolve to a
`CombatQueueCommand` in the `ObjectController`, drops names in a Lua exclusion list, and
collapses tiers with a pure helper `SimBotAbilityTiers` (chain key = command name with
trailing digits stripped, lower-cased; tier = trailing integer, 0 if none; keep max tier
per chain). The snapshot carries `abilities` (kept) and `supersededAbilities` (dropped,
for inspection only). Nothing new persists — the list is re-derived from `simbot_skills`
exactly like the mod overlay.

**B. Installation and use (agent, under the agent lock).** `AiAgent` gains a transient
**skill-derived attack source**: a `CreatureAttackMap` reference plus an
`abilityPolicy` POD (special chance, HAM reserve, free-state-ability preference).
`setupAttackMaps` uses that source **instead of** the template's primary/secondary lists
when it is set, running the unchanged weapon-bitmask filter, so weapon swaps
(`equipPlayerBotWeaponLocked` already calls `setupAttackMaps`) re-filter automatically.
`loadTemplateData` clears the source (same reset site as `simPlayerBot = false`,
`AiAgentImplementation.cpp:368`) so reused objects can never leak it — the F_0.4.x
sticky-flag lesson. `applyProgressionToBody` installs or clears it and calls
`setupAttackMaps`.

When the source is set:
- `SelectAttack` leaf: roll `specialAttackChancePercent`; on a miss call
  `selectDefaultAttack`. **Exception:** if `preferFreeStateAbilities` is on and a
  zero-cost, **non-damaging** control ability exists whose state the current target lacks
  (Intimidate on a non-intimidated target), use **exactly that ability** regardless of the
  roll, then do not force it again on the same target for `freeStateRetrySeconds`.
- `selectDefaultAttack`: returns plain `defaultattack` (real auto-attack) and skips the
  priority/heuristic map search.
- `selectSpecialAttack()` scoring: **unchanged** — the owner's state-aware scorer
  (Intimidate only if not intimidated, KD recovery, blind/dizzy/stun) is reused as-is.
  Two added pre-filters (skill-derived agents only): a candidate whose HAM cost would drop a
  primary pool **it actually spends** below `hamReserveFraction` is skipped (in addition to
  `canAffordAttackCommand`), and a candidate that `validateStateAttack` would reject is skipped.
Agents without the source (every wild NPC, PvP bots, legacy hunters, gate off) take the
existing code paths byte-for-byte.

**C. Inspection (read-only).**
- **API:** `GET /v1/aieconomy/playerbot/<identityId>/` on `APIProxyAiEconomyManager`,
  Bearer-gated like the dashboard, built on demand by
  `SimPlayerManager::getPlayerBotInspectJson(identityId)`.
- **Web:** bot names on WILDS roster and PlayerBot progression tables become clickable;
  a right-side drawer fetches the endpoint and renders plain-English cards. Existing
  tables are unchanged.
- **In-game:** `/server playerinfo` with a SimBot targeted shows the same facts in the
  existing SUI message box instead of the admin's own info.

**Selection vs. fight invariant (from F_0.9.6):** the scorer reads live target state that
a player can also see (states, posture, HAM bars). No damage, accuracy or cost advantage
is introduced; commands dispatch through the normal `enqueueCommand` →
`CombatQueueCommand` path. Stock NPC specials currently pay **no HAM**
(`CombatManager::applySpecialAttackCost` returns early for AiAgents), which would be a cost
advantage, so skill-derived agents alone are switched onto the player HAM cost rule (§5a).

## Implementation Details

### 1. Pure tier-collapse helper

**File**: `MMOCoreORB/src/server/zone/objects/creature/simplayer/SimBotAbilityTiers.h` (new, header-only)

- `parseAbilityTier(name) → (chainKey, tier)`: lower-case; strip trailing decimal digits
  only (so `melee1hhit2` → chain `melee1hhit`, tier 2; `saber2hfrenzy` → chain
  `saber2hfrenzy`, tier 0; `intimidate1` → `intimidate`, 1).
- `collapseAbilityTiers(const Vector<String>& in, Vector<String>& kept, Vector<String>& superseded)`:
  dedupe, keep the highest tier per chain, preserve first-seen chain order (stable output
  so dashboards and tests are deterministic), append every dropped name to `superseded`.
- No engine dependencies beyond `engine.h` strings/vectors, so it is unit-testable.

### 2. Derivation in the snapshot

**File**: `SimPlayerManager.h` / `SimPlayerManager.cpp`

**Current state**: `SimBotBodyProgression { Vector<String> skills; VectorMap<String,int> modDeltas; }`
(`SimPlayerManager.h:363`); `buildBodyProgressionSnapshot` (`.cpp:~8046`) fills them.

**Modifications**:
- Extend `SimBotBodyProgression` with `Vector<String> abilities`,
  `Vector<String> supersededAbilities`, `Vector<String> excludedAbilities` (with reason
  suffix, inspection only) and `bool abilitiesApplicable`.
- In `buildBodyProgressionSnapshot`, after the mod loop, gather `skill->getAbilities()` for
  each trained skill. Resolve each name through
  `ServerCore::getZoneServer()->getObjectController()->getQueueCommand(name)` and keep only
  `CombatQueueCommand` casts (the same test `setupAttackMaps` applies); non-combat
  commands go to `excludedAbilities` as `name:not_combat`, config-excluded as
  `name:config`. Then `collapseAbilityTiers`. The ObjectController lookup is a read of
  a boot-time registry and takes no object lock, so doing it under `progressionMutex`
  adds no lock order edge. If the registry is unavailable, return an empty ability list
  and set `abilitiesApplicable=false` (fail closed = template behaviour).
- **Applicability is decided by the caller and passed in; the snapshot never reads
  identity state.** `buildBodyProgressionSnapshot(identityId)` gains a
  `const SimBotAbilityApplicability& applicability` parameter (POD:
  `bool gateEnabled; String trainingPlan; String profession; bool harnessOptIn;` — identity
  facts only, no config). Every caller computes it in this order, never nested:
  1. evaluate `playerBotCombatAbilitiesGateEnabled()` (takes `playerBotParityTestMutex`
     for the harness override) with no manager mutex held;
  2. take `pveMutex`, copy the identity's `trainingPlan` and `profession` (and, for
     harness identities, whether the active scenario opted this identity in), release it;
  3. only then call `buildBodyProgressionSnapshot`, which takes `progressionMutex` alone and,
     **under that same acquisition**, copies the whole `SimBotCombatAbilityConfig`
     (chance, preferFreeState, hamReserve, `excludedCommands`, history size) into the
     snapshot before deriving.
  The combat-ability config is **owned by `progressionMutex`**: the config refresh writes it
  only while holding `progressionMutex` (the same owner F_0.9.5 gave
  `progressionTrainingPlans` after the lock-free-read review finding), and every reader —
  spawn/reapply, inspect, admin text, the dashboard counters block — copies it under that
  mutex. No reader touches it lock-free, and it is never read under an agent lock (the agent
  receives plain copied values via `setSkillDerivedAttacks`).
  `applicable = gate && !trainingPlan.isEmpty() && (profession != "harness" ||
  harnessOptIn)`. Legacy hunters with no plan keep their template attacks. Callers to
  update: the spawn path and `reapplyPlayerBotProgressionToLiveBody` (both already copy
  identity fields under `pveMutex` before locking the body), plus the inspect/admin
  builders (§9, §11), which call it with `applicable` forced true for the **derivation
  view only** so an admin can see what a gate-off bot *would* get — the view never
  installs anything.

### 3. Gate and config

**File**: `MMOCoreORB/bin/scripts/managers/sim_player_manager.lua`; parsing in
`SimPlayerManager::applyPlayerBotProgressionConfig`

Add under `playerBotProgression`:
- `combatAbilitiesEnabled = false` — capability gate.
- `combatAbilities = { specialAttackChancePercent = 35, preferFreeStateAbilities = true,
  hamReserveFraction = 0.40, freeStateRetrySeconds = 10, excludedCommands = {"taunt", "warcry1", "warcry2"}, usageHistorySize = 12 }`.
  Clamp: chance 0..100; reserve 0..0.95; history 0..64. `hamReserveFraction` default
  sits above the shipped `fleeHamFraction` so a special can never be the thing that
  pushes a bot into flee; the parser logs a warning (not an error) if reserve ≤ the
  configured `fleeHamFraction`.
- New gate helper `playerBotCombatAbilitiesGateEnabled()` with the reference shape of
  `playerBotProgressionAwardGateEnabled` (`SimPlayerManager.h:2684`): **master
  `playerBotProgression.enabled` first, harness override second, capability last.**
- Harness control: new op `setCombatAbilitiesGate {expect="true"|"false"}` modelled on
  `setEarlyGameGate` (`SimPlayerManager.cpp:14790`) — it writes the harness override
  consulted second by the gate helper, is registered in the arming-op precondition map
  next to `setEarlyGameGate`/`setGate` (`:10245-10251`) so a scenario that uses ability
  assertions without arming it fails as `precondition_gate_off_combatAbilitiesEnabled`,
  and is **restored by the scenario cleanup pass** exactly like the other gate overrides.
  Setting or clearing the override enqueues `reapplyPlayerBotProgressionToLiveBody` for
  the scenario's live identities only, so the installed source follows the override
  within the scenario and never touches production bodies. Harness opt-in for an
  identity is recorded by the same op (`identityRef` optional) in scenario-scoped state
  cleared by cleanup.
- Gate transitions: the config refresh records the previous gate/policy signature; on a
  change it enqueues `reapplyPlayerBotProgressionToLiveBody` for every identity with a
  live body, bounded by the existing `trainingSweepBatch` per maintenance tick, so turning
  the gate off restores template attack maps without a respawn.

### 4. AiAgent skill-derived attack source

**File**: `MMOCoreORB/src/server/zone/objects/creature/ai/AiAgent.idl`,
`AiAgentImplementation.cpp` (never `src/autogen`)

- IDL: `protected transient CreatureAttackMap skillDerivedAttackMap;` (same declaration form
  as `primaryAttackMap`, `AiAgent.idl:93-95`), plus transient policy fields
  (`int skillAbilitySpecialChance`, `boolean skillAbilityPreferFreeState`,
  `float skillAbilityHamReserve`).
- IDL native methods: `setSkillDerivedAttacks(const Vector<String>& commands, int chance,
  boolean preferFreeState, float hamReserve)`, `clearSkillDerivedAttacks()`,
  `boolean hasSkillDerivedAttacks()`, and a `@read` accessor returning a copy of the
  installed command names for inspection. All are `@preLocked` (caller holds the agent).
- `loadTemplateData`: clear the source next to `simPlayerBot = false` (`:368`), **before**
  its trailing `setupAttackMaps()` (`:613`).
- `setupAttackMaps`: when `skillDerivedAttackMap != nullptr`, use it as the raw source for
  **both** the primary and the secondary passes (a trained command's weapon bitmask decides
  which built map it lands in, exactly as template entries do today) and skip the template
  lists. Everything after the raw-source selection — bitmask filter, duplicate guard,
  empty→nullptr — is unchanged. An empty-but-installed map yields null maps, i.e. a bot with
  no combat abilities auto-attacks (player parity: no boxes, no specials).

### 5. Attack selection policy

**Files**: `bt/leaf/SimpleActions.h` (`SelectAttack::execute`, `:250-302`),
`AiAgentImplementation.cpp` (`selectSpecialAttack()` `:~2850-3250`,
`selectDefaultAttack` `:~3405`)

- `SelectAttack::execute`: after the Force-weapon branch and **before** the blackboard
  branch, if `agent->hasSkillDerivedAttacks()`: compute `wantSpecial` =
  `System::random(99) < skillAbilitySpecialChance` (engine `random(n)` is inclusive of `n`,
  so 0–99 makes 0 never and 100 always). **Before** the roll, with `preferFreeState`, call
  `findFreeStateAbilityForTarget()`; if it names a command and
  `selectNamedSpecialAttack(command)` succeeds, call `noteFreeStateAbilityForced()`, count
  `freeStateForced` and return (checking only on a missed roll meant a high special chance
  never applied Intimidate — repro matrix, 3 of 6 boots). Otherwise `selectSpecialAttack(-1)` on `wantSpecial` with
  `selectDefaultAttack()` fallback, else `selectDefaultAttack()`. Agents without the source
  reach the untouched existing branches.
- New natives on AiAgent (all `@preLocked`):
  - `string findFreeStateAbilityForTarget()` scans the **currently selected weapon-category
    map** for a command that is **non-damaging** (`getPoolsToDamage() == CombatManager::NONE`),
    whose shared HAM cost (§5a) and Force cost are zero, that `canAffordAttackCommand` accepts,
    and whose state effect (from the command's `StateEffect` list, not name matching) the
    follow target does not already have; it returns that command's name. It returns empty
    while the same target is inside the retry window.
  - `boolean selectNamedSpecialAttack(string)` selects exactly that command (validates the
    queue command and follow target; `SPECIAL_SELECT … source=skill_derived_free_state`).
  - `void noteFreeStateAbilityForced()` records the target OID and time; transient fields
    `freeStateForcedTargetOid`/`freeStateForcedAtMs`/`skillAbilityFreeStateRetryMs` are reset in
    `loadTemplateData` and `clearSkillDerivedAttacks`; `setSkillAbilityFreeStateRetryMs(int)`
    installs `combatAbilities.freeStateRetrySeconds` (default 10, clamp 0..300).
  - **Why (live Run N, 2026-09-16):** the first cut forced `selectSpecialAttack(-1)` whenever
    any zero-cost stateful special existed. The unarmed default weapon's base attack cost is
    0/0/0, so every unarmed special was "free"; `unarmedlunge1` carries a posture effect the
    target never holds, and the general scorer preferred the lunge over Intimidate, so every
    swing was forced special (`freeStateForced` 56, `defaultsEnqueued` 0).
- `selectDefaultAttack`: at the top, if `hasSkillDerivedAttacks()`, set
  `cmd = "defaultattack"`, `selectionSource = "skill_default"` and skip the template-default
  and map search. Everything below (queue stuffer, diag) unchanged.
- `selectSpecialAttack()` scoring loop: add a HAM-reserve pre-filter **only when
  `hasSkillDerivedAttacks()`**: skip a candidate whose health/action/mind cost from the
  shared helper (§5a) would leave a pool **with a non-zero cost** below `skillAbilityHamReserve × max`, or would
  fail the player rule `pool <= cost`. (`canAffordAttackCommand`, `:2817`, only predicts
  Force cost and stays as-is for every other agent.) Diag: extend the existing `SPECIAL_SELECT` detail with
  `source=skill_derived` and `reserveSkipped=N` when the source is set. The scoring
  weights are not modified.
- Second pre-filter in the same loop, same scope: skip a candidate for which
  `validateStateAttack(target, command)` is false. The tree's `CheckAttackIsValid` runs after
  `SelectAttack` and aborts the tick on such a command, and the scorer's state heuristics do not
  mirror it (lunge is scored as knockdown but carries POSTUREDOWN), so without the filter a bot
  re-selected the same invalid lunge every tick and never attacked (repro loop
  `abilities_used_in_kill_r04`, 600 s budget exceeded).

### 5a. Player-parity HAM cost for skill-derived specials

**Files**: `MMOCoreORB/src/server/zone/managers/combat/CombatManager.{h,cpp}`
(`applySpecialAttackCost`, `:~3273`)

**Current state**: for any AiAgent, `applySpecialAttackCost` handles Force only and returns
`true` before the HAM block ("Preserve stock NPC behavior for HAM costs"), so NPC specials
are free in Health/Action/Mind. Players pay
`weapon->get{Health,Action,Mind}AttackCost() × data.get{…}CostMultiplier()`, adjusted by
`calculateCostAdjustment(STRENGTH/QUICKNESS/FOCUS, …)`, refused when `pool <= cost`, then
deducted with `inflictDamage(attacker, pool, cost, true, true, true)`.

**Modifications**:
- Extract that player computation into one const helper
  `CombatManager::computeSpecialAttackHamCost(CreatureObject* attacker, WeaponObject* weapon,
  float healthMultiplier, float actionMultiplier, float mindMultiplier, float& health,
  float& action, float& mind) const`; the player branch calls it (no behaviour change for
  players — same arithmetic, same order).
- In the AiAgent branch, after the existing Force handling: **if
  `agent->hasSkillDerivedAttacks()`**, compute via the helper, return `false` on the player
  refusal rule, **then recheck the reserve at the moment of deduction**: return `false` if
  any pool with a non-zero cost, minus that cost, would fall below `agent->getSkillAbilityHamReserve() × max` (a pool the special does not spend never refuses it — the first cut tested every pool, and the live repro loop showed a hurt bot refusing free unarmed specials 186 times and never finishing a kill)
  (the value installed on the agent, so no manager state is read under the lock). Only then
  deduct exactly as players do and return `true`. Checking and deducting happen in one call
  with the attacker locked, so HAM lost between selection and execution cannot make the
  special's own spend cross the reserve. A refusal counts in
  `combatAbilities.reserveRefusedAtExecution` (atomic) and behaves like a player's
  unaffordable special (the queued command fails; the next tick selects again).
  Scope of the invariant, stated precisely: *a special's own cost never takes a pool below the
  reserve*; incoming damage can still push a bot into flee, as today. Otherwise keep the existing
  early `return true`, so wild NPCs, Jedi NPCs, PvP bots and legacy hunters are unchanged.
- Selection (§5) calls the same helper with the multipliers read from the
  `CombatQueueCommand` (`getHealthCostMultiplier()` etc.) and the agent's current weapon, so
  prediction and deduction can never disagree.
- Caller context is unchanged: `applySpecialAttackCost` already runs inside the combat action
  with the attacker locked; `inflictDamage` on self is the player path's existing call.
- **Known parity risk, measured not assumed:** the bot's `creature_default_weapon` (unarmed)
  or template weapon may carry different base attack costs from a player's weapon. The
  inspect endpoint (§9) reports the equipped weapon's three base costs and each active
  ability's predicted cost; the live-derivation probe records them in this plan before the
  gate is enabled for grind bots. If a bot weapon's costs are zero where a player's are not,
  that is logged as a follow-up rather than silently patched here.

### 6. Install on the body

**File**: `SimPlayerManager.cpp` — `applyProgressionToBody` (`:~8083`),
`equipPlayerBotWeaponLocked` (`:~8160-8250`), `reapplyPlayerBotProgressionToLiveBody` (`:~8256`)

- `applyProgressionToBody` (precondition unchanged: caller holds agent, no manager mutex):
  after `addSkill`, if `snapshot.abilitiesApplicable` → `setSkillDerivedAttacks(snapshot.abilities,
  policy…)`, else `clearSkillDerivedAttacks()`; then `setupAttackMaps()`. Policy values are
  copied into the snapshot before locking, never read from manager state under the agent lock.
- Ordering: every path that calls `applyProgressionToBody` and then equips must end with
  `setupAttackMaps` after the weapon is final. `equipPlayerBotWeaponLocked` already calls it
  after equip; verify the spawn path order (apply → equip) so the final map reflects the
  final weapon, and add an explicit call where a path applies progression after equip.
- `reapplyPlayerBotProgressionToLiveBody` needs no change beyond the new fields flowing
  through the snapshot; training a box that grants `…2` therefore replaces `…1` on the
  live body immediately.

### 7. Ability usage telemetry (bounded)

**Files**: new `SimBotAbilityUsageLog.h` (leaf-mutex log, modelled on `SimEarlyGameDeathLog.h`);
`AiAgentImplementation.cpp` attack enqueue path (`ATTACK_ENQUEUE`, `:~3560-3690`)

- When the agent `hasSkillDerivedAttacks()` and an attack is actually enqueued, record
  `{bodyOid, command, targetOid, targetStateBefore bitmask, nowMs, source(special/default)}`
  into a per-body ring (size `usageHistorySize`, total bodies bounded by live PlayerBot
  count; entries for a body OID dropped in `onPveHunterDied`/body drain) plus **lifetime
  aggregates that survive ring eviction**: per-body per-command counts and
  `targetStatesSeen`, the OR of every recorded `targetStatesBefore`. The ring is the only
  place a command, its source and the target's state stay correlated; the aggregates answer
  "did this body ever use X" and "was a target ever in state Y" after eviction.
- Leaf mutex, atomic enable flag, no other lock taken inside — same shape as
  `SimEarlyGameDeathLog`, which is already recorded from under an agent lock.
- Counters on the dashboard: `playerBotProgression.combatAbilities.{gate, bodiesWithAbilities,
  specialsEnqueued, defaultsEnqueued, freeStateForced, reserveSkips}`.

### 8. Harness scenarios

**File**: `sim_player_manager.lua` (`playerBotParityTest.scenarios`), parity harness ops in
`SimPlayerManager.cpp`

- New ops, each with a stated data source:
  - `assertAbility {identityRef, command, expect=present|absent}` — reads the **installed**
    command names through the agent's `@read` accessor under the agent lock (names copied
    out, lock released before comparing). This is the only thing that proves the body
    carries the ability.
  - `assertAbilitySuperseded {identityRef, command, supersededBy}` — reads a **freshly
    derived manager snapshot** (`buildBodyProgressionSnapshot` with the §2 applicability
    order), because superseded names are never installed on the agent. Pass requires the
    command in `supersededAbilities`, `supersededBy` in `abilities`; a scenario pairs it
    with `assertAbility … expect=absent` for the same command so both the derivation and
    the body are proven.
  - `assertAttackSource {identityRef, expect=skill|template}` — `hasSkillDerivedAttacks()`
    under the agent lock.
  - `setCombatAbilitiesGate` — see §3.
- Scenarios:
  - `abilities_from_trained_box`: mint brawler novice, `setCombatAbilitiesGate expect=true`
    with the identity opted in, respawn → `intimidate1` present on
    the body; a command from an untrained box absent.
  - `abilities_highest_tier_only`: grant two boxes whose commands form a tier chain (chosen
    from the §Live-derivation probe below) → `assertAbility` higher present,
    `assertAbilitySuperseded` lower by higher, `assertAbility` lower absent.
  - `abilities_gate_off_template`: `setCombatAbilitiesGate
    expect=false` (after having been true, proving the reapply path) → `assertAttackSource template` and the
    template maps equal a fresh non-bot body of the same template.
  - `abilities_used_in_kill`: novice kills `dwarf_nuna` with
    `setCombatAbilitiesGate expect=true`, opt-in, and a scenario-scoped chance of 100 →
    usage log shows an enqueued skill-derived command and the target held `INTIMIDATED`
    at some sample while alive. `assertAbilityUse` reads the ring first and falls back to the
    lifetime aggregates for a command-only or state-only step (a step naming both still needs
    one matching ring entry, since only the ring correlates them). The fallback exists because
    a 22 s fight enqueues far more than `usageHistorySize` attacks and scrolled the single
    early Intimidate out of the ring (live matrix, `ability_use_not_observed`).
- Harness identities opt in through the scenario (harness override), never through the
  production eligibility predicate.

### 9. Per-bot inspection JSON

**Files**: `SimPlayerManager.h/.cpp` (`getPlayerBotInspectJson`),
`src/server/web/APIProxyAiEconomyManager.{h,cpp}`, `src/server/web/RESTServer.cpp:115`

- Endpoint: `addEndpoint(RESTEndpoint("GET:/v1/aieconomy/playerbot/(\\d+)/", {"identityId"}, …))`
  → `APIProxyAiEconomyManager::handlePlayerBotGET` → 404-style `apiRequest.fail` for an
  unknown id. Same Bearer auth as every other endpoint; no unauthenticated path.
- Choreography mirrors the dashboard identity rows (`SimPlayerManager.cpp:~15300-15330`):
  copy identity/progression/next-step/early-game state under their mutexes, release all
  manager mutexes, then `getObject(bodyOid)` + `Locker agentLock(bodyAgent)` for live body
  reads, then read the usage log (leaf mutex, after the agent lock is released).
- Shape (all plain values; the SPA does the wording):
  - `identity`: id, name, profession, trainingPlan, homePlanet/homeCity, skillTier, kills,
    deaths, createdAt.
  - `templates`: `body` {key (e.g. `sim_playerbot_novice`), objectName, level,
    HAM range/`bodyHam` override, default weapon kind, attacks-from-template count},
    `appearance` (the chosen `.iff`), `aiTree` (e.g. `simHunter`), `weapon` {template,

## Technical Considerations

- **Pattern Usage**: derivation mirrors `buildBodyProgressionSnapshot`/`applyProgressionToBody`
  (F_0.9.5 SKILLBOX overlay — full reconcile, idempotent on respawn and mid-life training);
  usage log mirrors `SimEarlyGameDeathLog`; REST mirrors `APIProxyAiEconomyManager::handleDashboardGET`;
  gate helper mirrors `playerBotProgressionAwardGateEnabled`; transient reset mirrors the
  `simPlayerBot` fix in `loadTemplateData`.
- **Locking & References**:
  - Snapshot: gate helper (parity-test mutex) → `pveMutex` copy → release → `progressionMutex`
    alone inside `buildBodyProgressionSnapshot`; never nested. ObjectController lookup is a
    lock-free registry read.
  - HAM cost (§5a): inside `applySpecialAttackCost` with the attacker already locked by the
    combat action; self `inflictDamage` exactly as the player path.
  - Install: caller holds the agent `Locker`; no manager mutex (existing precondition of
    `applyProgressionToBody`).
  - Selection: runs inside the behaviour tree with the agent locked; reads target states via
    the follow object exactly as the scorer already does — no new lock.
  - Usage log: leaf mutex taken under the agent lock, never nests anything.
  - Inspect/admin: manager mutexes copied then released → agent `Locker` alone → leaf mutex
    after release. Same order as the dashboard identity rows. Admin SUI built under the admin
    lock only, in a task.
- **IDL Impact**: `AiAgent.idl` gains transient fields and native methods; `src/autogen/`
  regenerates at build. Expect wide build fan-out (F_0.9.1 precedent). No `@json`
  persistence change — all fields transient.
- **C++ vs Lua Placement**: policy knobs, gate, exclusion list and harness scenarios in Lua;
  derivation, selection and locking in C++.
- **Gating & Simulation-Only**: `combatAbilitiesEnabled` default false. With the gate off no
  agent ever gets a source, so every AI path is unchanged. Persists nothing; P.10 roster
  policy unchanged. Miners and PvP bots have no roster identity and are untouched. Inspection
  surfaces are read-only.
- **Dashboard Visibility**: `playerBotProgression.combatAbilities` counters + gate; per-bot
  detail via the new endpoint rather than the snapshot (keeps polls small).
- **Live Verification Plan**: see Test Impact; ground truth is the new endpoint, the usage
  counters, `bin/log/simcombat.log` `SPECIAL_SELECT`/`ATTACK_ENQUEUE` lines for an allowlisted
  novice, and the target's `INTIMIDATED` state.
- **Edge Cases**:
  - Skill granting a command unknown to the ObjectController → `excluded:unknown_command`.
  - Command without trailing digits (`saber2hfrenzy`) → its own chain, never superseded.
  - Commands across weapon families share no chain (`melee1hhit` ≠ `unarmedhit`).
  - Bot with a plan but zero combat commands → installed empty source → pure auto-attack.
  - Weapon swap mid-life → `setupAttackMaps` re-filters; inactive-for-weapon shown in UI.
  - Target dies/changes between the free-state probe and scoring → scorer re-reads state;
    worst case one auto-attack.
  - Reused AiAgent object → source cleared in `loadTemplateData`.
  - Harness bodies → only via scenario opt-in.
  - Gate flipped at runtime → bounded reapply sweep restores template maps.
  - Admin targets a wild NPC, or a SimBot whose identity was retired between target and
    task → the admin's own info, as today, delivered one task hop later.
  - Inspect id with no body → identity/progression only, `bodyAttached=false`.

## Performance & Cost Impact

- Derivation runs only at spawn/training/gate-transition, O(trained boxes × commands) — tens of strings.
- Selection adds one branch per attack for agents without the source; for PlayerBots one extra map scan (≤ ~30 entries) when `preferFreeState` is on.
- Usage recording: one leaf-mutex push per enqueued PlayerBot attack; bounded memory
  (bodies × (`usageHistorySize` entries + one count per distinct command used + one state
  mask)), with the body count itself bounded by the live PlayerBot population.
- Inspect endpoint: on demand, one body lock; no change to snapshot size beyond ~6 counters.
- IDL change widens the incremental build (dozens of targets).
