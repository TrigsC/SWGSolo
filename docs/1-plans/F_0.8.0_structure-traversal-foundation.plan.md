## Overview

Build a single, hardened, reusable **structure traversal** capability in the
`SimPlayerController` base class so that *any* PlayerBot (miner, PvE hunter,
PvP, future types) can reliably: go from the outside world into any structure
interior (POB cell), dwell there for any duration (a minute or an hour), then
find its way back out via the best exterior portal (same door or a different
one, depending on where it is inside), and resume whatever it was doing —
**including when combat starts mid-traversal** (combat-wins policy: pause,
fight where it stands, auto-resume). This is a **silo feature**: it ships with
its own scripted multi-scenario test harness bot, a structured PASS/FAIL
scenario matrix, maximal gated logging, and a dashboard section, so the
foundation is proven before PvE/PvP bots adopt it.

## Problem Statement

Cell/POB navigation machinery exists on `miner-ai` (F_0.4.8 entry fix, F_0.4.9
egress leg, F_0.4.10 nearest-exterior-portal, F_0.4.11 collector travel) but
it is **scattered, partially broken, and not a formal API**:

1. **Cross-building traversal is refused.** On `miner-ai`,
   `SimPlayerController::beginCellEgressIfNeeded` (SimPlayerController.cpp:345)
   unconditionally returns `false` for any cell target (`targetCell != nullptr`
   branch, :372-376), so a bot inside building A that needs a cell in building
   B has no walk-out-then-re-enter path. (This was root-caused during the
   F_0.7.x doctor/entertainer work — that fix stack is *uncommitted on
   `fix/doctor-buff-anchor`* and, per owner decision, is **not** the baseline;
   this feature re-implements the traversal-relevant parts fresh on `miner-ai`.)
2. **Engine egress pathfinding fails for asymmetric POBs.**
   `PathFinderManager::findPathFromCellToWorld` (PathFinderManager.cpp:740)
   logs `exitpath is nullptr` (e.g. `hospital_naboo.iff`, `hospital_corellia.iff`,
   cell 6): the interior-rooted `getPath(exitNode, exteriorNode)` A* search
   fails even though the entry direction works. Diagnosed causes (from the
   F_0.7.4d/e/f investigation, to be re-implemented here): the exit node is
   hinted with the *door* position instead of the agent's own cell position,
   and `findNearestGlobalNode(door)` can select an exterior global node that
   the source cell is not portal-linked to.
3. **Combat hard-blocks traversal.** `beginCellEgressIfNeeded` refuses while
   `agent->isInCombat()` (:347-349) and `checkArrival` bails on combat
   (:1093), with no stashed resume state — a bot attacked mid-traversal simply
   stalls and its traversal intent is lost or clobbered.
4. **No formal contract, no test coverage.** Callers (hunter buff approach,
   PvP collector travel) each hand-roll sequences of
   `moveToInterior`/`moveTo`/egress and each has independently hit one-off
   bugs (teleport-into-wall, wall-hug, stranded-in-hollow, wrong-door egress).
   There is no rerunnable scenario suite; every fix has required owner-observed
   live restarts.

## Solution Architecture

Three layers, all on the silo branch, all gated default-off:

1. **Engine correctness fix (PathFinderManager)** — make cell→world egress
   pathfinding succeed for every POB where entry succeeds. **Strictly a
   retry-after-legacy-failure**: the existing node selection and the
   interior-rooted `getPath(exitNode, exteriorNode)` run first, completely
   unchanged; only when that legacy attempt returns null (today's `exitpath
   is nullptr` error path) does the repair sequence run. This makes the
   "additive / current-failure-only" property true by construction —
   currently-working POBs never see the new code. Repair sequence (attempted
   in order until one yields a path), re-implemented fresh (the uncommitted
   `fix/doctor-buff-anchor` working tree may be *consulted as a reference
   diff*, but the silo authors its own commit):
   - Retry with the interior exit node re-hinted by the agent's own cell
     position (`pointA.getPoint()`), not the door — matches how the (working)
     entry direction selects a connected node.
   - Retry with the exterior global node the source cell is actually
     portal-linked to (map the cell's global-graph node IDs onto the exterior
     floor mesh via `getGlobalNode(globalID)`; choose the linked candidate
     nearest the door; skip when a cell exposes no linked node).
   - Final fallback: run the proven entry-rooted
     `getPath(exteriorNode, exitNode)` and reverse the node list, feeding the
     existing downstream processing (keeping the outdoor
     `findPathFromWorldToWorld` leg intact).

2. **Formal traversal state machine in `SimPlayerController` base** — one
   documented API that every subclass inherits with zero adoption code:
   - `enterStructure(worldPos, localPos, targetCell)` — from outdoors *or*
     from inside another building. Same cell / same building → interior nav;
     different building → egress leg (walk out the nearest exterior portal)
     then re-enter the target from outdoors via `moveToInterior` (the proven
     entry path). Replaces the unconditional cell-target refusal.
   - `exitStructure(outdoorDest)` — cell→outdoor via nearest exterior portal
     (`BuildingObject::getNearestExteriorPortalPoint`, existing), then resume
     to the real destination ("pick up where it left off").
   - A queryable traversal phase (`enum class StructureTraversalPhase`
     — `Idle / ApproachDoor / InteriorRoute / Egress / Reentry /
     CombatPaused / Resuming`; a scoped enum, because the base controller
     already has an unscoped state enum with an `IDLE` enumerator and a
     collision must be impossible) plus a durable **traversal intent** record
     that survives combat pauses: final target (world/local/cell), **owning
     structure context** (building OID + the entry/re-entry waypoint used),
     attempt budgets, and a generation counter. The structure context is what
     lets a recompute know that a bot standing at cell 0 inside an *enclosed
     outdoor pocket* (starport hollow) is still "inside" a structure and must
     re-enter a cell to get out — a bare outdoor intent would wrongly select
     a plain world move (the both-endpoints-cell-0 findPath limitation).
     `exitStructure` records the building being exited for the same reason,
     and the context persists across dwell (set on enter, cleared only when
     the bot is genuinely outdoors clear of the structure or state is reset).
   - Internally this consolidates and rewires the existing
     `moveToInterior` / `beginCellEgressIfNeeded` / `CELL_EGRESS_RESUME`
     machinery rather than duplicating it; egress-resume toward a cell target
     re-arms via `moveToInterior` (re-establishes `interiorApproachLeg`), not
     plain `moveTo`, so hybrid movement can never drop the cell.
   - All attempt budgets bounded; exhaustion funnels into the existing
     `onPathFailed` / recovery path (never a wedge). `prepareForRelocation`,
     recovery resets, and controller teardown all clear traversal state.

3. **Combat-wins pause/resume (owner-selected policy: always combat-wins)** —
   remove the `isInCombat()` hard-refusals *inside the gated path*; instead:
   - On combat start at any phase: freeze traversal (issue no further
     movement legs), keep the traversal intent stashed, phase →
     `CombatPaused`. The bot fights where it stands (stock behavior-tree /
     controller combat drives movement while paused — the traversal layer
     must not double-drive, mirroring the P.6.6 "traversal vs combat"
     single-driver lesson, inverted).
   - **Combat movement is non-preempting, and the traversal has its own
     generation.** Caller preemption (scenario 20) is defined as a *new
     intent* issued through the public API (`enterStructure` /
     `exitStructure` / plain `moveTo`) **from outside the traversal state
     machine** while the traversal is not combat-paused. Movement legs the
     state machine issues for itself (egress, re-entry, resume) go through a
     private internal move helper (equivalently: an explicit movement-origin
     discriminator on the shared path), so an internal leg can never cancel
     its own intent or advance the traversal generation. While phase is
     `CombatPaused`, movement issued by a combat driver goes through a
     dedicated non-preempting entry point (a combat-move variant/flag) that
     neither clears the stashed intent nor cancels the resume monitor — this
     is what PvP's `driveCombatMovement` will use at adoption time. To make
     that robust, the intent + resume monitor are tagged with a
     **traversal-specific generation counter**, *not* the general work-loop
     generation (which every ordinary `moveTo` advances): combat legs can
     churn the work-loop generation freely without erasing the traversal or
     orphaning its monitor. Only genuine intent changes (external public-API
     preemption, relocation/recovery, death, traversal completion/failure)
     advance the traversal generation.
   - **External calls during `CombatPaused` preempt too — uniformly.** An
     ordinary external public-API call *replaces* the stashed intent in
     every phase (advancing the traversal generation and re-arming the
     resume monitor against the new generation); what it can never do while
     combat is live is *move* the bot — the new intent enters `CombatPaused`
     frozen and is pursued once the peace predicate holds. One rule for all
     phases: external calls preempt; combat drivers use the dedicated
     non-preempting entry point; internal legs preempt nothing.
   - On combat start, the pause transition **schedules exactly one
     traversal-generation-tagged resume-monitor task** (recurring ~1s) that
     owns peace detection — regardless of *where* the pause was detected
     (`moveTo`, `onPathFound`, `checkArrival`, or an egress leg). This is
     required because a `CombatPaused` bot may have no pending arrival-check
     task at all, so no existing cadence can be relied on to notice peace.
     The monitor self-discards on stale traversal generation (preemption /
     relocation / death) and is the only writer of the pause→resume
     transition, so double scheduling is impossible.
   - **Peace is a compound predicate, not just engine combat state.** The
     engine's `isInCombat()` alone is insufficient: PvP's controller-driven
     combat clears engine combat state while its own engagement loop is
     still active (`SimPvPController.cpp:356-384` clears combat before
     moving), so an engine-only check would resume traversal into a live
     fight. The monitor's peace condition is `!agent->isInCombat()` **AND**
     a new base-class virtual `isCombatDriverActive()` returning false
     (base implementation: false; combat-capable controllers override it to
     report their engagement loop / combat lease) — both must hold
     continuously for the settle window before `Resuming` begins.
   - On combat end (peace predicate held through the settle delay): phase →
     `Resuming`, and **recompute the traversal from the bot's *current*
     position** toward the stashed final target — never replay the stale
     phase. Wherever combat dragged it (different room,
     different floor, outdoors, or an enclosed hollow — resolved via the
     stashed structure context), the recompute picks the correct leg type
     (interior route / egress / re-entry / plain move). Bounded resume
     attempts; exhaustion → `onPathFailed`.
   - Death/despawn/incapacitation mid-traversal clears all state (no
     dangling tasks — the existing work-loop generation counter pattern
     rejects stale scheduled tasks).

**Gating:** a new `structureTraversal` Lua config block, master
`enabled=false`. When off, every touched decision point takes the legacy
branch byte-for-byte (same standard F_0.4.11 was held to). The
PathFinderManager repair, being a retry that runs only after the legacy
attempt has already returned null, is a candidate for always-on in a later
release — but for the silo phase it too sits behind the gate so the binary
is provably inert until enabled, and scenario 1/3/4-class runs double as
regression coverage for previously-working POBs before any always-on
promotion is proposed.

**Test harness:** a scripted multi-scenario runner following the
`cellNavDiag` pattern (`SimCellNavDiagController`, spawn task, gated log):
- New `SimTraversalTestController` (subclass of `SimPlayerController`,
  declared alongside `SimCellNavDiagController` in SimPlayerController.h:366)
  that executes a Lua-configured **scenario table** sequentially, with an
  exact schema (authored in `sim_player_manager.lua`):
  ```
  structureTraversalTest.scenarios = {
    { name = "hospital_enter_exit",
      planet = "naboo",
      bots = 1,                       -- 2 for concurrency scenarios
      spawn = { {x=,y=,z=}, ... },    -- one entry per bot
      budgets = { enterMs=90000, exitMs=90000, totalMs=300000 },
      steps = {                       -- steps[botIndex] for bots>1
        { op="enter",  target={x=,y=,z=}, buildingOid=..., cellOid=... },
        { op="dwell",  ms=10000 },
        { op="combatInterrupt", ms=8000 },   -- spawns attacker, despawns after ms
        { op="exit",   dest={x=,y=,z=},
          -- optional mid-movement interrupt: a strictly sequential step list
          -- cannot start combat DURING a movement op, so movement steps may
          -- carry an armed trigger instead — the runner watches the bot's
          -- traversal phase and fires the attacker spawn mid-leg:
          interrupt = { phase="Egress", afterMs=500, durationMs=8000,
            -- optional deterministic displacement (scenarios 15/16): while
            -- the bot is CombatPaused, the runner repositions it to this
            -- point (cellOid=nil ⇒ outdoor world coords; cellOid set ⇒
            -- cell-local coords) via the DEDICATED combat-displacement
            -- path (below), simulating combat drift into another room or
            -- outdoors so the resume recompute runs from a KNOWN position:
            displace = { x=, y=, z=, cellOid=nil } } },
        { op="moveTo", dest={x=,y=,z=} },
      } },
    ...
  }
  ```
  Target-cell resolution is **explicit-first**: a step may pin `cellOid` (or
  `buildingOid` + cell name) for determinism; when only a world point is
  given, the F_0.4.7-style resolver maps it to a cell **with the F_0.4.8
  round-trip guard** (accept only if the cell-local candidate round-trips to
  within 3m of the requested world point). Per-op assertions are implicit
  (enter ⇒ agent parent == target cell within `enterMs`; exit ⇒ genuinely
  outdoors clear of the structure within `exitMs`; combatInterrupt ⇒ phase
  reached `CombatPaused` then left it after despawn; every step ⇒ no
  teleport/z-sanity anomaly).
- **Runner lifecycle (setup/reset algorithm):** scenarios run strictly
  sequentially. Between scenarios the runner performs a full reset: despawn
  any surviving attacker, then execute the **established safe relocation
  choreography exactly as `cancelTicketCollectorTravel`'s arrival-exit
  recovery does it** — `prepareForRelocation()` (also clears traversal
  state) → `Locker` on the agent → `setMovementState(OBLIVIOUS)` →
  `clearPatrolPoints` / `clearSavedPatrolPoints` / `clearCurrentPath` →
  `switchZone(zone, x, z, y, 0)` to the next scenario's planet/spawn →
  `setHomeLocation` at the new spawn — so no stale patrol/path state can win
  after a cross-planet reset; then verify the bot is alive and outdoors
  before starting. If a
  scenario ends with the bot dead/incapacitated (scenario 22 by design), the
  runner **respawns a fresh harness bot** via the same deferred spawn-task
  path and continues; the dead bot's scenario verdict is recorded first. For
  `bots = 2` scenarios the runner spawns/positions both bots and drives each
  bot's own step list, joining on both completing (or either failing) before
  the verdict.
- Combat scenarios: the harness spawns a short-lived hostile creature near
  the bot to trigger *real* combat, then despawns it after the scripted
  duration to trigger peace + auto-resume. The harness bot therefore needs an
  AI tree with live combat sockets (the `simHunter.lua` IDLE-only-override
  pattern, §10 ARCHI), not the no-op `simMiner` tree the diag artisan used.
  The new tree must be **registered** like its siblings: an
  `includeFile("simTraversalTest.lua")` line plus a `simTraversalTest`
  custom-AI-map entry (IDLE slot only) in `bin/scripts/ai/templates.lua`
  (see the existing `simMiner`/`simPvp`/`simHunter` entries at
  templates.lua:11-13 and :43-70) — without both, the tree never loads.
- Each scenario emits structured `PASS` / `FAIL(reason)` with per-step
  timings to the log **and** to a new dashboard section, with explicit
  assertions: reached target cell within budget; outdoors within budget;
  resumed post-combat and reached final target; **no teleport** (per-step
  world-position delta above a threshold = automatic FAIL); **z-sanity**
  (position vs floor/terrain within tolerance = no in-air / underground);
  state-cleanliness (no residual traversal state after scenario end).
- Rerunnable after every change: flip the Lua gate, restart, read the
  dashboard section — no in-game observation required for the core matrix.

**Logging (maximal, gated):** new `StructureTraversalDiagLog.h` (mirrors
`CellNavDiagLog.h` → writes `bin/log/structuretraversal.log`, master-gated by
`structureTraversal.logging`, dormant compiled-in when off). Tag families:
`ST_ENTER / ST_EGRESS / ST_REENTRY / ST_COMBAT_PAUSE / ST_RESUME /
ST_PHASE / ST_PATH / ST_TELEPORT_ANOMALY / ST_ZSANITY / ST_FAIL /
SCENARIO_*` — every phase transition, every path request/result (node count,
end cell, end distance), every anomaly, with agent OID + building/cell OIDs +
both coordinate spaces on every line (the world-coord-as-cell-local class of
bug is caught by logging both). The existing `CellNavDiagLog` engine traces
remain available under their own gate for cross-correlation. Anomaly
*counters* (teleports detected, egress path failures, resume failures,
pathfinder fallback activations) also aggregate into the dashboard section so
a regression is visible without reading logs.

### 2. PathFinderManager — cell→world egress repair

**File**: `MMOCoreORB/src/server/zone/managers/collision/PathFinderManager.cpp`

**Current state**: `findPathFromCellToWorld` (:740) picks
`exteriorNode = exteriorPathGraph->findNearestGlobalNode(transformedPosition)`
(:813) and errors `exitpath is nullptr` (:826) when the interior-rooted
`getPath` fails — hospitals reproduce this deterministically.

**Modifications** (all scoped inside `findPathFromCellToWorld`; the entry
direction `findPathFromWorldToCell` is NOT touched). **The legacy node
selection and legacy `getPath` run first, byte-for-byte unchanged; the new
code is a retry block entered only where today's code errors and returns
null** (:826):
- Retry 1 — interior exit-node re-hint: re-select the exit node using the
  agent's own cell position rather than the door-transformed position, and
  re-attempt `getPath`.
- Retry 2 — linked exterior-node selection: prefer the exterior global node
  portal-linked to the source cell's graph (iterate the source path graph's
  global nodes, map IDs onto the exterior floor mesh), nearest the door;
  skipped when no linked node exists; re-attempt `getPath`.
- Retry 3 — reversal fallback: entry-rooted `getPath(exteriorNode, exitNode)`
  + reverse node list into the existing downstream node-processing loop
  (outdoor final leg preserved).
- Gate + logging: the retry block runs only under the `structureTraversal`
  gate (silo phase); every retry activation + which retry succeeded logged
  (`ST_PATH` tag + dashboard counter).

### 3. SimPlayerController — formal traversal state machine

**Files**: `MMOCoreORB/src/server/zone/objects/creature/simplayer/SimPlayerController.{h,cpp}`

**Current state**: cell-egress fields (:144-152 in .h), `moveToInterior`
(.cpp:241), `beginCellEgressIfNeeded` (.cpp:345 — combat refusal :347, cell-
target refusal :372), `checkArrival` egress-resume (`CELL_EGRESS_RESUME`,
.cpp:1246) resuming via plain re-path, combat bail in `checkArrival` (:1093),
`prepareForRelocation` (.h:280) clearing interior/egress state.

**Modifications**:
- New `enum class StructureTraversalPhase` (scoped — avoids colliding with
  the existing unscoped controller state enum's `IDLE`) + intent struct
  (final target world/local/cell, owning-building OID + entry/re-entry
  waypoint, attempt counters, **traversal generation** — a new counter
  distinct from the work-loop generation) as base-class members; accessors
  (`getTraversalPhase()`, `isTraversalActive()`) for subclasses and
  diagnostics. A non-preempting combat-move entry point (variant/flag on
  `moveTo`) lets combat drivers move a `CombatPaused` bot without clearing
  the intent or advancing the traversal generation.
- New public API `enterStructure(...)` / `exitStructure(...)` implemented on
  top of the existing `moveToInterior` / egress machinery; `moveTo` overloads
  keep working unchanged for legacy callers (gate off ⇒ identical behavior).
  Internal state-machine legs (egress, re-entry, resume) route through a
  private internal move helper / movement-origin discriminator so they are
  never classified as external preemption — only externally-originated
  public-API calls cancel an active traversal.
- `beginCellEgressIfNeeded` (gated path): same-cell / same-building cell
  targets → return false (interior nav handles it); different-building cell
  target → egress with the *cell target stashed* in the resume record;
  `CELL_EGRESS_RESUME` re-issues via `moveToInterior` when the stashed resume
  target is a cell.
- Combat interlock (gated path): replace the `isInCombat()` refusals with
  pause bookkeeping (`ST_COMBAT_PAUSE`); the pause transition schedules
  exactly one **traversal-generation-tagged resume-monitor task**
  (recurring ~1s) that owns peace detection and flips
  `CombatPaused → Resuming` after the settle delay, then triggers the
  recompute-from-current-position. The monitor is scheduled at every pause
  entry point (`moveTo`, `onPathFound`, `checkArrival`, egress legs) — a
  paused bot may have no live arrival-check task, so no existing cadence can
  be relied on — and self-discards on stale traversal generation, making it
  the single writer of the resume transition. Peace = `!isInCombat()` AND
  `!isCombatDriverActive()` (new base virtual, default false, overridden by
  combat-capable controllers) held through the settle window. Combat-driver
  movement while paused advances only the work-loop generation, never the
  traversal generation, so it cannot orphan the monitor or the intent.
- State hygiene: traversal state cleared (and traversal generation advanced)
  in `prepareForRelocation`, recovery resets, `onPathFailed`, public-API
  preemption, destructor; movement legs remain tagged with the work-loop
  generation (existing pattern, .cpp:412) while traversal-owned tasks (the
  resume monitor) are tagged with the traversal generation.
- Teleport/z-sanity watchdogs: in the gated path, each applied movement step
  compares previous vs new world position (threshold from config) and floor/
  terrain height; violations log `ST_TELEPORT_ANOMALY` / `ST_ZSANITY` and
  bump dashboard counters (log-only — no behavior change on anomaly, this is
  the "find any crazy one-off issue" instrumentation).

## Scenario Matrix (the test cases)

Grouped; each is one Lua scenario entry with explicit assertions. Buildings
chosen to cover the known topology classes: single-door POB (Mos Eisley
cantina, bldg 1082874), asymmetric-graph POB (Theed/Coronet hospital — the
`exitpath is nullptr` class), multi-door multi-cell POB (Mos Eisley starport
1106368), enclosed-outdoor-hollow (starport landing pad, cell 0), hangar-in-
cell (Theed starport).

**A. Core ingress/egress**
1. Outdoor → cantina cell → dwell 10s → exit → outdoor dest (baseline).
2. Outdoor → hospital deep cell → dwell → exit (exercises the engine fix;
   FAIL today).
3. Outdoor → starport front hall → exit (multi-door: must leave via FRONT,
   asserted by exit-point distance to the entry door).
4. Starport deep cell (foyer4-class) → exit (multi-cell egress route).
5. Enter → immediate exit (zero dwell; state-machine reentrancy).
6. Long dwell (10 min scaled stand-in for "an hour") → exit (state decay).
7. Enter from behind/odd angle (nearest-portal entry selection).
8. Multi-floor: upper-floor cell → exit (elevation + z-sanity).

**B. Cross-building**
9. Hospital cell → cantina cell (egress + re-enter — the F_0.7.4 killer).
10. Cantina cell → hospital cell (reverse; both orders must work).
11. Cell → enclosed hollow (starport collector pattern: interior-directed
    route with egress suppressed) → back out via re-enter + egress.

**C. Combat-wins (attacker spawned by harness).** Scenarios 12-14 and 17 use
the step-attached `interrupt = {phase=..., afterMs=...}` trigger so combat
starts *during* the named movement phase (`ApproachDoor` / `InteriorRoute` /
`Egress` / `Reentry`), not between steps; 15-16 additionally use
`interrupt.displace` to move the paused bot deterministically (different
cell / outdoors) before peace, so the resume recompute is tested from a
known position rather than relying on emergent combat drift.
`interrupt.displace` deliberately does **not** use the full safe-relocation
choreography — `prepareForRelocation` clears the intent and advances the
traversal generation, which would invalidate the very state under test, and
`switchZone(...,0)` cannot place a bot inside a cell. Instead it uses a
**dedicated combat-displacement path**: under the agent `Locker`, set
`OBLIVIOUS`, clear current path + patrol + saved patrol points, and advance
only the *work-loop* generation (stale movement tasks self-discard), then
reposition with `switchZone(zone, x, z, y, parentID = cellOid or 0)` —
cell-local coordinates when a cell OID is given, world coordinates for
outdoor — and `setHomeLocation` at the displaced position (so stock AI can
neither restore the pre-displacement route nor home-pull the bot back
before resume), while preserving the `CombatPaused` phase, the stashed
intent, the traversal generation, and the live resume monitor. The helper
also **re-baselines the teleport/z-sanity watchdog** (records the one
expected position jump) so the intentional relocation does not trip the
mandatory no-teleport assertion — any *other* jump in the scenario still
fails it.
12. Combat during door approach (outdoors) → fight → resume enter.
13. Combat mid-interior-route → fight in cell → resume to target cell.
14. Combat during egress → fight → resume exit + outdoor destination.
15. Combat drags bot into a different room/cell → resume recomputes.
16. Combat ends with bot back outdoors → resume recomputes (skip egress).
17. Combat during the re-entry leg of a cross-building traversal.
18. Attacker dies instantly (near-zero combat) → clean pause/resume cycle.

**D. Failure & recovery**
19. Unreachable/disconnected target cell → bounded attempts → clean
    `onPathFailed`, bot recovered outdoors, phase returns to `Idle`.
20. New `moveTo`/`enterStructure` issued mid-traversal (caller preemption) →
    old traversal cancels cleanly, no stale resume fires.
21. `prepareForRelocation` (recovery teleport) mid-traversal → all state
    cleared, no stale task acts.
22. Bot incapacitated/killed mid-traversal → no dangling tasks, no wedge;
    the runner records the verdict, respawns a fresh harness bot, and the
    suite continues (lifecycle rule).

**E. Stress & concurrency**
23. 10× sequential enter/exit cycles, same building (attempt-counter and
    generation-counter leak check; all cycles must PASS).
24. Two harness bots traversing the same building simultaneously (opposite
    directions where possible).
25. Bot A dwelling inside while bot B enters and exits (interference).

Every scenario additionally asserts, throughout: no teleport-anomaly, no
z-sanity violation, and zero residual traversal state at scenario end.

## Technical Considerations

- **Pattern Usage**: `SimCellNavDiagController` + `CellNavDiagSpawnTask` +
  `CellNavDiagLog` are the explicit precedents for harness bot, deferred
  spawn, and gated file logging. `stationTravel` is the dashboard-section
  precedent. The traversal state machine consolidates existing base-class
  machinery rather than adding a parallel driver (the A/B dual-driver lesson).
- **Locking & References**: match existing choreography exactly —
  `getNearestExteriorPortalPoint`/`getEjectionPoint` reads under a short
  building `Locker` released before scheduling the async pathfind (as
  `beginCellEgressIfNeeded` does today, .cpp:388-394); cells/buildings held
  via `ManagedReference`; harness results under a manager-side mutex with
  agent locks never taken inside it (P.6.6b rule); scheduled tasks carry the
  work-loop generation. No new lock orderings are introduced.
- **IDL Impact**: none expected. `SimPlayerController` is not IDL-managed;
  `BuildingObject::getNearestExteriorPortalPoint` already exists on
  `miner-ai`; PathFinderManager is a plain manager. If implementation
  discovers a needed `BuildingObject` addition, it goes through the `.idl` +
  regen path (never hand-edit `src/autogen/`).
- **C++ vs Lua Placement**: state machine, pathfinding, watchdogs = C++ (hot
  path, structural). All tunables, gates, and the entire scenario matrix =
  Lua (`sim_player_manager.lua`), editable without rebuild.
- **Gating & Simulation-Only**: `structureTraversal.enabled=false` and
  `structureTraversalTest.enabled=false` by default; gate-off ⇒ legacy
  behavior byte-for-byte. Nothing here mutates inventory/credits/market;
  harness attacker spawns use existing NPC spawn APIs and despawn after use.
- **Dashboard Visibility**: new `structureTraversal` section (config echo,
  live phases, scenario matrix, anomaly counters) — the acceptance surface.
- **Live Verification Plan**: (1) build clean `-Werror`; (2) owner restart
  with harness enabled on tatooine (cantina/starport) + a naboo/corellia
  hospital scenario pass; (3) read `structureTraversal` dashboard section:
  all scenarios PASS, anomaly counters 0; (4) `log/pathfinder.log` shows no
  `exitpath is nullptr` for hospitals during the run; (5) gate-off regression
  snapshot: miners/hunters/PvP dashboards unchanged vs pre-restart baseline.
- **Edge Cases**: combat relocation into arbitrary cells; both-endpoints-
  cell-0 findPath limitation (hollow ↔ outside requires the re-enter rule —
  encoded in the recompute logic, scenario 11); zero-dwell reentrancy;
  attempt-budget refresh semantics (only reset when the situation genuinely
  changes — outdoors again or generation advance); stale scheduled tasks
  after preemption/relocation/death.

  controller-combat half of the compound peace predicate.
