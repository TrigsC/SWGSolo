# Sim-Bot Combat Observability (F_0.9.6-D1) Implementation Plan

**Kind**: diagnostic sub-chunk (D-chunk), following the `F_0.8.0-D1/-D2b/-D7/-D8`
precedent — a D-chunk takes no version of its own and ships with its parent.
**Parent**: F_0.9.6 (P.10g novice early-game loop)
**Gate**: `combatDiag.logging` (default off)
**Schema**: none
**Scope**: diagnose only. The fix is a separate chunk, per the
F_0.4.7-diagnostics → F_0.4.8-fix precedent.

## Overview

Sim bots enter combat and never attack. `CombatManager::startCombat` returns
true, the target is spawned 3 m away, `activateAiBehavior(true)` is called — and
then nothing happens for ten minutes. This chunk adds default-off, run-scoped
instrumentation that makes the AI attack-selection decision path observable, so
the cause can be read from live evidence instead of inferred. It changes no
behaviour and fixes nothing.

## Problem Statement

`unarmed_novice_kills_nuna` and `harness_bot_kills_nuna_and_earns_xp` both fail
`step_budget_exceeded` with `kills=0`, deterministically, across five runs on two
different binaries. The failure is **pre-existing**: it reproduces on a
marker-verified HEAD binary with no F_0.9.6 code present (all five F_0.9.6
strings absent, 339,858,816 bytes vs 340,214,416 for the F_0.9.6 build), and
standalone with no other scenario able to contaminate state. F_0.9.5's receipt
(`live_p10f-skill-training_20260906-223926`) records both scenarios passing with
`kills=1`, `totalAwarded=93`, and `git log` shows **no commit since
`a9cbfd2221` touching** `managers/combat`, `objects/creature/ai`,
`scripts/mobile` or `scripts/object/weapon`. Same code, different outcome —
so the delta is runtime/world/database state.

**The sharpest available characterisation**: it is not "the bot cannot attack" —
**neither side attacks**. A novice stood 3 m from a `dwarf_nuna` for ten minutes
with `hunterDeathsTotal = 0`, while that same creature is recorded killing a
weak novice in ~17 s. That is consistent with a single failure: the bot never
lands the first hit, so nothing escalates and the creature never retaliates.

Ten candidates have already been eliminated with evidence (full table in
`docs/4-unit-tests/live_p10g-novice-early-game_20260909-112152-....md`):
F_0.9.6 code, AI template files, AI map assignment, global AI config, server
`LOADING` state, load saturation, command loading, body/equip failure, weapon
configuration (`hunterWeaponTemplate = rifle_t21.iff`), and body-slot
contention.

**Why this needs code.** The remaining candidates are invisible:

- `DEBUG_AI_ATTACK` is commented out at `AiAgentImplementation.cpp:112`, so the
  attack-selection trace is not compiled.
- The per-agent `aiDebug` blackboard trace in `bt/Behavior.cpp:67-79` has no
  external setter, and its non-`aiDebug` branch broadcasts *spatial chat*, not
  log lines — useless without a connected client.
- `pveActivity` exposes no per-agent `followObject`, defender count, or command
  queue depth.

This is TRIP-verify's `OBSERVABILITY_GAP` condition.

## Primary root-cause candidate (found during plan review, 2026-09-11)

Plan review surfaced a **fork-consistency defect** that explains every observed
symptom. `activateAiBehavior` carries a sim-bot bypass this fork added
(`:6007`):

```
if (getSimAlwaysActive() || getSimPlayerBot() || !getDespawnOnNoPlayerInRange())
    alwaysActive = true;
```

`runBehaviorTree` has the **same gate with no such bypass** (`:5108-5119`):

```
bool alwaysActive = false;                      // DEBUG_AI off -> always false
...
if ((!alwaysActive && numberOfPlayersInRange.get() <= 0
     && getFollowObject().get() == nullptr && !isRetreating()) || ...) {
    cancelBehaviorEvent();
    setFollowObject(nullptr);
    return;                                     // re-arm at :5143 unreachable
}
```

This server runs with **zero human players** by design, so
`numberOfPlayersInRange.get() <= 0` is permanently true and the gate reduces to
"no follow object and not retreating". The branch then does two things that make
it **self-latching**: it cancels the behaviour event, and it force-clears the
follow object. Because the event is cancelled, the `activateAiBehavior(true)`
re-arm at the end of `runBehaviorTree` is never reached — so a single qualifying
tick permanently removes that agent from AI scheduling until something external
calls `activateAiBehavior` again.

It accounts for every observation: the bot never attacks; the spawned creature
never attacks (it is subject to the identical gate, also with no players in
range); the failure is deterministic and silent; and it passed on 2026-09-06
only when the follow object happened to be set before the first tick won the
race.

**This chunk's job is therefore to CONFIRM or KILL this candidate**, not to
explore blindly. It remains diagnose-only — the fix is a separate chunk.

**Secondary hypotheses, if the candidate is disproved:**

1. **The tree runs but has no follow object.**
   `selectDefaultAttack` (`:3310`) computes a command but **enqueues it only
   when `getFollowObject()` is non-null** (`:3449-3459`).
2. **The command enqueues but never executes** (queue stuffing, cooldown, HAM,
   `validateStateAttack`).

**Hypothesis explicitly RETRACTED.** An earlier draft claimed the 3600-second
IDLE `Wait` parks the agent for an hour and made `already_scheduled_noop` the
headline signal. That is **wrong**. `Wait::execute`
(`bt/leaf/SimpleActions.h:419-435`) only calls `setWait()`, writes an
`isWaiting` blackboard flag and returns `RUNNING`; the behaviour task keeps
re-arming at `BEHAVIORINTERVAL = 400` ms (`AiAgent.idl:208`,
`AiAgentImplementation.cpp:5143`). A no-op activation therefore delays
re-evaluation by about one tick, not 3600 s. The outcome is still worth
labelling, but it is not evidence of paralysis and must not be prioritised as
such.

## Solution Architecture

Three pieces, mirroring the established diagnostic pattern exactly.

```
(1) SimCombatDiagLog.h      header-only, default-off, log/simcombat.log
                            + a bounded OID allowlist (who to trace)
(2) engine trace points     AiAgentImplementation: runBehaviorTree (PRIMARY),
                            activateAiBehavior, selectDefaultAttack,
                            selectSpecialAttack, getNextAction
                            -- READ-ONLY, no behaviour change
(3) dashboard section       pveActivity.combatDiag: per-traced-agent
                            followObject / defenders / queue depth / posture
```

### Why an allowlist rather than a global switch

The trace sits in a per-combat-tick path shared by **every NPC on the server**.
A global switch would write thousands of lines per second. The diag class
therefore holds a small OID set, and a trace point is inert unless the agent's
OID is in it. Population is owned by the sim layer:

- `spawnPveIdentityBody` adds each roster/harness bot body OID;
- `spawnPlayerBotParityKillTarget` adds the spawned kill-target OID — this is
  what makes the creature's own side observable and separates "the creature is
  idle too" from "the creature is simply waiting to be hit";
- deregistration must cover **every** teardown path, not just the happy one:
  death finalisation, identity retirement, governor drain/disable,
  duplicate-attachment destruction, parity-harness cleanup, and spawn failure
  (including a `startCombat` that returns false). The set is also cleared
  wholesale on harness cleanup and roster reload so it can never grow
  unbounded.

**`AiAgentImplementation` must not call into `SimPlayerManager`** to ask whether
to trace. That would invert the layering and, worse, take a manager mutex from
an AI thread that may already hold an agent lock — the ABBA shape ARCHI §12
records as a real deadlock. The allowlist lives in the header-only class; the
manager pushes into it.

## Implementation Details

### 1. The diagnostic log class

**File**: `src/server/zone/objects/creature/simplayer/SimCombatDiagLog.h` (new)

**Pattern to copy**: `MissionDiagLog.h` — header-only, a function-local
`static bool` shared across translation units, `setLoggingEnabled` flipped from
`sim_player_manager.lua`, one `log/<name>.log` file, every line `key=value` as
`t=<ms> ev=<EVENT> oid=<oid> ...` so it greps and splits cleanly.

**One deliberate deviation from that pattern**: `MissionDiagLog::write` returns
silently when the file cannot be opened. For this chunk that is unacceptable —
`logging=true` producing an empty log would be **indistinguishable from the
paralysis under investigation**, and we would draw a conclusion from the absence
of evidence. The writer therefore counts failures and exposes `writeErrors` /
`lastWriteError`, which are surfaced in `pveActivity.combatDiag` and must be
asserted **zero** before any finding is accepted.

**Additions beyond that pattern**:

- An OID allowlist (`addTraced` / `removeTraced` / `clearTraced` / `isTraced`).
- A `Mutex` guarding the set, because AI threads read it while the PvE
  maintenance and harness threads write it.
- **The gate flag must be `std::atomic<bool>`, not a plain `bool`.** The
  existing diag classes use a bare `bool` and this plan will not copy that:
  concurrent read/write of a non-atomic `bool` is undefined behaviour, not a
  benign race, and this flag is written from the config-refresh thread while AI
  threads read it every tick. Same for the error counter (`std::atomic<uint64>`).
  `lastWriteError` is a `String` and needs the mutex.
- **File appends must be serialised.** Multiple AI threads can emit
  concurrently; two unsynchronised `ofstream` appends can interleave mid-line
  and corrupt the very evidence being collected. Writes take a dedicated write
  mutex (separate from the allowlist mutex, and never held across it).
- **Failure must be checked after write and flush, not only after open.** A
  successful `open` says nothing about a failed write — checking only the open
  would reproduce the silent-failure trap this design exists to avoid.
- **Check order is load-bearing**: every trace point tests the atomic
  `isLoggingEnabled()` **first** and only then takes the mutex for
  `isTraced(oid)`. Reversed, a default-off server would pay a mutex acquisition
  per agent per behaviour tick (every 400 ms, every NPC).
- **Runtime config changes** (`setLoggingEnabled`, `setMaxLinesPerAgent`) are
  applied through the atomics / under the mutex, never as plain assignments
  racing live readers.
- A per-OID emit budget (`maxLinesPerAgent`, Lua-tunable) so a stuck agent
  cannot fill the disk. **Budget it against the real cadence**: the behaviour
  task ticks every 400 ms, so a 600 s window is ~1500 invocations per agent and
  several lines each — a 2000-line budget would expire in well under a minute
  and silently truncate the run. Default to **transition-only** emission (log a
  line when an outcome *changes*, plus the periodic heartbeat) with a rate limit
  for repeated identical outcomes, and size the budget from
  `window / cadence * linesPerTick` rather than a round number.
- A **run identifier**. The logger appends across runs, so every line carries
  `run=<id>` and `setLoggingEnabled(true)` starts a new run id and resets
  per-OID budgets; otherwise "run-scoped" is a claim the file cannot support.

### 2. Engine trace points

**File**: `src/server/zone/objects/creature/ai/AiAgentImplementation.cpp`

**Current state**: `runBehaviorTree` (`:5096`), `selectDefaultAttack` (`:3310`),
`selectSpecialAttack` (`:2866`, `:3219`), `getNextAction` (`:3469`) and
`activateAiBehavior` (`:5995`) all make silent decisions. `activateAiBehavior`
already has exactly the diagnostic text we want at `:6019-6028`, but behind
`#ifdef DEBUG_AI`.

**`runBehaviorTree` is the PRIMARY trace point** and the one the root-cause
candidate turns on. Without it the log can report "scheduled" followed by
silence, never showing that the tree was entered and immediately cancelled.
Emit, per invocation:

| Outcome | Source |
|---|---|
| `tree_early_return_noop` | `:5098` zone/AIENABLED guard — returns, **leaves the event alone** |
| `tree_dead_cancelled` | `:5101` `isDead()` → `cancelBehaviorEvent()` + `setFollowObject(nullptr)` |
| `tree_gate_cancelled` | `:5115` the no-players/no-follow gate → cancel + clear follow object (**the candidate**) |
| `tree_ran` | root `doAction` executed — carry the returned `Behavior::Status` and `nextBehaviorInterval` |
| `tree_exception_cancelled` | the `catch (Exception&)` at `:5144` |

`tree_gate_cancelled` must carry every operand of that gate —
`numberOfPlayersInRange`, whether `getFollowObject()` was set **on entry**,
`isRetreating`, `isServerLoading`, `isServerShuttingDown` — plus the sim flags
(`getSimAlwaysActive`, `getSimPlayerBot`, `getDespawnOnNoPlayerInRange`) that
`activateAiBehavior` honours and this gate does not. That single line
confirms or kills the candidate outright.

`tree_ran` must also record enough running-chain / socket state to distinguish
"sat in IDLE" from "failed earlier in the root target/equip/attack chain" —
**"never reached `selectDefaultAttack`" does not prove the agent stayed in
IDLE.**

**Modifications** — all read-only; no control flow, no state, no ordering change:

- `activateAiBehavior` (`:5995`): emit one line per call with an **explicit
  outcome**, because "did not cancel" is not the same as "woke the tree". The
  scheduling block at `:6035-6044` has five distinguishable results and they
  must be reported separately:

  | Outcome | Source condition |
  |---|---|
  | `early_return_noop` | the `:5996` AIENABLED/zone guard — returns and **leaves any existing event alone** |
  | `gate_cancelled` | the `:6014` gate — calls **`cancelBehaviorEvent()`** before returning; carry which sub-condition tripped |
  | `created_scheduled` | `behaviorEvent == nullptr` → new event scheduled |
  | `rescheduled` | existing event, `reschedule` **true**, `!isScheduled()` → scheduled |
  | `already_scheduled_noop` | existing event, `reschedule` **true**, **already scheduled** → **nothing happens** |
  | `existing_no_reschedule_noop` | existing event, `reschedule` **false** (whatever its scheduled state) → **nothing happens** |

  These are **mutually exclusive and total**, matching the branch structure
  at `:6035-6044` exactly: `nullptr` → create; else `reschedule` → (`isScheduled`
  ? noop : schedule); else → noop. `already_scheduled_noop` must be qualified
  with `reschedule == true`, or a scheduled event passed `false` would match two
  rows and the log would be ambiguous where it most needs to be precise.

  That last row matters more than it looks: `activateAiBehavior`'s `reschedule`
  parameter **defaults to `false`** (`AiAgent.idl:368`), so every caller that
  does not pass `true` explicitly lands there and the `else if (reschedule)`
  branch at `:6037` is skipped entirely.

  **Outcome must be proven, not inferred.** `AiBehaviorEvent::schedule`
  (`events/AiBehaviorEvent.h:72-112`) wraps `Task::schedule` in its own
  `try`/`catch (...)` that only decrements `AiMap::scheduledBehaviorEvents` —
  it swallows **every** exception silently. The outer
  `catch (IllegalArgumentException&)` at `AiAgentImplementation.cpp:6042` is
  therefore unreachable, and a `schedule_exception` outcome derived from it
  would be dead code. Two changes instead:

  - add one trace emit inside that existing `catch (...)` in
    `AiBehaviorEvent.h`. **This is the authoritative failure signal** — it is
    the only place a swallowed scheduling failure is observable at all;
  - emit `scheduledAfter=<bool>` by reading `behaviorEvent->isScheduled()`
    **after** the schedule call, still under `behaviorEventMutex`, but treat it
    strictly as **instantaneous state, never as a success postcondition**.
    `TimedTaskQueue` calls `task->clearTaskScheduler()` the moment it dequeues
    a task (`engine3/.../TimedTaskQueue.cpp:222`), so a correctly scheduled
    10 ms event can legitimately read `false` a few milliseconds later.
    Reading `scheduledAfter=false` as "the schedule failed" would manufacture a
    false root cause — exactly the error this chunk exists to avoid. Failure is
    established by the inner-catch line, or not at all.

  **`already_scheduled_noop` is informational, not evidence of paralysis.**
  `activateAiBehavior(true)` only schedules when the event is not already
  scheduled, so an external wake-up call can be a no-op — but the behaviour task
  re-arms itself every `BEHAVIORINTERVAL` (400 ms), so the cost is roughly one
  tick of delayed re-evaluation. It is recorded for completeness and to show the
  wake-up contract's real (small) effect; the paralysis signal lives in
  `runBehaviorTree`'s `tree_gate_cancelled`, not here. Carry the operands
  already assembled for the `DEBUG_AI` block — `playersInRange`, whether `getFollowObject()` is set,
  `isRetreating`, `getSimAlwaysActive`, `getSimPlayerBot`,
  `getDespawnOnNoPlayerInRange`, the derived `alwaysActive` — plus
  `nextBehaviorInterval`, whether the event existed on entry, and whether it was
  already scheduled on entry.
- `selectDefaultAttack` (`:3310`, and at the enqueue decision `:3449-3459`):
  emit `ATTACK_SELECT` with the chosen command, whether it came from the
  priority list / heuristic / `defaultattack` fallback, the command-queue size,
  and — critically — whether `getFollowObject()` was null so **no enqueue
  happened**. **This answers hypothesis 2.**
- `selectSpecialAttack` (`:2866`, `:3219`): emit `SPECIAL_SELECT` with the
  candidate count and the reject reason (no candidates / HAM unaffordable /
  `getQueueCommand` null).
- `getNextAction` (`:3469`): emit `NEXT_ACTION` with the resolved
  `nextActionCRC` and whether `getQueueCommand` returned null.

**Selection logging alone cannot prove enqueue or execution.**
`selectDefaultAttack` does its own conditional queue stuffing (`:3449-3459`,
only when `getCommandQueueSize() < 2`), while the behaviour tree separately
calls `enqueueAttack`. A queue size of zero in the heartbeat therefore cannot
distinguish "never inserted" from "inserted and drained immediately". Both
enqueue paths must log **queue size before and after** plus an explicit
`enqueue_outcome` (`enqueued` / `suppressed_queue_full` /
`suppressed_null_follow`). Execution itself is only partially covered: unless
`validateStateAttack` rejection reasons or the command result are also
instrumented, hypothesis 3 cannot be closed — so **exit question 4 is
deliberately narrowed** to "was a command enqueued, and did the queue depth
change", with full execution tracing deferred to a follow-up if the candidate
is disproved.

Do **not** re-enable the `DEBUG_AI_ATTACK` `#define`: it is compile-time and
unconditional, so it cannot be turned off on a live server. The new trace is
runtime-gated, which is the whole point.

### 3. Config surface

**File**: `bin/scripts/managers/sim_player_manager.lua`

A new top-level `combatDiag` block beside the existing `travelDiag`,
`missionDiag` and `cellNavDiag` blocks, matching their comment style (what it
exists for, that it is compiled in and free when off, that flipping it needs no
rebuild):

- `logging` (default **false**) — master gate for all `log/simcombat.log` output.
- `traceSpawnedTargets` (default true) — include the harness kill target, so the
  creature's side is observable.
- `maxLinesPerAgent` — per-OID emit budget.
- `heartbeatSeconds` — periodic "still in this state" line, mirroring
  `travelDiag.heartbeatSeconds`; a paralysed agent emits no transitions at all,
  so without a heartbeat the log is silent in exactly the failure we are chasing.
  **Its effective value is bounded below by the emitting lane's own cadence**:
  the PvE maintenance task ticks every `pveMaintenanceIntervalSeconds`
  (default **30**, `SimPlayerManager.h:2346`), so the real interval is
  `max(heartbeatSeconds, pveMaintenanceIntervalSeconds)`. Default it to 30 to
  match rather than advertise a cadence the caller cannot honour; if finer
  granularity is needed for a diagnostic run, lower
  `pveConfig.maintenanceIntervalSeconds` for that run and restore it afterwards.
  The plan does not add a second scheduler just for a heartbeat.

**The heartbeat needs a caller that does not depend on the behaviour tree.**
None of the four engine trace points runs while an agent is stalled — that is
the defect. The heartbeat is therefore emitted from the **PvE maintenance lane**
(`runPveFoundationMaintenanceTask`, which already ticks every
`pveMaintenanceIntervalSeconds`), which walks the traced-OID snapshot and emits
one `AGENT_HEARTBEAT` line per agent carrying the same fields as the dashboard
row: follow object, defender count, command-queue size, posture, `inCombat`,
whether the behaviour event exists and is scheduled, and HAM. It resolves each
agent through `ZoneServer::getObject`, takes the agent lock briefly, and copies
out before formatting — never holding a manager mutex across the agent lock.
This guarantees evidence even in total paralysis, which is the case we most need
to see.

Wired in `SimPlayerManager::loadLuaConfig` next to the existing
`MissionDiagLog::setLoggingEnabled` / `CellNavDiagLog::setLoggingEnabled` calls
(`SimPlayerManager.cpp:6617-6665`).

### 4. Allowlist population and dashboard

**File**: `src/server/zone/objects/creature/simplayer/SimPlayerManager.cpp`

- `spawnPveIdentityBody` (around the existing `setCustomAiMap` / `setAITemplate`
  block at `:15427`): register the new body OID.
- `spawnPlayerBotParityKillTarget`: register the target OID **before** the
  `CombatManager::startCombat` call at `:11712-11713`, not after. `startCombat`
  releases the target's lock on return, so its live AI task can run before
  registration and the first — possibly only — selection event would be lost.
  Deregister idempotently if `startCombat` fails and the target is despawned.
  Gated on `traceSpawnedTargets`.
- `despawnPlayerBotParityKillTarget`, `drainPveIdentityBody` and the harness
  cleanup path: deregister; clear wholesale on roster reload, alongside the
  existing `pveDeathSpawnOverrides.removeAll()` sites.
- Dashboard: a `combatDiag` object inside the existing `pveActivity` section
  (not a new root, so no frontend change is required) carrying `logging`,
  `tracedCount`, and a bounded `agents` array with, per traced OID:
  `followObjectOid`, `defenderCount`, `commandQueueSize`, `posture`,
  `inCombat`, `aiTemplate`, `hamHealth`, plus whether the behaviour event exists
  and is currently scheduled. The section also carries `writeErrors` and
  `lastWriteError` so a silent log failure is visible rather than mistaken for
  paralysis. Assembled on the REST thread from `snapshotTraced()` (which
  releases the allowlist mutex before any agent lock is taken), following the
  `getPlayerBotProgressionDashboard` shape.

## Technical Considerations

- **Pattern usage**: `MissionDiagLog` / `TravelDiagLog` / `CellNavDiagLog` are
  the exact precedent — header-only, default-off, own log file, key=value lines,
  Lua-flipped without a rebuild.
- **Locking & references**: the allowlist mutex is the only new lock, it is
  leaf-level (nothing is acquired while holding it), and the plain-bool check
  precedes it. Dashboard snapshots take the agent lock briefly and release it
  before serialising, as `buildBodyProgressionSnapshot` does. Agents are held
  via `ManagedReference`. **No manager mutex may be taken from an
  `AiAgentImplementation` trace point.**
- **IDL impact**: **an `AiAgent.idl` change IS required** — an earlier draft
  wrongly said none was expected. `behaviorEvent` is `protected` (`:54`),
  `behaviorEventMutex` is `private` (`:126`) and `aiTemplate` is `private`
  (`:182`), so neither the dashboard nor the heartbeat can read behaviour-event
  state or the AI template today. Add **one read-only diagnostic snapshot
  accessor** on `AiAgent` that returns a small POD — behaviour-event exists,
  behaviour-event scheduled, `aiTemplate`, follow-object OID, defender count,
  command-queue size, posture, `inCombat`, HAM — assembled internally **under
  `behaviorEventMutex`** and returned by value. The manager must never be handed
  the event pointer or be expected to reach the private mutex. `src/autogen/`
  regenerates; it is never hand-edited. Expect build fan-out (F_0.9.1's single
  additive `.idl` line took the incremental build from 17 to 89 targets).
- **C++ vs Lua placement**: all knobs in Lua; C++ holds only the emit points.
- **Gating**: `combatDiag.logging` default off. With it off the change must be
  **behaviourally identical** to today — the only cost is one static bool test
  per trace point.
- **Simulation safety**: read-only. No inventory, credit, market, XP, skill or
  persistence mutation. This chunk cannot alter combat outcomes, which also
  means it cannot mask the defect it is measuring.
- **Shared-engine caution**: `AiAgentImplementation.cpp` is shared by every NPC
  in the world. That is why the trace is read-only, allowlisted, and why the
  compile-time `DEBUG_AI_ATTACK` is deliberately left off.
- **Live verification plan**: enable `combatDiag.logging`, run the harness's
  `unarmed_novice_kills_nuna` scenario standalone (the trimmed single-scenario
  config used for the HEAD A/B), then read `log/simcombat.log` plus
  `pveActivity.combatDiag`. The chunk succeeds when the log **answers the exit
  questions below**, not merely when it produces output.
- **Edge cases**: an agent destroyed mid-trace (deregistration must be
  idempotent); the allowlist surviving a harness abort; log growth over a 600 s
  window (bounded by `maxLinesPerAgent`); the spawned target despawning before
  its first tick; `getFollowObject()` racing a concurrent clear.

## Exit criteria — the questions this run must answer

A diagnostic chunk is done when it has decided something. This run must return a
definite yes/no for each:

1. **Does `runBehaviorTree` reach the root at all, or does the `:5115` gate
   cancel it?** If `tree_gate_cancelled` appears with `playersInRange=0` and
   `followObject` unset while the sim flags are set, the root-cause candidate is
   **confirmed** and the chunk is done.
2. Does `activateAiBehavior` schedule, no-op, or cancel — and which outcome?
3. If the tree runs, where in the root chain does it stop: IDLE, or an earlier
   target/equip/attack socket failure?
4. Is a command enqueued (queue depth before/after, explicit
   `enqueue_outcome`)? Full execution tracing is out of scope unless (1) is
   disproved.
5. Does the **spawned target** show the same `tree_gate_cancelled` line? That
   distinguishes "the creature's AI is cancelled too" from "the creature is
   simply waiting to be hit".

If the answers do not isolate the cause, the chunk reports that honestly and
names the next missing fact rather than guessing.

## Performance & Cost Impact

Off (the shipped default): one function-local `static bool` test per trace
point. The mutex is never touched, no file is opened, nothing is formatted.

On: bounded by the allowlist — a handful of agents, not the world. Note the
established pattern opens and closes the log file **per write**
(`MissionDiagLog::write`), which is acceptable for bounded diagnostics but
would be costly if the allowlist were ever removed; `maxLinesPerAgent` is the
backstop. The dashboard section adds one bounded array to an existing root.

## Backward Compatibility

Additive only. No schema, no migration, and no existing dashboard field
altered. One additive `AiAgent.idl` accessor (see Technical Considerations) with
the usual `src/autogen/` regeneration and build fan-out. `combatDiag` nests
inside `pveActivity`, so nothing in the existing frontend **breaks** — but note
it will **not render** in the SPA without frontend work either; for this chunk
the JSON is read with `curl`, which is sufficient for a diagnostic. A gate-off
deployment must behave identically to today.
