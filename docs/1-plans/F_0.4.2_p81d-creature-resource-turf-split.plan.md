# P.8.1d PvE Creature-Resource Turf Split (Activates Hunters) Implementation Plan

## Overview

Live verification of P.8.1c proved the acquisition ledger works, but hunters
stay idle because **miners already bank huge amounts of creature-resource
"meat"** (confirmed live: a single `meat_carnivore_corellia` lot of 117,162
units) which satisfies chef meat-demand, so the demand-pull hunter sees no
shortage. This slice makes creature resources **hunter territory**: (A) exclude
SimMiners from targeting the entire `organic>creature_resources` subtree while
the ledger is enabled, and (B) tag hunter harvests with a distinct origin and
count **only hunter-origin** creature lots as the hunter `familySupply`, so the
banked miner meat is discounted. Result: meat demand becomes real and hunters
finally hunt via the existing P.8.1c value/time matchmaker (which still
self-limits at the ceiling once hunters produce enough).

## Problem Statement

- Miners chase chef demand, which lists `meat_carnivore` (and other creature
  families) as satisfiers, so `selectDemandWeightedMinerTarget` sends miners to
  extract meat resource nodes — banking 117k+ meat that is indistinguishable
  from (non-existent) hunter meat.
- P.8.1c's `familySupply(meat)` = boot baseline (all durable hive meat lots,
  incl. the 117k miner-banked) + session tally. Since 115,220 ≫
  `effectiveCeiling` (25k), `allocComponent`/`reserveComponent`/`signalUnits` are
  all 0 → no dispatch. Verified live 2026-07-17.
- Hunter harvest and miner harvest both flush to the hive as
  `acquisitionSource="conceptual_miner"` (hardcoded at
  `SimPlayerManager.cpp:16701`), so they cannot be told apart — the baseline
  can't currently discount only the miner-banked meat.

## Solution Architecture

Owner decisions (2026-07-17): **creature resources are PvE-hunter territory**
(only hunters should ever produce meat/hide/bone/milk/egg/seafood; miners
produce none), and the turf split is **gated by the existing
`acquisitionLedger.enabled`** flag (flag off ⇒ miners behave exactly as today).
v1 hunters only produce `meat` (all species `harvestKind=meat`); hide/bone/etc.
demand is intentionally left **unfilled** (waiting for future hunter harvest
kinds) rather than wrongly filled by miners.

Two coupled mechanisms:

- **(A) Miner exclusion.** When `acquisitionLedger.enabled`, the miner target
  picker skips any resource whose class chain is under
  `organic>creature_resources` (config-driven marker). Miners stop banking meat;
  the mined "active opportunity" for chef profiles falls back to non-creature
  satisfiers (vegetables/cereals/etc.).
- **(B) Origin-scoped hunter supply.** Add an `acquisitionOrigin` to the
  in-memory `MinerSpawnYieldAccumulator` (default the existing miner value);
  `recordPveHunterHarvest` tags its accumulator `"pve_hunter"`; the flush deposit
  carries the accumulator's origin instead of hardcoding `"conceptual_miner"`;
  and the P.8.1c boot baseline (`snapshotStockpileTotalsByFamily`) counts **only
  lots whose `acquisitionSource == "pve_hunter"`**. The banked 117k
  (`conceptual_miner`) is thus discounted; `familySupply(meat)` reflects only
  hunter production. The session tally is already hunter-only by construction
  (incremented solely in `recordPveHunterHarvest`).

Net effect: with the flag on, `familySupply(meat)` starts near 0 (no hunter meat
yet, miner meat discounted) → real meat shortage → matchmaker dispatches hunters
→ they kill → typed harvest flushes as `pve_hunter` meat → `familySupply(meat)`
climbs → `allocComponent` shrinks to 0 at the ceiling (self-limits, as designed).

Simulation-only: the banked 117k miner meat is **not deleted** (no hive
mutation), only discounted from the hunter supply view. Reversible: flag off
restores today's behavior (miners gather everything; baseline counts all meat).

## Implementation Details

### 1. Exclude miners from creature-resource families

**File**: `MMOCoreORB/src/server/zone/objects/creature/simplayer/SimPlayerManager.cpp`

**Current state**: `selectDemandWeightedMinerTarget` (`:2458`) iterates
`Vector<ResourceIntelligenceEntry>` (each has a `classChain`, `:struct
ResourceIntelligenceEntry`) and picks the highest demand-weighted resource for a
profile; called from the miner planning paths (`:2623`, `:19177`).

**Modifications**:

- Add a static helper `isCreatureResourceEntry(const ResourceIntelligenceEntry&
  entry, const Vector<String>& creatureClassMarkers)` — true when
  `entry.classChain.toLowerCase()` contains any configured marker (default
  `"creature_resources"`). (Type/prefix fallback: also treat
  `entry.type`/`classChain` beginning with a creature family root as creature.)
- In `selectDemandWeightedMinerTarget`, when the exclusion is active, `continue`
  past any entry for which `isCreatureResourceEntry(...)` is true, so miners
  never select a creature resource. Thread the exclusion decision (the **latched
  `pveTurfSplitEffective`**, §4 — not the live config) + markers into the function
  signature (snapshotted under `pveMutex` by the callers), defaulting to *no
  exclusion* so behavior is unchanged when off.
- Verify this is the sole miner target-selection chokepoint; if the sibling
  planning helpers (`buildDemandWeightedMinerPlan`-style, `:2365`/`:2601`) filter
  candidates independently, apply the same guard there. (Plan-review focus
  point.)

### 2. Origin field on the yield accumulator + hunter tagging

**File**: `SimPlayerManager.{h,cpp}`

**Current state**: `MinerSpawnYieldAccumulator` (`SimPlayerManager.h:371`) has no
origin field. Hunter harvest builds an accumulator at `~:8492`
(`recordPveHunterHarvest`, `resourceClassChain = resourceSpawn->getFinalClass()`);
miner yield builds one at `~:10664` (`recordSpawnIdentifiedMinerYield`). The
flush at `:16701` hardcodes `deposit.acquisitionSource = "conceptual_miner"`.

**Modifications**:

- Add `String acquisitionOrigin = "conceptual_miner";` to
  `MinerSpawnYieldAccumulator` (default preserves miner behavior for every
  existing writer).
- **Composite accumulator key end-to-end (Codex P1).** The in-memory
  `spawnYieldAccumulators` map is keyed by `uint64` spawn id
  (`SimPlayerManager.h:597`); a miner and a hunter writing the same spawn id in
  one session would collide on a single accumulator (and its per-accumulator
  `lastFlushedQuantity` watermark), so the durable composite key alone is not
  enough. Re-key the map to a composite **`(resourceSpawnObjectID,
  acquisitionOrigin)`** (e.g. `VectorMap<String,MinerSpawnYieldAccumulator>` with
  key `String::valueOf(spawnID) + "|" + origin`). Update the small,
  self-contained set of accessors (all in `SimPlayerManager.cpp`):
  `recordPveHunterHarvest` (writes the `pve_hunter` entry, `:8481-8508`),
  `recordSpawnIdentifiedMinerYield` (writes the `conceptual_miner` entry,
  `:10658-10681`), `collectSpawnYieldAccumulators` (iterate — unaffected),
  **`markSpawnYieldFlushed`** (`:10692` — the watermark advance; must take/derive
  the composite key so it advances the correct origin's `lastFlushedQuantity`),
  and the P.8.1c unflushed-delta snapshot. Each origin thus keeps its own session
  accumulator + watermark; no re-tagging.
- At the flush, set `deposit.acquisitionSource = acc.acquisitionOrigin`, and
  carry the composite identity into `updateStockpileSpawnLots`' deposit/delta map
  (§3a) so the delta and durable lot are matched by `(spawnID, source)`
  throughout — miner accumulators yield `"conceptual_miner"` lots, hunter ones
  yield `"pve_hunter"` lots. The persisted `AiEconomyStockpileLot.acquisitionSource`
  (IDL getter `getAcquisitionSource()`) records provenance durably — no IDL
  change (field already exists).

### 3. AiEconomyManager: origin-aware lots, allowlist, origin-scoped baseline

**File**: `MMOCoreORB/src/server/zone/managers/aieconomy/AiEconomyManager.{h,cpp}`

**3a. Origin-aware durable lot keying (Codex P1 — critical).** `updateStockpileSpawnLots`
indexes durable lots by `resourceSpawnObjectID` alone (`spawnLots`, `~:449`,
match at `:527`), so a hunter deposit for a spawn a miner already banked would
merely *increment the existing `conceptual_miner` lot* — the hunter quantity
would be reclassified as miner and then discounted after restart, silently
losing hunter production.
- Change the durable spawn-lot index to a **composite key
  `(resourceSpawnObjectID, acquisitionSource)`** (e.g. `String key =
  String::valueOf(spawnID) + "|" + acquisitionSource`), both when building the
  `spawnLots` map from existing lots and when matching a deposit. A `pve_hunter`
  deposit for spawn X then creates/updates its **own** lot, never touching spawn
  X's `conceptual_miner` lot. Existing single-origin lots are unaffected (each
  keeps its source; the composite key just namespaces by origin).
- Keep the `MAX_STOCKPILE_LOTS` accounting correct with the new key (a spawn may
  now have up to one lot per distinct acquisition source).

**3b. Persistence allowlist (Codex P1 — critical).** `validateEconomyData`'s
`acquisitionSources[]` allowlist (`:1664`) does not include `"pve_hunter"`; a
persisted hunter lot would fail validation and disable persistence. Add
`"pve_hunter"` to that array (and update any hardcoded element count / loop
bound). (`"future_ai_harvester"` is already reserved but we use the explicit
`"pve_hunter"` for clarity; the allowlist add is the required change either way.)

**3c. Origin-scoped family baseline.** `snapshotStockpileTotalsByFamily(families,
totals, status)` (`:1282`) sums every non-despawned lot matching a family. Add a
parameter `const String& requiredAcquisitionSource` (empty ⇒ count all,
preserving generality); when non-empty, only sum a lot when
`lot->getAcquisitionSource() == requiredAcquisitionSource`, read inside the
existing per-lot `Locker lotLocker(lot)` block (same lock choreography). The
P.8.1c baseline caller passes `"pve_hunter"` **only when the turf split is
active** (see gating, §4) — otherwise it passes empty (count all), so the
baseline and the miner exclusion move together.

### 4. Config surface + the single gate contract

**File**: `MMOCoreORB/bin/scripts/managers/sim_player_manager.lua`

- Under `pveConfig.acquisitionLedger`, add
  `minerCreatureResourceExclusion = true` and
  `creatureResourceClassMarkers = { "creature_resources" }` (class-chain
  substrings marking a resource as creature-sourced).
- **One gate contract (resolves Codex P2).** Define
  `turfSplitActive = acquisitionLedger.enabled && minerCreatureResourceExclusion`.
  This single boolean governs **both** mechanisms together:
  - active ⇒ miners skip creature-resource entries (§1) **and** the baseline
    passes `requiredAcquisitionSource="pve_hunter"` (§3c, counts hunter meat
    only);
  - inactive ⇒ miners target creature resources exactly as today **and** the
    baseline passes empty (counts all meat).
  There is no state where exclusion and origin-filtering disagree. Origin
  *tagging* (§2) and origin-aware lot keying (§3a) run **unconditionally** (they
  only record provenance and never change what is counted unless `turfSplitActive`
  reads it) — this is safe and keeps provenance correct even after toggling.
- **Defaults & current deployment (Codex P2):** the code/config default is
  `minerCreatureResourceExclusion=true` with `acquisitionLedger.enabled` shipping
  `false` in-repo ⇒ `turfSplitActive` false by default (zero behavior change).
  **Note the live-deployed Lua currently has `enabled=true`** (flipped during
  P.8.1c verification, `sim_player_manager.lua:647`), so on the next restart the
  turf split **activates immediately** — which is intended for this slice's live
  verification. Snapshot these fields under `pveMutex` with the other ledger
  config.
- **Restart-required gate via a LATCHED effective value (Codex P1 — full fix).**
  The boot baseline is captured once and frozen (P.8.1c) with a
  `requiredAcquisitionSource` decided from the gate. A runtime config refresh must
  change **neither half** of the gate before restart — otherwise miner exclusion
  (which reads live config) would flip while the baseline keeps its old filter,
  desyncing the two halves. So introduce a **latched effective gate**
  `pveTurfSplitEffective` (bool, `pveMutex`-guarded), set **once** on the first
  `applyPveConfig` after process start (`pveTurfSplitEffectiveLatched`), from the
  then-configured `acquisitionLedger.enabled && minerCreatureResourceExclusion`.
  **All three consumers read `pveTurfSplitEffective`, never the live config
  fields:** (1) miner creature-resource exclusion (§1), (2) the baseline's
  `requiredAcquisitionSource` at capture (§3c), and (3) the dashboard (§5).
  A later `applyPveConfig` refresh updates the *configured* fields as usual but
  leaves `pveTurfSplitEffective` unchanged; if configured ≠ effective it logs
  `PveTurfSplitGateChangeRequiresRestart` and the dashboard exposes
  `turfSplitPendingRestart=true`. A real process restart re-latches effective from
  the new config, re-captures the baseline, and resets the session tally to 0 —
  the only consistent point. Document restart-required in the config comment.

### 5. Dashboard visibility

**File**: `SimPlayerManager.cpp` dashboard assembly (`pveActivity`)

- Add to `pveActivity` (all reading the **latched** effective gate):
  `turfSplitEffective` (bool), `turfSplitPendingRestart` (bool — configured ≠
  effective), `minerCreatureExclusionActive`, and a `familySupplyOrigin`
  (`"pve_hunter"` when active, else empty), plus keep the existing
  `demandFamilies.familySupply` (now hunter-only) as the live-verification
  surface. Surface `bootBaselineHunterMeat` so we can confirm the discount took
  (baseline should drop from 115,220 to ~0 on the first restart with this slice).

## Technical Considerations

- **Pattern Usage**: reuses the P.8.1c ledger, the demand-weighted miner
  selection, and the accumulator/flush/stockpile pipeline. No new manager or IDL
  object.
- **Locking & References**: config snapshotted under `pveMutex` before use (as
  P.8.1c does); the origin read stays inside the existing per-lot lock in
  `snapshotStockpileTotalsByFamily`; `recordPveHunterHarvest`'s accumulator write
  stays under `spawnYieldAccumulatorMutex`. No new lock ordering — avoids the
  P.4.4-class regression (ARCHI.md §5).
- **IDL Impact**: none. `AiEconomyStockpileLot.acquisitionSource` already exists
  with a getter; the accumulator/deposit are plain structs. No `src/autogen`
  edits, no schema migration. Existing persisted lots keep their recorded
  `acquisitionSource` and are simply filtered — no data migration.
- **C++ vs Lua Placement**: structural filtering/tagging in C++ beside the
  existing pipelines; the exclusion toggle and class markers are Lua tunables.
- **Gating & Simulation-Only**: the counting behavior (miner exclusion +
  origin-scoped baseline) is governed by the single `turfSplitActive` gate (§4);
  gate false reproduces today's miner and baseline behavior exactly. Origin
  tagging + origin-aware lot keying always run (provenance only). No hive
  mutation — banked meat is discounted, not deleted. Within simulation-only
  policy.
- **Dashboard Visibility**: new `pveActivity` fields + the existing
  `demandFamilies` are the acceptance surface.
- **Live Verification Plan**: restart with the flag on and confirm on the
  dashboard: (1) `demandFamilies.familySupply(meat)` drops from ~115,220 to ~0
  (miner meat discounted); (2) a non-zero `allocComponent`/`signalUnits` for
  meat appears (real shortage); (3) hunters leave `IDLE_HOME` →
  `ANNOUNCE_JOB`/`TRAVEL_OUT`/`HUNTING`; (4) `hunterKillsTotal` and typed
  `hunterHarvestUnitsTotal` climb, `familySupply(meat)` rises as they produce,
  and `allocComponent` shrinks back toward 0 at the ceiling (self-limits); (5)
  the miner side no longer accrues new `meat_*` lots (miner exclusion working).
- **Edge Cases**: gate off (no exclusion, baseline counts all — unchanged);
  banked 117k persists but discounted (no mutation); a spawn id used by both a
  miner and a hunter now yields **two distinct lots** keyed by
  `(spawnID, source)` — the hunter lot counts as `pve_hunter`, the miner lot
  stays `conceptual_miner` (correct separation, §3a); creature resource
  whose classChain lacks the marker (fallback family-root prefix check);
  non-creature resource whose classChain coincidentally contains a marker
  substring (markers chosen specific enough — `creature_resources` — to avoid
  false positives); hide/bone/seafood demand intentionally unfilled in v1 (no
  producer — documented, not a bug).

## Performance & Cost Impact

- Miner exclusion adds an O(markers) substring check per resource entry during
  the existing miner selection scan — negligible. The baseline origin filter is
  a single string compare per lot in the already-once-per-boot durable scan. No
  new per-tick work, no new O(n²).

## Backward Compatibility

- `turfSplitActive` false (the default, since the ledger defaults off — or with
  `minerCreatureResourceExclusion=false`) reproduces today's miner targeting and
  counts all meat in the baseline. New struct/param fields default to existing
  behavior. No IDL, no schema, no data migration — persisted lots keep their
  `acquisitionSource`; the composite `(spawnID, acquisitionSource)` key is a
  runtime index change that groups existing single-origin lots identically to
  today (each already has one source), only *namespacing* future dual-origin
  spawns. Origin tagging is forward-only (old lots keep their recorded source).
