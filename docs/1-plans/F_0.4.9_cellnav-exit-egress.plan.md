# POB Cell-Exit Egress (Pass 3) Implementation Plan

## Overview

Pass 2 (`F_0.4.8`) fixed the world→cell **entry** teleport, and it is live-verified:
SimPlayer bots (and real NPCs) now walk correctly *into* building cells. That fix
exposed a pre-existing, previously-unreachable gap on the way **out**: a bot that is
inside a cell and issues a move to an outdoor destination cannot leave — it gets
stuck inside and never resumes its task.

Pass 3 adds a **cell-egress leg**: when an agent is inside a cell and its
destination is outdoors, it first walks out through the portal to the building's
exterior exit point, then resumes its original travel to the final destination
("path to the exit and pick up where it left off"). Owner decisions for this plan:
**compute the egress waypoint from the building exterior**, and apply the fix
**universally** (any SimPlayer leaving a cell, hybrid or not).

This is the last functional piece; once verified, the whole train — `F_0.4.8`
entry fix + `F_0.4.9` cell egress — ships together and the Pass-1 diagnostic
scaffolding is stripped (`F_0.4.8` Phase 3, deferred until now).

## Problem Statement

Root cause is confirmed from the live round-trip trace (`cellnav.log`) plus the
movement code:

- The diagnostic bot's exit *succeeded* — but only because it is **non-hybrid** and
  its exit target was a **navmeshed city point**, so the default
  `PathFinderManager::findPath(cell-origin → outdoor)` returned a proper
  portal-following path (15 nodes: cell → portal → outdoor). `DIAG_ROUNDTRIP_COMPLETE`.
- The **real** stuck bots (PvE hunters after a cantina buff, PvP squads) use
  **hybrid movement** and travel to **off-navmesh wilderness**. For them, inside a
  cell `agent->isInNavMesh()` is `false` (cells are not navmeshed), so
  `SimPlayerController::requestHybridPath` sets `onMeshMode = false` and calls
  `scheduleHybridDirectPath(finalDestination, HYBRID_LEG_OVERLAND_FINAL)`. That
  builds a **direct 2-node overland path** (`useDirectOverlandPath`: straight
  world-start → world-end, **no portal, no cell**) — i.e. it tries to walk the bot
  in a straight line *from inside the building, through the walls*, toward a target
  ~1,600 m away. The bot cannot make progress and wedges.
- `SimHunterController.cpp:529` issues `moveTo(species.huntGround)` immediately
  after the cantina buff completes, while the hunter is still inside the cell —
  hitting this exact path.

The engine `findNextPosition` (Pass-2 fix) is correct; the gap is purely that the
**movement request** from a cell origin never routes out through the portal before
going overland.

## Solution Architecture

A **cell-egress pre-leg**, inserted at the movement-request boundary so it covers
both the hybrid and non-hybrid pipelines:

1. **Detect** a cell-exit: the agent's parent is a `CellObject` and the requested
   destination is outdoors (`targetCell == nullptr`). (Intra-building cell→cell
   moves are left to `findPath`'s internal portal graph; the reported failure is
   cell → outdoor.)
2. **Compute the egress waypoint** from the building exterior via the native
   `BuildingObject::getEjectionPoint()` — a world-space, ground-snapped point just
   outside the building's portal (with a portal-geometry fallback built in). This
   is the same "where you end up when you leave the building" point the engine uses
   for `ejectObject`.
3. **Egress leg**: schedule a **portal-following default `findPath`** (not the
   straight direct-overland) from the agent's cell position to the ejection point
   (outdoors, `cell == nullptr`). This is exactly the request the diagnostic proved
   walks out through the portal correctly.
4. **Resume**: on arrival at the ejection point (the agent is now outdoors on/near
   the navmesh), re-issue the **original** destination. The normal hybrid/overland
   pipeline then runs from an outdoor origin and works as designed — "pick up where
   it left off." The hybrid mover already preserves `finalDestination`.

Because the egress only triggers when an agent is inside a cell heading outdoors —
a case that fails today — the regression surface is minimal.

## Implementation Details

### 1. Cell-egress detection + leg (shared movement layer)

**File**: `src/server/zone/objects/creature/simplayer/SimPlayerController.{h,cpp}`

**Current state**: `moveTo(worldPos, localPos, targetCell)` splits into the hybrid
branch (`requestHybridPath`) and the non-hybrid default-`findPath` tail;
`requestHybridPath` is also the hybrid resume entry from `checkArrival`.
`scheduleHybridDirectPath` / `SimPathFindTask` already exist for scheduling legs.

**Modifications**:
- Add controller state: `bool cellEgressActive`, the stashed original request
  (`Vector3 cellEgressResumeWorld/Local`, `ManagedReference<CellObject*>
  cellEgressResumeCell`), and an `int cellEgressAttempts` guard.
- Add `bool beginCellEgressIfNeeded(worldPos, localPos, targetCell)`:
  - Return `false` if `cellEgressActive`, or `agent->isInCombat()` (let the normal
    combat-hold handling apply — see placement below), or `cellEgressAttempts >=
    kMaxCellEgressAttempts` (see Failure/robustness), or the agent's parent is not a
    `CellObject`, or `targetCell` is that same cell, or the destination is not
    outdoors (`targetCell != nullptr`).
  - Resolve the building: `agent->getParent()->getParent()` (cell → building) or
    `agent->getRootParent()`, cast to `BuildingObject`. If none, return `false`
    (let the existing path attempt / fail normally).
  - `Vector3 ejection = building->getEjectionPoint();` Validate it (within zone
    boundaries, not the (0,0) sentinel). If invalid, return `false`.
  - Stash the original request into `cellEgressResume*`; set `cellEgressActive =
    true`; `cellEgressAttempts++`; then drive the ejection leg through the **same
    non-hybrid `findPath` mechanism the `moveTo` tail uses** — set the LEG state
    (`destination = destinationLocal = ejection`, `destinationCell = nullptr`,
    `stuckWatchdogCount = 0`, `lastWatchdogPos = agent->getWorldPosition()`,
    `state = CALCULATING_PATH`), advance the work-loop generation, and schedule
    `SimPathFindTask` with `useRecastPath=false, useDirectOverlandPath=false`,
    `startCoord = WorldCoordinates(agent)` (captures the cell), `endCoord =
    WorldCoordinates(ejection, nullptr)`. Return `true`. Setting `destination*` to the
    leg endpoint keeps `acceptFoundPath()` (e.g. `SimPvPController`'s) comparing the
    egress path against the correct target, while the real request lives only in the
    separate `cellEgressResume*` stash.
  - Crucially, the egress leg must behave as **non-hybrid for its duration**: it does
    not enter the hybrid branch (never hits `scheduleHybridDirectPath` while in the
    cell) and does **not** overwrite `finalDestination`.
- **Suppress hybrid behavior via a single chokepoint** (fixes the hunter case where
  `onPathFound`/`checkArrival` would drop a good egress path, and covers the
  stuck-repath branch at `SimPlayerController.cpp:1116` that would otherwise replace
  the stalled portal leg with `requestHybridPath()`): make
  `isHybridMovementActive()` return `false` while `cellEgressActive` (add
  `&& !cellEgressActive` to its definition). This makes the **entire** controller —
  `moveTo`, `onPathFound`, `checkArrival` (including the mode-debounce, hybrid-resume,
  and stuck-repath branches at `:417,1000,1021,1116`) — treat the egress leg as a
  plain non-hybrid path for its duration, with no need to audit each call site. The
  egress hook is still called before this check matters in `moveTo`/`requestHybridPath`,
  and `finalDestination` is preserved untouched in the stash.
- **Placement**: call `beginCellEgressIfNeeded(...)` in `moveTo` **after** the
  in-combat hold guard (so an in-combat bot still holds rather than starting egress)
  and before the hybrid branch; and in `requestHybridPath` before the `onMeshMode`
  logic. Return early when it fires.
- **Resume on egress arrival**: in `checkArrival`'s arrival branch, before firing
  the per-controller `onArrived()`, if `cellEgressActive` and the agent is now
  outdoors, clear `cellEgressActive`, reset `cellEgressAttempts = 0`, and re-dispatch
  the stashed original request (`moveTo(cellEgressResumeWorld, cellEgressResumeLocal,
  cellEgressResumeCell.get())`); do **not** call `onArrived()` for the egress
  waypoint. The re-issued move now starts outdoors and proceeds normally.
- **Failure/robustness**: `kMaxCellEgressAttempts = 2`. If the egress leg fails while
  `cellEgressActive`, **clear `cellEgressActive` and reset the leg state first**, then
  dispatch the controller's `onPathFailed()` — the cleanup must happen before that
  call because `onPathFailed()` is virtual and `SimHunterController` overrides it
  **without** calling the base, so relying on base cleanup would leak the flag.
  `cellEgressAttempts` resets to 0 on a successful resume and on any fresh logical
  `moveTo` (new destination), so the 2-attempt cap is per stuck-exit, not global. If
  the building/ejection point can't be resolved, the move behaves as today (no worse).
- **Egress-state lifecycle (must clear on every interruption)**: `cellEgressActive`
  and the `cellEgressResume*` stash are cleared — via a single
  `clearCellEgressState()` helper — in ALL of: (a) successful resume, (b) egress
  failure (before the virtual `onPathFailed()`), (c) `prepareForRelocation()`
  (teleport/`switchZone`/interruption — the existing route-invalidation point;
  otherwise a post-teleport outdoor move would skip egress detection and then
  wrongly resume the stale pre-teleport target), and (d) the cancellation/reset paths
  (`clearHybridMovementOnCancellation`, `SimMinerController::resetIntelligentAssignmentForRecovery`,
  and any controller recovery that abandons the current order). (e) **A fresh logical
  `moveTo` while `cellEgressActive` supersedes**: it first calls
  `clearCellEgressState()` (cancelling the in-flight egress leg) and then re-evaluates
  egress detection against the NEW request — the resume re-issue is distinguishable
  because it clears the flag *before* calling `moveTo`, so any `moveTo` that observes
  `cellEgressActive == true` is an external new request.

### 2. Building ejection-point access

**File**: same controller; reads `BuildingObject::getEjectionPoint()`
(`BuildingObjectImplementation.cpp:211`).

**Modifications**: obtain the `BuildingObject` from the agent's cell parent and read
its ejection point. `getEjectionPoint()` reads the template ejection offset (or
computes from portal geometry) and ground-snaps via
`CollisionManager::getWorldFloorCollision`. Match the existing caller's locking: the
engine calls it from `ejectObject` under the building lock, so acquire a short
`Locker` on the building for the read (released before scheduling the leg — no lock
held across the path task), mirroring the `refreshProvider` no-lock-across-query
discipline used in `SimHunterController`.

### 3. Diagnostic reproduction + verification (still gated, pre-strip)

**File**: `SimPlayerController.cpp` (`SimCellNavDiagController`) — the round-trip
diagnostic added in the previous step already exits to a navmesh point. To verify
the egress path faithfully, point the diagnostic's exit at an **off-navmesh
wilderness** target (config `cellNavDiag.exitX/exitY` — horizontal only; the exit Z
is **computed** from `zone->getHeight(exitX, exitY)` like the existing `spawnZ`, not
configured — defaulting to a wilderness point well outside Mos Eisley) so the
diagnostic bot exercises the same cell → off-navmesh route the real bots do. The new
`exitX/exitY` fields go in the `CellNavDiagConfig` struct in `SimPlayerManager.h` and
are read in `SimPlayerManager.cpp`'s `loadLuaConfig`. Confirm in `cellnav.log`: a
`CELL_EGRESS`-tagged leg walks out to the ejection point (portal-following nodes),
then the overland/hybrid leg resumes toward the wilderness target and the bot
reaches it (or gets acceptably close) — no straight-through-wall stall.

## Technical Considerations

- **Pattern Usage**: The egress leg reuses the existing `SimPathFindTask`
  default-`findPath` scheduling (the exact request the diagnostic proved follows the
  portal) and the `checkArrival` arrival→next-leg transition style already used by
  the hybrid leg state machine. `getEjectionPoint()` is the engine's own building-exit
  primitive.
- **Locking & References**: The egress-waypoint read locks the `BuildingObject`
  briefly (matching `ejectObject`'s caller) and releases before scheduling the path
  task — no lock held across the async `findPath`, consistent with the project's
  established no-lock-across-query discipline. No change to `findNextPosition`'s
  `targetMutex` usage. `cellEgressResumeCell` is a `ManagedReference`.
- **IDL Impact**: None. `getEjectionPoint`, `getParent`, `getRootParent`,
  `isCellObject`, `castTo` are existing accessors; no `.idl`/autogen changes.
- **C++ vs Lua Placement**: Movement pipeline → C++. The only Lua touched is the
  transient diagnostic exit-target config (removed in §4).
- **Gating & Simulation-Only**: Movement-only; no inventory/credit/market/persistence
  mutation. Universal scope, but the code path only executes when a SimPlayer is
  inside a cell moving outdoors — otherwise inert.
- **Preserve `finalDestination` (known-hazard care point)**: Per the P.8.3 lesson,
  the egress leg must not clobber the hybrid `finalDestination` or bump the work-loop
  generation in a way that strands the resume. The original request is stashed and
  re-issued cleanly on egress arrival; the egress leg advances the generation like any
  normal leg and reschedules the arrival loop via `onPathFound`.
- **Dashboard Visibility**: None required; verification is `cellnav.log` (pre-strip)
  and in-game observation of a bot leaving the cantina and reaching its hunt ground.
- **Live Verification Plan**: Owner restarts with the fix + the off-navmesh
  diagnostic exit target; confirm the diagnostic bot egresses to the ejection point
  then resumes to the wilderness target; and confirm a **real** PvE hunter leaves the
  cantina after buffing and reaches its hunt ground (`hunterKillsTotal` resumes
  climbing), and/or a PvP bot leaves a starport/cantina. This gates the strip + release.
- **Edge Cases**: bot spawned inside a cell with no travel history (ejection point is
  building-derived, so still works); building with no template ejection point (portal-
  geometry fallback in `getEjectionPoint`); ejection point itself off-navmesh/wilderness
  (still a valid outdoor origin — the subsequent overland leg handles it); egress
  `findPath` fails (bounded `onPathFailed` recovery); cell→cell within the same building
  (not treated as egress — `findPath`'s internal portals handle it); agent already
  outdoors (detection returns false — inert).

## Type Definitions (if applicable)

None. New controller members are plain (`bool`/`Vector3`/`ManagedReference<CellObject*>`/`int`).
No IDL/distributed-object types.

## Performance & Cost Impact

Negligible: one extra portal-following `findPath` and a short building-lock read only
when a SimPlayer actually leaves a cell (rare, event-driven). It *reduces* wasted work
(today such a bot spins stuck against interior geometry until some other system removes
it). The diagnostic cost is removed at strip.

## Backward Compatibility

Fully compatible: no schema/IDL/persistence changes. The egress leg only alters the
currently-broken in-cell-outbound case; all other movement is unchanged. The diagnostic
is removed cleanly (never committed).

## Test Impact

- No new unit tests: this is shared-mover movement behavior whose acceptance bar is
  live verification (per project norm); mocking building/portal/navmesh geometry
  exceeds the mock-pain tripwire. Record any deferral in `docs/4-unit-tests/COVERAGE-DEBT.md`.
- The release code review must cover the shared `SimPlayerController` changes; the
  live check must include a **real** hunter (leave cantina → reach hunt ground → kills
  resume), not only the diagnostic bot.
