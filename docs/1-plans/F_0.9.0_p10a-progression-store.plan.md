# P.10a — PlayerBot Progression Store Foundation Implementation Plan

**Version**: F_0.9.0 (minor — first chunk of the P.10 player-parity line)
**Branch**: `feat/p10-playerbot-parity` (cut from `miner-ai` at `266e6d02e7`, v0.8.2)
**Roadmap**: `docs/1-plans/ROADMAP_p10-playerbot-parity.md` (chunk F_0.9.0)
**Status**: PLAN

## Overview

Build the persistent **progression store** that every later P.10 capability
writes to — XP by type, bank/cash credits, skill points and trained skills —
keyed by roster identity id, owned by `SimPlayerManager`, persisted in MySQL
beside `simbot_identities`. Ship it with a **dashboard section**, an **orphan
reaper** with a "records with no roster entry" counter, an **award API with no
production caller**, and the **`playerBotParityTest` live harness** that later
chunks extend. No XP, credit, loot, skill or bazaar behaviour changes in this
release: a hunter's kill still pays nothing. The point is that the population
is inspectable and the store's invariants are proven live before any award
logic exists.

## Problem Statement

- A PlayerBot has nowhere to keep progress. Its body is an `AiAgent` with no
  `PlayerObject` ghost (XP lives on the ghost, `PlayerObject.idl:128`), and the
  body is destroyed on death and rebuilt (`SimHunterController.cpp:2024`
  `CLONE_HOME` → `spawnPveIdentityBody`, `SimPlayerManager.cpp:8729`), so
  nothing durable can live on it.
- The only persistent bot state today is the roster row (`SimBotIdentity`,
  `SimPlayerManager.h:102`; schema 1009 at `ServerDatabase.cpp:144`) holding
  lifetime counters, not progression.
- Any per-object flag is a leak risk: `simPlayerBot` leaked onto wild creatures
  through engine object reuse and needed a reset in `loadTemplateData`
  (`AiAgentImplementation.cpp:358-367`). A persistent record that could be
  created from an object would survive restarts and accumulate forever.
- There is no live harness for store semantics; the traversal matrix
  (`structureTraversalTest`, `sim_player_manager.lua:841`) is movement-only.

## Solution Architecture

Four pieces, all default-off, all inside the existing SimPlayer/roster pattern:

1. **Schema** — three additive MySQL tables via versioned
   `ServerDatabase::updateDatabaseSchema()` blocks (one statement per version,
   because `alterDatabase` runs a single `executeQuery`, `ServerDatabase.cpp:63`):
   `simbot_progression` (scalars, 1 row per identity), `simbot_experience`
   (identity × xp_type), `simbot_skills` (identity × skill), all `CREATE TABLE IF NOT EXISTS` so a
   fresh install whose dump already carries the tables does not fail the
   version step (a fresh import has no `db_metadata` and seeds version 1000,
   `ServerDatabase.cpp:33`; the existing 1009 block is unguarded and is
   converted to `IF NOT EXISTS` in the same edit — text-only, already applied
   on the live DB). No SQL backfill: pre-existing roster identities get their
   record from the boot repair in §2.
2. **Store** — `SimBotProgression` records in a `SimPlayerManager` map under a
   new `progressionMutex`, loaded after the roster loads (boot block) or on a
   later maintenance tick when the store is enabled at runtime, created by
   **one function** `ensurePlayerBotProgressionRecord(identityId)` that
   refuses ids absent from the loaded roster and is invoked (a) from
   `mintPveIdentitiesIfNeeded` for a freshly minted identity and (b) from
   reconciliation as an idempotent repair for roster identities with no record
   — the two inserts of a mint are not atomic on MyISAM, and a mint made while
   the store was disabled must be healed, so "roster-without-record" is a
   transient repaired on the next tick, not a permanent state. Flushed by an
   **atomically swapped** dirty batch on the PvE maintenance task (the
   roster's clear-after-write at `SimPlayerManager.cpp:8719` would drop an
   award landing during SQL, so that part of the shape is deliberately not
   copied).
   **Award API** (`grantPlayerBotExperience`, `grantPlayerBotCredits`,
   `spendPlayerBotCredits`, `recordPlayerBotSkill`) with award-requires-record
   semantics: missing record ⇒ reject + count, never create. A body→identity
   resolver (`resolvePlayerBotIdentity(bodyOid)`) that consults only
   `pveBodyIdentityIds` under `pveMutex`, so a leaked flag on a wild creature
   resolves to 0 and is rejected. **All SQL for the store runs on the PvE
   maintenance task** — the harness enqueues SQL-bearing requests to it and
   polls.
3. **Reconciliation + reaper** — on load and on every flush the store compares
   its keys with the roster: records without a roster identity are counted
   (`orphanRecords`), roster identities without a record are counted
   (`rosterWithoutRecord`) and immediately repaired through the single
   creation function when the DB is available (so the counter is nonzero only
   while the DB is down). The reaper deletes orphans only when
   `reaper.enabled` (default false) and the row is older than
   `reaper.minAgeSeconds`.
4. **Dashboard + harness** — `result["playerBotProgression"]` (config echo,
   store status, counters, per-identity rows, harness matrix) and the
   `playerBotParityTest` runner: a Lua scenario matrix over store operations,
   harness identities minted through the real mint path with
   `profession='harness'`, a `SimParityTestController` body for the
   body-lifecycle scenarios, and a per-identity oracle. The population governor,
   matchmaker and `maxHunters` count gain a `profession == "hunter"` filter so
   harness identities never receive hunter bodies, hunt orders, or a seat in
   the population target. Restart persistence is proven by a durable two-boot
   probe, and the three repaired failure windows (award during SQL I/O, flush
   failure + recovery, partial mint) have their own fault-injected scenarios.

Gating: `playerBotProgression.enabled=false` (C++ default and shipped Lua)
means no load, no create, no flush, no reaper, dashboard shows
`enabled=false, storeLoaded=false`; every award call returns rejected with
`rejectedDisabled`. Identities minted while the store is off get their record
from the repair on the next enable. The schema blocks run unconditionally
(they are additive, `IF NOT EXISTS`, and version-gated like every migration).
`playerBotParityTest.enabled=false`.

## Technical Considerations

- **Pattern Usage**: roster load/mint/flush (`SimPlayerManager.cpp:8508/:8574/:8677`) for SQL and thread discipline; `structureTraversalTest` runner/spawn task/results (`:306`, `:30555-31530`, `SimPlayerManager.h:1211-1260`) for the harness; `getPveActivityDashboard` (`:13682`) for the dashboard section; `SimTraversalTestController` (`SimPlayerController.h:783`) for the harness controller.
- **Locking & References**: new `progressionMutex` follows the `pveMutex`/`pvpSquadMutex` contract — **never held while locking an agent, never nested with `pveMutex`** (roster snapshots are copied under `pveMutex` and released before `progressionMutex` is taken; the resolver takes only `pveMutex`). `pveMaintenanceStateMutex` is a leaf lock (nothing is taken under it). Harness runner: `playerBotParityTestMutex` held for cursor ownership, task scheduling outside it (the ABBA lesson from F_0.8.0). Body destroy/respawn go through the identity body teardown/spawn functions under `Locker(agent)` with the F_0.8.1 post-lock lifecycle recheck. **All SQL runs on the PvE maintenance task** — the runner never issues SQL; it enqueues requests and polls.
- **IDL Impact**: none. No `.idl` change; `AiAgent` gains nothing (invariant §2.1 of the roadmap).
- **C++ vs Lua Placement**: store, SQL, API, reconciliation, reaper, runner = C++. Gates, flush/reaper tunables, the whole scenario matrix = Lua.
- **Gating & Simulation-Only**: this chunk performs no economy mutation; the only new persistence is the store's own tables, and the only writers are the harness and the mint path. `enabled=false` ⇒ byte-for-byte legacy except the additive schema migration. The award API has **no production caller** in F_0.9.0 (grep-verifiable at review, the F_0.8.1 "adoption is a separate step" rule).
- **Dashboard Visibility**: new `playerBotProgression` section — the acceptance surface; `orphanRecords` and `rosterWithoutRecord` make a leak visible rather than silent.
- **Live Verification Plan**: (1) build clean `-Werror`, `luac -p`, `node --check`; (2) restart with `playerBotProgression.enabled=true`, `flushIntervalSeconds=15`, and `playerBotParityTest.enabled=true`: schema upgrades to 1012, `records == roster size` (6 hunters repaired by reconciliation), `orphanRecords == 0`, `rosterWithoutRecord == 0`; (3) phase A: scenarios 1–16 (17 scenarios incl. 9b) resolve PASS on the dashboard, 9c shows `AWAITING_RESTART`, cleanup leaves exactly one harness row (the probe); (4) second restart with the harness still enabled: phase B adopts the probe, asserts 4242/777, deletes it, matrix reports 18/18 PASS and no harness rows remain; (5) gate-off regression: `pveActivity` hunter counters and miner/PvP dashboards unchanged vs the pre-change baseline, PvE maintenance cadence unchanged, measured over a **no-kick observation window** — after the harness run has finished, `maintenance.requestsQueued == 0` and `rerunPending == false` — `playerBotProgression.maintenance.ticksTotal` advances once per `pveMaintenanceIntervalSeconds` ± scheduler jitter over ≥ 10 intervals and `lastEntryAgeSeconds` never exceeds ~2× the interval (during the matrix itself harness kicks legitimately add zero-delay entries, so the counter is not checked then; `SimPveRosterFlushed` is not usable because it logs only when identities are dirty), production `awardsAccepted` stays 0 (no caller). TRIP-verify receipt + `docs/4-unit-tests/live_p10a-progression-store_<runid>.md`.
- **Edge Cases**: DB unavailable at boot → store stays unloaded, dashboard `dbAvailable=false`, awards reject `noRecord` (never in-memory-only records), bounded re-probe restores service; mint succeeds but record INSERT fails → identity exists without record, counted `rosterWithoutRecord`, repaired by the next reconciliation through the single creation function (idempotent `INSERT IGNORE`); runtime enable after boot → explicit maintenance-tick load path; reaper never touches roster-backed rows; harness disabled at boot with stale harness rows → counted, not deleted; all store SQL — flush, repair, reaper and every harness request — executes on the PvE maintenance task, so two SQL writers can never race (the harness `flushNow` is a queued request, not a call).
