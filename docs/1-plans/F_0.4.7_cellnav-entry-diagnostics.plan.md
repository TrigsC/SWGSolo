# POB Cell-Entry Navigation Diagnostics (Pass 1: Instrument) Implementation Plan

## Overview

SimPlayer NPCs (PvP squads, PvE hunters, and by extension miners) cannot reliably
traverse from the outdoor world into a building's interior **cell**. Observed
symptom: the bot runs to a structure doorway and then "teleports" into a corner /
into the wall of the cell it is entering, where it wedges until some unrelated game
system removes it. This has been seen at the Theed starport (PvP) and the Mos
Eisley / cantina doorway (PvE, during the v0.4.6 real-buff work).

This plan is **Pass 1 of a two-pass fix: instrumentation only.** It adds a gated,
default-off diagnostic that (1) auto-spawns a single test bot outside the Mos
Eisley cantina, (2) drives it through the doorway into the cantina interior cell
using the exact fork movement pipeline the production bots use, and (3) logs every
movement step — path nodes, cell/coordinate-space transitions, and the applied
position — to a dedicated `bin/log` file. **No behavior is changed and no fix is
attempted in this pass.** The captured trace is the input to Pass 2 (the actual
fix), which is out of scope here.

## Problem Statement

- **Interiors use POB (portal object building) portal/floor graphs**, not the
  outdoor Recast navmesh. Crossing a doorway is a transition from world space
  (parent cell = none, `parentID 0`) into a cell's **model-local** coordinate
  space.
- The fork's movement pipeline is cell-aware since P.6.5b: `SimPlayerController::
  moveTo(worldPos, localPos, cell)` carries a target cell, path nodes retain their
  `CellObject`, and `AiAgentImplementation::findNextPosition`
  (`AiAgentImplementation.cpp:4631`) does per-node coordinate-space transforms
  (`PathFinderManager::transformToModelSpace`) as `currentParentID != nextParentID`
  flips across the portal. `updateCurrentPosition` (`AiAgentImplementation.cpp:4541`)
  then applies the new position and calls `updateZoneWithParent(cell,...)` to move
  the agent into the cell.
- The "teleport into a corner" is consistent with a **coordinate-space / portal
  handoff defect** somewhere in that chain (a world coord applied as if
  cell-local, a bad `transformToModelSpace`, a wrong node cell from `findPath`, or
  an interpolation that snaps Z/floor incorrectly at the boundary), but the exact
  failing step is **unknown**.
- **Today it is effectively unobservable.** The existing traces
  (`#ifdef DEBUG_MOVE`, `DEBUG_AI`, `DEBUG_FINDNEXTPOSITION`) all route through
  `AiAgent->info()`, which — per this project's hard-won finding — **does not
  reach `core3.log`** (only `SimPlayerManager->info()` does). So the single most
  important moment (the doorway crossing) currently produces no readable output.

The goal of Pass 1 is to make that moment fully observable in a file we can read.

## Solution Architecture

Four gated, default-off pieces, all keyed to **one** tagged test bot so nothing
else in the world is affected or spammed:

1. **A dedicated file logger** (`bin/log/cellnav.log`) — a small append-only,
   timestamped sink mirroring the proven `dumptarget.log` pattern
   (`DumpTargetInformationCommand.h:295`). A single static helper both
   `SimPlayerController` and `AiAgentImplementation` can call, so the whole
   movement chain writes to one ordered trace.

2. **A gated auto-spawn test bot on a dedicated one-shot controller** — a new
   `sim_player_manager.lua` `cellNavDiag` config table (default `enabled=false`)
   drives `SimPlayerManager` to spawn one SimPlayer bot at the outdoor start
   (3395, -4775, tatooine) on boot, tag it, and issue a single interior route to
   the cantina target (3385, -4811). The bot runs on a **new `SimCellNavDiagController`**
   (sibling of `SimMinerController`, subclass of `SimPlayerController`) whose only
   job is to drive the one route and then stop — so, unlike a stock
   `SimMinerController`, it never resumes survey/sample/resource behavior that
   would pollute the one-shot trace. Spawn mirrors the existing single-miner spawn
   at `SimPlayerManager.cpp:26297-26331`.

3. **Faithful interior-cell target resolution** — transform the interior world
   point into the cantina building's model space, find the containing `CellObject`
   (and its floor Z) by ray-casting each cell's floor via
   `CollisionManager::getCellFloorCollision`, form the cell-local `localPos`, and
   derive `worldPos` from `WorldCoordinates(localPos, cell)`, then drive the
   route through the protected `moveToInterior(worldPos, localPos, cell)` — the
   same entry the PvE buff work uses to walk hunters into provider cells
   (`SimHunterController.cpp:342-365`). Because `moveToInterior` is `protected`
   on `SimPlayerController`, the route is issued from **inside**
   `SimCellNavDiagController` (a subclass), not from the manager. If the cell
   cannot be resolved, the run **fails loudly** rather than degrading to a
   world-only move that would not exercise the transition (see §3 details).

4. **Full-chain instrumentation, scoped to the tagged bot** — trace calls at every
   decision point in `SimPlayerController` (request/path/queue/arrival/failure) and
   in the engine mover `AiAgentImplementation::findNextPosition` /
   `updateCurrentPosition` (per-node consumption, cell transitions, applied
   position). The engine-mover traces run for **only** the one tagged OID via a
   lock-free manager check, so every other NPC's hot path is untouched.

## Implementation Details

### 1. Dedicated cell-nav diagnostic logger

**File**: `src/server/zone/objects/creature/simplayer/CellNavDiagLog.h` (new,
header-only static helper) — or, if a new file is undesirable, a static method on
`SimPlayerManager`.

**Modifications**:
- Provide `CellNavDiagLog::write(const String& line)` that appends a
  millisecond-timestamped line to `log/cellnav.log` via `std::ofstream(...,
  std::ios::app)`, exactly like `DumpTargetInformationCommand.h:295-297` (relative
  `log/` path lands next to `core3.log` in `bin/log/`).
- Keep it self-contained (open/write/close per call) so it is safe to call from
  multiple task-pool threads without adding a new mutex; append mode + short lines
  matches the existing `dumptarget.log` usage which already runs from command
  threads.
- A helper `CellNavDiagLog::fmtPos(agent-or-coords)` producing a compact
  `world=(x,y,z) cell=<oid|0> local=(x,y,z)` string so every site logs the same
  shape and world↔cell mismatches are visually obvious.

### 2. Gated test-bot spawn + tagging + drive

**File**: `src/server/zone/objects/creature/simplayer/SimPlayerManager.cpp`
(+ `SimPlayerManager.h`)

**Current state**: A single SimMiner is spawned at
`SimPlayerManager.cpp:26297-26331` (`spawnCreature` → reset flags →
`setSimAlwaysActive` / `setSimPlayerBot(true)` → `applySimNpcPresentation` →
`setCustomAiMap("simMiner")` → `new SimMinerController(agent,...)` →
`controllers.put(oid, ctrl)` → `activateAiBehavior(true)` → `ctrl->startSimLoop()`).
Lua config is loaded in `SimPlayerManager`'s config-load path alongside the other
`*Config` tables.

**Modifications**:
- Add a `cellNavDiagConfig` struct (enabled flag, planet string, spawn X/Y,
  target X/Y, doorway X/Y, optional Z) loaded from the new Lua `cellNavDiag` table
  in the existing `loadLuaConfig`/`applyConfig` path.
- Add a manager member `uint64 cellNavDiagBotOid = 0;` and a tiny public
  `bool isCellNavDiagBot(uint64 oid) const { return oid != 0 && oid ==
  cellNavDiagBotOid; }`. Written **once** at spawn, before the bot receives any
  move order, then only read — a plain-uint64 read/compare, no lock needed on the
  hot path (single-writer-before-first-read).
- Add `spawnCellNavDiagnosticBot()`, invoked from the same boot/init point that
  kicks off the other gated sim spawns, **only when `cellNavDiagConfig.enabled`**.
  It mirrors `26297-26331` to create the bot at (spawnX, spawnY, navHeight) on the
  configured planet, records `cellNavDiagBotOid = oid`, attaches a
  `SimCellNavDiagController` (not `SimMinerController`), then:
  1. resolves the interior cell target (see §3),
  2. logs the resolved target via `CellNavDiagLog::write`,
  3. stores the resolved (worldPos, localPos, cell) on the diagnostic controller
     and calls `ctrl->startSimLoop()`, which issues the single `moveToInterior`
     route from inside the controller.
- The bot uses the existing no-op `simMiner` AI tree so the controller is the sole
  mover (no dual-driver), reproducing the production movement path exactly.

### 2b. Dedicated one-shot diagnostic controller

**File**: `src/server/zone/objects/creature/simplayer/SimPlayerController.h` +
`SimPlayerController.cpp` (add `SimCellNavDiagController`, a sibling of
`SimMinerController`).

**Modifications**:
- `SimCellNavDiagController : public SimPlayerController` with a small
  `setDiagnosticRoute(worldPos, localPos, cell)` setter.
- `startSimLoop()` override: issue exactly one `moveToInterior(worldPos, localPos,
  cell)` (legal — it is `protected` on the base and this is a subclass) and log the
  request; do nothing else.
- `onArrived()` override: log `ARRIVED` with the final `world/cell/local` and
  **stop** — no re-targeting, no survey/sample. One-shot, so the trace ends cleanly
  at the crossing outcome.
- `onPathFailed()` override: log `PATH_FAILED` and **stop** (no reassignment).
- This keeps the trace to a single directed route and avoids the
  `SimMinerController` survey/sample/resource loop that would otherwise fire on
  arrival/failure and pollute the log.

### 3. Interior-cell target resolution

**File**: `SimPlayerManager.cpp` (helper used by `spawnCellNavDiagnosticBot`)

**Determine the containing cell (concrete method)**:
- Obtain in-range objects at the interior point (`targetX`, `targetY`) via the
  zone's in-range query and identify the Mos Eisley cantina `BuildingObject` (a
  cell-bearing building at that point; log all candidates).
- **Transform to building model space FIRST.** `getCellFloorCollision` does **no**
  transform — it ray-casts its `(x, y)` arguments directly against the cell's
  `FloorMesh` in **model-local** space, and the float it returns is a **model-local**
  Z. So compute `localXY = PathFinderManager::transformToModelSpace(worldPoint,
  building)` (`PathFinderManager.h:60`; all cells of a POB share the building's
  model frame) and use `localXY.getX()/localXY.getY()` for the ray, not the raw
  world `targetX/targetY`. (My earlier `getWorldFloorCollisions`/world-coord claim
  was wrong on both counts: `IntersectionResult` carries no owning cell, that query
  tests exterior portal appearance, and the args here are model-local.)
- Iterate the building's cells `getCell(i)` for `i` in `1..getTotalCellNumber()`
  (`BuildingObjectImplementation.cpp:745`) and call
  `CollisionManager::getCellFloorCollision(localXY.getX(), localXY.getY(), cell)`
  (`CollisionManager.h:73` / `CollisionManager.cpp:324`) for each. A cell returning
  a non-empty result **contains** the point; the returned float is the model-local
  floor **Z**.
- **Selection rule (deterministic):** more than one stacked cell can hit. Choose the
  hit whose floor Z is **closest to the expected local target Z** (`localXY.getZ()`,
  or `cellNavDiag.targetZ` transformed to local when set) — i.e. the floor the
  target actually stands on. Log every cell tested with its floor Z and the chosen
  one (cell OID, cell number, `getCellName` from
  `BuildingObjectImplementation.cpp:2007`).
- Form `localPos = (localXY.getX(), floorZ, localXY.getY())` (model-local, Z=floor
  height) and derive `worldPos = WorldCoordinates(localPos, cell).getWorldPosition()`.
  Pass `worldPos` (for the controller's distance math) and `localPos`+`cell` (for
  the path request) into the route. `cellNavDiag.targetZ` is a config fallback only
  if no cell floor hits.
- **Do NOT fall back to a raw-world `moveTo`** — a world→world route never crosses
  the portal and would silently defeat the diagnostic. Instead, on an unresolved
  cell at boot (zone/navmesh/building not ready), **defer and retry** on the
  **already-created** diagnostic bot/controller (no second bot is spawned): a
  manager-owned delayed task re-runs the resolution, and on success calls
  `setDiagnosticRoute(...)` + `startSimLoop()` on the existing controller. Concrete
  bounds: **up to 10 attempts at 3s each (~30s total)**, matching the other sim
  spawns' boot-readiness window. If all attempts fail, **abort with a loud
  `CELLNAV_RESOLVE_FAILED` log**; the idle bot moves nowhere — never issue a
  meaningless world-only leg.
- **Read-only**: this resolution only reads building/cell templates and geometry;
  it takes no manager lock beyond what the in-range/collision query already requires,
  and holds no lock across the query (matching the `refreshProvider` pattern at
  `SimHunterController.cpp:318-347`).

### 4. Controller-level instrumentation (the fork movement layer)

**File**: `src/server/zone/objects/creature/simplayer/SimPlayerController.cpp`

All sites gated by `agent != nullptr && SimPlayerManager::instance()->
isCellNavDiagBot(agent->getObjectID())` so only the test bot logs.

**Modifications** (trace only — no logic change):
- `moveTo(worldPos, localPos, cell)` (`:208`): on entry, log the agent's current
  `world/cell/local`, the requested `worldPos/localPos/cell`, straight-line
  distance, `interiorApproachLeg`, and hybrid-movement state.
- `onPathFound(path, usesNavmesh, overland)` (`:269`): log path acceptance and the
  **entire node list** — for each node its index, world position, local point, and
  cell OID — so a wrong or missing cell on the doorway/interior node is visible.
  Log the reject/short-path/stale-path branches too.
- `queueMorePathNodes()` (`:679`): log each `PatrolPoint` actually queued onto the
  agent (position + cell), since these are what `findNextPosition` consumes.
- `checkArrival()` (`:713`): per-tick log of `state`, current `world/cell`, the
  active `destination` (world/local/cell), 2D distance, patrol-point count, the
  next patrol point (pos + cell), and which branch fires (arrived / stuck-watchdog
  escalation / hybrid resume). Explicitly flag when the agent's **current parent
  cell changes** between ticks (the crossing event). The high-frequency per-tick
  line is gated by `cellNavDiagConfig.logEverySimLoopTick` (via a new
  `SimPlayerManager::getCellNavDiagLogEveryTick()` getter) so the option is
  actually consulted; the crossing-event flag and terminal outcomes always log
  regardless.
- `onPathFailed()` (`:612`): log the failure and cause.

### 5. Engine-mover instrumentation (where the corner-teleport happens)

**File**: `src/server/zone/objects/creature/ai/AiAgentImplementation.cpp`

The actual position/cell mutation happens here; this is the highest-value trace.
All sites gated by `getSimPlayerBot() && SimPlayerManager::instance()->
isCellNavDiagBot(getObjectID())` (the manager singleton is already referenced
throughout this file), so **only the one test bot** ever takes the logging path —
every other NPC's `findNextPosition` hot loop is byte-for-byte unchanged.

**Modifications** (trace only):
- `findNextPosition(maxDistance, walk)` (`:4631`): log `currentPosition` (parent
  space), `currentWorldPos`, current parent cell OID, the target
  `endMovementPosition` (world + local + cell), and the `findPath` result the
  mover computes internally at `:4751/:4756` (node count + each node's cell), so we
  see whether the **engine's own** portal path differs from the controller's.
- Inside the multi-node consumption loop (`:4776-4851`): when
  `currentParentID != nextParentID` (`:4789`) — i.e. a world↔cell crossing — log
  both the pre-transform `currentPosition` and the post-`transformToModelSpace`
  `checkPos`, plus the node being consumed/interpolated. This is the exact place a
  world coordinate would be mis-applied as cell-local.
- After `updateCurrentPosition(&nextStepPosition)` (`:4890`): log the resulting
  `getWorldPosition()`, `getPosition()`, and new parent cell OID — the definitive
  before/after of each step, which will show the jump-to-corner directly.
- `updateCurrentPosition(nextPosition)` (`:4541`): log the applied
  `setPosition(...)` args, the incoming cell OID, and whether it took the
  `updateZoneWithParent(cell,...)` (`:4554`) vs `updateZone` (`:4556`) branch —
  confirming whether/when the agent is actually re-parented into the cell.

## Technical Considerations

- **Pattern Usage**: Test-bot spawn mirrors the existing single-miner spawn
  (`SimPlayerManager.cpp:26297-26331`); interior-approach mirrors the PvE buff
  provider approach (`SimHunterController.cpp:342-365` `moveToInterior`); the file
  logger mirrors `dumptarget.log` (`DumpTargetInformationCommand.h:295`).
- **Locking & References**: Instrumentation is read-only and runs **inside**
  existing lock scopes (e.g. `checkArrival` holds `Locker locker(agent)`;
  `findNextPosition` holds `Locker locker(&targetMutex)`) — it adds no new lock and
  changes no lock ordering, so it cannot introduce the class of regression the
  project guards against. The cell-resolution query holds no lock across the
  in-range call. `cellNavDiagBotOid` is a single-writer-before-read plain uint64
  (no atomic/lock needed on the read path).
- **IDL Impact**: **None.** No `.idl` field/method changes; no `src/autogen/`
  regeneration. `getSimPlayerBot()`, `isCellObject()`, `getParent()`,
  `getObjectID()`, `getWorldPosition()` are all existing accessors.
- **C++ vs Lua Placement**: Instrumentation and spawn are C++ (they sit in the
  compiled movement pipeline); the trigger, coordinates, and verbosity are Lua
  config (`sim_player_manager.lua`), default-off.
- **Gating & Simulation-Only**: The entire feature is gated behind
  `cellNavDiag.enabled=false`. The test bot is a standard simulation-only SimPlayer
  (no inventory/credit/market/persistence mutation; it only moves). When disabled,
  no bot spawns and no logging site executes.
- **Hot-path safety**: The `findNextPosition`/`updateCurrentPosition` traces are
  guarded by a fast `getSimPlayerBot()` short-circuit **and** the single-OID
  `isCellNavDiagBot` compare, so for every other creature the added cost is one
  boolean check already dominated by the existing `getSimPlayerBot()` logic in
  that function.
- **Dashboard Visibility**: Not required for Pass 1 — the owner-requested sink is
  the `bin/log/cellnav.log` file. (An optional `cellNavDiag` dashboard field —
  bot OID / phase / last world+cell — could be added later but is out of scope.)
- **Live Verification Plan**: Owner flips `cellNavDiag.enabled=true`, restarts, and
  watches the bot walk to the cantina doorway in-game while the run writes
  `bin/log/cellnav.log`. Success for Pass 1 = a complete, readable step-by-step
  trace of the doorway crossing (path nodes with cells, the world↔cell transform,
  and the applied position at the moment it jumps to the corner) — **not** a fixed
  bot. We then read the log and author Pass 2 (the fix).
- **Edge Cases**: cantina building/cell fails to resolve at boot (log + bounded
  deferred retry on the existing bot, then loud `CELLNAV_RESOLVE_FAILED` abort —
  never a world-only move); the bot never reaches the doorway (trace still shows the outdoor
  approach and any stuck-watchdog escalation); multiple stacked cells at the point
  (log all candidates + chosen); zone/navmesh not ready at boot (spawn guarded like
  the other sim spawns; log if deferred/skipped).

## Performance & Cost Impact

- Disabled (default): zero — no bot, no logging site runs.
- Enabled: one extra NPC and one append-per-trace-line to a single file. The
  engine-mover traces execute for exactly one OID; all other NPCs pay only an
  already-present `getSimPlayerBot()` check plus one uint64 compare. Acceptable for
  a short, owner-supervised diagnostic run; the file is truncated/rotated by the
  owner between runs if it grows.

## Backward Compatibility

- Fully backward compatible: default-off, additive, no schema/IDL/persistence
  changes, no change to any existing NPC's movement. Reverting is deleting the
  gated code paths; nothing depends on them.

## Test Impact

- No unit tests are added in Pass 1 (per project norm, AI-movement work is verified
  live). The change is logging-only and gated off by default, so it affects no
  existing `src/tests/*Test.cpp` behavior.
- Acceptance is the **live run**: enable the flag, restart, confirm
  `bin/log/cellnav.log` captures a complete doorway-crossing trace.
- Pass 2 (the eventual fix) is where movement/coordinate-transform logic changes
  and where any targeted unit test (e.g. a `transformToModelSpace` boundary case)
  would be considered — explicitly out of scope here.
