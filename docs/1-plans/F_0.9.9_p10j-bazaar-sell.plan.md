## Overview

A roster PlayerBot that holds sellable loot in its vault bag walks to a city bazaar
terminal at the start of a job and lists items on the real bazaar, as a player would.
Listings are stock `AuctionItem`s, visible to and buyable by human players. The listing
fee comes out of the bot's credit store, sale proceeds go into it, and an item that does
not sell comes back to the bot's bag and is listed again at the same price. This is the
first P.10 surface shared with human players.

## Owner decisions (2026-10-15)

The roadmap (§8 item 2) deferred the human-listing policy and required this plan to
open with it. The owner chose:

1. **Seed the market, never undercut.** A bot never lists an item below the cheapest
   human listing of the same item on the same planet. Bots fill gaps; they never price
   a player out.
2. **Price anchor = loot value × markup.** The base price is the item's `junkValue`
   (rolled by `LootManagerImplementation::setJunkValue`, `:280-299`, already scaled for
   creature level and for yellow ×1.25 and legendary ×2.5 items) times a Lua markup,
   clamped to the bazaar limits.
3. **Sell everything except generic junk.** Items whose `junkDealerNeeded` carries the
   `JUNKGENERIC` bit (broken viewscreen, dud firework) stay in the vault for a later
   junk-dealer chunk.
4. **Relist an unsold item at the same price.** It comes back to the bag at expiry and is
   listed again on a later visit at the same price, still subject to rule 1.

**The formula** that combines them, evaluated at each listing:

```
base   = clamp(junkValue × markup, minPrice, MAXBAZAARPRICE)
anchor = the item's persisted ask (simbot_items.ask_price) if it has one, else base
floor  = lowest asking price of a human FORSALE instant-sale bazaar listing with the
         same game object type and the same name (colour codes stripped) on this planet
price  = max(anchor, floor)    // equal to a human's ask is allowed; below is not
skip the item if floor > MAXBAZAARPRICE, or junkValue <= 0
on the FIRST successful listing, ask_price := price (pre-tax) and never changes again
```

"Same price" therefore means **the first listing's pre-tax ask**, persisted on the item
row. A later change to `markup` does not reprice an item that has already been listed.
A human floor that has risen above the anchor still raises the relist, because rule 1
beats rule 4. The anchor is not lowered when the floor falls again.

"Human listing" means any bazaar listing that is not a bot listing (owner not an item
bag, see below). Seeded (`MarketSeeder`) listings count as human for rule 1. That is
the conservative reading, and it can be relaxed later.

## Problem Statement

The stock bazaar is built around a seller who is a player online:

| Stock behaviour | Where | Why it breaks for a bot |
|---|---|---|
| The item must be `isASubChildOf(player)`, the fee comes from `player->subtractBankCredits`, and replies go out as client messages | `addSaleItem` `AuctionManagerImplementation.cpp:519-801` | Bot items live in the vault, credits live in the store, and there is no client |
| **At boot, a listing whose `getPlayerName(ownerID)` is empty is deleted** | `initialize` `:115-121` | A bot body is not in the player name map, so every bot listing would vanish at the next boot |
| **Maintenance deletes the same listings every `CHECKEVERY` minutes** (`deleteItem(..., true)`) | `doAuctionMaint` `:377-399` | Same, while the server is running |
| The seller is resolved by **name** (`getPlayer(ownerName)`), a null seller aborts the payout, and mail goes to `ownerName` | `doInstantBuy` `:1059`, `:1206-1214`, `:1179-1180` | Proceeds are lost. Roster names come from `NameManager::makeCreatureName`, so a bot can share a name with a real character: that player would be **paid for the bot's sale** and mailed about it |
| `updateAuctionOwner` short-circuits when `getPlayer(ownerName) == buyer` | `:2369-2388` | A human buyer who shares the bot's name would keep the bot as owner |
| Expiry and cancel mail `ownerName`; an expired sale is destroyed 7 days later | `expireSale` `:2116-2158`, `deleteExpiredSale` `:2314-2354` | Same name collision; an item the bot never collects is destroyed |
| Only the owning body may retrieve or cancel (`player->getObjectID() == ownerID`) | `checkRetrieve` `:1442-1446`, `cancelItem` `:2015` | A bot body gets a new OID every death |

`MarketSeederBridge` already lists from a ghostless "system seller" creature
(`createVendorItem` `:996-1015`). Its listings hit the same boot and maintenance
deletion, a pre-existing seeder problem that this chunk does not fix.

## Solution Architecture

### Ownership: the bag is the seller

A bot listing's `AuctionItem.ownerID` is the **identity's vault bag OID**, and
`ownerName` is the identity's first name. This one choice carries most of the design:

- **It is stable.** The bag survives every body death and every restart; it is the same
  object F_0.9.3 already uses as the item's owner record.
- **It is self-identifying from the object store alone.** `isSimBotListing(item)` is
  `AiEconomyManager::isItemBag(zoneServer->getObject(item->getOwnerID()))`, a template
  check on a persistent object. It does not depend on `SimPlayerManager` having loaded
  anything, so `AuctionManager::initialize` can use it at boot.
- **It can never match a player.** Every stock owner check (`checkRetrieve`,
  `cancelItem`, the "my sales" search, `getCommodityCount`) compares a player OID with
  `ownerID`, so no human can retrieve, cancel or count a bot listing.
- **It replaces every name lookup.** Bot listings are decided by `ownerID`, never by
  `ownerName`.

### Two stores, one authority (deviation from the roadmap's journal)

The roadmap sketched a MySQL write-ahead phase journal (`prepared → fee_debited →
auction_created → listed → …`). F_0.9.3 showed why that does not hold here: a store
write sits in a batch until the next flush, so a "write-ahead" row is not durable when
written (`tuto_0.9.10.md` §1). This plan uses F_0.9.3's rule instead: **the object store
is the authority, and MySQL follows and is reconciled at boot.**

- The `AuctionItem` (BDB `auctionitems`) is the authority for "this item is listed by
  identity X" (owner = X's bag) and for "it sold" (status `SOLD`).
- `simbot_listings` (MySQL, schema 1016) records each listing's identity, price, fee,
  state and settlement, so the dashboard can show it, and so boot reconciliation can
  detect a sale that one store remembers and the other has forgotten.
- `simbot_items` gains the state `listed` (the `state` column is `varchar(12)`) and a
  column `ask_price INT NOT NULL DEFAULT 0` (schema 1016 `ALTER`; 0 = never listed).
  `simbot_progression` gains the two ledger applied marks (next section).
  While listed, the item has no parent container, so the F_0.9.3 reconciliation must
  not treat it as missing.
- **A listed item is still owned.** `held` and `listed` both count toward
  `maxItemsPerBot` and toward the identity's item holdings. Listing and retrieving
  write **no** item-ledger row (ownership does not change). The item ledger moves −1
  only when the item leaves the identity, on a sale or on orphaning.

### The settlement receipt (MyISAM idempotency)

A sale touches four MySQL rows in no transaction: the ledger row, the balance, the item
row and the listing row. The listing row's `state` therefore cannot be what decides
whether proceeds were paid. Neither can the ledger row alone. The F_0.9.2 boot check
(`loadPlayerBotProgressionStore`, `SimPlayerManager.cpp:10931-10958`) keeps the
**balance** as the authority: when the newest `balance_after` differs, it appends a
compensating `reconcile` row; it does not re-apply the ledger. So a sale ledger row can
exist for credits that never reached the balance.

**The applied mark (single-row atomicity).** Schema 1016 adds
`simbot_progression.bank_ledger_applied_id` and `cash_ledger_applied_id` (BIGINT,
default 0).
- **Flush.** The flush already INSERTs an identity's ledger rows before its balance
  UPDATE. It now records the highest inserted ledger `id` per identity and kind, and
  writes it **in the same UPDATE statement as the balance**. MyISAM makes a single-row
  UPDATE atomic, so the balance and the mark always land together.
- **Meaning.** A credits ledger row is *applied* if and only if its `id` is ≤ its
  identity's mark for that kind. A row above the mark (a crash between the INSERT and
  the UPDATE) is void. The F_0.9.2 compensating row stays as it is, so the ledger sum
  still matches the balance, but nothing treats the void row as paid.
- **Voiding is made permanent at load, before the mark can move again.** Otherwise a
  later flush would advance the mark past a void row and "resurrect" it.
  - `loadPlayerBotProgressionStore` rewrites every credits row above its identity's
    mark as `source = CONCAT('void_', source)`. It is one UPDATE per identity and kind,
    issued before `progressionLoaded` is set, and no flush runs before that.
  - The rewrite is idempotent: a crash part-way through is finished by the next load.
  - **At runtime a row cannot become void.** The flush keeps a per-(identity, kind)
    **`insertedHighWater`** in memory, under `progressionMutex`. It is raised as soon as
    each ledger INSERT succeeds and is **never reset by a failed flush**, whether the
    failure lands at a later ledger INSERT, an item or listing write, or the balance
    UPDATE itself. Every early return merges the dirty balance back (existing
    behaviour), and the high-water mark survives with it. The next successful balance
    UPDATE writes `mark = insertedHighWater`. Already-inserted rows are never re-queued
    (existing behaviour), and the re-dirtied in-memory balance already contains their
    deltas. So by the time the mark passes a row, that row's delta is in the balance
    written in the same statement. Only process loss leaves a row above the mark, and
    load voids it.
  - Receipts never count `void_*` sources.
- **Migration.** It initialises each mark to the current `MAX(id)` for that identity
  and kind, so every pre-1016 row counts as applied, which matches F_0.9.2's semantics.
- **Generalization.** The mark is generic and also fixes the same ambiguity for future
  callers. The doctor fee, mission credits and loot cash keep their current behaviour,
  because none of them reads it.

**The receipts.**
- **Credit receipt.** Credits are *paid* for auction A when Σ `delta` over **applied**
  `credits_bank` rows with `ref_id = A` and source `bazaar_sale` or
  `bazaar_sale_reversal` is > 0. A reversal is a `bazaar_sale_reversal` row of −net with
  the same `ref_id`, so the sum returns to 0.
- **Item receipt.** The item −1 for auction A is *written* when Σ `delta` over
  `kind = item` rows with `ref_id = A` and source `bazaar_sale` or
  `bazaar_sale_reversal` is < 0. Item rows carry no balance (holdings are derived from
  `simbot_items`), so a single INSERTed row is its own atomic receipt; no mark is
  needed. A reversal writes +1 with source `bazaar_sale_reversal`.
- **Checked before writing.** Settlement and reconciliation evaluate **both** receipts
  before writing either. Each one is written only if its sum says it is missing, so a
  partial earlier attempt is completed rather than repeated. The receipts are loaded for
  every open listing at boot and kept in memory under `progressionMutex` afterwards.
  Writes are queued through the existing ledger path, so the mark advances with them.
- **The daily prune** never deletes `bazaar_sale` / `bazaar_sale_reversal` rows whose
  auction still has a listing row. Listing rows are pruned first, once they are closed
  and older than `ledgerRetentionDays`.

**Crash windows, accepted and bounded:**

- **Listing fee (20 credits).** It can be lost if a crash lands after the store flush
  and before the BDB save of the new `AuctionItem`. The item comes back to the bag
  because its removal was not saved either. No refund; this is documented.
- **Sale lost by the object store.** An applied credit receipt exists, but the
  `AuctionItem` is `FORSALE` again under the bag. Boot reconciliation writes the
  reversals, so credits are never duplicated.
- **Sale lost by the store** (the sale task was lost, the backlog overflowed, or the
  process crashed). The buyer-owned `SOLD` `AuctionItem`, or the item under a player
  creature once it has been retrieved, is the evidence. Boot reconciliation pays it (see
  *Instant pickup* below).
- **Listing never recorded.** A listing made and sold before its row was flushed, then a
  crash: no row names the bot. The proceeds are lost, which fails in the safe direction
  (accepted).

### Instant pickup (owner decision 2026-10-15, replaces the retrieval hold)

The plan first held a bot sale (`SOLD` with the bag still the owner) until the bot's
receipts were flushed, so that the `AuctionItem` stayed as durable evidence. Live
verification showed the cost: a buyer waited up to one 60-second flush interval to collect
the item. The owner rejected any wait. Instead:

- **Ownership.** `doInstantBuy` hands a bot sale to the buyer at once, through the stock
  `updateAuctionOwner`. Its bot branch never resolves the bag by name, so a buyer who
  shares the bot's name still becomes the owner. Seller mail stays suppressed. The bag
  OID is captured before the owner change and carried in the sale POD.
- **Settlement.** Enqueueing a sale raises `progressionBazaarFlushRequested` and kicks the
  maintenance lane. That pass settles the sale and force-flushes, so the receipts are
  durable within seconds rather than within the 60-second flush interval. Settlement
  marks the listing released.
- **Recovery of a lost POD.** A lost POD (a crash, or backlog overflow) no longer leaves a
  bag-owned record. Boot reconciliation (`findBuyerOwnedBotSaleLocked`) recovers the sale
  from the buyer-owned `SOLD` `AuctionItem`. Once the buyer has retrieved it, recovery
  falls back to the item itself sitting under a player creature
  (`settledByEvidence`).
- **Accepted risk (owner).** If the server crashes in the few seconds between a sale and
  its forced flush, after the buyer has collected the item, and the item then leaves the
  buyer's inventory, the bot loses that sale's credits. The player is never affected, and
  credits are never duplicated.
- **Older builds.** A held sale from an older build (bag-owned `SOLD`) is still refused
  at retrieval and released by the sweep.

### The flow

```
ANNOUNCE_JOB (bot in its city, gate on, sellable items, slots free, cooldown elapsed)
  -> BAZAAR_VISIT: nearest OUTDOOR bazaar terminal within maxDetourMeters
  -> walk (arriveMeters) -> at terminal:
       for up to maxListingsPerVisit candidates:
         price by the formula; reserve the fee from the store
         register a PENDING live listing keyed by the item OID (progressionMutex)
         AuctionManager::listSimBotItem(bag, name, item, terminal, price, expiry)
         success: settle-wins publish (below); commit the fee; persist ask_price
         failure: drop the PENDING entry, release the fee, count the reason
  -> beginBuffUp() (the normal job continues)

Human buys (stock doInstantBuy, a player thread):
  bot listing captured BEFORE updateAuctionOwner; no name lookup, no seller mail
  the buyer is debited (stock); the city tax goes to the treasury (stock arithmetic)
  AuctionItem SOLD with owner = bag: a HELD sale; the buyer cannot retrieve yet
  -> SimPlayerBotBazaarSaleTask (deferred POD, keyed by item OID + auction OID)
     -> no receipt yet: store += price - tax with the receipt ledger row,
        listing 'sold', item row deleted, item ledger -1
     -> receipt already present: repair the rows only, pay nothing
  -> next flush applies both receipts -> releaseSimBotSale: owner := buyer (by OID)
     -> the buyer retrieves as stock

Expiry or kill switch (SimPlayerBotBazaarSweepTask, bounded batch):
  FORSALE past expiry, EXPIRED, or every bot listing while gate off + drainOnDisable
  -> AuctionManager::retrieveSimBotItem -> the item is back in its bag
  -> item row listed->held, listing 'retrieved'; it is relisted at a later visit
```

## Implementation Details

### 1. Schema 1016: `simbot_listings`

**Files**: `src/server/db/ServerDatabase.cpp` (schema ladder, next to 1015 at the
F_0.9.3 block), `sql/swgemu.sql`.

The new MyISAM table, current state only (history is `simbot_ledger`):

- `auction_oid` BIGINT PK: the `AuctionItem` object id. It is new for every listing,
  available the moment `createVendorItem` returns, and needs no AUTO_INCREMENT
  round-trip.
- `identity_id` BIGINT NULL (NULL = orphaned), `object_id` BIGINT (the listed item).
- `state` VARCHAR(12): `listed`, `sold`, `retrieved` or `orphaned`. The in-memory
  `pending` state is never flushed.
- `price`, `fee`, `tax`, `net_paid` INT; `vendor_oid` BIGINT; `planet` VARCHAR(32);
  `buyer_name` VARCHAR(64).
- `listed_at`, `closed_at`, `released_at` (NULL until a held sale is released)
  `updated_at` DATETIME.
- Indexes: `identity_id`, `object_id`, `state`.

Closed rows (`sold` with `released_at` set, `retrieved`, `orphaned`) are pruned by the existing daily ledger
prune when older than `ledgerRetentionDays` (0 = keep). The same migration adds
`simbot_items.ask_price INT NOT NULL DEFAULT 0`.

### 2. `AuctionManager`: the bot surface and seven guarded branches

**Files**: `src/server/zone/managers/auction/AuctionManager.idl`,
`AuctionManagerImplementation.cpp`. No engine3 change.

**New IDL methods** (native, additive; `src/autogen/` regenerates):

- `boolean isSimBotListing(AuctionItem item)`: the owner object is an item bag. It is
  used by every branch below and by `SimPlayerManager`.
- `int listSimBotItem(SceneObject bag, final string sellerName, SceneObject item,
  SceneObject terminal, int price, unsigned int expireSeconds)`: returns an
  `ItemSoldMessage` code and writes the new auction OID through an out-parameter
  equivalent (return struct or a follow-up `getItem(itemOid)` lookup, as
  `MarketSeederBridge::listOnBazaar` does at `:242`). It is the bazaar-only subset of
  `addSaleItem` + `checkSaleItem` + `createVendorItem`:
  - **Checks kept from stock:**
    - the terminal `isBazaarTerminal()` with a zone;
    - `isNoTrade` / `containsNoTradeObjectRecursive`;
    - `isIntangibleObject` and the arrangement-descriptor rejection (`:907-917`);
    - `1 <= price <= MAXBAZAARPRICE`;
    - `auctionMap->containsItem`;
    - the item's parent is `bag`.
  - **City tax** is added to the price exactly as stock does (`:668-672`).
  - **The `AuctionItem` is built by a shared helper**, extracted from
    `createVendorItem`'s field setup (`:928-990`) so the stock and bot paths cannot
    drift. Ownership is then set by hand: owner = bag OID, name = `sellerName`. The
    commodity limit is keyed by bag OID. The expiry is
    `min(stock COMMODITYEXPIREPERIOD, expireSeconds)`.
  - Then `auctionMap->addItem(nullptr, terminal, item)`, `destroyObjectFromWorld(true)`
    on the item and `setPersistent(1)`, with stock order and locks. The `TransactionLog`
    entry uses `TrxCode::AUCTIONADDSALE` with the bag as the source.
  - **No fee and no client messages.** The fee is the store's business (§3).
- `int retrieveSimBotItem(AuctionItem item, SceneObject bag)`: requires
  `isSimBotListing(item)`, owner == bag, and status `FORSALE` (not an auction) or
  `EXPIRED`. Steps: `bag->transferObject(object, -1, false)`, status `RETRIEVED`,
  `deleteItem` from the map, `removeFromCommodityLimit`, `setAuctionedItemObjectID(0)`
  (the same tail as `retrieveItem`, `:1567-1574`), `TrxCode::AUCTIONRETRIEVE`.
- `int releaseSimBotSale(AuctionItem item)`: requires a held bot sale (`SOLD`, owner is
  an item bag). It resolves the buyer with `zoneServer->getObject(item->getBuyerID())`,
  never by name, and calls `updateAuctionOwner(item, buyer)` under the `AuctionItem`
  lock (branch 4's name-blind path). **Buyer gone** (null `getObject(buyerID)`): under
  the `AuctionItem` lock, it calls `auctionMap->removeFromCommodityLimit(item)` (the
  bag's entry), then sets `ownerID = buyerID` and `ownerName = bidderName` directly, so
  the item stops being a held bot sale and stock's missing-owner maintenance cleans it
  up. Counted `releaseBuyerGone`. Either way, the caller then sets the listing's
  `released_at`.
The human-floor lookup is **not** an `AuctionManager` method; see §3 *Listing*, step 3.
It reads the map through the existing public `getAuctionMap()` accessor (used by
`MarketSeederBridge::listOnBazaar`, `:242`) and classifies owners from a precomputed
bag-OID set, so it loads no foreign object.

**Guarded branches in stock code** (each one an `if (isSimBotListing(item))` that leaves
the stock path byte-identical for every other listing):

1. **`initialize` `:115-121`**: an empty owner name does not delete a bot listing. It
   is loaded into the map and its commodity limit as usual. A bot listing whose bag
   object cannot be loaded is still deleted (`deleteAuctionedObject` as stock decides);
   reconciliation then marks its rows orphaned.
2. **`doAuctionMaint` `:377-399`**: the same exemption from "missing owner" deletion.
3. **`doInstantBuy` `:1038-1236`**:
   - **Captured at entry:** `simBotSale`, the bag OID and the price. The owner then moves
     to the buyer at once (instant pickup).
   - **For a bot sale:**
     - no `getPlayer(ownerName)`;
     - no seller mail (the buyer mail is kept, so the buyer still gets the waypoint);
     - the `seller == nullptr` error is not logged.
   - **After the buyer debit (stock, unchanged):**
     - the tax is computed as stock does (`:1053-1054`);
     - the city treasury gets the tax as stock does (`:1231-1234`);
     - `SimPlayerManager::enqueuePlayerBotBazaarSale(POD)` carries the auction OID,
       item OID, bag OID, price, tax and buyer name.
   - The `TransactionLog` keeps `INSTANTBUY` with a null seller.
4. **`updateAuctionOwner` at sale**: called for a bot sale as for any sale. A guarded
   branch skips the name-based `previousOwner` short-circuit (`:2369-2388`), so a buyer
   who shares the bot's name still becomes the owner.
5. **Mail suppression** in `expireSale`, `expireBidAuction`, `deleteExpiredSale` and
   `cancelItem`: a bot listing sends no seller mail (the name may belong to a real
   character). The status transitions stay stock.
6. **`checkRetrieve` `:1403-1483`**: refuses only a held sale from an older build
   (bag-owned `SOLD`). A current bot sale is buyer-owned and is retrieved as stock.
7. **`doAuctionMaint` / `initialize` on a held sale**: the owner is a bag, so the
   missing-owner deletion exemption (branches 1 and 2) also keeps held sales.

`ExpireAuctionTask` and bidding never apply: bots list instant sales only
(`auction = false`, `premium = false`).

### 3. `SimPlayerManager`: config, gate, listing state, settlement, sweep

**Files**: `SimPlayerManager.h`, `SimPlayerManager.cpp`.

**Config** (`loadPveConfig` beside the `loot` block): `playerBotProgression.bazaarSell`
(bool, default false) and a `bazaar` block:

| Setting | Default | Notes |
|---|---|---|
| `markup` | 3.0 | Multiplies `junkValue`; clamped 0.1–100 |
| `minPrice` | 50 | Floor of `base` |
| `maxListingsPerBot` | 10 | Clamped 1..`MAXSALES` (25), parity with the stock per-player cap |
| `maxListingsPerVisit` | 3 | |
| `listingDurationHours` | 168 | Clamped 1..168 (stock 7 days) |
| `visitCooldownMinutes` | 120 | Per identity |
| `maxDetourMeters` | 300 | Terminal search radius from the bot |
| `arriveMeters` | 4 | |
| `visitTimeoutSeconds` | 180 | |
| `sweepIntervalSeconds` | 300 | |
| `sweepBatch` | 20 | |
| `drainOnDisable` | true | |

**Gate** `playerBotBazaarSellGateEnabled(identityId)`, in the reference shape
(`playerBotProgressionAwardGateEnabled`): master `progression.enabled` first, the
harness per-identity override second, the capability last. It also requires:
- `isItemVaultAvailable()`;
- `!progressionListingReconcilePending`;
- `!progressionItemReconcilePending`;
- `auctionManager->isMarketEnabled()`.

It is evaluated **before** taking `progressionMutex` (the F_0.9.5 lock-order lesson).
**This gate decides only whether a NEW listing may be created.**

**Settlement mode (the obligations lane is gate-independent).** Today
`loadPlayerBotProgressionStore` returns early when `progression.enabled` is off
(`SimPlayerManager.cpp:10825`), and the flush only runs on a loaded store. Open bot
listings are obligations that must be serviced even with every gate off. So:

- At each maintenance tick, while the store is not loaded, the maintenance lane checks
  for **open** obligations only:
  - a `listed` row;
  - a `sold` row with `released_at` NULL (a held sale not yet released);
  - a `sold` row whose **credit receipt or item receipt is missing**, by the same
    aggregate rules as above (applied `credits_bank` sum ≤ 0, or `item` sum ≥ 0), as one
    `EXISTS` query over `simbot_ledger` joined with
    `simbot_progression.bank_ledger_applied_id`;
  - or at least one `AuctionItem` owned by a vault bag (a live listing or a held sale),
    found by a walk against the vault's bag-OID set.
  Historical, fully settled `sold` rows never trigger a load, so retention 0 does not
  pin the store open. If any open obligation exists, the lane loads the store in
  **settlement mode**.
- Settlement mode is the normal load (roster, records, items, listings, ledger
  receipts) with the master flag left off. In it, the following run:
  - flush;
  - sale settlement;
  - sweep (expiry, plus drain when `bazaarSell` is off and `drainOnDisable` is set);
  - listing reconciliation;
  - item rows for listed and retrieved items;
  - deletion-path retrieval.
- Everything else stays gated as today: awards, XP, training, loot, doctor fees and new
  listings. Every award entry point already checks the master gate itself, and the
  plan adds a gtest-backed assertion (`SimBotBazaar::settlementModeAllows`) listing
  what settlement mode permits.
- **Before the store is loaded**, sale PODs are held in a bounded in-memory queue
  (`bazaarSaleBacklogMax`, default 256; overflow is counted and dropped). A dropped or
  lost POD is recovered at boot from the buyer-owned `SOLD` `AuctionItem`, or from the
  item under a player creature once it has been retrieved (*Instant pickup*). It is lost
  only in the owner-accepted crash window.

**Listing state**:
- **Live** listings are a `VectorMap<uint64, PlayerBotListing>` keyed by the **item
  OID** (an object has at most one live listing), plus a per-identity count, under
  `progressionMutex`.
- **Closed** listings are dirty rows flushed by auction OID.
- Dirty listing ids are flushed in `flushPlayerBotProgressionStore` with the same
  atomic-swap and merge-back shape as the item rows, after the ledger INSERTs.
- At boot the listings are loaded with the store, together with their receipt sums.

**Listing** (`listPlayerBotItemsAtTerminal(identityId, body, terminal)`, called by the
controller at arrival on its own thread):

1. Snapshot the bag's direct children (bag lock only, released before anything else).
   Candidates are `TangibleObject`s with:
   - `junkValue > 0`;
   - no `JUNKGENERIC` bit;
   - not no-trade;
   - a `held` row for this identity, and no live listing.
   They are ordered by descending `junkValue`.
2. Count the live listings (including `pending`) against `maxListingsPerBot`.
3. **Floors, one pass per visit.** Collect the candidate keys (game object type +
   colour-stripped name) first. Then:
   - take one `getItemBagMapSnapshot()` and turn its values into a bag-OID set;
   - walk `getAuctionMap()->getBazaarTerminalData(planet, "", nullptr)` **once**, under
     each `TerminalItemList`'s `rlock` (as `fillAuctionQueryHeadersResponseMessage`
     reads it, `:1645-1650`);
   - consider only `FORSALE` non-auction listings that have not expired, whose
     `ownerID` is not in the bag set and whose key is one of the candidates.
   The pass yields the minimum price per key. It reads `AuctionItem` fields only and
   loads or locks no other object. Each candidate is then priced with
   `SimBotBazaar::priceListing` (§5), using its persisted `ask_price` as the anchor.
4. Reserve the fee through a new `reservePlayerBotCredits(identity, amount, source)` /
   `commit` / `release`. This generalizes the doctor-fee reservation rather than adding
   a parallel one: one reservation map keyed by (identity, purpose); the doctor fee
   becomes its first caller with no behaviour change. The fee is `SALESFEE` × the stock
   merchant reduction (`:752-760`), using the identity's trained `simbot_skills`.
5. **Register before publishing.** Under `progressionMutex`, insert a live listing in
   state `pending`, keyed by the item OID (identity, bag OID, price). Release the mutex.
6. Call `listSimBotItem` with **no manager mutex held**.
   - **On success, under `progressionMutex`:** set the auction OID. If the entry is
     still `pending`, make it `listed`; if a settlement already moved it to `sold`
     (a human bought within that window), leave it `sold`. *Settlement wins.* Then:
     - commit the fee (ledger `credits_bank`, source `bazaar_fee`, ref = auction OID);
     - set the item row to `listed` **only if it still exists and is `held`**;
     - set `ask_price` if it was 0.
   - **On failure:** remove the `pending` entry (it was never visible), release the fee
     and count the reason.

**Sale settlement** (`enqueuePlayerBotBazaarSale` → `SimPlayerBotBazaarSaleTask`,
deferred exactly like `SimPlayerBotKillXpTask`, so a player-thread caller takes no
manager mutex). The POD carries the item OID, auction OID, bag OID, price, tax and
buyer name.

1. Resolve bag OID → identity via `getItemBagMapSnapshot()`.
2. Under `progressionMutex`, look up the live listing by **item OID**. Its state may be
   `pending` (the lister has not returned yet) or `listed`. If no live entry exists, a
   closed or reconciled row is found by auction OID.
3. Evaluate the auction's **two receipts** (credit: applied `credits_bank` sum > 0;
   item: `item` sum < 0). Including in-memory rows not yet flushed, they make
   re-delivery, the sweep and boot replay idempotent.
4. Write only what is missing:
   - **no credit receipt:** grant `price - tax` to the bank with the receipt row
     (`kind = credits_bank`, source `bazaar_sale`, ref = auction OID), through
     `grantPlayerBotCredits`, so the applied mark follows on the next flush;
   - **no item receipt:** write the item ledger −1 (`kind = item`, source
     `bazaar_sale`, ref = auction OID);
   - always: mark the listing `sold` with `net_paid` and the buyer name (a `pending`
     entry gets the auction OID from the POD), and delete the item row if present.
5. Settlement is **gate-independent** (settlement mode above): value promised to a buyer
   is always settled.
6. An unresolvable bag or an identity without a record is counted
   (`saleUnresolved`). Nothing is created; the credits vanish, as the stock null-seller
   path does.

The pure transition `SimBotBazaar::applyListingEvent(state, event)` (events:
`PUBLISHED`, `PUBLISH_FAILED`, `SOLD`, `RETRIEVED`, `RECONCILED_*`) encodes
"settlement wins" and is unit-tested in both orders.

**Sweep** (`SimPlayerBotBazaarSweepTask`, scheduled from the PvE maintenance tick every
`sweepIntervalSeconds`, running on the task pool; never holds a manager mutex while
locking objects):

- Candidates (copied under `progressionMutex`, then released):
  - `listed` rows whose `AuctionItem` is `EXPIRED`, or `FORSALE` past its expire time;
  - every `listed` row when the gate is off and `drainOnDisable` is set.
- For each, up to `sweepBatch`: `retrieveSimBotItem`. On success the item row goes to
  `held` and the listing to `retrieved`. A listing found `SOLD` with no settlement is
  settled (it covers a lost sale task). A listing whose `AuctionItem` is gone goes to
  reconciliation's single-listing path (§3, Reconciliation).

**Deletion** (`destroyPlayerBotItemsAndBag`, used by the reaper, retirement and the
harness `deleteIdentity`): first retrieve every live listing of the identity into its
bag, then destroy as today. If any listing cannot be retrieved, deletion is deferred and
counted (`deleteBlockedByListing`), honouring the roadmap's "never deleted while it
still owns items or listings".

**Reconciliation** (`reconcilePlayerBotListings`, run after `reconcilePlayerBotItems` on
the same boot pass, and only once `isMarketEnabled()` is true so the stock startup
maintenance has finished). Decisions come from the pure table in §5. It holds the
listing gate closed until it finishes.

| Listing row | Object store says | Result |
|---|---|---|
| `listed` | bot listing live (owner = this identity's bag) | unchanged |
| `listed` or `sold` | held bot sale (`SOLD`, owner = this bag) | write each missing receipt (credit, item); row `sold`; item row deleted if present; release after the flush applies both |
| `sold` | `SOLD` owned by the buyer (already released), or gone (retrieved or cleaned up) | set `released_at` if it is still NULL (the release reached BDB but the row update was lost); otherwise unchanged |
| `listed` | no listing; object in the identity's bag | row `retrieved`, item row `held` (no item ledger) |
| `listed` | no listing; object missing, or parentless | row and item row `orphaned`, item ledger −1 (item-receipt-checked) |
| `listed` or `sold` | bot listing live, an applied credit receipt and/or an item receipt present (BDB forgot the sale) | reverse each receipt that is present (credits −net, item +1, both `bazaar_sale_reversal`); row `listed`; item row `listed` (re-created if the sale deleted it) |
| none | bot listing live, bag mapped | adopt: row `listed` (fee 0); item row `listed` (created with item ledger +1 if absent) |
| none | held bot sale, bag mapped | adopt as `sold`. First repair acquisition: if the item has no `simbot_items` row and no `item` ledger +1 for it, write the +1 (source `reconcile_adopt`). Then follow the held-sale row above. **Tax is estimated**: `AuctionItem` stores only the gross price, so tax is recomputed from the terminal's current city rate (counted `adoptedTaxEstimated`); see the note below the table |
| none | bot listing live, bag unmapped | retrieve into the vault root, row `orphaned` (counted) |

The decision keys on **the object store's evidence plus the two receipt sums**, never
on the listing row's `state` alone.

**Why the adopted tax is an estimate.** The estimate applies only when **neither** the
listing row **nor** any sale receipt reached MySQL. That is a listing made and sold
within one ~60 s flush window, followed by a crash. The alternative is a new persisted
field on `AuctionItem` (sale-time tax or net), which changes a stock BDB object class
that every human listing also uses. For a double-crash-window edge whose only error is
the difference between two city tax rates on one item, that cost is out of proportion.
The estimate never duplicates credits, and it is visible on the dashboard. That is what makes it safe whichever of the four MyISAM
writes landed before a crash.

`SimBotItemReconcile` gains `ROW_LISTED` and `LOCATION_LISTED` (the object is held by
an `AuctionItem` whose owner is a bag), so a `listed` item row with no parent is never
mistaken for a missing item, and a `held` row whose object is listed by its own bag
becomes `listed`.

## Technical Considerations

- **Pattern usage:**
  - the vault and bags, plus a reconciliation table in a pure header (F_0.9.3);
  - the deferred POD hand-off (F_0.9.1 kill XP);
  - the reservation (F_0.9.2 doctor fee, generalized);
  - the gate shape (`playerBotProgressionAwardGateEnabled`);
  - the city terminal scan (`MarketSeederBridge::findBazaarTerminal`, P.8.2 pattern).
- **Locking & references:**
  - **Global object order: `AuctionItem` → item → bag → vault.** It extends F_0.9.3's
    item → bag → vault, and puts the `AuctionItem` first exactly as `addSaleItem` does
    (`Locker locker(item)` `:686`, then the object `:704`).
  - `listSimBotItem` keeps stock's order. `retrieveSimBotItem` locks the `AuctionItem`,
    then the item, then cross-locks the bag (a transfer needs both the destination and
    the object locked).
  - `AuctionsMap`'s internal locks and `commoditiesLimit` stay leaves as in stock.
  - **Manager mutexes (`progressionMutex`, `pveMutex`) are never held while any object
    lock is taken.** The listing call, the sweep and the settlement each copy under the
    mutex, release, then lock objects.
  - Settlement from `doInstantBuy` takes no manager mutex on the player's thread.
- **IDL impact:** `AuctionManager.idl` gains four native methods (`isSimBotListing`, `listSimBotItem`, `retrieveSimBotItem`, `releaseSimBotSale`). This is additive;
  `src/autogen/` regenerates (expect fan-out similar to F_0.9.1). No IDL fields change,
  and `AuctionItem.idl` is unchanged.
- **C++ vs Lua:** every tunable is in `sim_player_manager.lua`; the decisions are in a
  pure header.
- **Gating & mutation:** a real economy mutation, approved by the P.10 mandate, gated
  default-off. A kill switch (`drainOnDisable`) withdraws listings. Settlement and
  retrieval of existing listings are deliberately gate-independent.
- **Shared surface with humans:**
  - every stock branch is guarded by `isSimBotListing`, which is false for every
    existing listing, so human and seeder listings behave byte-identically;
  - bot listings never undercut;
  - no mail is sent to a bot's name;
  - no human can retrieve or cancel a bot listing.
- **Dashboard:** §6.
- **Live verification:** the harness matrix in §7 plus a production observation:
  - `bazaar.listingsLive` > 0 while the gate is on;
  - no `ERROR` line from `AuctionManager` mentioning a bag OID;
  - after an owner restart, the bot listings are still in the map (the auction log
    line "Auction with invalid owner" never names one).
- **Edge cases:**
  - an item that is itself a container (the "A Locked Briefcase" family) goes through
    `containsNoTradeObjectRecursive` and `getSizeOnVendorRecursive` as stock;
  - a terminal destroyed while listed is handled by stock's orphaned-bazaar re-homing
    (`:246-265`), and the owner is unchanged;
  - a body death mid-visit ends the visit, and no value was staged on the body;
  - a bag discarded while one of its items is listed: `discardItemBag` refuses a bag
    with a live listing (new check);
  - a human with the bot's name: branches 3–5;
  - the price cap after city tax: the bot-side price is capped before tax, as for a
    player.

## Performance & Cost Impact

- **Human-floor lookup:** exactly one pass over a planet's bazaar listings per visit,
  for all candidates at once. Owners are classified against a precomputed bag-OID set,
  only `AuctionItem` fields are read under list read-locks, and no object is loaded. Visits are at most one per bot per `visitCooldownMinutes`.
- **Sweep:** at most `sweepBatch` retrievals every 5 minutes.
- **Boot reconciliation:** one pass over the bot listings, which are bounded by
  `maxListingsPerBot` × roster.
- **Stock paths:** one extra `getObject(ownerID)` plus a template check per listing in
  `initialize` and `doAuctionMaint`, only on the "owner name empty" branch (already the
  error path). `doInstantBuy` adds one `getObject` per sale.

## Backward Compatibility

- Schema 1016 is additive: a new table plus `simbot_items.ask_price` with default 0.
  Existing rows are unaffected; `listed` is a new state value.
- `HuntPhase` is append-only.
- With the gate off and no bot listings in existence, every stock branch evaluates
  `isSimBotListing` false and behaves exactly as before.
- Rollback: turning the gate off (with `drainOnDisable`) withdraws all bot listings to
  the vault within a few sweeps. Code rollback then leaves nothing in the bazaar that
  stock would mishandle.
