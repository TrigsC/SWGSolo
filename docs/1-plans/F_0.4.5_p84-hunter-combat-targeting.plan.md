# PvE Hunter Combat-Targeting Fixes Implementation Plan (v0.4.5 / P.8.4)

## Overview

Two owner-observed PvE hunter combat bugs share one root cause: `SimHunterController`
drives combat off its own acquired `targetOid` pin (plus a narrow self-defense hook)
instead of following `CombatManager`'s real defender/threat state. This patch makes
the hunter (1) never able to damage or target a real player — closing an AoE-grenade
splash that let the neutral bot get stuck attacking a player — and (2) re-engage
whatever is actually attacking it mid-fight instead of chasing a stale first target.

## Problem Statement

**Bug 1 — bot's AoE grenade splashes a player, then sticks to attacking the player.**
Hunters are `setFaction(0)` so they can fight neutral wildlife. But a neutral
(faction-0) player is `isAttackableBy` a faction-0 attacker:
`CreatureObjectImplementation::isAttackableBy(CreatureObject* attacker)` for a neutral
player vs a faction-0 bot takes none of the "return false" faction branches
(`thisFaction==0 && creatureFaction>0` is false; the `thisFaction!=0` and player-vs-player
blocks are skipped because the attacker is faction 0 and not a player) and falls through
to `return true` (~CreatureObjectImplementation.cpp:3681). `CombatManager::getAreaTargets`
gates each AoE splash victim on `tano->isAttackableBy(attacker)` (CombatManager.cpp:1042),
so the grenade damages the nearby player, forming a defender relationship, and the
controller's self-defense then locks onto the player. The branch already added the
**reverse** guard (players can't attack the bot: `AiAgentImplementation.cpp:6599`,
`getSimPlayerBot() && getFaction()==0 && creature->isPlayerCreature() → false`); the
symmetric "player not attackable BY a sim bot" guard is missing. Additionally
`SimHunterController::defendAgainstInterceptor` selects `getMainDefender()` with **no**
player/attackable filter, so even with the engine guard a player already on the defender
list would be picked (startCombat then refuses but the function never sheds the player →
phantom combat).

**Bug 2 — bot switches to a nearer womp rat but never fires on it.** With
`targetOid`=wr1 and a second creature (wr2) attacking after wr1 flees, the HUNTING
in-combat branch of `runActiveTick` (SimHunterController.cpp:803-851) only ever
`moveToTarget()`s toward `targetOid` (chases the fleeing wr1) and never issues
`startCombat`/`setTargetObject`/`activateAiBehavior` against the real attacker wr2. The
self-defense `onTick` that would engage wr2 early-returns because `targetOid` (wr1) is
still "live" — but `targetIsLive` only means exists + species-match + not-dead, NOT
still-engaged/reachable/attacking (SimHunterController.cpp:224-229). So whenever the real
attacker differs from the pinned target, neither path engages it.

## Solution Architecture

Two coordinated layers, both gated behind the hunter's existing `getSimPlayerBot()`
identity so miners/PvP/normal NPCs are byte-for-byte unchanged and no new runtime flag
is required (this is a correctness fix to already-gated hunter behavior, not a new
feature surface):

1. **Engine guard (Bug 1 root):** mirror the existing `AiAgentImplementation:6599`
   sim-bot guard inside `CreatureObjectImplementation::isAttackableBy(CreatureObject*, bool)`
   — a player creature is not attackable by a faction-0 `getSimPlayerBot()` AiAgent. This
   is the single chokepoint both `startCombat` (:78) and `getAreaTargets` (:1042) consult,
   so it stops the grenade splash, direct targeting, and any retaliation lock in one place.

2. **Controller target-selection alignment (Bug 1 defense-in-depth + Bug 2):** teach the
   in-combat paths to follow the actual defender/threat state, while **strictly separating
   two distinct concepts** (this separation is what resolves Codex P1 #1/#2/#4):
   - **The quota-bearing mission/contract target** = the controller's `targetOid`. It is
     species-gated (`targetMatchesSpecies`/`targetIsLive`), drives the kill observer, the
     manager quota (`recordPveHunterKill` **requires** `order.targetOid == targetOid`), and
     the social-aggro cap (`checkMissionSocialAggro` requires `targetOid` to pass the
     species-gated `targetIsLive` and derives `socialTarget` from it). It must be mutated
     **only** through `selectTarget()`, which is the ONE synchronized retarget operation:
     it drops the old observer, sets `targetOid`, and calls `recordPveHunterPhase(...)` —
     which sets `order.targetOid` on the manager side (SimPlayerManager.cpp:8988), keeping
     controller and manager in lockstep — then `moveToTarget()`→`engageTarget()` registers
     the new observer. `targetOid` is **only ever** a species-valid creature.
   - **The actual combat attacker** = whoever is currently attacking the hunter, regardless
     of species. Fought via the existing interceptor contract
     (`startCombat + setTargetObject + activateAiBehavior`, **no** species filter, **no**
     `targetOid` mutation, **no** quota observer). This is what `defendAgainstInterceptor`
     already does; it is generalized and reused.
   - **Dispatch rule** (owned by one shared `engageActiveAttacker` dispatcher, §3, called by
     both `onTick` and the HUNTING active tick) when the real attacker differs from the
     engaged creature: if the attacker is **species-valid**, promote it to the mission target
     via `selectTarget()` (synchronized retarget → its kill credits quota, social-aggro stays
     correct — this is Bug 2's second womp rat). If the attacker is **off-species** (a random
     wild interceptor), fight it via the interceptor path and leave `targetOid` untouched (no
     quota observer on off-species creatures — Codex P1 #2). If nothing valid attacks (only
     players / dead / unreachable): `resetInterceptorCombat()` (the §3a combat-only reset that
     sheds all transient defenders yet **preserves** a still-live species-valid `targetOid` +
     its observer) if a mission target remains, else `clearStaleCombat` so movement resumes.
   - Loosen the `onTick` early-return so it defers to the active tick **only when the
     corrected selector returns `targetOid`** (the mission target genuinely IS the current
     attacker) — not on mere defender-list membership (Codex P2 #5).

## Implementation Details

### 1. Engine attackability guard (Bug 1 root)

**File**: `src/server/zone/objects/creature/CreatureObjectImplementation.cpp`

**Current state**: `isAttackableBy(CreatureObject* creature, bool bypassDeadCheck)`
(line 3502) runs faction/PvP checks only when `this` is a player creature, otherwise
falls through to `return true` (~:3681). There is no consideration of a sim-bot attacker.

**Modifications**:
- Inside the `if (isPlayerCreature())` block (this CreO is the player), before the
  faction/PvP branches return, add a guard: if the attacking `creature` is an AiAgent
  with `getSimPlayerBot()` and `getFaction()==0`, return false. Placement mirrors the
  existing reverse guard's intent and is scoped so it only affects neutral sim bots vs
  players; every other combatant path is unchanged.
- Reference the mirror explicitly in a comment (`AiAgentImplementation.cpp:6599`) so the
  two symmetric guards are discoverable together.
- Note: `creature->asAiAgent()` + `getSimPlayerBot()` is the exact idiom already used at
  the reverse guard; reuse it. No lock is taken here (consistent with the surrounding
  read-only predicate checks in this method).

### 2. Active-combat-attacker selector (shared by Bug 1 D-i-D + Bug 2)

**File**: `src/server/zone/objects/creature/simplayer/SimHunterController.{h,cpp}`

**Modifications**:
- Add a private helper `bool selectActiveCombatAttacker(AiAgent* hunter,
  ManagedReference<CreatureObject*>& outAttacker, ManagedReference<AiAgent*>& outAttackerAgent)`
  (Codex round-3 P2: a **strong-reference** out-param result, so the chosen attacker cannot
  be reclaimed between selection and use; returns false / null out-params when nothing
  qualifies) that walks the hunter's defender list (`getDefenderList()`), filtering to
  candidates that are: live (not dead/incapacitated, `getParent()==nullptr`),
  `isAttackableBy(hunter)`, **not** a player creature, **not** a sim-presence creature,
  **not** another sim bot (`getSimPlayerBot()`), and within `scanRadius + 24m`.
- **No `species.templateFilter` gate here** — an interceptor need not be the hunted species
  (Codex P1 #1). Factor the player/sim-bot/attackability/reachability checks separately
  from the species-name check; the species check is applied later only to decide the
  dispatch path (§4), not to reject an attacker from being fought.
- **Selection order (Codex P1 #3):** choose the **nearest** qualifying candidate first.
  Retain the current `followObject` only under bounded hysteresis — i.e. keep it **only if**
  no other candidate is materially closer (e.g. by more than `weaponRange * 0.5`) **and**
  the `followObject` itself is still within weapon range. This prevents a fled first target
  (still inside the broad reachability radius) from being preferred over a nearer attacker,
  while avoiding per-tick thrash between two roughly-equidistant attackers.
- Match the read pattern of existing defender inspection already in `runActiveTick`
  (`getMainDefender()` / `getDefenderList()` reads happen under the active-tick call; keep
  the same lock posture — these are the same reads the current code performs).

### 3. Unified `engageActiveAttacker(hunter)` dispatcher (Bug 1 D-i-D + Bug 2)

**File**: `src/server/zone/objects/creature/simplayer/SimHunterController.cpp`
(new method; `defendAgainstInterceptor` :1304 refit as its off-species arm)

To keep `onTick` and the HUNTING active tick from diverging (Codex round-2 P1 #4), a
**single** dispatcher owns "fight the real attacker." Both call sites use it, so their
notion of the current threat and the species-dispatch policy are identical.

**Signature / return contract (Codex round-3 P2):**
`ManagedReference<CreatureObject*> engageActiveAttacker(AiAgent* hunter)` — it calls the §2
selector **once**, performs the dispatch below, and **returns the creature the hunter is now
engaging** (the selected attacker, or null when nothing valid was found and combat was
reset). §4 uses this returned strong reference for its reachability/phantom/stalemate
bookkeeping — no second selection anywhere. The off-species arm (`defendAgainstInterceptor`)
is refit to **accept the already-selected attacker** as a parameter rather than reselecting
via `getMainDefender()`.

**Behaviour** — run the §2 selector once at the top (Codex round-2 P1 #2: selection precedes
all reachability/stalemate decisions), then:
- **Selector returns null** (nothing valid — only a player / dead / unreachable on the
  list): this is phantom or player-contaminated combat.
  - If `targetOid` is still a live species-valid mission target → invoke the **combat-only
    reset** `resetInterceptorCombat()` (§3a below): it cross-removes **every** current
    defender from **both** defender lists and clears the hunter's transient combat state,
    while **preserving** `targetOid`, the quota observer, and `finalDestination`. A bare
    `disengageTarget(false)` is **insufficient** — it cross-removes only the `targetOid`
    agent, so an off-species interceptor that has fled just out of range would retain the
    hunter in *its own* defender list and keep chasing/attacking (Codex round-3 P1). The next
    tick then re-drives the still-live mission target.
  - Else (no live mission target) → keep the existing phantom-combat guard: increment
    `phantomCombatTicks`, and at the threshold `clearStaleCombat("phantom_combat")` (this
    fully drops observer + `targetOid`, which is correct when there is no mission target).
- **Selector returns an attacker already being engaged** (`followObject`'s OID == the
  selected attacker's OID): combat is already running against the right creature — leave it.
  Issue controller `moveToTarget()` **only** when that engaged creature is the species-valid
  `targetOid` and it is beyond weapon range (Codex round-2 P1 #3: do NOT `moveToTarget()`
  toward `targetOid` while engaging an off-species interceptor — that would abandon the
  interceptor fight to chase the stale mission target).
- **Selector returns a new attacker** → dispatch by species:
  - **Species-valid** (`targetMatchesSpecies` true, e.g. Bug 2's second womp rat): promote
    it to the mission target via `selectTarget(attackerAgent)` — the single synchronized
    retarget (drops old observer, sets `targetOid`, `recordPveHunterPhase` syncs
    `order.targetOid` on the manager @SimPlayerManager.cpp:8988, then
    `moveToTarget()`→`engageTarget()` registers the new observer). Its kill then credits
    quota because manager and controller `targetOid` agree (Codex P1 #2). This applies in
    **both** call sites, so a species-valid attacker is never fought as a throwaway
    interceptor (Codex round-2 P1 #4).
  - **Off-species** (a random wild interceptor): fight via the `defendAgainstInterceptor`
    arm, **passing the already-selected attacker** — `startCombat + setTargetObject +
    activateAiBehavior`, **no** `targetOid` change, **no** quota observer. `targetOid` (the
    species-valid mission target, or 0) is left intact.

**`defendAgainstInterceptor` refit (:1304)**: change its signature to accept the
already-selected attacker (`defendAgainstInterceptor(AiAgent* hunter, CreatureObject*
attacker)`); it must **not** re-select via `getMainDefender()` (Codex round-3 P2 — no double
selection). It performs only the engage step on the passed attacker (which the §2 selector
already validated for player/sim-bot/attackability/reachability). Preserve its lock
choreography exactly: `Locker agentLock(hunter)` → `startCombat` (cross-locks the defender)
→ `setTargetObject` → `activateAiBehavior(true)`.

### 3a. Combat-only reset `resetInterceptorCombat()` (Codex round-3 P1 / round-4 P2)

**File**: `src/server/zone/objects/creature/simplayer/SimHunterController.cpp` (new method)

A dedicated reset that fully sheds **all** transient defenders (off-species interceptors /
player contamination / stale creatures) **without** abandoning the mission target.

**Shared primitive `shedAllDefendersBilaterally(hunter)`** — because the bilateral cleanup is
also needed by `clearStaleCombat` (Codex round-5 P1), factor it once and reuse. It is
**fully self-locking** and owns no lock on return (Codex round-6 P1 — it must NOT leave the
caller to mutate a `@preLocked` field with no lock held):
- Take `Locker agentLock(hunter)`; **snapshot strong references** to every entry currently on
  `hunter->getDefenderList()` into a local `Vector<ManagedReference<CreatureObject*>>` (Codex
  round-4 P2 — copy first; do not mutate the list while iterating it).
- For each snapshot entry that is a live creature, `Locker defLock(defender, hunter)` (nests
  the defender under the already-held hunter lock — the proven `disengageTarget` cross-lock
  pattern) then cross-remove **both** directions (`hunter->removeDefender(defender)`;
  `defender->removeDefender(hunter)`), so no other attacker retains the hunter in its
  reciprocal list and re-contaminates combat (the gap Codex found: `clearCombatState` /
  `disengageTarget(false)` clear only the hunter side of one relationship).
- Release all locks on return (its `Locker` scope ends inside the helper).

`resetInterceptorCombat()` then:
- calls `shedAllDefendersBilaterally(hunter)` (self-locked, returns unlocked);
- **reacquires** its own `Locker agentLock(hunter)` (Codex round-6 P1: `clearCombatState` is
  `@preLocked` in `CreatureObject.idl:387` — it and the setters below MUST run under a held
  hunter lock) and, under it, `hunter->clearCombatState(true)`, `setTargetObject(nullptr)`,
  `setFollowObject(nullptr)`, `setWatchObject(nullptr)`, `clearQueueActions(true)`. This fresh
  `Locker` is **not** nested around the internally-locking helper (avoids re-entrant/double
  locking; matches the existing "each op self-locks" choreography of `disengageTarget` /
  `applyHunterBuffs`). The brief unlocked window between the helper and this relock mirrors
  the pre-existing `clearStaleCombat`→`disengageTarget` gap and is acceptable — a re-added
  defender is handled on the next tick.
- **Preserves** `targetOid`, the quota observer (`targetObserver`/`observerTargetOid`), and
  `finalDestination`; leaves `state = IDLE` so the arrival watchdog / next tick re-drives the
  still-live mission target (re-engagement re-establishes its defender relationship via
  `startCombat`).

**`clearStaleCombat` fix (Codex round-5 P1)**: prepend `shedAllDefendersBilaterally(hunter)`
to `clearStaleCombat` **before** its existing observer/target/movement cleanup, so its callers
(the no-mission-target phantom path and the species-target stalemate case) also cross-remove
**every** attacker — not only the `targetOid` agent that its inner `disengageTarget(false)`
handles. Otherwise a second attacker immediately re-contaminates the "cleared" combat.

`resetInterceptorCombat()` is called by the §3 null-path, the refit `defendAgainstInterceptor`
invalid-attacker path, and the §4 off-species stalemate case when a live species-valid
`targetOid` remains; `clearStaleCombat` is used for the no-mission-target case and the
species-target stalemate case (both intentionally drop observer + `targetOid`). Both now shed
all defenders bilaterally via the shared primitive.

### 4. HUNTING in-combat branch — drive off the selected attacker (Bug 2)

**File**: `src/server/zone/objects/creature/simplayer/SimHunterController.cpp`
(`runActiveTick`, :803-851)

**Current state**: when `isInCombat()`, inspects `getMainDefender()` for the stalemate
guard and phantom guard, then only `moveToTarget()`s toward `targetOid` if that (main)
defender is beyond weapon range. It can early-return on an unreachable **stale**
`getMainDefender()` before ever considering the real attacker, and never re-engages a
defender that differs from `targetOid`.

**Modifications**:
- **Call `engageActiveAttacker(hunter)` (§3) FIRST**, so selection precedes the reachability,
  phantom, and stalemate bookkeeping (Codex round-2 P1 #2). Those guards then operate on the
  **selected** attacker returned by the dispatcher, not on a raw `getMainDefender()` that may
  be a stale/unreachable creature.
- The dispatcher owns re-targeting and the `moveToTarget()`-only-for-species-`targetOid`
  rule; this branch keeps the stalemate/phantom progress tracking (keyed on the selected
  attacker) and reschedules.
- **Stalemate reset must be conditional (Codex round-4 P1)** — the 45s no-HAM-progress guard
  can no longer unconditionally `clearStaleCombat`, because that now discards a healthy
  mission target when the stalled creature is an off-species interceptor, while blindly
  preserving would loop forever on a genuinely-stuck mission target. Rule keyed on the
  selected stalled attacker:
  - **Selected attacker == the species-valid `targetOid`** (the mission target itself is the
    stalled fight): `clearStaleCombat` — abandon it and rescan (preserving would re-engage the
    same stuck creature next tick and loop).
  - **Selected attacker is an off-species interceptor AND a live species-valid `targetOid`
    remains**: `resetInterceptorCombat()` — shed the stalled interceptor, keep the hunt.
  - **Otherwise** (off-species stall with no live mission target): `clearStaleCombat`.
- Interaction with `checkMissionSocialAggro` (called just above, :800): it requires
  `targetOid` to pass the species-gated `targetIsLive` and derives `socialTarget` from it
  (SimHunterController.cpp:432-439). Because `targetOid` is **only ever** a species-valid
  creature under this design (never an off-species interceptor), the add-cap retreat logic
  stays correct (Codex P1 #4). When only an off-species interceptor is present and there is
  no live mission target, `checkMissionSocialAggro` returns false (no cap) — acceptable, as
  the cap governs the mission lair pull, not incidental wild interceptors.

### 5. `onTick` self-defense — share the dispatcher (Bug 2)

**File**: `src/server/zone/objects/creature/simplayer/SimHunterController.cpp` (:198-232)

**Current state**: if `targetOid != 0 && targetIsLive(targetOid)` → return (defers to the
active tick), which strands the bot when the acquired target fled but a different creature
is attacking; otherwise calls the raw `defendAgainstInterceptor`.

**Modifications**:
- Replace the raw `defendAgainstInterceptor` call **and** the `targetOid`-live early-return
  with the shared §3 `engageActiveAttacker(hunter)`. Because the dispatcher runs the
  selector first, defer to the active-tick HUNTING handler only when the selected attacker
  **is** the current `targetOid` (the mission target genuinely IS what is attacking) — not on
  mere defender-list membership, which is ambiguous with several defenders (Codex P2 #5).
- Sharing the dispatcher guarantees a species-valid attacker seen first by `onTick` (e.g. on
  a pure-movement leg or lair pre-acquisition) is promoted via `selectTarget()` and can
  credit quota, rather than being killed as a no-credit interceptor (Codex round-2 P1 #4).
  This keeps the round-1-working path (a genuinely-engaged live mission target stays driven
  by the active tick) unchanged while closing the fled-target-blocks-self-defense gap.

## Technical Considerations

- **Pattern Usage**: Bug 1 guard mirrors the existing `AiAgentImplementation::isAttackableBy`
  sim-bot guard (§13/§12 SimHunter conventions in ARCHI.md). Controller changes reuse the
  already-proven engage contract (`startCombat + setTargetObject + activateAiBehavior`,
  ARCHI.md §10/§12) rather than inventing a new combat entry.
- **Locking & References**: No new lock ordering. §1 is a lock-free read predicate
  (consistent with its neighbours). §3/§4 keep the existing `Locker agentLock(hunter)` →
  `CombatManager::startCombat` (cross-locks the defender) → setters sequence used by
  `engageTarget`/`defendAgainstInterceptor` today. Defender-list reads use the same posture
  as the current `getMainDefender()`/`getDefenderList()` reads in `runActiveTick`. The §3a
  `shedAllDefendersBilaterally` primitive is **self-locking** (hunter lock + per-defender
  `Locker(defender, hunter)` cross-lock, the proven `disengageTarget` pattern) and returns
  unlocked; every caller that then mutates a `@preLocked` field (`resetInterceptorCombat`'s
  `clearCombatState`/setters) **reacquires its own** `Locker agentLock(hunter)` afterward
  rather than nesting it around the self-locking helper (Codex round-6 P1). Strong references
  (`ManagedReference`) are used for the selector out-params and the defender snapshot so no
  object is reclaimed mid-operation. Do NOT bump the work-loop generation in these paths
  (prior code-review lesson: it strands the live arrival-check loop).
- **IDL Impact**: None. No `.idl` change; `getSimPlayerBot()` already exists on `AiAgent`.
  No `src/autogen/` regeneration needed beyond the normal build.
- **C++ vs Lua Placement**: All changes are structural combat-targeting logic → C++. No new
  tunable is warranted; the existing `pveHunterScanRadiusMeters`/`WeaponRangeMeters` Lua
  knobs are reused for the reachability filter.
- **Gating & Simulation-Only**: No behavior mutation of inventory/credit/market. Both fixes
  are scoped to `getSimPlayerBot()` faction-0 hunter bodies via existing identity checks,
  so miners, PvP squads, and all real NPCs/players are unaffected. No new default-off flag
  is added because this corrects already-gated (`missionHunt.enabled`) hunter behavior;
  the fix is inert unless hunters are running. (If the reviewer prefers an explicit
  kill-switch, a `pveConfig.combat.playerSafeTargeting` default-true Lua gate can wrap the
  controller-side changes — noted as an option, not baseline.)
- **Dashboard Visibility**: No new JSON section required. Existing `pveActivity` fields
  (`hunterKillsTotal`, `hunterAbandonsTotal`, per-roster `targetOid`, phase) are the
  verification surface. Consider adding a lightweight counter for "player-target rejected"
  / "attacker re-engaged" only if needed for live confirmation (optional, low priority).
- **Live Verification Plan**: After build + owner restart, verify in-game and via
  `curl -sk https://127.0.0.1:44443/v1/aieconomy/dashboard/`:
  (a) Bug 1 — stand an admin player inside the bot's grenade-AoE radius while it fights a
  creature: the player must take **no** AoE damage and the bot must never target/lock the
  player; `hunterKillsTotal` keeps climbing on wildlife only. Note `/dumpTargetInformation`
  is **not** a valid check here — it evaluates the target against the human command issuer,
  not against the bot (DumpTargetInformationCommand.h:261), so it cannot confirm
  `player->isAttackableBy(bot)`. If a direct predicate check is wanted, add a **temporary**
  manager-routed diagnostic (`SimPlayerManager::instance()->info`) logging
  `player->isAttackableBy(hunter)` from the controller when a player is seen on the defender
  list, and remove it after confirmation (per the project's temp-diagnostic convention).
  (b) Bug 2 — stage two creatures; confirm that when a second creature attacks after the
  first flees, the bot re-fires on the actual attacker within ~1 tick (roster `targetOid`
  updates to the new attacker; no long no-shot stall; `hunterAbandonsTotal` does not spike).
- **Edge Cases** (all "reset" choices follow the §3 conditional rule:
  `resetInterceptorCombat` when a live species-valid `targetOid` remains, else
  `clearStaleCombat`):
  - Player already on the defender list from a pre-fix session → the §2 selector rejects the
    player, so the dispatcher takes the null path: `resetInterceptorCombat()` if a live
    mission target remains (cross-removes the player + any other stale defenders, keeps the
    hunt), else `clearStaleCombat`. Either way the player is cross-removed and never engaged.
  - A full pack (social aggro) attacking → §4 engages the nearest valid attacker; because
    `targetOid` stays species-valid, `checkMissionSocialAggro` still governs the over-cap
    retreat/abandon.
  - Re-target thrash between two roughly-equidistant attackers → mitigated by the §2
    bounded hysteresis (keep `followObject` only if no materially-closer candidate and it
    is still in weapon range), not unconditional followObject preference.
  - Off-species interceptor killed → no quota credit (correct: only species-valid mission
    targets bear quota). When it dies the selector returns null; if a live `targetOid`
    remains → `resetInterceptorCombat()` then the next tick re-drives the mission leg; else
    `clearStaleCombat`.
  - `targetOid` (mission target) fled but is the sole live threat again later → normal
    reacquisition via `scanForTarget` when out of combat is unchanged.
  - Factioned PvP sim bots (faction != 0) → §1 guard's `getFaction()==0` condition excludes
    them, so PvP targeting rules are untouched.

## As-Built Deviations (v0.4.5, from code review)

The design above describes `onTick` and the HUNTING active tick as *both* calling the
shared `engageActiveAttacker` dispatcher. Implementation review found that
`SimHunterActiveTickTask` (`runActiveTick`) and `ArrivalCheckTask` (`onTick`) are
independently scheduled and can run on different task-pool threads, so having both
mutate `targetOid` / the mission observer is a data race. Two as-built changes resolve it:

1. **Single-writer ownership (concurrency fix).** `targetOid` is HUNTING-scoped (only
   `selectTarget` sets it, only during HUNTING; it is 0 in every phase where `onTick`'s
   interceptor code runs — RETREATING/HEALING/HUNTING return earlier). `runActiveTick`
   is the **sole** writer of `targetOid`/observer among the tick loops: it runs the full
   dispatcher (species promotion + interceptor). `onTick` **defers to `runActiveTick` in
   HUNTING** and, on the travel legs (where `runActiveTick`'s combat handler doesn't run),
   self-defends via the interceptor path only — never calling `selectTarget`/
   `engageActiveAttacker`. Consequence: a species creature killed incidentally on a travel
   leg is fought as an interceptor and does **not** credit the mission quota (lair aggro is
   HUNTING and is still promoted/credited). This also removes a travel-derail risk (a
   roadside creature is never promoted to the mission target mid-travel).

2. **Pending-destruction guard (kill-credit correctness).** Destruction handoffs
   (`onHuntDestruction`) are queued asynchronously and are rejected once `targetOid`
   advances (`targetOid != destroyedTargetOid`). Because the dispatcher retargets
   proactively, a just-killed mission target's queued handoff could be clobbered by a
   `selectTarget(next)`, silently losing the kill. `engageActiveAttacker` now defers
   retargeting for a tick while the current `targetOid` object exists and `isDead()` with
   its handoff not yet processed. The deferral is gated on an observer actually being
   installed on that target (`observerTargetOid == targetOid && targetObserver != nullptr`)
   — `targetOid` is set while approaching but the observer is registered only in weapon
   range, so a target that dies externally before then has no handoff coming and must not
   be deferred (else combat would be suppressed indefinitely). Bounded: a real kill's
   handoff runs promptly and clears `targetOid`/`destructionHandled`.

Also as-built: the §2 selector snapshots the defender list + follow OID under
`Locker agentLock(hunter)` before filtering (add/remove defender are `@preLocked`), so a
concurrent shrink cannot cause an out-of-bounds `getSafe` read.

Negligible. §2 iterates the hunter's own defender list (typically 1–small-pack sized),

QuadTree). §1 adds two cheap predicate checks to a hot combat path but only for player
defenders; it is O(1) and short-circuits.
