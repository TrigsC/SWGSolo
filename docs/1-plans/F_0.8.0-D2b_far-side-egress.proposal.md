# F_0.8.0 — D2b: far-side egress (proposal)

**Status: PROPOSAL. Nothing implemented. Default-off when built.**

Addresses the dominant remaining failure: 13 of 15 matrix failures, all
`controller_path_failed`, all the same shape.

## 1. The problem, measured

Run `20260826-195419-d8-egress-resume`, Mos Eisley starport (building 1106368):

```
t=667033  ST_PHASE ApproachDoor -> InteriorRoute reason=entered_structure
t=667033  ST_PATH request botPos=(3613.79,-4845.36,5.97457) world=(3527,-4803,5) cell=0
t=667139  ST_PATH accepted nodes=8 world=(3616.28,-4845.67,5.10497) cell=0
```

The bot is inside cell 15. It asks to reach **x=3527** (west, outside the
building). The accepted path ends at **x=3616.28** — the pad-side door it just
entered, back inside the hollow. It walks out, is still in the hollow,
escalates, and loops until the attempt cap fails it.

**The repair ladder never engages.** Every `repair=multicell` line in that run
belongs to building 1697358 (naboo hospital, which routes correctly:
`exitChoice cell=11 depth=4 distToTarget=10.5533 candidates=6`). The starport
produces none, because base pathfinding **succeeds** — it returns a valid 8-node
route out the nearest portal. The ladder only runs on path FAILURE. A path that
succeeds but makes no progress is invisible to it.

Underlying cause is the known D2 topology fact: the interior path graph from the
pad-side cells does not reach the west exterior doors (source cell global IDs
{10,13,14,15,16} versus exterior {1}, disjoint), so the pathfinder does the only
thing available to it.

Building geometry, measured (`ST_HOLLOW buildingExits`, 6 world portals,
`outsideHollow=4`):

| cell | door x,y | inHollow |
|---|---|---|
| 1, 2, 3 | x ~ 3539-3541 | 0 (real exits to the world) |
| 15, 16 | x ~ 3608-3614 | 1 (pad-side) |

## 2. Why `requireCompletePath` is not the answer

The existing gate rejects on raw end-distance against a tolerance. Measured
2026-08-25: it works (15 rejections, med-centre ingress retried and still
passed) **but costs `cantina_to_corellia_hospital`**, whose route legitimately
ends short. A raw distance threshold cannot distinguish "ended short because the
route genuinely ends there" from "ended back where I started".

## 3. Proposed predicate — destination-driven, not hollow-driven

Reject a found path only when BOTH hold:

1. `pathEnd` is inside the owning building's hollow, AND
2. the traversal's `destination` is NOT inside that same hollow.

Written against the existing helper: `isWithinOwningBuildingHollowAt(pathEnd,
building) && !isWithinOwningBuildingHollowAt(destination, building)`.

This is deliberately destination-driven per the owner constraint of 2026-08-27
([[starport-hollow-is-a-destination]]). Consequences:

- **Starport far-side case: rejects.** pathEnd in hollow, destination x=3527
  outside it.
- **Transit case: does NOT reject.** A bot walking cell -> pad has its
  destination IN the hollow, so condition 2 is false. The verified
  `starport_transit_terminal_to_collector` PASS must not regress.
- **`cantina_to_corellia_hospital`: does NOT reject.** Its short route is not
  ending inside a hollow it is trying to leave; condition 1 is false.

## 4. Rejection alone is insufficient — the retry must differ

`acceptFoundPath` returning false routes into the existing bounded
`onPathFailed` retry (SimPlayerController.cpp:1873). A plain retry recomputes
the same inputs and yields the same path, so this would loop to the attempt cap
without the two-leg route below.

**Two-leg interior route.** On rejection, select the nearest exit-set candidate
with `inHollow == 0` — cells 1/2/3 — and issue it as an explicit INTERIOR
waypoint (a cell-targeted leg, using the entry-arrival guard already shipped),
then resume toward the final destination from there. The exit set already
computes `inHollow` per candidate and already orders by 3D distance, so no new
geometry work is required.

This is the same shape Codex proposed in D8 review round 1 ("enter the
accessible pad-side cell first and carry the selected west exit into the
interior route"), deferred then because the bot could not yet cross a door. It
can now.

## 5. Safety analysis

| Risk | Mitigation |
|---|---|
| Transit regression (the owner's multi-hop flow) | Condition 2 makes the predicate inert whenever the destination is the pad. `starport_transit_terminal_to_collector` is the regression test and must stay PASS. |
| `cantina_to_corellia_hospital` regression (what `requireCompletePath` broke) | Condition 1 makes the predicate inert for routes not ending in a hollow. Must stay PASS. |
| Interior leg loops between cells | Reuse `egressCandidateAttemptCap` / `egressTotalAttemptCeiling`, already implemented and bounded. |
| New leg treated as terminal | Route through `HollowEscalationOutcome::InProgress` and the entry-arrival guard, both shipped and verified in runs 5-6. Do NOT add a new arrival path. |
| Clipping on the interior leg | The zero-clip probe already covers every path request; the interior leg is not exempt. |
| Cross-thread lifecycle | Adds no new AI-map or cross-thread state. D9 is untouched by this change. |

## 6. Gating

New gate `structureTraversal.farSideEgress` (default **false**), separate from
`requireCompletePath` so the two can be measured independently. With it off,
behaviour is byte-identical to today.

## 8. Owner decision (2026-08-27): NEAREST REACHABLE

The interior leg takes the **nearest reachable** non-hollow exit, not the
destination-nearest one. The exit set is already ordered by 3D distance from the
bot, so this is simply the first candidate with `inHollow == 0` — no
`distToTarget` ranking needed.

## 9. Why the two-leg route works — CORRECTED BY MEASUREMENT

**The original reasoning in this section was WRONG and is retained here only as
a record of the correction.**

I predicted the interior leg (cell 15 -> cell 1) would FAIL base pathfinding and
thereby trigger `repair=multicell`, which would BFS the portal links across the
disjoint path-graph regions. Falsifiable prediction: `repair=multicell` lines
tagged `building=1106368`.

**Measured 2026-08-27 (run `20260827-200923-d2b-farside`): ZERO such lines.**
The only `exitChoice` lines belong to buildings 1697358 and 1855529. The repair
ladder still never engages for the starport.

**What actually happens:**

```
t=950237  ST_PATH rejected reason=far_side_no_progress pathEnd=(3573.4,-4813.2)
                                                     destination=(3527,-4803)
t=950238  ST_HOLLOW farSide action=interior_leg door=(3539.62,-4814.24)
                    cellIndex=1 cellOid=1106369 distance=80.4406
t=950339  ST_PATH accepted nodes=44 world=(3539.62,-4814.24) cell=1106369
t=951342  ST_PHASE ApproachDoor -> InteriorRoute reason=entered_structure
t=982958  bot now at (3539.62,-4814.23) -- traversed the interior, west side
t=987201  ST_PATH accepted nodes=5 world=(3527,-4803) -- destination reached
t=990231  ST_PHASE to=Idle reason=exit_complete_outdoors
```

The 44-node route to cell 1 is produced by BASE pathfinding, directly, with no
repair. So the interior cell-to-cell route was routable the whole time.

The real defect was narrower than D2 was framed: **only the "from inside, reach
an outdoor far-side point" request is broken**, because it is satisfied greedily
by the nearest portal. Asking for a CELL on the far side instead of an outdoor
point makes the pathfinder produce a proper interior route. The fix is a
retargeting, not a graph repair.

This also means the disjoint global-ID observation from D2, while true, was not
the operative blocker here.

## 10. Known inefficiency (not a blocker)

The first egress path of each attempt is still accepted and walked (~42s) before
the predicate fires. Measured: the first path ends at (3616.28,-4845.67), on the
hollow BOUNDARY, which the containment test does not count as inside; the bot
walks there, re-requests, and the second path ends mid-pad at (3573.4,-4813.2),
clearly inside, and is rejected. Net cost ~42s of an 82s exit against a 120s
budget. Tightening the containment margin or predicting at request time rather
than acceptance time would remove it. Deferred.
