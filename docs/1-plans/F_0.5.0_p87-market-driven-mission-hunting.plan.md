# P.8.7 — Market-Driven Mission Hunting (Real Missions, Galactic Travel) Implementation Plan

## Overview

PvE hunters currently run a *scripted* hunt: a hand-written `pveConfig.species`
table pins each hunter to one creature, one hand-picked hunt-ground coordinate,
and one home city; the "mission" completes after **one kill** and the lair is
then despawned by cleanup. This slice replaces that with the real thing: the
hunter reads the **market demand ledger**, resolves which **planet currently has
the best-quality spawn** of the demanded creature resource, **travels there over
the real fare matrix** (multi-hop starport routing, never a shuttle), walks to
the nearest **general Mission Terminal**, takes **two real level-appropriate
destroy missions in the same direction**, runs out to each, triggers the lair at
~120 m with the real "Transmission Received" update, fights the **real 3-wave
lair** to destruction, and only then counts the mission complete. It also fixes
the two owner-visible defects: five of six hunters are structurally unable to be
dispatched, and the dashboard kill counters under-report.

Owner decisions (discovery 2026-07-24):

- **All four feature groups ship in this version** (A dispatch+counters,
  B real missions, C cross-planet market dispatch, D cross-planet buff runs).
- **Mimetic missions with real data** — no `MissionObject`/datapad graph on
  `AiAgent` bodies; every *input* (spawn group, level filter, lair template,
  distance/direction rules, wave observer) is the genuine engine data.
- **"Wherever it is" is the operating base** — `homeCity`/`homePlanet` degrade
  to a spawn/clone origin; mission eligibility becomes proximity-based.
- **No credits at all this slice** — mission completion is counted, not paid.
  Harvest continues to feed the existing simulation-only hive supply.

## Problem Statement

Verified against the live dashboard and source on 2026-07-24
(`pveActivity`: 6 hunters, `hunterKillsTotal=30`, `missionLairsSpawned=2549`,
`hunterAbandonsTotal=2507`, roster lifetime kills 317):

1. **Five of six hunters can never be dispatched.**
   `SimPlayerManager.cpp:9188-9224` requires *all* of:
   `species.planet == identity.homePlanet`, the hunter's `homeCity` present in
   `species.eligibleHomeCities`, and `huntGround` within
   `pveMaxHuntDistanceMeters` (1500 m) of the home shuttleport. Only two species
   rows are `usable && soloable` — womprat (`mos_eisley`) and kreetle
   (`bestine`). The Moenia/Theed/Keren (naboo) and Mos Entha hunters match
   nothing and sit in `IDLE_HOME` forever. This is structural, not a missed
   setting.

2. **A "mission" is one kill, then the lair is deleted.**
   `combat.huntQuota = 1` → `SimHunterController.cpp:2007` calls
   `beginMissionCleanup(false, "quota")` after the first credited kill, and
   cleanup destroys the lair (`queuePveHuntLairCleanup`). The owner observes
   exactly this: kill one creature, the lair vanishes, the bot leaves.

3. **Mission churn is ~98 % abandonment.** 2549 lairs spawned, 2507 abandons.
   Dominant abandon reasons are reachable from the code paths
   (`social_adds_above_cap` with `maxSimultaneousAdds = 1`,
   `phase_timeout_*`, `max_retreat_cycles`, `lair_path_failed`).

4. **Any mission terminal is accepted.** `SimPlayerManager.cpp:8311` filters on
   `SceneObject::isMissionTerminal()`, which is true for entertainer, artisan,
   bounty, imperial, rebel, scout, newbie and statue terminals. The general
   "Mission Terminal" is `MissionTerminal::isGeneralTerminal()`
   (`terminalType == "general"`) — the same predicate
   `MissionManagerImplementation.cpp:594` uses to offer destroy missions.

5. **Kill counters under-report.** `recordPveHunterKill` credits only when
   `order.targetOid == targetOid`, so interceptor kills, lair-aggro adds fought
   by the active tick, and the lair itself are never counted. Separately the
   dashboard shows a **session** counter (`hunterKillsTotal`, reset in
   `applyPveConfig` at `:5654`) directly beside **lifetime** per-identity
   `kills` from the MySQL roster, with no label distinguishing them — 30 vs 317.

6. **No hunt ground is a real mission.** Targets come from a hand-authored
   `huntGround` coordinate and `templateFilter` string, not from the planet's
   real `<planet>_destroy_missions` spawn group, so difficulty never tracks the
   hunter's level and the target creature is fixed rather than chosen from what
   the market needs.

7. **Hunters cannot leave their planet.** `beginInterplanetaryTravel` and the
   whole ticket-collector state machine live in **`SimMinerController`**, not
   the base `SimPlayerController`; the multi-hop fare-matrix BFS
   (`planPvpRoute`) is private to `SimPvpSquad`/`pvpSquadMutex`. Neither is
   callable from a hunter.

8. **A hunter whose home city has no buffer NPC is permanently on synthetic
   fallback.** `realBuffs.providerResolveState` shows
   `tatooine:bestine = absent`; the Bestine hunter has taken 48 synthetic
   fallbacks and never a real doctor buff (`doctorInteractions = 0`). There is
   no "go to a hub city that does have buffers" path.

## Solution Architecture

Five layers, built bottom-up. Each is independently gated in
`bin/scripts/managers/sim_player_manager.lua`, default **off**, so the legacy
P.8.2/P.8.6 behavior is byte-for-byte reproducible by leaving every new gate
false.

### Layer 0 — Shared travel substrate (`SimTravelPlanner`)

The fare-matrix BFS inside `planPvpRoute` is genuinely generic: it builds
`pads`/`routable`/`adjacency` from `allShuttleports` +
`PlanetManager::getTravelFare`, then BFS's city→city. Only the *destination
choice* and the *result storage* are squad-specific. Extract the graph build and
BFS into a squad-agnostic manager helper returning
`Vector<SimTravelLeg>` for an explicit `(fromPlanet, fromCity) →
(toPlanet, toCity)` pair. `planPvpRoute` becomes a caller that supplies its own
destination-selection and writes the result into `squad.pendingRoute`; PvP
behavior must be unchanged.

Symmetrically, lift the ticket-collector journey state machine
(`TicketTravelPhase`, `beginTicketCollectorDepartureApproach`,
`isAtTicketCollector`, `boardInterplanetaryShuttle`, `completeTicketCollectorTravel`
and friends) from `SimMinerController` into `SimPlayerController` as protected
members, with a virtual `onInterplanetaryTravelFinished(...)` hook the miner and
hunter each override. `SimMinerController`'s existing behavior (single-hop,
resource re-acquire on arrival) is preserved by its override; the hunter's
override pops the next leg and either repeats or enters its arrival phase.

`shuttleports` in Lua gains the planets the market can now demand
(dantooine, lok, dathomir, endor, talus, corellia already present) so the BFS
graph actually reaches them. A city with an empty `starport` string stays out of
the graph exactly as today.

### Layer 1 — Location-based dispatch + counter truth (group A)

Replace the three-way home lock with a **proximity** model:

- Eligibility becomes: the hunter's **current** planet/position, and a
  configurable `dispatchRadiusMeters` around the nearest routable city on that
  planet. `homeCity`/`homePlanet` remain in the identity row purely as spawn and
  clone origin (owner decision: *"current location is the base"*), and are no
  longer consulted by the matchmaker.
- `species.eligibleHomeCities` is retained in the schema but **ignored** when
  the new gate is on (it is the legacy path's field).
- `species.planet == identity.homePlanet` is replaced by
  `species.planet == identity.currentPlanet` in the legacy species path, and by
  the Layer 3 lair-yield index when market dispatch is on.

Counter truth (not gated — this is accounting correctness, and old field names
are kept so the frontend never sees a missing key):

- Credit **every** creature kill the hunter causes, not only the current
  mission target: the mission-credit path and the "creatures killed" telemetry
  become two counters (`missionCreditedKills` vs `creatureKillsTotal`).
  **Splitting the counter is not sufficient on its own** — the interceptor path
  (`defendAgainstInterceptor`, `SimHunterController.cpp:2149`) calls
  `startCombat` and never registers a destruction observer, so those kills are
  not merely uncredited, they are *unobserved*. The fix is a second, strictly
  write-only **telemetry observer**: whenever the hunter engages any creature
  (mission target or interceptor), register an `OBJECTDESTRUCTION` observer
  recorded in a per-order
  `VectorMap<uint64 /*creatureOid*/, Reference<Observer*>> engagedTelemetry`.
  Storing the **handle**, not a bool, is what makes the cleanup contract
  satisfiable — on order completion, abandonment, death and teardown the
  controller iterates the map, calls `dropObserver(OBJECTDESTRUCTION, handle)`
  on each still-live creature, and clears it. The map is also the dedup key, so
  re-engaging the same creature never double-registers.
  **Attribution**: the callback verifies the destruction participant
  (`arg1`) resolves to this hunter's `bodyOid` before counting — the same
  participant check `onHuntDestruction` already performs — so a creature killed
  by something else while merely on the hunter's defender list is not credited.
  **Threading**: the observer fires under the destroyed object's lock, so it
  must only capture `(identityId, bodyOid, creatureOid)` and hand off to the
  task manager; `pveMutex` is taken **in the handoff, never inside the
  observer**, exactly as the existing kill-attribution handoff does.
  It increments `creatureKillsTotal` and nothing else — it must **never** touch
  `targetOid`, `observerTargetOid`, `destructionHandled`, or the mission
  observer, so P.8.4's single-writer rule is untouched. Mission credit remains
  gated on the wave-mob predicate, so an interceptor kill counts as a kill but
  never as mission progress.
- Add `lairsDestroyedTotal`, `missionsCompletedTotal`, and an
  `abandonReasons` histogram keyed by the existing reason strings, so the 98 %
  churn becomes diagnosable rather than a single opaque number.
- Explicitly label lifecycle: every root counter gains a sibling under a new
  `lifetime` object sourced from the roster sum, and the existing root keys are
  documented in the JSON as session-scoped (reset on `applyPveConfig`).

### Layer 2 — Real mission board (group B)

A new manager component, the **bot mission board**, mirrors
`MissionManagerImplementation`'s destroy-mission generation without creating a
`MissionObject` graph.

- **Terminal type.** The terminal registry scan casts to `MissionTerminal*` and
  keeps only `isGeneralTerminal()` (optionally `isNewbieTerminal()` for
  tier-1 hunters, config-listed). The existing pending/resolved/absent per-city
  state machine is unchanged; a city with only entertainer/artisan terminals now
  correctly resolves `absent`.
- **Offer generation.** For a hunter at a terminal: read the planet's
  `<planet>_destroy_missions` `SpawnGroup` via
  `CreatureTemplateManager::getDestroyMissionGroup`, filter `LairSpawn`s by the
  hunter's level using the **same** `minDifficulty <= level+5 &&
  maxDifficulty >= min(level-5, minLevelCeiling)` window `getRandomLairSpawn`
  uses. Hunter level is `AiAgent::getLevel()` (the creature-template level) —
  `PlayerManager::calculatePlayerLevel` is a skill-mod lookup
  (`private_<weapon>_combat_difficulty`) that an `AiAgent` body does not carry,
  so it would silently return 1. Owner confirmed template level for now; the
  accessor is isolated in one helper so a later skill-based level is a one-line
  change.
- **Distance + direction.** Distance uses the real formula shape
  (`base + difficultyFactor*difficultyLevel + random`), with the four constants
  mirrored into `pveConfig.missionBoard` rather than reaching into
  `MissionManager`'s private members. Direction is the owner's rule: compute the
  bearing from the **city centre** (the city's shuttleport `spawn`) to the
  **terminal**, and constrain both offers' bearings to that heading ±
  `sameDirectionArcDegrees`. Candidate points are validated exactly as the real
  generator does: `Zone::isWithinBoundaries`, `TerrainManager::getWaterHeight`
  above ground rejects, and no `ActiveArea::isCityRegion` overlap.
- **Two held missions.** A hunter holds up to `maxHeldMissions` (2) offers,
  ordered nearest-first. It runs the first to completion, then the second, then
  returns to a terminal. Only one lair is ever *spawned* at a time (see below),
  so `maxActiveLairs` is not pressured.
- **Proximity trigger.** The real system uses a 128 m `MissionSpawnActiveArea`
  whose `notifyEnter` is `isPlayerCreature()`-gated
  (`MissionSpawnActiveArea.idl:28`). Rather than relax another core
  player-gate, the controller performs the equivalent check itself: once
  within `lairRevealRadiusMeters` (default 120) of the offer's advertised
  position, it calls the manager to place the lair at a validated point near
  that position and emits the real string, *"Transmission Received: Mission
  Target has been located.  Mission waypoint has been updated to exact
  location"*, through the existing `announcePveHunterEvent` channel so it is
  visible in-world and on the dashboard.
- **Real waves.** `CreatureManager::spawnLair` attaches a base `LairObserver`
  (which also repopulates on `NOPLAYERSINRANGE`). The mission-lair variant must
  instead mirror `DestroyMissionObjectiveImplementation::spawnLair`: create the
  `LairObject` from `LairTemplate::getMissionBuilding(difficulty)`, set
  `maxCondition = difficultyLevel * (900 + random(200))`,
  `setDespawnOnNoPlayersInRange(false)`, register a
  **`DestroyMissionLairObserver`** (whose `checkForNewSpawns` implements the
  three waves: initial force-spawn, first damage, and past half condition), plus
  our own `OBJECTDESTRUCTION` observer for completion, then
  `transferObject` + `checkForNewSpawns(lair, nullptr, true)`.
- **Completion = lair destroyed.** `combat.huntQuota` no longer terminates the
  mission. The mission completes when the `OBJECTDESTRUCTION` observer on the
  **lair** fires. Harvest still accrues per creature killed (unchanged
  simulation-only path); no credits are granted (owner decision).
- **Which creatures are "the mission".** Removing `species` also removes
  `templateFilter`, which is today's `targetMatchesSpecies` predicate — without
  a replacement the hunter would either ignore its own wave mobs or treat
  ambient wildlife as wave blockers, so the field would never read clear.
  The correct predicate is ownership, not template name:
  `LairObserverImplementation.cpp:728` calls `agent->setHomeObject(lair)` on
  every creature a lair spawns. **A wave mob is any `AiAgent` whose home object
  is non-null and whose OID equals `missionLairOid`** — the home object is
  retained into a local `ManagedReference` and null-checked before the OID
  comparison, since ambient wildlife (and any creature not lair-spawned)
  legitimately has none. That single predicate
  drives all three uses: `scanForTarget` candidate filtering, field-clear
  detection before `ENGAGING_LAIR`, and mission-progress credit. Ambient
  wildlife that aggros is still fought — but through the interceptor path, and
  it never counts as mission progress nor blocks the lair engagement.
- **Wave tactics.** The hunter attacks wave mobs one at a time while any are
  alive; with the field clear it attacks the **lair** itself
  (`CombatManager::startCombat(CreatureObject*, TangibleObject*)` accepts the
  lair). When a new wave spawns, if engaged adds exceed
  `maxSimultaneousAdds` it uses the existing retreat/break-off path — the
  player "peace at the wave boundary" behaviour — instead of abandoning. The
  current `addsAbandonCycles` abandon stays as the last resort but its default
  is raised, and `maxSimultaneousAdds` is raised off 1 (the value that is
  producing most of today's 2507 abandons).

### Layer 3 — Market-driven planet + target selection (group C)

This is what makes the hunt *economic* rather than scripted.

1. **What the market needs.** Take the existing acquisition-ledger family
   signals (`demandFamilies`) and extend them beyond `meat` to **`hide` and
   `bone` only**. `milk` is deliberately **excluded** this slice:
   `recordPveHunterHarvest` (`SimPlayerManager.cpp:9671`) branches on
   `hide` / `bone` and routes **everything else** through `getMeatType()` +
   `getMeatMax()`, so a milk contract would silently deposit meat. Milk (and
   `seafood`/`egg`) stay documented additive hooks, as P.8.1d already records.
   As a defensive fix in the same edit, an **unrecognised `harvestKind` becomes
   an explicit harvest miss** (`pveHunterHarvestMisses++`) instead of falling
   through to meat, so a future family added to config cannot silently
   mis-credit the ledger.
2. **Which resource, and where.** For the demanded family, scan the currently
   **in-spawn** `ResourceSpawn` set the resource scout already reads (the live
   dashboard proves per-resource `resourceType`, `zones`, and quality `stats`
   are available — e.g. `meat_insect_dantooine`, `meat_reptilian_naboo`), rank
   by the deterministic quality expression defined in §8, and take the winning
   spawn's planet. This is the owner's "highest-quality Scaley Hide is only on
   Dantooine → go to Dantooine" step.
2a. **A planet is not a routable destination.** `planSimTravelRoute` needs a
   *city*, and the terminal registry
   (`configurePveMissionTerminalCitiesLocked`, `:8224`) is today seeded
   **solely from `species.eligibleHomeCities`** — so with `species` no longer
   the targeting source, no Dantooine city would ever be scanned and the
   hunter would arrive at a planet with no known terminal. Two changes close
   this: (i) the registry is seeded from **every routable `shuttleports` city**
   (any city with a non-empty `starport`), not from species rows; and (ii)
   market dispatch ranks **`(planet, routableCity, resolvedGeneralTerminal)`
   tuples**, not planets. A resource planet with no city that has a `resolved`
   general terminal is **excluded before ranking**, so the winner is always a
   place the hunter can both reach and take a mission at. Cities still
   `pending` are not yet eligible but keep being retried by the existing
   per-city scan.
3. **Which lair on that planet.** Build a **lair-yield index** once per config
   publication: for each planet's destroy-mission `SpawnGroup`, for each
   `LairSpawn` → `LairTemplate::getWeightedMobiles()` → each mobile's
   `CreatureTemplate`, record which resource types it yields and in what
   amount, plus the lair's difficulty band. At mission-offer time the board
   ranks offers by (demand pressure × expected yield) / estimated time,
   subject to the level window and the direction constraint. The hand-written
   `pveConfig.species` table is no longer the targeting source when this gate
   is on; it remains the legacy path's data and the fallback if the index is
   empty for a planet.
4. **Getting there.** If the winning planet differs from the hunter's current
   planet, the manager plans a route with the Layer 0 planner and the hunter
   executes it: run to the origin starport's **ticket collector** (never a city
   shuttle — the intra-planet shuttle legs the PvP planner emits are excluded
   for hunters by a planner flag), board, arrive, and if the route has further
   legs repeat. On arrival at the final city it resolves the nearest general
   terminal *there* and enters the Layer 2 board flow.
5. **Conservative gating.** One relocation in flight per hunter, a global
   `maxConcurrentRelocations`, a minimum-dwell before a hunter may be
   re-relocated (so a flapping demand signal cannot ping-pong a bot between
   planets), and a `minHuntersPerActivePlanet` floor so market dispatch can
   never strip a planet bare — the same safety shape as the P.4.5b miner
   planet-dispatch design.

### Layer 4 — Cross-planet buff runs (group D)

Extend the P.8.6 need-gated buff detour with a hub fallback:

- Buff need detection (`computeBuffNeeds`, nine tracked CRCs, 900 s threshold)
  is unchanged.
- Provider resolution is retargeted from the hunter's **home** city to the
  nearest routable city on the hunter's **current** planet (consistent with
  Layer 1's "wherever it is" base).
- If that city resolves `absent` for a needed family, consult an ordered
  `buffHubs` list in config (e.g. `corellia:coronet`, then
  `tatooine:mos_eisley`, then `naboo:theed`). Pick the first hub that is
  route-reachable and whose providers resolve, route there with Layer 0, take
  the real buffs via the existing `startWatch`/`startListen`/
  `SmartDoctorBuffer:botBuffRequest` flow, then route **back** to the planet
  the hunt was on and resume.
- Bounded: `maxBuffTripsPerHunt`, a total trip deadline, and the existing
  `realBuffs.fallbackBuffs` synthetic set as the terminal fallback. A buff trip
  is never started while a lair is alive — the current mission is completed or
  cleanly abandoned first.

## Implementation Details

### 1. Shared travel planner extraction

**File**: `MMOCoreORB/src/server/zone/objects/creature/simplayer/SimPlayerManager.{h,cpp}`

**Current state**: `planPvpRoute` (`:28693`) builds `pads`, `cityLocations`,
`routable`, and an `adjacency` matrix from `allShuttleports` +
`PlanetManager::getTravelFare`, then picks a destination and BFS's under
`pvpSquadMutex`, writing `squad.pendingRoute` (`Vector<PvpTravelLeg>`).

**Modifications**:

- Rename `PvpTravelLeg` → `SimTravelLeg` (typedef the old name so PvP code and
  any `@json` dashboard shape keep compiling) and move it out of the PvP block
  of the header.
- Add `bool planSimTravelRoute(const String& fromPlanet, const String& fromCity,
  const String& toPlanet, const String& toCity, bool allowIntraPlanetShuttle,
  Vector<SimTravelLeg>& legsOut, String& summaryOut)`. It performs the graph
  build and BFS **with no squad state and no squad mutex** — all lookups are
  zone/planet-manager reads, exactly as the first half of `planPvpRoute`
  already is (that section is explicitly documented as taking no agent locks).
- Rewrite `planPvpRoute` to: choose its destination as today, call
  `planSimTravelRoute`, then take `pvpSquadMutex` only to store the result and
  compute convergence. **PvP output must be byte-identical** — this is a pure
  extraction, verified by the unchanged `pvpActivity` dashboard section.
- Add `getNearestRoutableCity(const String& planet, const Vector3& from,
  ShuttleportLocation& out)` — used by Layers 1, 2 and 4.

### 2. Ticket-collector travel lifted to the base controller

**Files**: `SimPlayerController.{h,cpp}`, `SimPlayerController.h` (miner section),
`SimHunterController.{h,cpp}`

**Current state**: `TicketTravelPhase`, `ticketCollector*` members,
`intelligentTravelActive`, `travelDestination*`, `beginInterplanetaryTravel`,
`boardInterplanetaryShuttle`, `beginTicketCollectorDepartureApproach`,
`beginTicketCollectorArrivalExit`, `isAtTicketCollector`,
`canRetryTicketApproach`, `retryTicketApproach`,
`cancelTicketCollectorTravel`, `completeTicketCollectorTravel` are all private
members of **`SimMinerController`** (`SimPlayerController.h:352-486`).

**Modifications**:

- Move the travel state and the collector state machine to
  `SimPlayerController` as `protected`. Rename the miner-flavoured
  `intelligentTravelActive` to `interplanetaryTravelActive` (keep the miner's
  `isInterplanetaryTravelActive()` accessor).
- **One generic terminal callback, invoked on every exit path.** An
  arrival-only hook is not enough: the lifted machine's non-success paths are
  miner-coupled today — `cancelTicketCollectorTravel`
  (`SimPlayerController.cpp:2052`) performs the stranded-in-hollow
  `switchZone` recovery *and* then calls
  `clearMinerIntelligentTargetAssignmentFromController`, and the
  invalid-destination / arrival-exit paths likewise reach miner-only manager
  APIs. Define instead:

  `virtual void onInterplanetaryTravelFinished(bool success, const String& destZone, const String& reason)`

  with an empty base body, invoked on **every** terminal path — successful
  board+arrival, cancellation, invalid destination, retry-budget exhaustion,
  and arrival-exit failure. The *generic* part of the cancel path (the
  stranded-hollow reposition to `ticketArrivalOutdoor`, which is safety, not
  policy) stays in the base; the *miner policy* part
  (`clearMinerIntelligentTargetAssignmentFromController`, re-entering the work
  loop, re-acquiring a target, any vehicle teardown) moves into
  `SimMinerController`'s override. `SimHunterController`'s override pops the
  next leg on success, and on failure drops the relocation and falls back to
  hunting on the planet it is actually standing on.
- `SimMinerController::isAvailableForDispatch()` keeps its current semantics;
  add an equivalent hunter-side readiness predicate (no live lair, not in
  combat, not mid-buff-flow).
- **Risk note**: this is the highest-regression-risk item in the plan because
  the miner path is live and proven. It must be a mechanical move with no
  behavioural edit, validated by the `stationTravel` / `planetDispatch`
  dashboard sections being unchanged after the restart.

### 3. Terminal registry: general terminals only

**File**: `SimPlayerManager.cpp` (`resolvePveMissionTerminals`, `:8251-8355`)

**Current state**: `:8311` accepts any `SceneObject::isMissionTerminal()`.

**Modifications**:

- `dynamic_cast<MissionTerminal*>` (header already included at `:69`) and
  accept only terminal types listed in
  `pveConfig.missionBoard.acceptedTerminalTypes` (default `{ "general" }`).
  A non-general mission terminal is skipped, so a city with only an
  entertainer terminal now transitions `pending → absent` and takes the
  documented fallback rather than sending a hunter to the wrong device.
- **Seed the registry from routable cities, not species rows.**
  `configurePveMissionTerminalCitiesLocked` (`:8224`) currently derives
  `missionTerminalCityState` from `species.eligibleHomeCities`. Behind the
  market-dispatch gate it is seeded from every `shuttleports` city with a
  non-empty `starport`, so the cities the travel graph can reach are exactly
  the cities whose terminals get scanned. The existing
  `pending → resolved | absent` state machine, the per-city retry, and the
  "shared state only changes on scan" invariant are unchanged.
- Store the resolved `terminalType` on `PveMissionTerminalLocation` and surface
  it on the dashboard so the owner can confirm which terminal each hunter
  walked to.
- Add `getNearestGeneralMissionTerminal(planet, fromPosition, ...)` — a
  **planet-scoped, position-nearest** lookup (today's
  `getNearestMissionTerminal` is city-keyed off the order's `homeCity`, which
  Layer 1 no longer trusts).

### 4. Bot mission board

**File**: `SimPlayerManager.{h,cpp}` (new section, and a new
`PveBotMissionOffer` struct)

**New state** (all under `pveMutex`, matching the existing
`pveHuntOrders`/`pveHuntLairs` discipline):

- `PveBotMissionOffer { offerId, identityId, bodyOid, planet, terminalOid,
  lairTemplate, missionBuilding, difficulty, difficultyLevel, size,
  advertisedPos, bearingDeg, revealedPos, revealed, lairOid,
  yieldResourceTypes[], expectedYieldUnits, issuedAtMs }`.
- `VectorMap<uint64 /*identityId*/, Vector<PveBotMissionOffer>> pveBotMissions`
  — at most `maxHeldMissions` per hunter.

**New methods**:

- `generatePveBotMissionOffers(identityId, bodyOid, terminal, hunterLevel,
  demandRanking, Vector<PveBotMissionOffer>& out)` — the mirrored
  `randomizeGenericDestroyMission` logic described in Layer 2, including the
  bearing constraint and the bounded candidate-position retry loop
  (`maxSpawnPointTries`, already in config).
- `revealPveBotMissionLair(bodyOid, offerId)` — the 120 m trigger's manager
  side: choose the validated exact lair point near `advertisedPos` (reusing
  `choosePveHuntSpawnPoint`'s guards plus
  `PlanetManager::isSpawningPermittedAt` and
  `CollisionManager::checkSphereCollision`, as
  `DestroyMissionObjectiveImplementation::findValidSpawnPosition` does), create

**Quality ranking is fully specified, not left to implementation.** A candidate
resource's score is `sum(weight_i * stat_i) / sum(weight_i)`, where `stat_i` is
the spawn's raw attribute value on the engine's 0–1000 scale (the dashboard
already exposes `stats.OQ`, `stats.SR`, … per spawn). Rules: a stat the spawn
does not carry (value 0 and not applicable to that resource class) is **dropped
from both numerator and denominator** rather than scored as zero, so a resource
is never penalised for an attribute its class doesn't have; if *every* weighted
stat is absent the candidate is skipped, not scored 0.

Because the ranked unit is a `(planet, routableCity, terminal)` tuple and a
single `ResourceSpawn` can cover **several zones** (the snapshot's multi-zone
support, `SimPlayerManager.cpp:5067`), the spawn identity alone does not order
the candidate set — several tuples can share one spawn. Ties therefore break on
the full chain, each level already available and stable: **spawn `ResourceSpawn`
object ID, then planet name, then city name, then terminal OID** (lower/
lexicographically-first wins at each level). That totally orders the candidates,
so selection is reproducible across restarts and independent of container
iteration order. `minQualityScore` (default 0) lets the
owner refuse to send a hunter across the galaxy for a mediocre spawn. The
weights above are the defaults, tunable without a rebuild.

Retuned existing values (these are the abandon drivers):
`missionHunt.maxSimultaneousAdds` 1 → 3, `missionHunt.addsAbandonCycles` 3 → 8,
`combat.huntQuota` becomes advisory only (lair destruction is completion).
`shuttleports` gains dantooine / lok / dathomir / endor / talus rows with real
`starport` `PlanetTravelPoint` names so the BFS graph reaches the planets the
market can demand.

## Technical Considerations

- **Pattern Usage**: The bot mission board follows the established
  manager-owns-state / controller-owns-motion split — the manager mirrors
  `MissionManagerImplementation`'s generator and owns lair lifecycle
  (`spawnPveHuntLair` / `queuePveHuntLairCleanup` are the models), the
  controller owns phases and movement. The lair-creation body is a direct
  mirror of `DestroyMissionObjectiveImplementation::spawnLair`, minus the
  mission graph.
- **Locking & References**: All new manager state lives under the existing
  `pveMutex`; nothing new is added to `pvpSquadMutex`. The Layer 0 extraction
  must keep its zone/planet-manager reads **outside** any squad lock exactly as
  today. `LairObject` is held via `ManagedReference`/`Reference` per the
  existing `spawnPveHuntLair` code; `PveMissionTerminalLocation` keeps its
  `Reference` (not `ManagedReference`) convention. The lair `OBJECTDESTRUCTION`
  observer must hand off **outside** the destroyed object's lock, matching
  `onHuntDestruction`. P.8.4's single-writer rule for `targetOid` (only
  `runActiveTick` writes it, only during `HUNTING`) is preserved unchanged —
  `ENGAGING_LAIR` targets a `TangibleObject`, not a creature, and must not
  touch `targetOid`.
- **IDL Impact**: None expected. No `.idl` is modified; `src/autogen/` is not
  regenerated. If `MissionSpawnActiveArea` reuse is later chosen over the
  controller-side distance check, that *would* touch an `.idl` — the plan
  deliberately avoids it.
- **C++ vs Lua Placement**: All tunables (arc degrees, radii, distance formula
  constants, hub list, family list, quality weights, rate limits, retuned adds
  caps) are Lua. C++ holds the index build, the offer generator, the BFS
  extraction and the phase machine.
- **Gating & Simulation-Only**: Four new default-off gates
  (`dispatch.locationBasedEligibility`, `missionBoard.enabled`,
  `marketDispatch.enabled`, `realBuffs.buffHubs.enabled`). With all four false
  the P.8.2/P.8.6 behavior is unchanged. **No credits are granted** (owner
  decision); harvest keeps feeding the existing simulation-only hive supply; no
  inventory/market/persistence mutation is added. The lair is a genuine world
  object but non-persistent and manager-owned, as it already is.
- **Dashboard Visibility**: Three new sections (`missionBoard`,
  `marketDispatch`, `buffTrips`), a `lifetime` counter sub-object, an
  `abandonReasons` histogram, and `terminalType` on terminal rows. The `#/wilds`
  route is extended. Bearer-token auth and the `APIProxyAiEconomyManager`
  facade are reused; no new endpoint.
- **Live Verification Plan**: Before/after dashboard snapshots. Concretely:
  (1) all 6 hunters leave `IDLE_HOME` and hold `assignmentSpecies` /
  offers — today 5 are stuck; (2) `missionBoard` shows two offers per hunter

- **Edge Cases**: hunter dies mid-relocation (clone origin is still
  `homeCity`; the in-flight route must be dropped, not resumed); demand signal
  flips planet while a hunter is mid-route (finish the route, re-evaluate at
  arrival — never re-plan in flight); a planet has a destroy-mission spawn
  group but no lair inside the hunter's level window (fall through the same
  three-tier relaxation `getRandomLairSpawn` uses, then skip the planet); the
  terminal city resolves `absent` after the general-only filter (existing
  documented adjacent-spawn fallback still applies); a second held offer's
  advertised point becomes invalid (drop that offer, return to terminal);
  `maxActiveLairs` reached (defer the reveal, do not abandon); a buff hub is
  unroutable (next hub, then synthetic fallback); zone switch mid-combat
  (forbid relocation while any defender is live).

## Performance & Cost Impact

- The lair-yield index is built once per config publication (boot + explicit
  refresh), not per tick — it walks every planet's destroy-mission spawn group
  once. Bounded by static template data.
- Offer generation runs once per terminal visit per hunter (~1 per mission
  cycle), with a bounded `maxSpawnPointTries` retry loop — the same cost shape
  as today's `choosePveHuntSpawnPoint`.
- The 120 m reveal check is a `Vector3` distance comparison on the existing 2 s
  active tick. Negligible.
- Route planning is a BFS over ≤ ~15 cities, run once per relocation decision,
  not per tick. `planPvpRoute` already does this per squad journey.
- Net effect on lairs is a **reduction**: today's 2549 spawns for 317 kills
  become one lair per completed mission.
