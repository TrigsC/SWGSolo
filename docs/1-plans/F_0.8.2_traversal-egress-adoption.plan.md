# F_0.8.2 — Traversal EGRESS adoption (plan)

**Status: PLAN, not implemented.** Follow-up from F_0.8.1, which migrated the
ENTRY half only. Carries a diagnosed root cause and a candidate one-line fix.

## 1. Why this exists

F_0.8.1 asked "how do I make every bot type enter *and exit* building cells
correctly?" It delivered the entry half. After it,

```
enterStructure  ->  6 production callers  (1 hunter, 5 PvP)
exitStructure   ->  1 caller: SimPlayerController.cpp:5292 -- the test harness
```

`exitStructure` is in exactly the state `enterStructure` was in before F_0.8.1.
Production bots enter buildings through the state machine and leave through the
legacy `moveTo` + cell-egress ladder.

**This is dormant, not broken.** With no production caller, the defect below
cannot fire, and the legacy egress is measurably healthy (post-review run: 67
collector boardings, 0 collectorFallbacks, 0 orphaned bots). Nothing is failing
in production today. This plan unblocks an improvement; it does not fix an
outage.

## 2. What was measured

Migrating the two arrival-EGRESS legs to `exitStructure` was implemented during
F_0.8.1 stage 3, measured, and reverted:

- **29 `ST_FAIL reason=path_failed`**, every one on an `exit_requested`
  generation and **none** on an enter.
- `ST_EGRESS escalation=result status=still_inside reason=attempt_cap` **29/29**.
- `exit_complete_outdoors` 3 against `exit_requested` 36.

Observed shape (agent 281475040882431, building 4255419):

```
Idle -> ApproachDoor -> InteriorRoute -> target_cell_arrived     (entry, fine)
Idle -> Egress  exit_requested   dest world=(-3157,2876) cell=0
  accepted nodes=37  end=(-3195,2873) cell=0        <- 38m PAST the destination
  request  dest=(-3188,2885) cell=6035913           <- a DIFFERENT building
Egress -> ApproachDoor  reason=entry_path_found     <- exit abandoned
ApproachDoor -> InteriorRoute -> Egress internal_egress
... loops to attempt_cap -> ST_FAIL
```

## 3. Root cause (diagnosed, not yet fixed)

`SimPlayerController.cpp:2192-2207`, in the path-acceptance phase selection:

```cpp
if (cellEgressActive) {
    setStructureTraversalPhase(Egress, "egress_path_found");
} else if (structureTraversalPhase != Reentry) {
    ManagedReference<SceneObject*> currentParent = agent->getParent().get();
    if (currentParent != nullptr && currentParent->isCellObject())
        setStructureTraversalPhase(InteriorRoute, "interior_path_found");
    else if (destinationCell != nullptr)
        setStructureTraversalPhase(ApproachDoor, "entry_path_found");
}
```

This branch consults `cellEgressActive`, the phase, the parent, and
`destinationCell` — and **never `structureTraversalIntent.exitIntent`**, which
is consulted in ten other places in the same file. So on an exit leg where
`cellEgressActive` is false (the traversal Egress phase driving its own
portal-derived waypoint), a path whose final point lands in ANY cell is read as
an entry, and the exit is abandoned.

D2b does not cover this: it rejects a path ending back in the **owning**
building's hollow, whereas here the path ends in a **neighbouring** building.

## 4. Candidate fix

An exit leg's destination is outdoors by definition, so a returned path ending
inside some cell is never an entry:

```cpp
if (cellEgressActive || structureTraversalIntent.exitIntent) {
    setStructureTraversalPhase(Egress, "egress_path_found");
} else if (...)
```

**Confidence: high on the diagnosis, moderate on completeness.** The trace also
shows an egress path ending 38m PAST its destination (step 2 above), which may
be an independent pathfinder problem or may be a downstream effect of the phase
confusion. Do not assume one line closes this until the matrix says so.

## 4b. ATTEMPTED 2026-08-31 — the fix in section 4 is CORRECT but INSUFFICIENT

The section-4 guard plus the two egress migrations were implemented, built
clean, and run against a live restarted server (timeboxed to one matrix run).
**Reverted.** The branch returned to `249d53193d`.

What the run proved:

- **The diagnosis was right.** `entry_path_found` went **13 -> 0**. The
  Egress -> ApproachDoor flip is entirely gone. Adding `exitIntent` to that
  condition does exactly what section 3 predicted.
- **It is not the blocker.** The egress still fails:

  | assertion | before | after | verdict |
  | --- | --- | --- | --- |
  | E1 `exit_complete_outdoors` / `exit_requested` | 3 / 36 | 5 / 40 | FAIL |
  | E2 `still_inside reason=attempt_cap` | 29 | 30 | FAIL |
  | E3 `ST_FAIL` on exit generations | 29 | 31 | FAIL |

So the phase flip was a SYMPTOM. Keep the section-4 guard when this is next
attempted — it is a genuine latent correctness fix and it cleanly removed one
whole failure mode — but it closes nothing on its own.

## 4c. THE REAL BLOCKER (found by the attempt, high confidence)

The egress candidate generator emits a **constant cell-local coordinate**.
`local=(52.2111, 10.3264, 0.593417)` appears identically across **eight
different cells, in different buildings, across two independent runs**:

```
run e2:  cell=5625461  cell=5625466  cell=5995627  cell=6336230
run s3:  cell=5625461  cell=5625466  cell=6035913  cell=6055693
         ...all with local=(52.2111,10.3264,0.593417)
```

It is the second most frequent egress target in the run (40 requests). A real
portal-derived waypoint cannot be the same local point in every building, so
this is a fixed/stale value rather than a per-building position — the same bug
CLASS as F_0.4.7 world-coord-as-cell-local, which ARCHI section 12 warns about
and which F_0.8.1 already had to fix once at the PvP collector sites.

Observed consequence (agent 281475041146924, building 2125378): the bot reaches
(1371.44, 2706.82), issues three consecutive requests to that constant local in
cell 6336230, each returns `result=accepted nodes=4`, **`botPos` is byte-identical
across all three** — the bot never moves — and then the attempt cap trips.

**Start here next time.** Find what produces that local coordinate in
`buildCellEgressExitSet` / `startNextCellEgressCandidate` and check whether it
is being written as a world coordinate, a model-space point, or a stale cached
candidate. Fixing the phase selection without fixing this just changes which way
the egress fails.

## 5. Scope

1. The phase-selection guard above.
2. Re-apply the two reverted egress migrations (`moveTo(arrivalOutdoor)` ->
   `exitStructure(arrivalOutdoor)`) in `SimPvPController::onArrived` and
   `SimPvPMemberController::onArrived`. Both are marked in-code with the revert
   rationale; `exitStructure` degrades to exactly `moveTo` with the gate off.
3. Consider whether hunters need a paired exit (stage 1 migrated entry only).
