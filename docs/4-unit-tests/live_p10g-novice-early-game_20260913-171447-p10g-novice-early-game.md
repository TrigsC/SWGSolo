## Defect 1 — D1 dashboard 502 while tracing (proven, blocking)

`getCombatDiagDashboard()` materialises each `key=value` token with
`pair.subString(split + 1)` (`SimPlayerManager.cpp:20839`). The snapshot line
always contains `aiTemplate=` with an **empty** value, because sim bots select
their tree through `customAiMap`. For that token `split + 1 == length`, and
engine3's `String::subString(int beginIndex)` throws when
`beginIndex >= count` (`utils/engine3/MMOEngine/src/system/lang/String.cpp:306`).
RESTServer catches the exception and returns 502, which fails the whole
dashboard, not just the `combatDiag` section.

Evidence (`core3_api.log`, excerpt in `…runAt-api502.txt`):

```
(381 s) Thread 40 - [RESTServer] ERROR - Unexpected exception in RESTAPITask: ArrayIndexOutOfBoundsException at 11
```

`"aiTemplate="` is exactly 11 characters. The watcher saw 502 with a 38-byte body
("Unexpected exception handling request.") from t=180 s to t=420 s, then 200 as
soon as harness cleanup emptied the allowlist.

This defect was introduced by the last Codex fix ("dashboard collapsed planned
fields into an opaque string"). The review's claim that "the pre-fix parity
result remains applicable" was not true for the dashboard path. Consequence: the
diagnostic makes the owner's primary debugging surface unusable during the very
run it exists for.

Fix direction (TRIP-2): take the value with `subString(split + 1, pair.length())`,
which returns "" at the boundary, or skip empty values.

  and the nuna died (posture 14, action pool −1652) within ~10 s. The bot was
  its only defender, and no other traced agent followed it.
- **`awaitKillTargetDeath` still timed out.** It requires three things
  (`SimPlayerManager.cpp:11860`):
  1. the target is dead;
  2. `killXp.kills` has risen above the baseline;
  3. **both** the bot's `combat_rangedspecialize_rifle` and `combat_general`
     rows **exactly** equal an oracle that assumes a sole attacker whose whole
     damage sits under the one weapon xpType.

  Condition 1 was met, so condition 2 or 3 failed.
- **Unproven**: which condition, and why. The killXp counters and the bot's XP
  rows during the window are unavailable: the dashboard was returning 502
  (Defect 1), and identity 253 was reaped by harness cleanup before the final
  snapshot. Candidates to check next:

    `totalDamage == 0 || baseXp <= 0`);
  - an attacker filtered out by the 80 m / same-zone check (`PlayerManagerImplementation.cpp:2107`).

  The attack choice is random (`System::random` over priority commands), which
  would explain intermittent failure.

This corrects the 2026-09-11/12 conclusion that kill failures were entirely the
`awardKillXp=false` misconfiguration. That was the cause of the deterministic
failures, but a second, intermittent failure remains with the gate on.
