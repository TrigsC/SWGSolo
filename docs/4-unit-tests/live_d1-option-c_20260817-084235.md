## Crash — `LIVE_VERIFICATION_FAIL` cause

SIGSEGV at **15:58:45**, during `cantina_long_dwell`'s idle dwell. gdb halted
the process; the game was down until the post-mortem completed.

Post-mortem artifacts (in `MMOCoreORB/bin/log/`):
`trip-verify-20260817-084235-d1-optionc-crash-backtrace.txt`,
`…-postmortem.log`, `…-postmortem-allthreads.log`,
`…-structuretraversal.log`.

**Findings — the crash is not attributable to the D1/Option C change:**

| Evidence | Detail |
| --- | --- |
| Crash site | Stock `CheckProspectInRange::check` (`Checks.cpp:57`) under `LookForTarget` — stock aggro scanning, no structure-traversal frames anywhere on the stack |
| Concurrency | `thread apply all bt` across **120 threads**: exactly one thread (`TW-naboo0`) was executing; every other thread was idle in futex/epoll/accept/select. No concurrent writer, no SimPlayer frame on any stack |
| Crashing agent | `light_jedi_sentinel`, OID `281475036375860`, `simPlayerBot=true`, on **Naboo** — a P.7 Jedi bot, **not** the traversal test bot (`281475036375311`, on Tatooine) |
| Timing | Fired during an idle dwell, not during an escalation; runs 1–4 on adjacent binaries were clean |

**Mechanism — single-byte pointer corruption.** The agent's blackboard
`targetProspect` entry is otherwise pristine: correct `BlackboardData::Data<
ManagedReference<SceneObject*>>` vtable, live shared_ptr (use_count 2), and a
sibling `loadedOID = 281475036351893`. The stored raw pointer is
`0x7f4ac561c3ff`. The object at **`0x7f4ac561c400`** — exactly one byte higher —
is a live `NonPlayerCreatureObject` whose `_objectID` is `281475036351893`,
i.e. **the same object the sibling OID names**.

So one byte, and only one byte, is wrong: the pointer's low byte reads `0xff`
instead of `0x00`. Everything else in the structure, and the target object
itself, is intact. The observed fault address `0x7f4ac517240000` is exactly the
true `referenceCounters` value `0x00007f4ac5172400` shifted left 8 bits, which
independently confirms the one-byte offset.

That signature does not match a use-after-free (which leaves an *aligned*
pointer into reused memory) or a data race (which leaves whole-word garbage).
It is consistent with a stray single-byte write or a hardware memory fault.
Host EDAC counters read `ce_count 0` / `ue_count 0` on both controllers, but
this platform may not report ECC at all, so that is not exculpatory.

**Not established:** what wrote the byte. Recorded as an open question, not a
root cause. Prior crashes in this environment (Jun 9 → Jul 31) were all
different signatures (Lua, ChatManager, ScreenPlayObserver); this is a new one.
